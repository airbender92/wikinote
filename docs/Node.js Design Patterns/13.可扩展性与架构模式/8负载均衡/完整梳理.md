# 一、你现在跑的这 4 个东西分别是什么？
```
1. consul agent -dev
2. node app.js webapp-service
3. node app.js api-service
4. node loadBalancer.js
```

## 1）consul agent -dev
**作用：服务通讯录 + 健康检查**
- 你可以把它理解成**微服务的“电话本”**
- 所有服务启动后，都来这里**登记自己的名字、IP、端口**
- 它会实时盯着服务活没活，挂了就从通讯录删掉
- 别人想调用服务，不用记死 IP，问 Consul 就行

## 2）node app.js webapp-service / api-service
**作用：真实的后台服务**
- 你启动一个，就是多开一个“服务实例”
- 可以启动 **1 个、3 个、10 个**
- 每个服务都会自动去 Consul 注册：
  - 我叫 `webapp-service`
  - 我在 `127.0.0.1:xxxx`
- 服务关掉时，自动注销

## 3）node loadBalancer.js
**作用：网关 + 负载均衡器**
- 外界（浏览器 / 前端 / 调用方）**只访问这一个入口**
- 它收到请求，去 Consul 问：
  - “`webapp-service` 现在有哪些实例在跑？”
- 拿到地址列表后，**轮流转发请求**（轮询）
- 这就叫**负载均衡**

# 二、整个闭环流程（超级清晰版）
## 第一步：启动通讯录
```
consul agent -dev
```
→ 空的电话本准备好。

## 第二步：启动服务，自动上通讯录
```
node app.js webapp-service
node app.js webapp-service
node app.js api-service
```
每个服务启动后都会做：
1. 随机找一个可用端口
2. 去 Consul 注册：
   - 名字：webapp-service / api-service
   - 地址：127.0.0.1:端口
3. Consul 每分钟检查服务活没活

现在 Consul 里就有：
- webapp-service：2 个实例
- api-service：1 个实例

## 第三步：启动网关
```
node loadBalancer.js
```
它只干一件事：
**接收外部请求 → 问 Consul 服务在哪 → 转发过去**

## 第四步：用户访问
```
curl localhost:8090/
```
网关流程：
1. 看到 `/` → 对应 `webapp-service`
2. 去 Consul 查：webapp-service 有 2 个实例
3. 轮流选一个转发
4. 返回结果给用户

下一次再来，换另一个实例 → 负载均衡。

# 三、这套东西到底有什么用？（核心价值）
## 1）不用写死 IP、端口
以前：
```
nginx 里写死 127.0.0.1:3000、127.0.0.1:3001
```
服务一改端口，全炸。

现在：
- 服务随便换端口
- 网关永远只问 Consul：“服务在哪”
- **零配置改动**

## 2）可以无限扩容服务
你想扛更多流量：
```
node app.js webapp-service
node app.js webapp-service
node app.js webapp-service
```
直接开 10 个，网关自动均匀分发流量。
**不用改任何配置，热扩容。**

## 3）服务挂了自动剔除
如果某个服务崩了：
- Consul 健康检查发现它挂了
- 从通讯录删掉
- 网关再也不会把流量转发过去
- **自动高可用**

## 4）统一入口，架构干净
外界只认识 `localhost:8090`
里面拆成：
- web 服务
- api 服务
- 订单服务
- 用户服务
…

网关统一路由，这就是**微服务架构**。

# 四、一句话总结你这套系统
**你搭建了一套完整的微服务系统：**

- **Consul = 服务注册中心（通讯录）**
- **app.js = 可水平扩展的微服务实例**
- **loadBalancer = 网关 + 负载均衡**
- **外部请求 → 网关 → 自动找服务 → 自动分流 → 高可用**
