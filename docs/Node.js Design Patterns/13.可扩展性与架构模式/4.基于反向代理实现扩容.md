# 基于反向代理实现扩容 译文+核心知识点
## 原文翻译
虽然`cluster`模块简单好用，但它并不是Node.js Web应用扩容的唯一方案。在对高可用有严格要求的生产环境，人们更倾向使用传统成熟方案，可控性更强。

替代`cluster`的思路：启动多套完全独立的应用实例，各实例监听不同端口，甚至部署在多台机器上；再通过**反向代理（网关）**作为统一入口，把流量分发到各个后端实例。
这种架构不再依靠主进程向worker分发请求；后端是一批独立进程，可以部署在单机不同端口，也可以分布在网络中多台服务器。
**反向代理**部署在客户端和后端实例中间，接收全部客户端请求，转发给后端服务，再把后端的响应返回客户端，对外表现为唯一服务。反向代理在这里同时承担负载均衡的职责。

> 补充说明：`cluster`模块**默认不支持粘滞会话**，可以使用npm库`sticky‑session`实现该能力。典型需要粘滞会话的库就是`Socket.IO`（基于长连接）。

架构图：反向代理作为前置负载均衡，对接多机器、多进程后端实例。

选择反向代理而非`cluster`的几点理由：
1. 反向代理可以跨多台机器做流量分发，而`cluster`仅局限单机内部多进程；
2. 主流反向代理原生支持粘滞负载均衡；
3. 不关心后端语言与平台，可以转发请求给任意语言编写的服务；
4. 可选用更丰富成熟的负载均衡算法；
5. 附带大量增强能力：URL重写、缓存、SSL证书卸载、DDoS安全防护、静态文件服务等。

当然两种方案可以组合使用：单机内部使用`cluster`做垂直扩容（榨干单机多核），再上层部署反向代理做多机器水平扩容。

主流反向代理/负载均衡选型：
- **Nginx**：非阻塞IO模型实现的Web服务器、反向代理、负载均衡；
- **HAProxy**：高性能TCP/HTTP负载均衡器；
- **Node.js自研代理**：直接用Node编写反向代理与负载均衡，有优势也存在短板；
- **云厂商负载均衡服务**：云计算环境下托管式负载均衡，维护成本低，弹性伸缩。

本章后续会讲解Nginx的示例配置；之后我们将纯使用Node.js手写一套简易负载均衡。

## 核心知识点
### cluster vs 反向代理负载均衡
|对比项|cluster模块|前置反向代理(Nginx/HAProxy)|
|---|---|---|
|部署范围|仅限单机多进程|单机、多机器集群均支持|
|进程管理|master主进程管理worker生命周期|后端实例完全独立，代理不管理进程启停|
|粘滞会话|无原生支持，依赖第三方库sticky‑session|原生支持ip_hash/cookie会话保持|
|附加能力|仅负载分发、进程监控|SSL终止、缓存、静态资源、安全防护、URL路由|
|适用场景|单机内部利用多核CPU|生产多机器分布式集群|

### 组合架构（生产常用）
> 每台服务器内部用`cluster/PM2`启动多进程；多台机器上层部署Nginx/云LB，实现「单机垂直扩容 + 多机水平扩容」。

### Socket.IO为什么需要粘滞会话
Socket.IO基于长连接，握手阶段会绑定到某一个后端实例；若后续请求被调度到别的实例，握手状态丢失，连接无法建立，因此必须开启sticky session。

### 四类负载均衡方案简要说明
1. **Nginx**：七层HTTP代理，生态成熟，适合Web业务；
2. **HAProxy**：专注负载均衡，四层七层均可，健康检查、会话保持能力更强；
3. **Node自制代理**：代码可控，但要自行处理连接管理、错误恢复，生产要谨慎评估性能；
4. **云托管LB**：阿里云SLB、AWS ALB，无需维护代理服务器，弹性伸缩，适合云原生业务。

### 关键提醒
`cluster`只能解决一台机器内部多进程，无法实现跨机器流量分发；真正线上分布式系统，几乎都要搭配反向代理/负载均衡。
