# 动态水平扩容（Dynamic Horizontal Scaling）译文 + 核心要点

## 原文翻译
现代云基础设施的一大重要优势，就是能够**根据当前或预测的流量动态调整应用的服务容量**，这也被称为**动态扩缩容**。
如果实现得当，这种方式可以**极大降低 IT 基础设施成本**，同时保持应用高可用和响应速度。

核心思路非常简单：
- 当应用因流量峰值出现性能下降时，系统**自动新增服务器**来应对高负载；
- 当发现已分配资源利用率过低时，就**下线部分服务器**以降低运行成本；
- 也可以**基于定时策略**扩容/缩容：比如在已知低峰时段关停部分机器，高峰前再重新启动。

这类机制要求**负载均衡器必须实时维护最新的服务拓扑**，时刻知道哪些后端服务器处于可用状态。

---

## 核心知识点梳理
1. **什么是动态水平扩容**
   - **水平扩容**：增加/减少**实例数量**（多进程 / 多机器）
   - **动态**：根据负载、时间、监控指标自动扩缩，无需人工干预

2. **典型触发条件**
   - CPU / 内存使用率高
   - 请求排队、响应时延上升
   - QPS 突增/突降
   - 定时策略（按小时、按天、按活动周期）

3. **收益**
   - 高峰期保证性能
   - 低峰期节省成本
   - 无需人工值守扩缩容

4. **关键技术要求**
   - 服务必须**无状态**（session 存在 Redis / JWT）
   - 负载均衡器支持**动态后端节点**（不能写死 upstream）
   - 服务注册 + 服务发现机制（Consul、etcd、K8s Service 等）
   - 健康检查（自动剔除宕机实例）

5. **与本章前面内容的衔接**
   - 之前 Nginx 示例是**静态节点列表**（写死在 nginx.conf）
   - 动态扩容需要**动态节点列表**：
     - 新实例启动 → 自动注册到 LB
     - 实例下线 → 自动从 LB 移除
   - 这是云原生和微服务架构的标配能力

---

## 一句话总结
动态水平扩容 = **自动加减实例 + 负载均衡器实时感知节点变化**，
是现代高可用、低成本架构的标配能力。

# 使用服务注册中心（Service Registry）
## 原文翻译
解决动态扩缩容问题的一个通用模式，是使用一个叫作**服务注册中心**的中央存储，它会持续记录正在运行的服务器及其提供的服务信息。

为了简化理解，你可以手动完成这些步骤：通过云厂商管理界面启动服务器，再用 SSH 登录操作。
或者，也可以选择**基础设施即代码**工具来自动化这些任务，例如：
- Terraform
- Ansible
- Packer

图 12.7 展示了一个前端带有负载均衡器、并通过服务注册中心**动态配置**的微服务架构：

该架构包含两种服务：**API** 和 **WebApp**。每种服务都可以有一个或多个实例，分布在多台服务器上。

当请求到达 `example.com` 时，负载均衡器会检查请求路径前缀：
- 如果前缀是 `/api`，就将请求负载均衡到可用的 API 实例之间；
- 其他路径前缀，则负载均衡到可用的 WebApp 实例之间。

负载均衡器是通过**服务注册中心**来获取每台服务器上运行的服务实例列表的。

要让这套架构实现完全自动化，每个应用实例必须在**启动时向服务注册中心注册自己**，并在**停止时注销自己**。
这样，负载均衡器就能始终拥有网络中可用服务与服务器的最新视图。

该模式不仅能实现负载均衡，还有一个额外好处：
它能将**服务实例**与**运行它的服务器**解耦。
我们可以把服务注册中心模式，看作是**服务定位器模式**在网络服务上的一种落地实现。

---

## 核心知识点梳理
1. **服务注册中心是什么**
   一个集中式组件，维护：
   - 服务名
   - 实例地址（IP + 端口）
   - 健康状态
   - 负载/权重等信息

2. **核心流程**
   - 服务启动 → 自动注册
   - 服务下线 / 崩溃 → 自动注销或被健康检查剔除
   - 负载均衡器 → 实时从注册中心拉取可用节点

3. **作用**
   - 支持**动态扩缩容**，无需改 LB 配置
   - 实现**服务发现**：让调用方知道谁可用、在哪里
   - 健康检查自动剔除故障实例
   - 解耦服务与物理机器

4. **典型产品（对应书中思想）**
   - etcd
   - Consul
   - ZooKeeper
   - Kubernetes Service（自带注册发现）

5. **与本章前面 Nginx 示例的区别**
   - 之前：upstream 写死静态地址
   - 现在：动态从注册中心获取，支持自动扩缩容

6. **设计模式归属**
   属于 **Service Locator Pattern（服务定位器模式）**
   → 让组件能动态找到依赖服务，而不是硬编码地址。

# 基于 http-proxy + Consul 实现动态负载均衡  
## 全文翻译+精简要点

### 一、思路概述
要支持动态扩缩容，除了用 Nginx/HAProxy 并自动 reload 配置外，还可以**直接用 Node.js 实现一个负载均衡器**，配合服务注册中心（Consul）实现动态节点发现。

优势：
- 完全自由定制负载均衡策略
- 深度理解 Nginx/HAProxy 这类工具的底层原理
- 无缝对接服务注册中心，支持动态扩缩容

### 模式（服务注册中心）
使用一个**中央存储**，实时维护系统中可用的服务与服务器列表。

---

## 二、实现服务实例（app.js）
每个服务启动时**自动注册到 Consul**，退出时**自动注销**。

```javascript
import { createServer } from 'http'
import consul from 'consul'
import portfinder from 'portfinder'
import { nanoid } from 'nanoid'

const serviceType = process.argv[2]
const { pid } = process

async function main () {
  const consulClient = consul()
  const port = await portfinder.getPortPromise()
  const address = process.env.ADDRESS || 'localhost'
  const serviceId = nanoid()

  // 注册服务到 Consul
  function registerService () {
    consulClient.agent.service.register({
      id: serviceId,
      name: serviceType,
      address,
      port,
      tags: [serviceType]
    }, () => {
      console.log(`${serviceType} registered successfully`)
    })
  }

  // 退出时注销服务
  function unregisterService (err) {
    err && console.error(err)
    consulClient.agent.service.deregister(serviceId, () => {
      process.exit(err ? 1 : 0)
    })
  }

  process.on('exit', unregisterService)
  process.on('uncaughtException', unregisterService)
  process.on('SIGINT', unregisterService)

  // 启动 HTTP 服务
  const server = createServer((req, res) => {
    let i = 1e7; while (i > 0) { i-- }
    res.end(`${serviceType} response from ${pid}\n`)
  })

  server.listen(port, address, () => {
    registerService()
    console.log(`Started ${serviceType} at ${pid} on port ${port}`)
  })
}

main().catch(console.error)
```

### 关键点
1. **自动找端口**：portfinder 自动获取可用端口
2. **服务注册**：启动时把服务名、地址、端口写入 Consul
3. **自动注销**：进程退出/崩溃时从注册中心移除
4. **服务类型区分**：通过命令行参数区分 api-service / webapp-service

## 三、实现动态负载均衡器（loadBalancer.js）
```javascript
import { createServer } from 'http'
import httpProxy from 'http-proxy'
import consul from 'consul'

// 路由规则
const routing = [
  { path: '/api', service: 'api-service', index: 0 },
  { path: '/',    service: 'webapp-service', index: 0 }
]

const consulClient = consul()
const proxy = httpProxy.createProxyServer()

const server = createServer((req, res) => {
  // 匹配路由
  const route = routing.find(r => req.url.startsWith(r.path))

  // 从 Consul 获取服务列表
  consulClient.agent.service.list((err, services) => {
    const servers = !err && Object.values(services)
      .filter(s => s.Tags.includes(route.service))

    if (err || !servers.length) {
      res.writeHead(502)
      return res.end('Bad gateway')
    }

    // 轮询负载均衡
    route.index = (route.index + 1) % servers.length
    const targetServer = servers[route.index]
    const target = `http://${targetServer.Address}:${targetServer.Port}`

    // 转发请求
    proxy.web(req, res, { target })
  })
})

server.listen(8080, () => {
  console.log('Load balancer started on port 8080')
})
```

### 工作流程
1. 根据 URL 路径匹配路由（/api → api-service，其他 → webapp-service）
2. 每次请求都从 Consul 查询**当前可用实例列表**
3. 使用**轮询（round-robin）**分发请求
4. 通过 http-proxy 转发到目标服务

## 五、可优化点（书中明确指出）
- **每次请求都查 Consul 开销大**：应缓存服务列表，定时刷新

- 缺少健康检查、超时、重试、熔断等生产特性
