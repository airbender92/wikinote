# cluster 模块 译文+核心知识点
## 原文翻译
在 Node.js 中，想要在单台机器上将流量分摊到多个应用实例，最简单的方案就是使用内置核心 `cluster` 模块。该模块简化同应用多进程的创建逻辑，并自动把外部连接分发到各个工作进程，参考架构图：

> 补充说明：对 Node.js 来说，垂直扩容（升级单台机器硬件）和水平扩容（新增多台服务器）用到的技术思路高度相近，二者都是通过多实例方式充分利用全部计算资源。

集群架构分为**主进程（master）**与**工作进程（worker）**：
1. 主进程负责批量创建多个 worker 子进程，每个 worker 都是一份完整的应用副本；
2. 所有外部网络连接由主进程统一接收，再分发至各个 worker，实现流量负载分摊；

每个 worker 都是独立操作系统进程，我们通常会创建与CPU核心数量相等的工作进程。借助该机制，Node 应用就能充分利用整机所有CPU算力。

## 核心机制拆解
### 1. 进程分层
- Master 主进程：调度管理者，**不处理业务请求**，只负责 fork worker、分发TCP连接、监控worker崩溃并重启；
- Worker 工作进程：执行业务HTTP/网络服务，独立事件循环，互不阻塞。

### 2. 连接分发机制（默认调度策略）
Linux/Windows 采用**句柄分发**：master监听端口，新TCP连接到达时，将socket句柄传递给空闲worker，不会重复拷贝连接数据，性能很高；
默认调度策略为轮询，均匀分流请求。

### 3. 核心价值（X轴单机克隆扩容）
1. 解决Node单线程只能占用单核的短板，单机多核全部利用；
2. 进程隔离：单个worker崩溃，master自动重启该进程，服务整体不宕机，提升可用性；
3. 零第三方依赖，Node原生内置，轻量无额外开销。

### 4. 使用硬性前提（无状态）
所有worker之间不共享内存数据：会话、缓存、全局业务数据必须存入Redis、数据库等共享存储，不能存在内存/本地文件中，否则多实例数据不一致。

### 5. 局限
仅适用于**单台服务器**扩容；多机器集群无法单独依靠cluster，需要Nginx/服务注册中心做上层负载均衡。

# cluster 模块行为说明 翻译+核心要点
## 原文翻译
绝大多数操作系统下，`cluster` 模块内部采用**轮询（round-robin）**负载均衡算法。主进程通过该算法将请求均匀分摊给所有工作进程。
除 Windows 系统外，轮询调度默认全局开启；可通过 `cluster.schedulingPolicy` 全局修改调度策略，支持两个常量：
- `cluster.SCHED_RR`：轮询调度
- `cluster.SCHED_NONE`：交由操作系统内核自行调度

使用 `cluster` 时，所有 worker 中执行的 `server.listen()` 底层都会委托给 master 主进程统一处理。主进程统一接收外部连接，再分发给worker池，该机制对绝大多数场景开箱即用，但存在几个边界特殊场景会出现不符合预期的行为：
1. `server.listen({fd})` 指定文件描述符监听
文件描述符是进程级资源，worker 内直接使用 fd 监听时，主进程无法识别对应资源，会产生异常。
解决方案：在主进程创建fd，再传递给worker使用。
2. `server.listen(handle)` 传入FileHandle句柄监听
worker 会直接占用该句柄，不再把监听逻辑委托给 master，负载均衡失效。
3. `server.listen(0)` 随机端口监听
普通单进程下 `listen(0)` 会分配随机端口，但集群环境所有 worker 拿到的是**同一个固定随机端口**（仅首次随机生成，后续复用）。
若需要每个 worker 监听不同端口，必须手动生成端口号。

## 核心关键知识点
### 1. 调度策略区分
- Linux/macOS：默认 `SCHED_RR` 轮询，master 主动均分请求，负载更均衡；
- Windows：默认 `SCHED_NONE`，内核调度连接，容易出现请求分配不均；
- 可全局覆盖 `cluster.schedulingPolicy` 修改策略。

### 2. 端口监听底层逻辑
集群模式下 worker 本身不会独立绑定对外端口，全部监听操作上交给 master，由 master 统一接收TCP连接后分发，这是单机负载均衡的核心基础。

### 3. 三个坑点避坑总结
1. 禁止在 worker 直接自定义fd监听，fd进程隔离会导致master无法接管；
2. 不要在worker直接传入handle监听，会绕过集群分发逻辑；
3. `listen(0)` 在cluster中不会每个进程分配独立随机端口，多端口场景手动分配。

### 4 适用范围限制
该负载均衡仅作用于**单机多进程**，多服务器集群无法依靠cluster实现分流，需要Nginx/网关做上层负载。

# 翻译 + 核心代码&知识点
## 一、原文翻译
我们来实操示例，搭建一套基于 `cluster` 实现多进程克隆、自带负载均衡的简易HTTP服务。
首先编写基础HTTP业务服务 `app.js`：
```javascript
import { createServer } from 'http'
const { pid } = process

const server = createServer((req, res) => {
  // 模拟CPU密集型运算
  let i = 10_000_000;
  while (i--) {}
  console.log(`Handling request from ${pid}`)
  res.end(`Hello from ${pid}\n`)
})

server.listen(8080, () => console.log(`Started at ${pid}`))
```
服务收到任意请求后，返回当前进程PID，方便区分是哪个工作进程处理流量；
代码中千万次空循环用来模拟数值计算类CPU耗时任务，如果去掉这段运算，服务器负载极低，压测看不出性能差异。

### 单机单进程运行验证
直接启动文件，浏览器/`curl http://localhost:8080` 即可访问，所有响应PID完全一致。
### 压测工具 autocannon 参考命令
```bash
npx autocannon -c 200 -d 10 http://localhost:8080
```
参数含义：200并发连接，持续压测10秒。
参考环境：2.5GHz 4核i7、Node14，单进程压测结果约300 QPS。

> 补充说明：cluster内置轮询调度并非简单顺序分发，内部增加保护逻辑，避免单个worker进程负载过高。
本示例未使用Express/Fastify等框架，极简原生http实现，你可自行替换任意Web框架。
有了基准服务与压测数据，接下来使用cluster多进程方案优化性能。

## 二、关键要点
1. **PID作用**
区分不同工作进程处理的请求，直观验证cluster分流效果；
2. **CPU循环模拟**
制造CPU阻塞，凸显单线程瓶颈，多进程扩容后QPS会随CPU核心数接近线性提升；
3. 基准压测意义：拿到单进程性能基线，方便对比cluster多进程优化收益；
4. 轮询调度优化：cluster的RR轮询并非单纯顺序分配，内置负载均衡保护机制，不会出现进程负载失衡。

## 三、配套 cluster 启动文件示例（书中后续代码逻辑）
新建 `cluster.js` 管理主进程，fork多个app工作进程：
```javascript
import cluster from 'cluster'
import os from 'os

if (cluster.isPrimary) {
  const cpuNum = os.cpus().length
  console.log(`主进程PID：${process.pid}，创建${cpuNum}个工作进程`)
  // 根据CPU核心数创建worker
  for (let i = 0; i < cpuNum; i++) {
    cluster.fork('./app.js')
  }
  // 监听进程崩溃，自动重启
  cluster.on('exit', worker => {
    console.log(`进程${worker.process.pid}异常退出，重启新进程`)
    cluster.fork('./app.js')
  })
}
```
运行 `node cluster.js`，多进程均分请求，4核机器QPS理论提升至接近4倍单进程数值。

## 四、重要注意事项
示例服务为**有状态**（仅演示，生产禁止）：无共享存储，若存放session、内存缓存会出现多进程数据不一致；
生产环境需把会话、缓存迁移到Redis等共享中间件，满足无状态服务要求。

# 译文 + 核心代码与知识点
## 一、完整改造代码（集成cluster）
```javascript
import { createServer } from 'http'
import { cpus } from 'os'
import cluster from 'cluster'

// 1. 主进程逻辑
if (cluster.isMaster) {
  const cpuCount = cpus().length
  console.log(`创建 ${cpuCount} 个工作进程`)
  // 根据CPU核心数批量fork子进程
  for (let i = 0; i < cpuCount; i++) {
    cluster.fork()
  }
} else {
  // 2. Worker工作进程：启动HTTP服务
  const { pid } = process
  const server = createServer((req, res) => {
    // 模拟CPU密集计算
    let i = 10_000_000
    while (i--) {}
    console.log(`Handling request from ${pid}`)
    res.end(`Hello from ${pid}\n`)
  })
  server.listen(8080, () => console.log(`Started at ${pid}`))
}
```

## 原文翻译
我们现在改造`app.js`，集成`cluster`模块实现多进程扩容：
执行逻辑拆解：
1. 程序启动时默认运行**主进程**，`cluster.isMaster`为`true`；读取CPU核心数量，创建同等数量的worker子进程，最大化利用整机算力。
2. 调用`cluster.fork()`时，会再次执行当前`app.js`文件，但此时进程为工作进程，`isMaster`为false，进入业务逻辑分支，启动独立HTTP服务。

`cluster`使用固定通用模板：
```js
if (cluster.isMaster) {
  // 主进程：创建worker
} else {
  // 工作进程：执行业务
}
```
关键特性：每个worker都是独立Node进程，拥有独立事件循环、独立内存堆、独立加载的模块。

底层原理：`cluster.fork()`内部基于`child_process.fork`实现，自动提供IPC通信通道；可通过`cluster.workers`获取所有子进程，向全体worker广播消息：
```js
Object.values(cluster.workers).forEach(worker => worker.send('来自主进程的消息'))
```

### 运行效果
四核机器启动后，终端会打印4个不同进程PID；访问服务时，响应里的PID会交替变化，证明请求被负载均衡分发到不同工作进程。

### 压测对比
```bash
npx autocannon -c 200 -d 10 http://localhost:8080
```
单进程基准约300 QPS，四核多进程版本达到1000 QPS，性能提升约3.3倍。

> 提示：本章压测仅作学习参考，不能完全等同于线上真实场景。线上优化需要结合自身业务做专属基准压测，不同业务场景下各类扩容方案收益差异很大。

## 二、核心知识点
1. **单核瓶颈解决**
单Node进程仅占用一个CPU核心；cluster自动创建多进程，充分利用整机多核，CPU密集任务性能接近核心数倍提升。
2. 进程隔离
每个worker内存、事件循环完全独立，单个进程卡死/崩溃不会让整体服务宕机；主进程可监听`exit`事件自动重启故障进程。
3. 内置负载均衡
Linux/macOS默认轮询调度，master统一监听8080端口，TCP连接均匀分发给所有worker，无需额外反向代理。
4. IPC通信能力
主进程与worker自带消息通道，可用于广播配置、下发任务等进程间交互。
5. 局限：仅支持**单台服务器**扩容，多机器分布式场景无法使用，需Nginx/K8s等上层负载均衡。
6. 生产硬性要求
多进程环境下禁止内存存储session、全局缓存等共享数据，必须使用Redis、数据库等外部共享存储保证多实例数据一致。

## 1. 为什么你看不出明显提升？
### ✅确实有提升（实实在在变好）
1. **每秒处理请求从227 →405，总请求从2000变成4000，10秒多处理一倍流量**
2. **平均、中位数延迟直接减半**，一半请求从875ms降到486ms。
👉普通用户的请求响应变快了。

### ❌但是有坏现象：长尾延迟拉高（97.5%/99%延迟上涨到1280/1407ms，最大1706ms）
> 什么叫长尾延迟：大部分请求很快，但有一小部分请求卡的很慢。
> 这就是你疑惑的根源：**平均变好了，但最差的那批请求反而更慢**。

### 为什么没有达到理论的1000QPS（3.3倍提升）？
1. **Windows平台cluster的特殊开销**
Windows没有原生socket fd共享；主进程接收全部TCP连接，通过IPC把连接句柄转发给worker。高并发新建连接场景，**IPC转发会带来额外开销**，损耗一部分性能。Linux下cluster的提升会更接近核数倍数。

2. 200并发连接数，大量TCP短连接疯狂新建，Windows的cluster连接分发成为瓶颈。
> 内核分发连接给worker会排队，造成一部分请求排队等待，就拉高99分位长尾延迟。

3. 你的机器不是理想4核，`os.cpus().length`返回的是**逻辑核（含超线程）**，不是物理4核；超线程的性能增益本身就达不到2倍每核。

## 2. 指标通俗翻译，不用死记表格
- **50%（中位数）：一半的请求耗时**
  - 单进程：一半请求 ≥875ms
  - cluster：一半请求 ≥486ms
👉 50%的用户，请求直接快一倍，这是实实在在收益。

- **99%：100个请求里面，最慢那1个请求耗时**
> ⚠️本次：cluster 99% =1407ms，比单进程1067ms更高！
意思：**绝大多数请求变快，但少数倒霉请求排队，等待时间更长，长尾恶化**。

> 💡为什么多进程还会出现长尾？
Windows：所有新连接全部过主进程IPC转发；并发瞬间爆发的时候，连接转发队列积压，少数请求卡在socket分发环节，还没到达worker业务逻辑，就已经耗掉大量时间。

- `Req/Sec Avg`：每秒平均处理请求数
单进程227，cluster405，**真实提升约1.78倍，不是理论3.3倍**。

3. 理论3.3倍是Linux下的理想预期，Windows环境不要直接套用。

# cluster 实现弹性容灾与高可用 译文+核心代码+要点
## 原文翻译
所有工作进程相互独立，单个worker崩溃、销毁不会影响其余进程。只要还有存活worker，服务就能持续接收连接；若全部worker退出，现有连接会断开、新连接拒绝接入。Node不会自动维护进程数量，必须由主进程代码自行管理进程池。
多实例天然带来**弹性（resiliency）**与**高可用（availability）**：单实例故障时，其余副本承接流量，形成冗余系统。基于`cluster`可轻松实现该能力。

### 改造1：模拟worker随机崩溃
在worker分支增加定时抛出异常逻辑，进程1~3秒内随机崩溃：
```js
else {
  const { pid } = process
  // 随机1~3秒后崩溃
  setTimeout(() => {
    throw new Error('Ooops')
  }, Math.ceil(Math.random() * 3) * 1000)

  const server = createServer((req, res) => {
    let i = 10_000_000; while(i--) {}
    res.end(`Hello from ${pid}\n`)
  })
  server.listen(8080)
}
```
单进程模式下，进程崩溃服务完全不可用，重启还存在启动耗时空档；但多集群模式下，其余进程持续处理请求，不中断服务。

### 改造2：主进程监听exit，自动重启故障worker
主进程增加`exit`事件监听，区分**正常关闭**和**异常崩溃**，仅故障进程自动重建：
```js
if (cluster.isMaster) {
  const cpuCount = cpus().length
  for(let i=0; i<cpuCount; i++) cluster.fork()

  // 监听worker退出事件
  cluster.on('exit', (worker, code) => {
    // code !==0 异常退出 / exitedAfterDisconnect=false 非主动关闭
    if (code !== 0 && !worker.exitedAfterDisconnect) {
      console.log(`进程${worker.process.pid}崩溃，启动新worker`)
      cluster.fork()
    }
  })
}
```
逻辑说明：
1. `worker.exitedAfterDisconnect`：标记是否为主进程主动调用`kill()`关闭；
2. 非正常崩溃时，立刻fork新进程补齐进程池；
3 旧进程销毁期间，其余worker持续处理流量，整体服务不中断。

### 压测验证结果
使用autocannon压测，总请求8000次，仅674次失败（含7次超时），可用性约92%。
失败请求大多是崩溃瞬间已建立的连接被强制断开，程序崩溃场景下该容错表现已经十分可观；可用性数值随进程数量、崩溃频率浮动。

## 核心知识点
### 1. 高可用核心原理：进程冗余
多worker并行运行，单点故障流量自动分流至其余健康进程，无服务断档。
### 2. 进程退出区分两个关键标识
- `code === 0`：正常退出；
- `worker.exitedAfterDisconnect = true`：主进程主动关闭（优雅下线）；
两者任一满足都不重建，仅意外崩溃才重启。
### 3. 崩溃带来的不可避免损耗
进程崩溃时正在处理的长连接会直接中断，无法保存现场恢复请求；生产可通过重试机制缓解这类报错。
### 4. cluster 容灾局限
仅单机多进程容灾；若整机宕机，所有worker全部失效，必须搭配Nginx/云负载均衡做多机器集群才能实现机房/机器级高可用。
### 5 生产补充优化点
1. 增加进程健康检测，识别卡死无响应worker；
2. 优雅停机逻辑，收到信号先停止接收新连接，处理完存量请求再退出；
3. 结合日志监控，告警频繁崩溃的异常进程。

# 零停机重启（Zero-downtime restart）完整译文+代码解析
## 原文翻译
线上发布新版本时，Node 服务需要重启更新代码。如果只有单实例，重启期间服务完全不可用；但多进程集群架构可以解决这个问题。
普通重启会存在一段服务中断窗口，对于有SLA服务等级保障、持续交付高频迭代的线上业务完全不可接受。**零停机重启**方案可以在不中断业务的前提下完成代码更新。

基于`cluster`实现零停机重启的核心思路：**逐个重启工作进程**。每次只下线一个worker，其余进程持续承接流量，全程服务不中断。

### 主进程新增信号处理代码
```javascript
import { once } from 'events'

if (cluster.isMaster) {
  // 原有创建worker、崩溃重启逻辑省略
  // 监听自定义SIGUSR2信号，触发灰度重启
  process.on('SIGUSR2', async () => {
    const workers = Object.values(cluster.workers)
    // 逐个遍历所有工作进程
    for (const worker of workers) {
      console.log(`Stopping worker: ${worker.process.pid}`)
      // 优雅断开当前worker
      worker.disconnect()
      // 阻塞等待该进程完全退出
      await once(worker, 'exit')
      // 拉起新版本worker
      const newWorker = cluster.fork()
      // 等待新进程完成端口监听、就绪后再处理下一个
      await once(newWorker, 'listening')
    }
  })
}
```

### 执行流程拆解
1. **信号触发**：监听系统`SIGUSR2`自定义信号，收到信号后启动全量滚动重启逻辑，处理函数使用async异步语法方便等待；
2. **遍历所有worker**：获取当前全部工作进程，循环逐个处理；
3. **优雅下线**：调用`worker.disconnect()`，不会强行切断正在处理的请求，worker会处理完存量连接后再退出；同时阻塞等待`exit`退出事件；
4. **创建新进程**：旧进程完全退出后，fork一份加载最新代码的worker；
5. **等待就绪**：等待新worker触发`listening`事件（端口监听成功、可接收流量），再进入下一个进程的重启流程。

## 实操测试步骤
1. 查询主进程PID：
```bash
ps -af | grep node
```
主进程是所有worker的父进程，可区分PID；
2. 发送`SIGUSR2`信号触发滚动重启：
```bash
kill -SIGUSR2 主进程PID
```
3. 日志输出示例：
```
Stopping worker: 19389
Started 19407
Stopping worker: 19390
Started 19409
```
4. 压测验证：执行autocannon并发压测，重启全过程请求无大规模失败，可用性几乎不受影响。

## 核心关键知识点
### 1. 核心优雅下线API：`worker.disconnect()`
区别于暴力`kill`：
- 暴力杀进程：正在处理的请求直接中断，连接报错；
- disconnect：停止接收新连接，存量请求处理完毕后自动退出，实现平滑下线。

### 2. 滚动重启优势
同一时刻仅下线一个worker，其余进程完整承载流量，无服务中断窗口，满足线上SLA高可用要求。

### 3. 两个关键等待事件
- `once(worker, 'exit')`：确认旧进程彻底销毁；
- `once(newWorker, 'listening')`：必须等新进程监听端口就绪，再重启下一个，避免出现无可用worker的空档。

### 4. 信号说明
`SIGUSR1/SIGUSR2`是Linux自定义用户信号，不会终止进程，适合自定义运维操作；
不要使用SIGINT/SIGTERM，这类信号会直接杀死主进程。

### 5. cluster零停机局限
仅适用于**单机多进程**场景；多服务器分布式集群（Nginx/K8s多机器）需要在网关层配置灰度分批发布，逻辑思路一致但实现方式不同。

### 6 生产补充注意事项
1. 代码更新后需要重新fork才能加载新代码，内存中旧进程依旧运行旧版本；
2. 可增加最大并发限制、超时机制，防止进程卡死阻塞发布流程；
3. 搭配监控，重启期间观察QPS、错误率指标。

# 有状态通信问题与解决方案 译文+要点
## 原文翻译
如果应用的状态没有在多个实例间共享，那么**有状态通信**在 `cluster` 模块下就无法正常工作。
原因在于：同一个用户会话的不同请求，可能会被负载均衡器分发到不同的应用实例上。
这个问题并非 `cluster` 独有，而是**所有无状态负载均衡算法**都会遇到的通用问题。

举个典型场景（如图12.3）：
1. 用户 John 发送请求登录，认证成功；
2. 登录状态只存在于处理该请求的 **Instance A** 的内存中；
3. John 下一次请求被负载均衡转发到 **Instance B**；
4. Instance B 没有 John 的登录状态，会直接拒绝操作。

这样的有状态应用是**无法直接扩容**的，好在有两种简单有效的解决方案。

---

### 补充说明
- 本章示例使用了 **Unix 信号（SIGUSR2）**，因此在 Windows 上无法正常运行（除非使用 WSL）。
  除了信号，还可以用 socket、管道、标准输入等方式接收控制指令。
- **pm2** 是一个基于 `cluster` 封装的进程管理工具，内置负载均衡、进程监控、零停机重启等功能，是 Node 生产环境常用方案。

## 核心问题总结
**状态只存在于单个实例内存 = 集群环境下必然失效**
- 登录态、会话、内存缓存、限流计数等
- 只要请求被分到另一个 worker，状态就丢失

## 书中提到的两种通用解决方案（后文会展开）
1. **会话粘滞（Sticky Sessions / IP Hash）**
   让同一个用户的请求**始终被转发到同一个 worker/实例**，保证状态只在该实例使用。
2. **集中式状态存储（无状态化改造）**
   把所有状态从应用内存移出，存入 **Redis、数据库** 等共享存储，
   所有实例都能访问同一份状态，实现真正无状态服务。

## 关键要点
- `cluster` 本身**不解决状态问题**，只解决算力和负载问题；
- 生产环境 Node 集群**必须设计成无状态服务**；
- 本地内存永远不能存会话、用户态、全局计数等共享数据。

# 多实例间状态共享 译文+核心要点
## 原文翻译
要让有状态通信的应用实现扩容，第一种方案是**在所有实例之间共享状态**。

这一点可以通过**共享数据存储**轻松实现，例如：
- 数据库：PostgreSQL、MongoDB、CouchDB 等
- 内存存储（更佳选择）：**Redis**、Memcached

如图 12.4 所示，这是一种简单且有效的方案：所有应用实例都访问同一份集中式的状态数据。

使用共享存储来维护通信状态唯一的缺点是：
应用这种模式可能需要对代码库进行**大量重构**。
例如，你可能正在使用某个现成库，它默认把状态保存在内存中，
那么你就需要配置、替换或重新实现该库，让它改用共享存储。

如果重构成本过高——比如改动量太大、项目时间紧张，来不及做无状态化改造——
我们可以采用一种**侵入性更小**的方案：
**粘滞负载均衡（sticky load balancing）**，也叫**粘滞会话（sticky sessions）**。

---

## 核心知识点
1. **方案一：集中式共享状态（推荐生产使用）**
   - 把 session、登录态、缓存等全部从**内存**移到**外部共享存储**
   - 优先用 Redis：性能高、支持过期、适合会话场景
   - 优点：真正无状态，实例可以随意扩缩容，负载均衡可以任意分发
   - 缺点：需要改代码，引入外部依赖

2. **方案二：粘滞会话（Sticky Sessions）**
   - 同一个用户的所有请求，始终路由到**同一个应用实例**
   - 优点：几乎不用改代码，对原有有状态逻辑兼容
   - 缺点：
     - 负载均衡不够均匀
     - 某实例挂掉，对应用户的状态直接丢失
     - 不利于弹性扩缩容

3. 本书明确倾向：
   > 能重构就用**共享存储（无状态化）**，实在不行再用 sticky sessions。

4. 对 Node + cluster 的意义
   - cluster 多进程之间**内存不共享**
   - 所以必须用外部存储，不能依赖进程内状态

   # 粘滞负载均衡（Sticky Load Balancing）译文 + 核心要点
## 原文翻译
支持有状态通信的另一种方案，是让负载均衡器**把同一个会话的所有请求，始终路由到同一个应用实例**上。这种技术就叫做**粘滞负载均衡**。

如图 12.5 所示：
- 当负载均衡器收到一个新会话的请求时，会通过负载均衡算法选择一个实例，并建立**会话–实例**映射关系；
- 下次收到同一会话的请求时，直接跳过均衡算法，转发到之前绑定的那个实例。

这种实现通常是通过解析请求中的**会话 ID**（一般放在 Cookie 里）来实现的。

另一种更简单的实现方式是**基于客户端 IP 做哈希**：
把客户端 IP 传入哈希函数，计算出固定对应的应用实例。
优点是负载均衡器**不需要记忆映射关系**；
缺点是如果用户 IP 频繁变化（比如切换网络、移动漫游），会话就会失效。

---

粘滞负载均衡的一个**重大缺陷**是：
它几乎抵消了冗余系统的大部分优势——本来所有实例都是等价的、任何一个都可以顶替故障实例，但粘滞会话破坏了这种对等性。

因此，书中给出明确建议：
**尽量避免使用粘滞负载均衡**，优先将应用改造成无状态，把会话状态存入共享存储。
如果条件允许，也可以设计**完全无状态的应用**，例如把状态直接放在请求本身里（如 JWT）。

---

## 核心要点总结
1. **粘滞会话是什么**
   同一个用户/会话 → 永远落在同一个应用实例（worker/服务器）上。

2. **两种常见实现**
   - **Cookie / Session ID 粘滞**：最精准，但负载均衡器需要记录映射
   - **IP Hash 粘滞**：简单、无状态，但 IP 变动会导致会话丢失

3. **优点**
   - 基本不用改代码
   - 可以直接兼容原有内存式有状态逻辑

4. **严重缺点（重点）**
   - 负载分配不均
   - 实例挂掉 → 对应用户会话直接丢失
   - 扩缩容困难，新增实例无法有效分担流量
   - 破坏集群“对等冗余”的核心价值

5. **书中最终推荐方案**
   1. 无状态应用 + **Redis 共享会话**（首选）
   2. 或使用 **JWT** 等自包含令牌，把状态存在客户端
   3. 实在没办法时，才用 sticky sessions
