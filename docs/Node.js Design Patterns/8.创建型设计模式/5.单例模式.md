# 单例模式（Singleton）
单例模式的目的：**保证一个类全局只有一个实例，并提供统一访问点**，常用于数据库连接、配置管理、连接池等。

## Node.js 里最简单的“单例”
直接导出一个实例即可：
```js
// dbInstance.js
import { Database } from './Database.js'

export const dbInstance = new Database('my-app-db', {
  url: 'localhost:5432',
  username: 'user',
  password: 'password'
})
```

因为 **Node.js 模块会被缓存**，所以多次 import 得到的都是同一个对象。
```js
import { dbInstance } from './dbInstance.js'
```

这就是 Node.js 里最普遍、最实用的单例写法。

---

## 巨大坑点：模块缓存按路径缓存
Node 模块缓存的 key 是**模块完整路径**，不是包名。

下面这种结构就会破坏单例：
```
app/
└── node_modules/
    ├── package-a/
    │   └── node_modules/mydb/
    └── package-b/
        └── node_modules/mydb/
```

- package-a 依赖 mydb@1.0.0
- package-b 依赖 mydb@2.0.0

它们会加载**两个完全不同的 dbInstance**，`===` 比较为 `false`。
**严格意义上的单例失效了**。

---

## 真正全局唯一的单例（不推荐）
只有挂到 `global` 才能真正全局唯一：
```js
global.dbInstance = new Database(...)
```

但问题：
- 污染全局命名空间
- 难以测试、难以模拟
- 工程上不规范

---

## 书中结论
- 严格意义的 **GoF 单例在 Node.js 中不存在**
- 工程上，**导出实例的方式已经够用**
- 只有跨包、多版本依赖时才会出问题
- 本书后续所说的“单例”，都指**模块导出的单实例**

---

一句话记住：
**Node.js 单例 = 导出实例 + 模块缓存，但多版本嵌套依赖会破坏它。**

---

# 模块间的依赖连接（Wiring modules）
随着应用变大，**组件如何互相依赖、如何连接**，直接决定项目是否可维护。

当组件 A 要用到组件 B 才能工作时：
- **A depends on B**（A 依赖 B）
- **B is a dependency of A**（B 是 A 的依赖）

书中用一个典型场景举例：
- 博客 API 系统
- `db.js`：数据库连接模块
- `blog.js`：博客文章业务逻辑，需要读写数据库

接下来会对比两种最核心的依赖组织方式：
1. **基于单例的硬依赖**（直接 import 单例）
2. **依赖注入 DI**（外部把依赖传给组件）

---

## 核心一句话总结
- **单例模式**：模块内部直接 import 固定实例，简单但耦合紧、难测试。
- **依赖注入**：外部把依赖“塞进去”，松耦合、易替换、易 mock。

# 单例依赖（Singleton dependencies）
这是 Node.js 中最直接、最常用的模块依赖方式：**一个模块直接 import 另一个模块导出的单例实例**。

## 示例结构
- `db.js`：创建并导出**唯一的 SQLite 数据库连接**
- `blog.js`：业务模块，直接 import 这个数据库实例
- `index.js`：使用 Blog 类

### 1. db.js（导出单例）
```js
import { dirname, join } from 'path'
import { fileURLToPath } from 'url'
import sqlite3 from 'sqlite3'

const __dirname = dirname(fileURLToPath(import.meta.url))

// 全局唯一的数据库连接（单例）
export const db = new sqlite3.Database(join(__dirname, 'data.sqlite'))
```

### 2. blog.js（硬依赖单例）
```js
import { promisify } from 'util'
import { db } from './db.js'  // 直接依赖单例

const dbRun = promisify(db.run.bind(db))
const dbAll = promisify(db.all.bind(db))

export class Blog {
  initialize() {
    const query = `CREATE TABLE IF NOT EXISTS posts (...);`
    return dbRun(query)
  }

  createPost(id, title, content, createdAt) {
    return dbRun('INSERT INTO posts VALUES (?,?,?,?)', id, title, content, createdAt)
  }

  getAllPosts() {
    return dbAll('SELECT * FROM posts ORDER BY created_at DESC')
  }
}
```

### 3. index.js（使用）
```js
import { Blog } from './blog.js'

async function main() {
  const blog = new Blog()
  await blog.initialize()
  const posts = await blog.getAllPosts()
  // ...
}
main().catch(console.error)
```

---

## 优点
- 极其简单、直观
- 不用手动传递依赖
- 天然利用 Node 模块缓存实现单例

## 致命缺点
- **紧耦合**：`Blog` 类**死死绑定 SQLite**
- **无法测试**：很难替换成内存数据库或 mock
- **无法切换数据源**：想换 MySQL/PostgreSQL 必须改源码
- **不灵活**：多实例、多配置场景很难支持

---

## 书中总结
单例依赖适合**简单、稳定、不需要替换**的场景。
但一旦需要**mock、多环境、多后端、可测试**，单例就变成障碍。

下一节：**依赖注入（Dependency Injection）**，专门解决这些问题。

# 依赖注入（Dependency Injection）
依赖注入的核心思想非常简单：
**组件不再自己“找”依赖，而是由外部把依赖“给”它。**

这样就能彻底解除紧耦合，让模块可替换、可测试、可复用。

---

## 改造后的代码结构

### 1. db.js —— 不再导出单例，改为工厂函数
```js
import sqlite3 from 'sqlite3'

// 工厂：按需创建数据库实例
export function createDb(dbFile) {
  return new sqlite3.Database(dbFile)
}
```

### 2. blog.js —— 不再硬编码 import db
```js
import { promisify from 'util'

export class Blog {
  // 依赖从构造器注入
  constructor(db) {
    this.db = db
    this.dbRun = promisify(db.run.bind(db))
    this.dbAll = promisify(db.all.bind(db))
  }

  initialize() {
    const query = `CREATE TABLE IF NOT EXISTS posts (...);`
    return this.dbRun(query)
  }

  createPost(id, title, content, createdAt) {
    return this.dbRun(
      'INSERT INTO posts VALUES (?,?,?,?)',
      id, title, content, createdAt
    )
  }

  getAllPosts() {
    return this.dbAll('SELECT * FROM posts ORDER BY created_at DESC')
  }
}
```

变化：
- 不再 `import { db } from './db.js'`
- 数据库实例通过 **构造器传入**
- `Blog` 不关心 db 是 SQLite、MySQL 还是 mock
- 只要实现 `run()` 和 `all()` 就能用（鸭子类型）

### 3. index.js —— 充当“注入器（injector）”
```js
import { dirname, join } from 'path'
import { fileURLToPath } from 'url'
import { Blog } from './blog.js'
import { createDb } from './db.js'

const __dirname = dirname(fileURLToPath(import.meta.url))

async function main() {
  // 1. 创建依赖
  const db = createDb(join(__dirname, 'data.sqlite'))

  // 2. 注入依赖
  const blog = new Blog(db)

  await blog.initialize()
  const posts = await blog.getAllPosts()
  // ...
}

main().catch(console.error)
```

---

## 依赖注入的优点
- **低耦合**：`Blog` 不绑定任何具体数据库
- **可测试**：测试时可以轻松传入内存数据库 / mock
- **可配置**：可以轻松切换 SQLite / MySQL / PostgreSQL
- **可复用**：同一个 `Blog` 类可以连接不同库实例
- **更清晰的依赖关系**：一看构造器就知道需要什么

---

## 缺点
- 必须手动维护**依赖创建顺序**
- 大型应用依赖关系复杂，手写会很繁琐
- 代码跳转不如直接 import 直观

---

## 三种注入方式
1. **构造器注入**（本节示例）
2. **方法注入**：调用函数时传入
3. **属性注入**：直接赋值给对象属性

---

## 进阶：控制反转（IoC）/ DI 容器
当依赖太多太复杂时，可以用容器自动管理：
- inversify
- awilix

它们会自动扫描、实例化、按顺序注入，不用手写依赖链。

---

## 一句话总结
**单例是“组件自己抓依赖”，DI 是“外部把依赖递给组件”。**
DI 让模块彻底解耦、可测试、可替换，是大型 Node.js 项目的标准工程实践。
