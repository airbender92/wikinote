# Middleware 中间件模式
中间件是 Node.js 最具代表性、最核心的模式之一，也是很多新手最容易困惑的概念。

## 核心一句话定义
**Middleware = 中间件 = 插在“请求/处理”流程中的一层或多层处理函数**
它们按顺序执行，每个中间件可以：
- 处理输入
- 修改数据
- 决定是否继续往后执行
- 提前结束流程

## 书中对“中间件”含义的澄清
在传统企业架构里：
- middleware 指**底层系统软件**，比如 CORBA、ESB、消息队列、应用服务器等，用来屏蔽 OS、网络、内存等细节。

但在 **Node.js / Web 开发**里：
- middleware 是**轻量级处理链条**
- 位于“请求 → 响应”之间
- 每个中间件只做一件事
- 可组合、可复用、可插拔

典型代表：
- Express/Koa 的中间件
- Redux 中间件
- Next.js 中间件

# Express 中的中间件
Express 让 **Middleware** 成为 Node.js 里的标准模式，核心就是：**管道化的请求/处理函数链**。

## 中间件签名
```js
function (req, res, next) { ... }
```
- `req`：请求对象
- `res`：响应对象
- `next()`：调用下一个中间件

## 典型作用（都属于“中间”任务）
- 解析请求体 body
- 压缩 / 解压
- 日志记录
- 会话管理
- CSRF 防护
- 权限校验
- 路由分发

它们**不属于核心业务逻辑**，但为业务提供支撑，让路由处理器只关心业务本身。

---

# 核心思想
**中间件 = 可插拔、可组合、可复用的处理层**
每个中间件只做一件事，按顺序执行，构成请求处理管道。

# 中间件作为通用设计模式
中间件本质是 **拦截过滤器 + 责任链模式** 在 Node.js 中的实现，也可以看作一条**异步处理流水线**，和流的思想非常像。

它早已不局限于 Express，而是一套通用架构模式：
用一组函数串联起来，对数据做**前置/后置处理**，实现高度灵活的插件化扩展。

---

## 核心结构
1. **Middleware 中间件**
   处理函数，负责数据加工、校验、日志等。
2. **Middleware Manager 中间件管理器**
   负责注册、排序、执行中间件。
3. **use()**
   注册中间件的约定方法（通用惯例）。

---

## 核心运行规则
- 中间件按注册顺序**异步串行执行**
- 每个中间件可以拿到上一步处理后的数据
- 每个中间件可以选择：
  - 调用 next() 继续下一个
  - 提前结束流程
  - 抛出错误，进入错误处理链
- 数据传递方式灵活：
  - 直接扩展对象（Express 的 req/res）
  - 或 immutable 方式，每次返回新副本

---

## 核心优势
- **极高灵活性**：像插件一样插拔
- **非侵入式扩展**：不改动核心逻辑
- **关注点分离**：日志、鉴权、压缩、业务逻辑解耦
- **复用性强**：一个中间件可在多处使用

---

一句话概括：
**中间件 = 可组合的异步处理流水线，是 Node.js 生态最通用的插件化架构模式。**

# 基于 ZeroMQ 实现中间件框架
这一节是用一个真实场景，**从零实现一套中间件引擎**，用来包装 ZeroMQ 底层消息，实现：
- 自动 JSON 序列化/反序列化
- 透明压缩/解压
- 日志、校验等可插拔处理层

## 核心思路
ZeroMQ 本身只收发字符串 / Buffer，我们用**中间件管道**包裹它：
1. 发送时：数据 → JSON → 压缩 → 发出
2. 接收时：收到 → 解压 → JSON 解析 → 业务逻辑

每层都是一个中间件，可自由增删。

---

## 结构要点
- **MiddlewareManager**：管理中间件列表，提供 `use()`
- 中间件签名：`(data, next)`
  - `data`：要处理的消息对象
  - `next()`：进入下一个中间件
- 支持**串行执行** + **提前终止** + **错误传递**

---

## 最终能实现的效果
```js
const zmqMware = new ZmqMiddlewareManager(socket)

// 中间件1：JSON 序列化/反序列化
zmqMware.use(jsonMiddleware())

// 中间件2：压缩/解压
zmqMware.use(compressMiddleware())

// 业务处理
zmqMware.use(async (data) => {
  console.log('received:', data)
})

// 发送业务对象，自动走管道
zmqMware.send({ hello: 'world' })
```

完全不用关心底层编解码、压缩，中间件自动处理。

# 中间件管理器核心精讲
这段代码是**整个中间件模式的底层引擎**，完全手写实现，看懂它就彻底懂了 Express/Koa。

## 1. 类结构
```js
export class ZmqMiddlewareManager {
  constructor(socket) {
    this.socket = socket          // ZeroMQ 原始 socket
    this.inboundMiddleware = []    // 接收消息的中间件链
    this.outboundMiddleware = []   // 发送消息的中间件链

    this.handleIncomingMessages().catch(console.error)
  }
}
```

---

## 2. 监听消息（异步迭代器）
```js
async handleIncomingMessages() {
  // ZeroMQ socket 是异步可迭代对象
  for await (const [message] of this.socket) {
    await this.executeMiddleware(this.inboundMiddleware, message)
      .catch(err => console.error('Error processing message', err))
  }
}
```
- 使用 `for await...of` 消费消息流
- 每收到一条消息，就**完整跑一遍 inbound 中间件**

---

## 3. 发送消息
```js
async send(message) {
  const finalMsg = await this.executeMiddleware(
    this.outboundMiddleware,
    message
  )
  return this.socket.send(finalMsg)
}
```
- 业务层传入 JS 对象
- 经过 outbound 中间件处理
- 最终发送二进制/字符串数据

---

## 4. 注册中间件（最精髓的细节）
```js
use(middleware) {
  if (middleware.inbound) {
    this.inboundMiddleware.push(middleware.inbound)
  }
  if (middleware.outbound) {
    this.outboundMiddleware.unshift(middleware.outbound)
  }
}
```

### 关键设计：**进出顺序相反**
- inbound：用 `push` → 顺序执行
- outbound：用 `unshift` → **逆序执行**

为什么？
示例：
- 收消息：解压 → JSON 解析
- 发消息：JSON 序列化 → 压缩

所以注册顺序必须反过来，才能对称处理。

---

## 5. 执行中间件管道（核心引擎）
```js
async executeMiddleware(middlewares, initialMessage) {
  let message = initialMessage

  for await (const middlewareFunc of middlewares) {
    // 每个中间件可以是 async 函数
    message = await middlewareFunc.call(this, message)
  }

  return message
}
```

### 工作模式
1. 从上一个中间件拿到结果
2. 传给下一个中间件
3. 全部执行完返回最终数据
4. 完全支持 **async/await**

这就是**异步责任链模式**。

---

# 整体流程总结
### 接收消息
socket 消息 → inbound 中间件1 → 中间件2 → … → 业务逻辑

### 发送消息
业务数据 → outbound 中间件1 → 中间件2 → … → socket 发送

且 **outbound 执行顺序与 inbound 相反**，实现对称编解码。

# 实现具体的消息处理中间件
现在基于我们的中间件引擎，实现两个通用中间件：**JSON 序列化/反序列化** 和 **压缩/解压**，完美体现中间件模式的解耦与复用。

## 1. JSON 中间件
```js
// jsonMiddleware.js
export const jsonMiddleware = () => {
  return {
    // 入站：Buffer/字符串 → JS 对象
    inbound(message) {
      return JSON.parse(message.toString())
    },

    // 出站：JS 对象 → Buffer
    outbound(message) {
      return Buffer.from(JSON.stringify(message))
    }
  }
}
```

---

## 2. Zlib 压缩/解压中间件
```js
// zlibMiddleware.js
import { inflateRaw, deflateRaw } from 'zlib'
import { promisify } from 'util'

const inflateRawAsync = promisify(inflateRaw)
const deflateRawAsync = promisify(deflateRaw)

export const zlibMiddleware = () => {
  return {
    // 入站：解压
    inbound(message) {
      return inflateRawAsync(Buffer.from(message))
    },

    // 出站：压缩
    outbound(message) {
      return deflateRawAsync(message)
    }
  }
}
```

特点：
- 是**异步中间件**，返回 Promise
- 我们的引擎支持 `await`，可以直接用

# 整体数据流（最关键）
假设先后注册：
```js

```

## 接收消息（inbound）顺序
1. 收到网络二进制
2. **zlib.inbound** → 解压
3. **json.inbound** → JSON.parse 转为对象
4. 交给业务逻辑

## 发送消息（outbound）顺序
因为 use() 里对 outbound 使用了 **unshift**，顺序会反过来：
1. 业务层传入 JS 对象
2. **json.outbound** → JSON.stringify + to Buffer
3. **zlib.outbound** → 压缩
4. 发送到网络

> 入站：先解压再解析
> 出站：先序列化再压缩
>
> 对称且自动完成，业务层完全无感。

# 使用 ZeroMQ 中间件框架（完整流程梳理）
最后这部分把前面写的**中间件管理器 + JSON + zlib 中间件**拼成一个可运行的 C/S 应用，彻底跑通整个模式。

## 一、服务端 server.js
1. 创建 ZeroMQ **Reply** 套接字并绑定端口
2. 用 `ZmqMiddlewareManager` 包装 socket
3. 按顺序加入中间件：
   - zlib 压缩/解压
   - JSON 序列化/反序列化
4. 最后加一个**业务中间件**，处理 `ping` 并回复 `pong`

```js
import zeromq from 'zeromq'
import { ZmqMiddlewareManager } from './zmqMiddlewareManager.js'
import { jsonMiddleware } from './jsonMiddleware.js'
import { zlibMiddleware } from './zlibMiddleware.js'

async function main() {
  const socket = new zeromq.Reply()
  await socket.bind('tcp://127.0.0.1:5000')

  const zmqm = new ZmqMiddlewareManager(socket)
  zmqm.use(zlibMiddleware())
  zmqm.use(jsonMiddleware())

  // 业务逻辑中间件
  zmqm.use({
    async inbound(message) {
      console.log('Received', message)
      if (message.action === 'ping') {
        await this.send({ action: 'pong', echo: message.echo })
      }
      return message
    }
  })

  console.log('Server started')
}

main()
```

## 二、客户端 client.js
1. 创建 ZeroMQ **Request** 套接字并连接服务器
2. 中间件配置和服务端**完全一样**
3. 定时 send 一个 `{ action: 'ping' }` 对象
4. 收到回包后打印日志

```js
import zeromq from 'zeromq'
import { ZmqMiddlewareManager } from './zmqMiddlewareManager.js'
import { jsonMiddleware } from './jsonMiddleware.js'
import { zlibMiddleware } from './zlibMiddleware.js'

async function main() {
  const socket = new zeromq.Request()
  await socket.connect('tcp://127.0.0.1:5000')

  const zmqm = new ZmqMiddlewareManager(socket)
  zmqm.use(zlibMiddleware())
  zmqm.use(jsonMiddleware())

  zmqm.use({
    inbound(message) {
      console.log('Echoed back', message)
      return message
    }
  })

  // 每秒发 ping
  setInterval(() => {
    zmqm.send({ action: 'ping', echo: Date.now() })
      .catch(console.error)
  }, 1000)

  console.log('Client connected')
}

main()
```

## 三、运行方式
```bash
node server.js
# 新开终端
node client.js
```

## 四、实际数据流（全程透明）
### 客户端发送
业务对象 → JSON 序列化 → zlib 压缩 → 网络发送

### 服务端接收
网络数据 → zlib 解压 → JSON 解析 → 业务逻辑处理

回复时再反向走一遍：
业务对象 → JSON → zlib → 发回客户端

业务代码**完全不关心编解码和压缩**，这就是中间件模式的威力。
