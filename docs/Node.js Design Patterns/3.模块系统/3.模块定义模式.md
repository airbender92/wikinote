# 模块定义模式 p62
模块系统不只是加载依赖的机制，更是**定义 API 的工具**。
和所有 API 设计一样，核心是平衡**私有逻辑与公开接口**：
尽量做到信息隐藏、API 易用，同时兼顾可扩展性与复用性。

本节介绍几种最常用的 CommonJS 模块定义模式：
命名导出、导出函数、导出类/实例、猴子补丁等，它们在封装性、扩展性上各有侧重。

---

## 命名导出（Named exports）
最基础的公开 API 方式，就是给 `exports` 添加属性，把一组相关功能放在同一个导出对象里，形成一个**命名空间**。

示例：`logger.js`
```javascript
exports.info = (message) => {
  console.log(`info: ${message}`)
}

exports.verbose = (message) => {
  console.log(`verbose: ${message}`)
}
```

使用：
```javascript
const logger = require('./logger')
logger.info('This is an informational message')
logger.verbose('This is a verbose message')
```

特点：
- 导出多个公开方法，结构清晰
- Node.js 内置核心模块大量使用这种模式
- **真正完全符合 CommonJS 规范**的唯一模式
- `module.exports` 是 Node 扩展，用来支持更灵活的导出方式

# 导出函数（Substack 模式）
## 核心定义
这种模块导出方案是 Node.js 最主流的模式之一：直接将 `module.exports` 完整赋值为一个函数，业内又称 **Substack 模式**（得名于知名开源作者 substack）。
### 核心优势
1. **单一清晰入口**：模块只暴露核心主功能，贴合「最小暴露面」设计原则，API 简洁易懂；
2. **单一职责（SRP）**：天然贯彻 Node 小模块思想，一个模块只聚焦一项核心能力；
3. 可扩展：导出的函数本身也是对象，能挂载附属方法作为扩展 API。

## 基础示例（仅导出主函数）
```js
// logger.js
module.exports = (message) => {
  console.log(`info: ${message}`)
}
```

## 扩展写法：函数挂载附属方法
把次要、高级功能作为主函数的属性挂载，保留唯一主入口的同时提供扩展能力：
```js
// logger.js
// 核心主方法
module.exports = (message) => {
  console.log(`info: ${message}`)
}
// 附属扩展API
module.exports.verbose = (message) => {
  console.log(`verbose: ${message}`)
}
```

## 使用方式
```js
// main.js
const logger = require('./logger')
// 调用核心主功能
logger('普通日志信息')
// 调用扩展方法
logger.verbose('详细日志信息')
```

## 设计思想
只把最重要的能力作为模块直接调用入口，次要功能依附于主函数，弱化内部/辅助逻辑的存在感，对外接口干净简约，完全契合 Node 模块化设计理念。

# 导出类（Class 导出模式）
## 核心说明
导出类是**导出函数（Substack 模式）**的衍生变体。二者都只提供单一模块入口，但区别在于：导出的类允许使用者通过构造函数创建多个实例，同时还能基于原型对类进行继承、扩展，灵活性更高。

## 代码示例
### 模块文件 logger.js（导出类）
```javascript
class Logger {
  constructor (name) {
    this.name = name
  }
  log (message) {
    console.log(`[${this.name}] ${message}`)
  }
  info (message) {
    this.log(`info: ${message}`)
  }
  verbose (message) {
    this.log(`verbose: ${message}`)
  }
}
// 将类整体导出
module.exports = Logger
```

### 引入使用 main.js
```javascript
const Logger = require('./logger')
// 创建数据库日志实例
const dbLogger = new Logger('DB')
dbLogger.info('This is an informational message')
// 创建访问日志实例
const accessLogger = new Logger('ACCESS')
accessLogger.verbose('This is a verbose message')
```

## 模式优缺点对比
1. **优势**
    - 依旧保持单一入口；
    - 支持多实例，每个实例拥有独立内部状态（如示例里的 `name`）；
    - 支持原型扩展、类继承，拓展能力远强于直接导出普通函数。
2. **劣势**
    相比 Substack 纯函数模式，会暴露更多内部原型与实例相关逻辑，对外暴露的内容更多，违背「最小暴露面」原则。

## 适用场景
需要维护独立状态、支持多实例、需要对外提供继承拓展能力的工具模块。

# 导出实例模式
## 核心原理
利用 CommonJS 的**模块缓存机制**，直接导出类的实例，实现跨文件共享同一个带状态对象，效果近似单例。

## 示例代码
### 模块 logger.js
```javascript
class Logger {
  constructor (name) {
    this.count = 0 // 实例状态
    this.name = name
  }
  log (message) {
    this.count++
    console.log('[' + this.name + '] ' + message)
  }
}
// 直接实例化并导出
module.exports = new Logger('DEFAULT')
```

### 调用文件 main.js
```javascript
const logger = require('./logger')
logger.log('This is an informational message')
```

## 关键特性
1. **全局共享状态**
`require` 会缓存模块，项目内所有文件导入该模块拿到的都是**同一个实例**，实例内部变量（如示例 `count`）会全局共用。

2. 并非真正全局单例
依赖 Node 路径解析规则：如果依赖树里不同目录下安装了该包，会生成多份 `node_modules`，对应多份模块缓存，产生多个独立实例，传统单例的全局唯一性无法保证。第七章会深入讲解单例模式的坑。

3. 仍可创建新实例（不推荐）
虽然没有直接导出 `Logger` 类，但导出实例自带 `constructor` 属性，可以手动新建对象：
```javascript
const customLogger = new logger.constructor('CUSTOM')
customLogger.log('This is an informational message')
```
模块作者隐藏类本意就是不对外暴露构造器，该写法破坏封装，生产环境慎用。

## 适用场景
需要全局统一状态、全局共享工具对象（全局日志、全局配置管理器等）。

# 猴子补丁：修改其他模块 / 全局作用域
## 概念说明
该模式又称**猴子补丁（Monkey Patching）**：模块可以不导出任何内容，仅在运行时修改全局变量，或是修改缓存中其他模块的导出对象，以此扩展、修复第三方模块能力。
### 适用有限场景
仅单元测试模拟接口（如 nock 拦截 HTTP 请求）等场景有使用价值，**整体属于反面实践、强烈不推荐业务代码使用**。

## 代码示例
### 补丁模块 patcher.js
引入 logger 模块，给它新增自定义方法，无任何导出：
```javascript
// 加载目标模块并修改其导出对象
require('./logger').customMessage = function () {
  console.log('This is a new functionality')
}
```

### 业务入口 main.js
只需先引入补丁模块，后续所有地方拿到的 logger 都会带上新增方法：
```javascript
require('./patcher') // 执行补丁逻辑
const logger = require('./logger')
logger.customMessage() // 可调用新增方法
```

## 核心风险（副作用问题）
1. **不可预期冲突**：多个补丁模块修改同一个模块的同名属性，后加载的会覆盖前者，行为不可控，难以定位BUG；
2. 污染全局/模块缓存：修改会作用于项目所有引入该模块的文件，影响范围是全应用；
3. 破坏封装：第三方模块未对外暴露的内部逻辑被强行篡改，版本升级后极易失效；
4. ESM 环境限制更大：ESM 导入是只读实时绑定，无法直接修改导入变量，仅能修改导出对象内部属性，补丁写法更受限。

## 使用建议
仅在单元测试、临时兼容补丁场景谨慎使用；业务业务开发优先通过封装、继承扩展模块功能，避免猴子补丁。
