# 全文翻译
## 模块系统
在第一章《Node.js 平台》中，我们简要介绍了模块在 Node.js 中的重要性，也讲到模块是支撑 Node 开发理念、塑造开发体验的核心支柱。但我们究竟该如何定义模块？模块又为何如此关键？

广义上来说，模块是构建复杂应用的基础单元。借助模块，我们可以把代码拆分成多个独立单元，分开开发、单独测试。同时，模块也是实现**信息隐藏**的核心机制：所有变量、函数默认私有，只有显式导出的内容才能被外部访问。

如果你接触过其他编程语言，会发现类似概念只是叫法不同：Java/Go/PHP/Rust/Dart 称之为包（package）、.NET 叫程序集（assembly）、Ruby 是库（library）、Pascal 系列语言称为单元（unit）。这些术语不能完全等同，但核心思想高度重合。

值得注意的是，Node.js 同时内置两套模块体系：CommonJS（简称 CJS）与 ES 模块（简称 ESM）。本章会讲解两套模块并存的由来、各自优劣，同时分析开发中常用的模块设计范式。读完本章，你将能结合实际场景，合理选择、编写自定义模块。

吃透 Node 的两套模块系统与相关设计模式至关重要，本书后续所有章节都会以此知识为基础。

本章核心内容概览：
1. 模块存在的意义，以及 JS / Node 中各类模块体系
2. CommonJS 底层原理与常用模块导出模式
3. Node 环境下的 ES 模块（ESM）完整用法
4. CJS 与 ESM 的差异、二者互操作方案

下面我们从「为什么需要模块」开始讲解。

# 核心要点解读
## 1. 模块三大核心价值
1. **代码拆分**：巨型项目拆分为独立小文件，降低维护成本；
2. **独立开发测试**：单个模块可单独调试、单元测试；
3. **封装隔离（信息隐藏）**：内部变量、函数默认私有，仅暴露对外 API，避免全局污染、外部随意篡改内部逻辑。

## 2. 各语言同类概念对比
不同语言命名有区别，但核心都是「代码隔离、复用单元」，各自附带语言独有的配套规则（如 Java 包访问修饰符、Go 包导出首字母大小写规则）。

## 3. 两套模块并存的背景
1. CommonJS：Node 诞生之初 JS 无官方模块标准，社区自研，长期是 Node 默认模块；
2. ESM：ES2015（ES6）官方标准化模块语法，浏览器与 Node 统一标准，Node 后期稳定支持；
两套标准语法、加载逻辑、循环依赖处理机制完全不同，是 Node 开发最易踩坑的知识点之一。

## 4. 本章学习意义
模块是所有 Node 代码的基础组织形式，异步、流、设计模式、微服务等全部代码示例都会基于模块编写，是全书前置核心基础。

# 中文翻译
## 模块存在的必要性
一套完善的模块系统，需要解决软件工程中的四大核心诉求：
1. **代码分文件管理**
能够将庞大代码库拆分为多个独立文件，让代码结构更清晰、易于阅读理解；同时各功能模块可独立开发、单独测试。
2. **跨项目复用代码**
模块可封装通用能力，多个项目都能直接引入使用，无需重复编写相同逻辑。
3. **封装（信息隐藏）**
隐藏内部复杂实现，只对外提供简洁、职责清晰的接口。绝大多数模块系统支持区分私有代码与公开API，内部变量/函数对外不可见，仅暴露供外部调用的函数、类、对象。
4. **依赖管理**
开发者可以便捷地基于第三方模块搭建业务；使用者引入模块时，能自动加载该模块所需的全部间接依赖（传递依赖）。

我们需要区分**模块**与**模块系统**两个概念：
- 模块：承载代码的独立软件单元；
- 模块系统：定义模块如何声明、导入导出的语法规则与配套工具体系。

# 中文翻译
## JavaScript 与 Node.js 中的模块系统
并非所有编程语言都内置模块系统，而 JavaScript 在很长一段时间里都缺失这项核心特性。

在浏览器环境中，可以把代码拆分成多个文件，再通过不同的 `<script>` 标签引入。多年以来，这种方式足以构建简单的交互式网站，JavaScript 开发者即便没有成熟的模块系统也能完成开发。

直到浏览器端 JavaScript 应用变得愈发复杂，jQuery、Backbone、AngularJS 等框架占据生态主流，社区才陆续推出多种方案，试图定义一套能在项目中广泛落地的模块系统。其中最成功的是由 RequireJS 普及的**AMD（异步模块定义）**，以及后来出现的**UMD（通用模块定义）**。

Node.js 诞生时，被定位为可直接访问文件系统的 JavaScript 服务端运行时，这为引入全新的模块管理方式提供了契机。它不再依赖 HTML 的 `<script>` 标签和 URL 资源，而是完全基于本地文件系统中的 JS 文件实现模块化。Node.js 采用并实现了 **CommonJS（CJS）** 规范，这套规范专为无浏览器环境的 JavaScript 设计了模块系统。

自诞生以来，CommonJS 一直是 Node.js 中占主导地位的模块系统；借助 Browserify、webpack 这类打包工具，它在浏览器端也得到了广泛应用。

2015 年，ECMAScript 6（ES2015）发布，JavaScript 终于有了官方标准模块系统：**ESM，即 ECMAScript 模块**。ESM 为 JS 生态带来诸多革新，其中一个重要目标就是统一浏览器与服务端的模块管理方式。

ES6 只从语法和语义层面定义了 ESM 规范，并未提供具体实现细节。各大浏览器厂商与 Node.js 社区花费数年时间，才推出稳定可靠的实现。Node.js 从 **13.2 版本**开始正式稳定支持 ESM。

截至本文撰写时，行业普遍认为 ESM 终将成为浏览器与服务端统一的事实标准。但现实是，目前绝大多数项目仍重度依赖 CommonJS，ESM 想要全面赶超并成为主流仍需要时间。

为全面讲解 Node.js 中的模块化模式，本章前半部分会基于 CommonJS 展开讨论，后半部分再用 ESM 重新梳理相关知识点。
本章目标是让你熟练掌握两套模块系统，而本书后续所有代码示例**只使用 ESM**，以此鼓励你尽量采用 ESM，让代码更具前瞻性。

如果你是在本书发布多年后才阅读本章，或许已经不太关心 CommonJS，可以直接跳到 ESM 部分。但我们仍建议你通读全章，因为理解 CommonJS 的特性，能帮你更深刻地理解 ESM 及其优势。

# 中文翻译
## 模块系统及其设计模式
正如我们所说，模块是构建复杂应用的基石，也是实现**信息隐藏**的主要机制——所有未被显式标记导出的函数和变量都会保持私有。

在深入 CommonJS 细节之前，我们先介绍一种通用的信息隐藏模式，它也是构建简易模块系统的基础：**揭示模块模式（Revealing Module Pattern）**。

### 揭示模块模式
早期浏览器端 JavaScript 最大的问题之一就是**缺少命名空间**。所有脚本都运行在全局作用域中，因此应用内部代码或第三方依赖都可能污染全局作用域，同时暴露自身功能。这会带来极大隐患。
例如，某个第三方库创建了一个名为 `utils` 的全局变量，如果其他库或应用代码意外重写或修改了 `utils`，依赖它的代码就可能以不可预料的方式崩溃。如果其他代码意外调用了某个库仅用于内部的函数，同样会产生不可预测的副作用。

简单来说，依赖全局作用域是非常危险的做法，尤其当应用规模变大、需要依赖越来越多外部代码时。

解决这类问题的一种流行技术叫做**揭示模块模式**，写法如下：
```javascript
const myModule = (() => {
  const privateFoo = () => {}
  const privateBar = []

  const exported = {
    publicFoo: () => {},
    publicBar: () => {}
  }

  return exported
})() 
// 括号解析完成后，函数会立即执行

console.log(myModule)
console.log(myModule.privateFoo, myModule.privateBar)
```

该模式利用了**自执行函数**，也常被称为**立即执行函数表达式（IIFE）**。它用于创建一个私有作用域，只对外暴露公开部分的功能。

在 JavaScript 中，函数内部创建的变量无法从外部作用域访问；函数可以通过 `return` 有选择地向外暴露内容。

该模式正是利用这一特性隐藏私有信息，只导出面向外部的公共 API。

在上面的代码中，`myModule` 变量只包含导出的 API，模块内部其余内容从外部几乎无法访问。

两条打印语句会输出类似这样的结果：
```
{ publicFoo: [Function: publicFoo],
  publicBar: [Function: publicBar] }
undefined undefined
```

这证明只有被导出的属性才能通过 `myModule` 直接访问，内部成员均为 `undefined`。

稍后我们会看到，这个模式背后的思想正是 CommonJS 模块系统的设计基础。

### 手写一个简易模块加载器
为了理解 Node.js 中 CommonJS 的工作原理，我们从零实现一个简化版的模块系统，模拟 Node 原生 `require()` 的部分行为。

首先创建一个函数，负责加载模块内容、包裹进私有作用域并执行：
```javascript
function loadModule (filename, module, require) {
  const wrappedSrc =
  `(function (module, exports, require) {
    ${fs.readFileSync(filename, 'utf8')}
  })(module, module.exports, require)`
  eval(wrappedSrc)
}
```
模块的源码会被**包裹进一个函数**，和揭示模块模式思路一致。区别在于，我们主动传入了 `module`、`exports`、`require` 三个变量。
注意包裹函数的 `exports` 参数，初始值就是 `module.exports`，这点后面会重点讲。

另一个重要细节：这里使用 `readFileSync` 同步读取文件。
虽然通常不推荐使用同步文件 API，但加载模块时**必须同步**。因为 CommonJS 设计就是**同步加载模块**，确保多个模块及其依赖能按正确顺序加载。本章后面会详细说明。

接下来实现 `require()` 函数：
```javascript
function require (moduleName) {
  console.log(`Require invoked for module: ${moduleName}`)
  const id = require.resolve(moduleName)      // (1)

  if (require.cache[id]) {                     // (2)
    return require.cache[id].exports
  }

  // 模块元数据
  const module = {                             // (3)
    exports: {},
    id
  }

  require.cache[id] = module                   // (4)

  loadModule(id, module, require)              // (5)

  return module.exports                        // (6)
}

require.cache = {}
require.resolve = (moduleName) => {
  /* 从模块名解析出完整绝对路径（模块 ID） */
}
```

> 注意：这只是教学示例，真实项目里极少需要手动执行源码。
> `eval()` 或 `vm` 模块功能若使用不当，极易引发代码注入攻击。
> 必须极度谨慎，或尽量避免使用。

上面的函数模拟了 Node 原生 `require` 的行为，虽不完全精确还原，但足以理解 Node 模块系统底层原理：模块如何被定义、加载、缓存。

简易模块系统的执行流程：
1. 接收模块名，通过 `require.resolve()` 解析出**完整路径 ID**。
2. 如果模块已加载过，缓存中存在，直接返回缓存的导出对象。
3. 首次加载时，创建 `module` 对象，包含一个空的 `exports` 对象，用于存放对外暴露的 API。
4. 将模块对象存入缓存。
5. 读取模块文件源码并执行，模块代码通过修改 `module.exports` 导出公共 API。
6. 最后将 `module.exports` 返回给调用方。

可以看到，Node 模块系统并没有什么魔法。
核心技巧就是：**给模块源码包一层函数，并构造一个特定运行环境**。

# 核心要点总结
1. **CommonJS 本质**
   每个模块都会被自动包裹进一个函数作用域，接收 `module`、`exports`、`require`，实现天然私有性。

2. **加载流程（极简版）**
   解析路径 → 查缓存 → 新建 module 对象 → 加载并执行源码 → 缓存 → 返回 exports

3. **同步加载**
   `require` 是同步的，保证加载顺序，这也是 CommonJS 只能用于服务端文件系统、不适合浏览器的原因。

4. **模块缓存**
   一个模块无论被 `require` 多少次，只会加载执行一次，导出单例对象。

5. **包裹函数是关键**
   正是这个外层函数，让每个模块拥有独立作用域，不会污染全局。


# 2. 为什么要包一层函数？
Node 里每个模块都有自己独立作用域，**不会污染全局**，靠的就是这层函数。

它相当于把你的代码从：
```js
// a.js
const a = 1
exports.a = a
```

变成：
```js
(function(module, exports, require) {
  const a = 1
  exports.a = a
})(module, module.exports, require)
```

这样：
- `const a` 只在这个函数作用域里
- 不会跑到 global 上
- 每个模块都有自己的 `module` 和 `exports`

这就是 Node 模块**私有化**的根本原理。

---

# 3. 参数是怎么传的？
```js
(function (module, exports, require) {
  // 你的代码
})(module, module.exports, require)
```

对应关系：
- 形参 `module` ← 实参 `module`
- 形参 `exports` ← 实参 `module.exports`
- 形参 `require` ← 实参 `require`

所以你在模块里写的：
- `require()`
- `module.exports`
- `exports.xxx`

其实都是**外面传进去的对象**，不是天生就有的。

---

# 4. eval 在这里干嘛？
`fs.readFileSync` 拿到的是**字符串**，不是可执行代码。

`eval(wrappedSrc)` 就是把这个拼接好的字符串**当成 JS 代码运行**。

这就是 Node 底层加载并执行模块的简化版逻辑。

---

这段代码是：
**手写模拟 Node.js 模块加载器**
- 读文件

- 注入 module、exports、require
- 执行代码

## 定义一个模块
通过我们刚才手写的 `require()` 原理，现在你应该能完全理解**如何定义一个 CommonJS 模块**了。看下面这个示例：

```javascript
// 加载另一个依赖模块
const dependency = require('./anotherModule')

// 私有函数（外部无法访问）
function log() {
  console.log(`Well done ${dependency.username}`)
}

// 导出供外部使用的公共 API
module.exports.run = () => {
  log()
}
```

这里最重要的原则是：
**模块内的所有内容默认都是私有的，除非被显式挂载到 `module.exports` 上。**

当其他文件用 `require()` 加载这个模块时，得到的就是 `module.exports` 的内容，并且会被**缓存**起来，后续重复引入都只会返回同一个对象。

---

## module.exports 与 exports 的区别
很多刚接触 Node.js 的开发者，都会对 `exports` 和 `module.exports` 感到困惑。
结合我们刚才手写的 `require()` 原理，一切就非常清晰了：

**`exports` 变量仅仅是 `module.exports` 初始值的一个引用。**

我们已经知道，模块加载前会创建一个空对象：
```javascript
module.exports = {}
```
然后 Node 会把它赋值给 `exports`：
```javascript
exports = module.exports
```

这意味着：
- 我们**只能给 `exports` 引用的对象添加新属性**，这样是有效的：
  ```javascript
  exports.hello = () => {
    console.log('Hello')
  }
  ```

- 但如果直接**重新赋值 `exports` 本身**，不会有任何作用，因为它只是一个局部变量，修改它不会改变 `module.exports`：
  ```javascript
  // 错误！不会对外导出任何东西
  exports = () => {
    console.log('Hello')
  }
  ```

- 如果想导出**函数、类、字符串等非对象类型**，必须直接覆盖 `module.exports`：
  ```javascript
  // 正确
  module.exports = () => {
    console.log('Hello')
  }
  ```

### 一句话总结
- **`exports` = `module.exports` 的快捷引用**
- 挂载属性用：`exports.xxx = xxx`
- 整个导出单一值用：`module.exports = xxx`
- 永远不要直接重新赋值 `exports`

---

# require 函数是同步的
我们必须牢记一个非常重要的设计：**`require()` 是同步执行的**。

我们手写的简易 `require` 是这样，Node.js 原生的 `require` 同样如此——它直接返回模块内容，不需要回调函数。
这也意味着：**所有对 `module.exports` 的赋值也必须是同步的**。

下面这段代码就是**错误**的，会导致严重问题：
```javascript
// 错误写法！
setTimeout(() => {
  module.exports = function() {...}
}, 100)
```

`require()` 的同步特性，对我们定义模块有重大影响：
**在模块代码执行阶段，只能使用同步逻辑**。
这也是 Node.js 核心库为什么对大部分异步 API 都额外提供同步版本的重要原因。

如果模块确实需要**异步初始化**，你只能导出一个“未初始化”的模块，再在后续异步完成初始化。
但这样一来，用 `require()` 加载后无法保证模块立刻可用。
本书第 11 章《高级方案》会详细分析这个问题，并给出优雅的解决模式。

补充一个小知识点：
Node.js 早期其实有**异步版 `require`**，但很快就被移除了。
因为模块加载本质上只发生在程序初始化阶段，异步 I/O 带来的复杂度远大于收益，只会把整个系统搞得更复杂。

---

### 一句话重点
- **`require` 同步 → 导出必须同步**
- 不能在异步回调（定时器、Promise、网络回调等）里给 `module.exports` 赋值
- 模块初始化逻辑尽量同步，异步初始化要单独设计模式处理

# 模块路径解析算法
“依赖地狱”指的是项目中的多个依赖，又共同依赖了**同一个库的不同不兼容版本**。Node.js 优雅地解决了这个问题：**根据调用 `require` 的位置，加载对应目录下不同版本的模块**。

这一特性的核心，一是 npm/yarn 管理依赖的方式，二就是 `require()` 内部的**路径解析算法**。

下面是这套算法的简要流程：
`require.resolve(moduleName)` 接收模块名，返回模块的完整绝对路径，用于加载代码和作为唯一缓存标识。

## 三大解析分支
1. **文件模块**
   - 以 `/` 开头：视为**绝对路径**，直接使用
   - 以 `./` 或 `../` 开头：视为**相对路径**，从当前模块所在目录计算

2. **核心模块**
   既不是绝对也不是相对路径时，优先查找 Node.js 内置模块（如 `fs`、`path`、`http`）

3. **包模块（node_modules）**
   没找到核心模块时，从**当前模块所在目录**开始，逐级向上查找 `node_modules` 目录，直到文件系统根目录。

## 具体匹配规则
找到对应目录后，会按以下顺序尝试匹配：
- `${moduleName}.js`
- `${moduleName}/index.js`
- 读取 `${moduleName}/package.json` 的 `main` 字段指定的文件

---

## 为什么能解决依赖地狱？
每个包都可以拥有自己私有的 `node_modules`，存放自己依赖的版本，互不干扰。

示例目录结构：
```
myApp
├── foo.js
└── node_modules
    ├── depA
    ├── depB
    │   └── node_modules
    │       └── depA
    └── depC
        └── node_modules
            └── depA
```

- 从 `foo.js` 执行 `require('depA')`
  → 加载 `/myApp/node_modules/depA`
- 从 `depB/bar.js` 执行 `require('depA')`
  → 加载 `/myApp/node_modules/depB/node_modules/depA`
- 从 `depC/foobar.js` 执行 `require('depA')`
  → 加载 `/myApp/node_modules/depC/node_modules/depA`

## 总结
路径解析算法是 Node.js 依赖管理健壮性的核心，
它让一个项目可以安全使用成千上万个包，**不会出现版本冲突或兼容问题**。

---

## 模块缓存
每个模块**只会在第一次被 require 时加载并执行**，之后再次调用 `require()` 都会直接返回缓存的版本。从我们手写的简易 `require` 代码就能清楚看出这一点。

缓存对性能至关重要，同时也带来重要的功能影响：
- 允许模块依赖中出现**循环引用**（循环依赖）
- 在一定程度上保证：从同一个包内多次引入同一模块，始终返回**同一个实例**

路径解析算法在调用 `require()` 时会自动运行；如果需要，你也可以直接调用 `require.resolve()` 手动触发。

---

### 模块缓存的访问与删除
模块缓存对外暴露在 `require.cache` 上，可以直接操作。
一个常见用途是**删除缓存**，让模块下次重新加载：
```javascript
delete require.cache[require.resolve('./my-module')]
```

这种做法在**开发/测试热更新**时很有用，但在正常运行的业务代码中非常危险，可能导致状态混乱、单例失效等问题。

---

### 一句话记住
**一次加载，永久缓存，多次 require 共享同一个导出对象。**
