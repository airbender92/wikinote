# 深入解析 ESM 模块加载机制
想要彻底理解 ESM 的运行原理，以及它为何能更优雅地处理循环依赖，需要深入 ES 模块的**解析、实例化、执行**三阶段加载流程，同时掌握**只读实时绑定（live binding）**核心概念，最后结合循环依赖实例对比 CommonJS 的缺陷。

## 一、ESM 完整加载三阶段（严格顺序执行）
ESM 不会边加载边执行，而是分三个分离阶段处理所有依赖，这是它和 CommonJS 最核心的区别：
1. **解析阶段（Parse / 构建依赖图）**
   读取模块源码，静态扫描所有 `import`/`export` 语句，收集全部依赖路径，递归构建完整依赖图谱。
   > 静态语法保证编译期就能拿到所有导入导出，无需运行代码；CommonJS 只能运行时才知道依赖。

2. **实例化阶段（Instantiate / 创建绑定映射）**
   为每个模块创建导出符号与导入符号之间的**实时只读绑定**，建立引用关系，但**不执行任何模块代码**。
   只是建立符号关联，变量此时没有实际值。

3. **执行阶段（Evaluate / 运行代码赋值）**
   按照依赖树顺序从上到下执行各模块代码，为绑定的变量填充真实值。
   哪怕存在循环依赖，所有模块的实例化步骤已全部完成，不会出现 CommonJS 那种“半成品导出对象”。

## 二、核心特性：只读实时绑定（read-only live bindings）
### 1. 与 CommonJS 拷贝导出的本质区别
- CommonJS：导入时**拷贝一份导出值**，模块内部变量后续修改不会影响导入方；
- ESM：导入不是值拷贝，而是**双向实时引用绑定**：导入方指向原模块的原始变量，且导入的绑定只读。

### 2. 两大关键特点
1. **实时同步更新**
   原模块修改变量后，所有导入该变量的模块会自动读取最新值；
2. **只读限制**
   导入方无法修改导入的绑定变量，只能在原模块内部修改。

示例：
```js
// a.js
export let count = 0;
export function add() {
  count++;
}

// b.js
import { count, add } from './a.js';
console.log(count); // 0
add();
console.log(count); // 1（自动同步最新值）
count = 10; // 报错，导入绑定只读，禁止修改
```

## 三、ESM 循环依赖处理优势
CommonJS 遇到循环依赖时，被依赖模块只执行到一半，导出的是不完整半成品对象；
ESM 依靠**分阶段加载 + live binding**完美解决该问题：
1. 解析阶段：扫描全部导入导出，构建完整依赖图；
2. 实例阶段：提前建立所有符号绑定，无论是否循环；
3. 执行阶段再统一运行代码，所有导出变量的绑定关系已存在，只是等待赋值。

哪怕出现循环引用，导入方拿到的是**实时引用**，等对应模块代码执行完毕、变量赋值后，就能读取到完整最新的值，不会拿到残缺数据。

# 只读实时绑定（Read-only live bindings）
## 核心概念
ESM 导入的变量本质是**指向原模块导出变量的只读实时绑定**，这一机制是 ESM 能优雅处理循环依赖的关键特性，和 CommonJS 的值拷贝有本质区别。

## 示例演示
### counter.js（导出模块）
```js
export let count = 0
export function increment () {
  count++
}
```
导出可变数字 `count` 和修改它的方法。

### main.js（导入使用）
```js
import { count, increment } from './counter.js'

console.log(count) // 输出 0
increment()
console.log(count) // 输出 1
count++ // 抛出 TypeError：常量赋值
```

## 两层核心特性拆解
1. **实时（live）绑定**
导入的 `count` 不是复制一份静态数值，而是**实时引用原模块的原始变量**。
原模块内部通过 `increment()` 修改 `count` 后，导入方读取到的永远是最新值。

2. **只读（read-only）限制**
在导入文件中，不能直接对 `count` 赋值修改；
只能在**导出模块内部**修改该变量，外部代码无权直接变更绑定源。
直接执行 `count++` 会触发语法/运行时报错，等同于修改 `const` 变量。

## 和 CommonJS 关键对比
CommonJS 使用**浅拷贝机制**：
`require` 加载模块时，会拷贝一份 `module.exports` 对象副本。
如果导出原始类型（数字、字符串），原模块后续修改变量，外部导入的拷贝值不会同步更新。

### CommonJS 反面示例（无实时同步）
```js
// counter.cjs
let count = 0
function increment () { count++ }
module.exports = { count, increment }

// main.cjs
const mod = require('./counter.cjs')
console.log(mod.count) // 0
mod.increment()
console.log(mod.count) // 仍然是 0，不会同步更新
```
原因：导出时只是把当时 `count=0` 的数值复制到导出对象，后续内部修改不会同步。

## 总结
- ESM live binding：引用原变量，内部修改外部自动可见，外部禁止直接赋值；
- CommonJS：加载时浅拷贝导出对象，原始值更新无法同步到导入方；
- 该机制让循环依赖场景下，所有模块都能拿到完整、最新的变量值。

# ESM 循环依赖解析机制
## 一、复用之前循环依赖场景，改用 ESM 实现
### a.js
```js
import * as bModule from './b.js'
export let loaded = false
export const b = bModule
loaded = true
```
### b.js
```js
import * as aModule from './a.js'
export let loaded = false
export const a = aModule
loaded = true
```
### 入口 main.js
```js
import * as a from './a.js'
import * as b from './b.js'
console.log('a ->', a)
console.log('b ->', b)
```
> 注意：不能用 `JSON.stringify` 打印，模块间存在循环引用，会抛出「循环结构无法序列化」错误。

## 二、运行输出结果
```
a -> <ref *1> [Module] {
  b: [Module] { a: [Circular *1], loaded: true },
  loaded: true
}
b -> <ref *1> [Module] {
  a: [Circular *1],
  loaded: true
}
```

## 三、核心结论（对比 CommonJS）
1. **双方都能拿到完整模块实例**
   CommonJS 循环依赖会拿到执行中途的半成品（`loaded: false`）；
   ESM 中 `a`、`b` 的 `loaded` 全为 `true`，两个模块都完整执行完毕。

2. **真实引用，而非拷贝副本**
   `a.b` 就是全局同一个 `b` 模块对象，`b.a` 就是全局同一个 `a` 模块，形成循环引用标记 `[Circular *1]`。

3. **导入顺序不影响最终结果**
   调换 `main.js` 中 `import a` 和 `import b` 的顺序，输出完全一致；
   CommonJS 的结果高度依赖加载先后顺序，会出现半成品差异。

## 四、背后根源：ESM 三段式加载流程
ESM 分 **解析 → 实例化 → 执行** 三个独立阶段，彻底解决循环依赖缺陷：
1. **解析阶段（Parse）**
   静态扫描所有 `import/export`，递归构建完整依赖图，提前识别所有循环关系，不执行代码。
2. **实例化阶段（Instantiate）**
   为每一个导出符号创建**实时只读绑定**，所有模块的导入导出引用关系全部建立完毕，此时还没运行任何代码。
   哪怕存在循环，双向绑定已经存在，不会出现找不到导出的情况。
3. **执行阶段（Evaluate）**
   按依赖树顺序执行所有模块代码，给变量赋值。
   等到代码执行时，所有绑定通道早已就绪，因此循环引用的模块能读取对方最终完成后的完整变量值。

## 五、和 CommonJS 本质差距
CommonJS 是**边加载、边执行**，遇到循环时对方模块只执行到中途，导出对象是不完整快照；
ESM 先建好全部符号引用再统一执行代码，搭配 live binding 实时引用，循环依赖不会产生残缺数据。

# 第一阶段：解析（Parsing）
## 核心流程
解析阶段以入口文件 `main.js` 为起点，仅扫描代码里所有 `import` 语句，读取对应模块源码，采用**深度优先遍历**构建全局依赖图；每个模块只会被访问一次，不会重复解析。

## 循环依赖示例分步解析（main → a → b，b 又引 a）
1. 从入口 `main.js` 读取第一条导入，进入 `a.js`；
2. 解析 `a.js`，发现导入 `b.js`，继续向下遍历；
3. 解析 `b.js`，其中导入 `a.js`，但 `a.js` 已标记为访问过，不再重复递归；
4. `b.js` 无其他导入，回溯回到 `a.js`；
5. `a.js` 无其他导入，回溯回到 `main.js`；
6. `main.js` 第二条导入 `b.js`，`b` 已遍历，直接跳过。

## 阶段产出
深度优先遍历完成后，会生成**去除循环的线性模块执行序列**，原本环形依赖被展平为有序列表，为下一阶段实例化做准备。

## 关键特点
1. 仅扫描静态 `import`，**不执行任何模块代码**；
2. 每个模块仅遍历一次，避免重复加载；
3. 提前识别所有循环引用，截断重复递归路径；
4. 输出扁平化无环模块序列，作为实例化阶段的处理顺序依据。

---# 第二阶段：实例化（Instantiation）
## 整体执行规则
基于解析阶段生成的线性模块序列，**自底向上**遍历所有模块；本阶段只做两件事：
1. 收集每个模块的所有导出标识符，生成导出映射表；
2. 在模块间建立跨文件的**实时绑定引用链路**；
全程**不执行任何代码、变量无实际赋值**，所有导出值均处于未初始化状态。

## 步骤1：收集各模块导出标识（自底向上遍历）
1. 先处理 `b.js`：识别导出 `loaded`、`a`，存入该模块导出映射；
2. 再处理 `a.js`：识别导出 `loaded`、`b`，存入导出映射；
3. 最后处理入口 `main.js`：无导出内容。
此时仅记录变量名，不存在具体运行时值。

## 步骤2：跨模块绑定引用链路
遍历完成后，再建立导入与导出之间的引用关联：
1. `b.js` 的 `import * as aModule` 绑定到 `a.js` 的全部导出符号；
2. `a.js` 的 `import * as bModule` 绑定到 `b.js` 的全部导出符号；
3. `main.js` 分别绑定 `a.js`、`b.js` 的全部导出，别名 `a` / `b`。

## 关键要点
1. 仅建立符号引用关系，**没有变量赋值**；
2. 循环依赖也能完整建立双向绑定，不会出现 CommonJS 那种缺失引用的情况；
3. 所有绑定均为只读实时绑定，为下一执行阶段做好引用通道准备；
4. 此阶段结束后，所有模块的导入导出关系已全部打通，只差执行代码填充真实数值。

# 第三阶段：执行求值（Evaluation）
## 核心规则
实例化完成后进入最后一步：执行所有模块真实代码。
执行顺序依旧遵循**后序深度优先、自底向上**，入口文件 `main.js` 最后运行；保证执行业务代码前，所有依赖模块都已完整初始化。

## 循环依赖示例分步执行流程
1. **执行 b.js**
   - 初始化导出变量 `loaded = false`；
   - 导出 `a` 绑定指向 a.js 的模块引用（实例化阶段已建立好链路）；
   - 执行 `loaded = true`，b.js 全部代码运行完毕。

2. **执行 a.js**
   - 初始化导出变量 `loaded = false`；
   - 导出 `b` 绑定指向完整 b.js 模块对象；
   - 执行 `loaded = true`，a.js 执行完成。

3. **最后执行 main.js**
   此时 a、b 两个模块代码均已完整运行，所有导出变量都拥有最终值，打印能看到双方 `loaded: true`。

## 关键优势
1. 所有导入都是**实时引用绑定**，不存在 CommonJS 浅拷贝快照；
2. 即便存在循环依赖，每个模块拿到的都是对方完整、最终的状态；
3. 入口文件最晚执行，业务代码访问依赖时不会遇到未初始化的半成品变量；
4. 对比 CommonJS 边加载边执行、循环产生残缺导出，ESM 三段式机制彻底规避该问题。


# ESM 下修改/猴子补丁模块的限制与可行方案
## 一、核心规则：导入绑定只读，但对象内部可修改
ESM 的导入是**只读实时绑定**，存在关键边界：
1. 不能直接对导入变量重新赋值（`import { readFile } from 'fs'; readFile = xxx` 直接报错）；
2. 若导入的绑定是**对象**，则允许修改该对象内部属性/方法，这是 ESM 中实现猴子补丁的唯一突破口。

## 二、示例：Mock fs 文件读取模块
### mock-read-file.js（补丁模块）
```js
import fs from 'fs'
// 保存原生方法
const originalReadFile = fs.readFile
let mockedResponse = null

// 模拟实现
function mockedReadFile(path, cb) {
  setImmediate(() => cb(null, mockedResponse))
}

// 开启 mock
export function mockEnable(respondWith) {
  mockedResponse = respondWith
  fs.readFile = mockedReadFile
}

// 恢复原生方法
export function mockDisable() {
  fs.readFile = originalReadFile
}
```

### main 使用入口
```js
import fs from 'fs'
import { mockEnable, mockDisable } from './mock-read-file.js'

mockEnable(Buffer.from('Hello World'))
fs.read('fake-path', (err, data) => {
  console.log(data.toString()) // 输出 Hello World
})
mockDisable()
```

### 原理说明
代码导入 `fs` 默认导出（一个包含所有文件操作方法的对象），只是修改**对象内部 `readFile` 属性**，没有对 `fs` 变量本身重新赋值，符合 ESM 语法规则。

## 三、两种错误导入方式（无法完成 mock）
`fs` 模块同时提供默认导出对象 + 顶层具名导出，下面两种写法补丁会失效：
1. `import { readFile } from 'fs'`
`readFile` 是独立只读绑定，无法执行 `readFile = mockFn` 赋值，直接抛语法错误。
2. `import * as fs from 'fs'`
`fs.readFile` 是具名导出的只读绑定，同样不能覆盖。

### 关键矛盾
我们只修改了**默认导出对象里的方法**，但顶层具名导出的 `readFile` 绑定不会同步更新。
如果业务代码用 `import { readFile }`，mock 完全不生效，方案十分脆弱。

## 四、Node 内置补救 API：syncBuiltinESMExports
仅对 Node 内置核心模块（fs/http 等）生效，调用后会把默认导出对象的变更同步到顶层具名导出绑定。
示例：
```js
import fs, { readFileSync } from 'fs'
import { syncBuiltinESMExports } from 'module'

// 重写对象内部方法
fs.readFileSync = () => Buffer.from('Hello, ESM')
// 同步更新所有具名导出绑定
syncBuiltinESMExports()

console.log(fs.readFileSync === readFileSync) // true
```
在 mock 工具开启/恢复 mock 后调用该方法，可兼容 `import { xxx }` 的业务代码。

## 五、ESM 猴子补丁的痛点与替代方案
1. 缺陷
- 仅修改默认导出对象时，具名导入代码不受影响；
- `syncBuiltinESMExports` 仅限 Node 内置模块，第三方包无效；
- 补丁逻辑脆弱，导入写法不同就失效，维护成本高。

2. 推荐成熟方案
- 测试框架内置 mock：Jest、Vitest 提供专用 ESM mock API；
- 第三方库 mocku：基于 Node `module` 核心钩子实现稳定模块劫持；

# ESM 与 CommonJS 的差异及互操作
## 一、基础重要差异：自动严格模式
ESM 文件**默认自动启用严格模式**，无需手动写 `"use strict"`，且无法关闭严格模式。
带来约束：
1. 不允许使用未声明变量；
2. 禁止 `with` 语句；
3. 禁止八进制字面量、删除不可删除属性等非严格模式危险语法。
严格模式提升代码安全性、减少隐性错误，是 ESM 自带优势。

## 二、前文已提及核心差异汇总
1. **导入路径后缀**
   - ESM：导入必须写完整文件后缀 `./logger.js`，不能省略 `.js`；
   - CommonJS：`require('./logger')` 可自动补全后缀、匹配目录 `index.js`。
2. **语法静态 vs 动态**
   - ESM：`import/export` 只能写在顶层，不能放在 if/循环/函数，支持 Tree Shaking；
   - CommonJS：`require()` 运行时动态调用，可任意嵌套，无法完整死代码消除。
3. **绑定机制**
   - ESM：只读实时 live 绑定，原模块变量修改后导入方同步可见；
   - CommonJS：加载时浅拷贝导出对象，原始基础类型更新外部无法感知。
4. **循环依赖处理**
   - ESM：分解析/实例化/执行三阶段，循环依赖拿到完整模块；
   - CommonJS：边加载边执行，循环会拿到半成品导出对象。
5. **绝对路径写法**
   - ESM 仅支持 `file://` URL 格式绝对路径；
   - CommonJS 可直接用 `/` 开头系统绝对路径。
6. **顶层变量**
   - ESM 无 `require` / `module` / `exports` / `__dirname` / `__filename`；
   - CommonJS 文件内置全部上述顶层变量。

# ESM 缺失的 CommonJS 内置变量与替代方案
## 一、ESM 不存在的内置标识
ESM 环境中**没有** CommonJS 自动注入的以下变量，直接使用会抛出 `ReferenceError`（ESM 默认严格模式，未定义变量直接报错）：
- `require`
- `exports` / `module` / `module.exports`
- `__filename`（当前文件绝对路径）
- `__dirname`（当前文件所在目录绝对路径）

示例直接使用报错：
```js
// ESM 文件，执行全部报错
console.log(exports)      // ReferenceError
console.log(module)       // ReferenceError
console.log(__filename)  // ReferenceError
console.log(__dirname)   // ReferenceError
```

## 二、ESM 专属：import.meta.url
ESM 提供元对象 `import.meta`，其中 `import.meta.url` 返回当前模块的 `file://` 协议 URL，是重构路径、模拟 `require` 的基础。
格式示例：`file:///Users/demo/project/main.js`

### 1. 模拟 __filename / __dirname
借助 Node 内置 `url`、`path` 工具包转换文件 URL 为系统路径：
```js
import { fileURLToPath } from 'url'
import { dirname } from 'path'

// 当前文件完整物理路径（等价 __filename）
const __filename = fileURLToPath(import.meta.url)
// 当前文件所在目录（等价 __dirname）
const __dirname = dirname(__filename)
```

### 2. 在 ESM 中创建 require，兼容引入 CommonJS
使用 `module` 内置的 `createRequire`，基于当前模块 URL 生成标准 `require` 函数，用于加载 `.cjs` 模块：
```js
import { createRequire } from 'module'
// 生成当前模块作用域的 require
const require = createRequire(import.meta.url)

// 正常加载 CommonJS 文件
const cjsUtil = require('./utils.cjs')
```

## 三、顶层 this 关键字巨大差异
1. **ESM 顶层 this**：全局作用域 `this` 为 `undefined`
```js
// esm.js
console.log(this) // undefined
```
2. **CommonJS 顶层 this**：`this === module.exports`，指向导出对象
```js
// cjs.cjs
console.log(this === exports) // true
```

## 四、补充关联知识点
ESM 强制严格模式，未声明变量、非法顶层操作都会直接抛出运行时错误；
如需深入严格模式规则，可查阅文中给出的 MDN 文档链接。

# ESM 与 CommonJS 互操作（Interoperability）
## 一、ESM 导入 CommonJS 模块
### 1. 标准 import 方式（有限支持）
只能用**默认导入**，**不支持具名导入**：
```js
// ✅ 有效
import pkg from 'commonjs-package'

// ❌ 报错
import { method } from 'commonjs-package'
```
原因：CommonJS 导出的是单个 `module.exports` 对象，ESM 无法静态分析其具名导出。

### 2. 完整兼容方式：createRequire
在 ESM 里创建 `require`，就能像 CommonJS 一样用：
```js
import { createRequire } from 'module'
const require = createRequire(import.meta.url)

// 完全正常使用
const cjsModule = require('./commonjs-module.cjs')
const { method1, method2 } = require('./commonjs-lib')
```

## 二、CommonJS 导入 ESM —— **完全不支持**
```js
// ❌ 永远报错
const esm = require('./esm-module.js')
```
CommonJS 是同步加载机制，而 ESM 是异步解析实例化，Node 不允许这种反向引入。

## 三、ESM 导入 JSON 文件
ESM **不能直接 import JSON**：
```js
// ❌ TypeError: Unknown file extension: .json
import data from './data.json'
```

### 解决方案：用 createRequire + require
```js
import { createRequire } from 'module'
const require = createRequire(import.meta.url)

// ✅ 正常读取 JSON
const data = require('./data.json')
```

### 未来展望
Node 与标准正在推进 **JSON modules** 原生支持，未来可直接：
```js
import data from './data.json' assert { type: 'json' }
```

## 四、互操作核心总结
- ESM → CJS：可以用默认 import，或用 `createRequire` 完全兼容
- CJS → ESM：**不支持**
- ESM → JSON：必须用 `createRequire` 实现（未来会原生支持）
