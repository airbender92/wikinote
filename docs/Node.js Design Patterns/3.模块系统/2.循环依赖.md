# 循环依赖
很多人认为循环依赖本身就是设计问题，但在实际项目中仍可能出现，所以我们需要了解 CommonJS 是如何处理它的。结合之前手写的 `require` 逻辑，你就能很快理解其原理和坑点。

![循环依赖2](/assets/node/循环依赖2.jpg)

下面用一个完整示例一步步看清楚。

---

## 示例场景
- `main.js` 依赖 `a.js` 和 `b.js`
- `a.js` 依赖 `b.js`
- `b.js` 又依赖 `a.js`
→ 典型的 **循环依赖**

### a.js
```javascript
exports.loaded = false
const b = require('./b')

module.exports = {
  b,
  loaded: true
}
```

### b.js
```javascript
exports.loaded = false
const a = require('./a')

module.exports = {
  a,
  loaded: true
}
```

### main.js
```javascript
const a = require('./a')
const b = require('./b')

console.log('a ->', JSON.stringify(a, null, 2))
console.log('b ->', JSON.stringify(b, null, 2))
```

### 运行结果
```json
a -> {
  "b": {
    "a": {
      "loaded": false
    },
    "loaded": true
  },
  "loaded": true
}
b -> {
  "a": {
    "loaded": false
  },
  "loaded": true
}
```

可以看到：
**`b.js` 拿到的 `a` 是一个未初始化完成的版本（`loaded: false`）。**

---

# 底层执行步骤（逐句拆解）
1. `main.js` 开始执行，`require('./a')`
2. `a.js` 先设置：`exports.loaded = false`
3. `a.js` 去 `require('./b')`
4. `b.js` 先设置：`exports.loaded = false`
5. `b.js` 又去 `require('./a')` → **进入循环**
6. 由于 `a.js` 已经在加载中，**直接返回当前缓存的半成品导出对象**
   → `b` 拿到的 `a` 只有 `{ loaded: false }`
7. `b.js` 继续执行，设置 `loaded: true`，完成加载
8. 回到 `a.js`，拿到完整的 `b`，然后设置 `loaded: true`
9. 回到 `main.js`，再 `require('./b')` → 直接读缓存
10. 最终输出：`b` 里的 `a` 依然是**半成品**

---

# 核心结论
在 CommonJS 中：
- 循环依赖时，**先被加载的模块会返回半成品给后加载的模块**
- 拿到的是模块**加载到一半时的缓存状态**
- 最终结果**高度依赖加载顺序**
  - 先引 a 再引 b → b 拿到不完整的 a
  - 先引 b 再引 a → a 拿到不完整的 b
- 项目变大后，极易出现难以排查的诡异问题

---

# 关键点总结
- **CommonJS 处理循环依赖并不完美**
- 模块未执行完就被引用时，会返回**当前已导出的部分内容**
- 这会导致不同地方看到的模块实例**状态不一致**
- 后面会讲到：**ESM 对循环依赖的处理更安全、更可预测**
- 使用 CommonJS 时，尽量避免循环依赖；无法避免时要格外小心导出顺序
