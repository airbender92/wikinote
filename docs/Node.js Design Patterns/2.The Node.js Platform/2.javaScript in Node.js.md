# 完整中文翻译
## Node.js 环境下的 JavaScript
通过上一节的架构分析能得出一个重要结论：Node.js 中运行的 JavaScript，和浏览器端 JS 存在显著差异。

最直观的区别是 Node.js 不存在 DOM、`window`、`document` 这些浏览器专属对象。反过来，Node.js 可以直接调用操作系统提供的各类底层服务，而浏览器无法做到。浏览器为了防止恶意网页侵害本地系统，设置了多重安全隔离机制，对系统资源做高层封装、严格管控，这也限制了浏览器 JS 的能力；但 Node.js 几乎可以无限制调用操作系统全部接口。

本节梳理在 Node 中写 JS 需要重点关注的核心要点：
### 放心使用最新 JavaScript 语法
浏览器开发最大痛点之一：代码要兼容五花八门的设备与浏览器，不同浏览器内置 JS 引擎对 ES 新特性支持参差不齐。虽然转译器、垫片库（polyfill）能一定程度缓解该问题，但仍存在无法完全兼容的场景，还会增加工程复杂度。

而 Node 开发不存在这类麻烦。服务端部署环境可控，运行时版本可以提前确定，我们可以针对性适配指定 Node/JS 版本，上线生产环境不会出现语法兼容意外。

再加上 Node 内置的 V8 引擎版本更新及时，开发者无需额外转译，就能直接使用绝大部分最新 ECMAScript（ES）标准特性。

但需要注意：如果你开发的是供第三方使用公共类库，仍要兼容多种 Node 版本。行业通用做法是**以当前最老的长期支持版（LTS）为最低适配基线**，并在 `package.json` 配置 `engines` 字段，这样用户安装包时，包管理器会自动校验 Node 版本，给出不兼容提示。

# 核心差异与知识点解析
## 一、浏览器 JS vs Node JS 核心区别
1. **全局对象与宿主API**
    - 浏览器：`window`、`document`、DOM/BOM API，隔离系统底层，无文件、网络、进程权限；
    - Node：无 DOM，提供 `process`、内置 `fs/net/child_process` 等模块，拥有完整操作系统操作权限。
2. **运行环境可控性**
    - 浏览器：多厂商、多版本引擎，ES 特性支持碎片化，必须 Babel 转译；
    - Node：服务端部署环境统一，V8 版本跟随 Node 升级，原生支持现代 ES6+，无需转译。
3. **安全沙箱**
    - 浏览器沙箱：限制文件读写、本地端口、系统进程，防止网页窃取本地数据；
    - Node 无浏览器级沙箱，代码拥有服务器完整读写、进程、网络权限，代码漏洞风险更高。

## 二、LTS 版本适配规范
1. LTS：长期支持版本，官方提供数年安全补丁，企业生产环境首选；
2. 库开发规范：最低兼容仍在维护的 LTS，避免使用新版独有的 API；
3. `package.json` 的 `engines` 字段示例：
```json
{
  "engines": {
    "node": ">=16.0.0"
  }
}
```
npm/yarn 安装时会校验本地 Node 版本，不满足则抛出警告。

## 三、ES 标准与 V8 关联
JS 语言标准由 ECMAScript（ES）规范定义，Node 内置新版 V8，会同步跟进最新 ES 提案，像 `async/await`、类、箭头函数、原生模块等语法开箱即用，不像浏览器需要转译兼容老旧设备。

# 完整中文翻译
## 模块系统
自诞生之初，Node.js 就内置了一套模块系统，彼时 JavaScript 语言本身还没有官方标准化模块方案。这套原生模块体系叫做 CommonJS，通过 `require` 关键字，我们可以导入系统内置模块、本地文件中导出的函数、变量与类。

CommonJS 对整个 JS 生态而言是一场变革。即便在浏览器客户端领域，配合 Webpack、Rollup 这类打包工具，它也得到广泛普及，打包后产物可直接在浏览器运行。正是依靠 CommonJS，Node.js 才能让开发者搭建出结构清晰、规模庞大的服务端应用，比肩其他后端平台。

如今 JavaScript 拥有 ES 模块规范（大家更熟悉 `import` 关键字）。Node.js 仅沿用了 ES 模块的语法，底层实现逻辑和浏览器存在差异：浏览器加载远程网络模块，而 Node.js 目前仅支持读取本地文件系统中的模块。下一章我们会深入讲解两套模块体系。

## 完整操作系统权限访问
前文提到，Node.js 并非运行在浏览器沙箱内，因此它通过绑定层封装了操作系统几乎所有核心服务，提供原生调用能力。
相关参考链接：
- Node.js 版本发布周期：nodejsdp.link/node-releases
- package.json engines 配置文档：nodejsdp.link/package-engines
- 各 Node 版本 ES 特性兼容对照表：nodejsdp.link/node-green

举例来说：
- `fs` 模块：在系统权限允许的前提下，读写本地任意文件；
- `net` / `dgram`：提供底层 TCP、UDP 套接字，开发网络程序；
- `http` / `https`：搭建 HTTP/HTTPS 服务；
- `crypto`：封装 OpenSSL，提供加密、哈希算法；
- `v8`：访问 V8 引擎底层能力；
- `vm`：创建独立 V8 执行上下文，隔离代码运行环境；
- `child_process`：创建、调用外部子进程；
- 全局 `process` 对象：获取当前进程全部信息
  - `process.env`：读取环境变量；
  - `process.argv`：获取程序启动时传入的命令行参数。

本书后续章节会大量使用上述内置模块，完整官方 API 文档可查看：nodejsdp.link/node-docs

# 核心知识点梳理
## 1. CommonJS 历史意义
在 ES6（ES2015）标准化 `import/export` 之前，CommonJS 是 JS 唯一成熟可用的模块标准，分两大使用场景：
1. Node.js 原生默认模块系统；
2. 前端打包工具（Webpack/Rollup）编译时解析的模块格式。

## 2. ESM 浏览器 vs Node.js 核心差异
- 浏览器：`import` 支持 HTTP 远程网络地址加载模块；
- Node.js ESM：仅支持本地文件路径，必须补全 `.js` 后缀，无网络模块加载能力。

## 3. Node 内置系统能力一览
Node 通过内置核心模块，突破浏览器安全限制，完整操作服务器硬件/系统资源：文件、网络、加密、子进程、虚拟机代码隔离、进程环境等，这是前后端 JS 最核心的能力分界线。

## 4. process 全局对象
Node 特有顶层全局变量，浏览器不存在；是服务端程序获取运行环境、启动参数、系统变量的核心入口。

文中给出的四个链接分别对应版本规划、包兼容性配置、ES 语法兼容清单、官方完整 API 文档，是开发中高频查阅的权威参考。

# 完整中文翻译
## 运行原生代码
Node.js 最强大的能力之一，就是支持开发**用户层原生扩展模块**，实现与 C/C++ 原生代码绑定。这项特性赋予平台巨大优势，我们可以直接复用各类已有的 C/C++ 组件。Node 通过 N-API 官方标准接口，为编写原生模块提供完善支持。

### 原生代码绑定的价值
1. **复用存量代码**：低成本复用海量开源 C/C++ 库；企业无需迁移老旧 C/C++ 遗留系统，直接在 Node 中调用。
2. **底层硬件交互**：JS 无法直接操作硬件驱动、串口、USB 等底层外设，原生模块是 IoT、自制机器人开发的核心方案，这也是 Node 在物联网领域流行的关键原因。
3. **提升CPU密集任务性能**：即便 V8 执行 JS 速度极快，但相比编译后的原生二进制代码仍存在性能损耗。大数据、复杂运算等 CPU 密集场景，交给原生代码处理能大幅提速。

除此之外，如今包括 Node 在内的主流 JS 虚拟机都支持 WebAssembly（Wasm）。它是一套底层指令格式，可将 C++、Rust 等语言编译为虚拟机可识别的字节码，无需编写原生扩展，就能获得近乎原生的性能优势。

## 本章小结
本章我们梳理了支撑 Node 平台的核心设计理念，这些思想同时决定了 Node 底层架构与开发者的编码风格。
1. **Node 核心哲学**：内核极简、微型单一职责模块、最小对外暴露面、简洁务实；遵循这套「Node 开发范式」写出的代码轻量化、易维护。
2. **底层核心架构**：反应器模式是 Node 异步机制核心；运行时三大支柱分别是 V8 JS 引擎、libuv I/O 引擎、Node JS 标准库。
3. **Node JS 与浏览器 JS 差异**：无 DOM 浏览器沙箱限制，拥有完整操作系统访问权限；可直接使用新版 ES 语法，同时存在两套模块系统（CommonJS / ESM）；支持 C/C++ 原生扩展与 WebAssembly。

除去底层架构带来的性能优势，这套极简、务实的开发理念与活跃社区，才是 Node 广受开发者喜爱的核心原因。很多开发者认为 Node 回归了简洁纯粹的编程本质。

# 核心概念解读
## 1. N-API
Node 官方稳定原生扩展接口，屏蔽不同 Node 版本 V8 接口变动，编写的原生模块可跨 Node 版本兼容，是开发 C/C++ 插件的标准方案。
## 2. 原生模块 vs WebAssembly
- **原生模块（N-API）**：直接编译为系统动态库（.so/.dll/.dylib），深度对接系统硬件，适合串口、驱动等底层设备开发；缺点是需要区分操作系统编译，兼容性差。
- **WebAssembly**：跨平台字节码，一套编译产物可在浏览器、Node 全平台运行，无需系统编译，适合纯计算密集场景，无法直接操作硬件底层驱动。
## 3. CPU密集场景适用场景
大数据解析、加解密、数值运算、音视频编解码等大量循环计算逻辑，JS 执行开销高，可下沉到 C++/Rust 编写的 Wasm / 原生模块提速。
## 4. 本章知识体系梳理
1. Node 四大开发哲学：Small core、Small modules、Small surface area、Simplicity and pragmatism
2. IO 演进链路：阻塞IO → 忙轮询非阻塞IO → 事件多路复用 → libuv 反应器模式
3. Node 四层架构：libuv + V8 + C++绑定层 + JS标准库 + 用户代码
4. Node 独有能力：操作系统全权限、原生插件、Wasm、双模块系统
