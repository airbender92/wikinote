# 译文 + 核心实操知识点
## 译文：使用 web
### 使用 webpack
搞懂打包工具底层原理后，我们来搭建一套**可同时运行在 Node 和浏览器**的简易项目。通过这个实操案例，学会编写一套无修改、两端通用的公共库，并用 webpack 打包浏览器端产物。

先搭建极简 HelloWorld 示例，本章后续小节会搭建更贴近真实业务的同构应用。

1. 全局安装 webpack 命令行工具
```bash
npm install --global webpack-cli
```
2. 新建文件夹，初始化 npm 项目
```bash
npm init
```
3. 项目使用 ESM 规范，需在 `package.json` 添加配置：`"type": "module"`
4. 执行自动生成 webpack 配置的引导命令
```bash
webpack-cli init
```
该命令会自动安装 webpack 依赖、生成配置文件。
**注意**：本书写作时使用 webpack4，自动生成的配置默认是 CommonJS 格式，和项目 ESM 规范冲突，需要两处修改：
- 将配置文件重命名为 `webpack.config.cjs`
- 修改 `package.json` 脚本字段：
```json
"build": "webpack --config webpack.config.cjs",
"start": "webpack-dev-server --config webpack.config.cjs"
```

### 1. 编写两端共享模块 `src/say-hello.js`
```js
import nunjucks from 'nunjucks'
const template = '<h1>Hello <i>{{ name }}</i></h1>'
export function sayHello (name) {
  return nunjucks.renderString(template, { name })
}
```
代码依赖模板库 nunjucks，需要提前 `npm install nunjucks`。
模块对外暴露 `sayHello` 方法，接收名字参数，返回拼接完成的 HTML 字符串，**服务端、浏览器可直接复用，无需修改源码**。

### 2. 浏览器端入口 `src/index.js`
```js
import { sayHello } from './say-hello.js'
const body = document.getElementsByTagName('body')[0]
body.innerHTML = sayHello('Browser')
```
引入共享方法，将生成的 HTML 插入页面 body。

- 开发预览：`npm start` 启动 webpack-dev-server，自动打开浏览器预览页面
- 生产打包：`npm run build`
打包后生成 `dist` 目录，包含：
1. `index.html` 页面入口
2. 哈希命名 JS 包（如 `main.12345678901234567890.js`）

#### 哈希文件名：缓存清除（Cache Busting）
打包产物文件名携带文件内容哈希值：
代码修改 → 哈希变更 → 生成全新文件。
CDN、浏览器会长期缓存静态资源，覆盖旧文件很难全局刷新；每次更新生成新文件，天然绕过缓存，彻底解决缓存失效问题。

打开 dist 内 html 即可本地预览打包结果；打开打包后的 JS 文件，能看到我们写的业务代码、完整 nunjucks 库都被内置进 bundle，结构和前文讲解的简易打包运行时逻辑一致，只是 webpack 增加了更多工程化逻辑。

### 3. Node 服务端入口 `src/server.js`
```js
import { sayHello } from './say-hello.js'
console.log(sayHello('Node.js'))
```
直接运行：
```bash
node src/server.js
```
终端输出：`<h1>Hello <i>Node.js</i></h1>`

至此完成目标：**一套公共库代码，浏览器、Node 两端直接复用，无需任何改造**。
后续小节会讲解一套代码针对两端编写差异化逻辑的设计模式。

## 核心实操知识点
### 1. ESM 项目兼容 webpack CJS 配置
项目 `package.json` 标记 `"type":"module"` 时，`.js` 文件默认按 ES 模块解析；
webpack 配置文件需要 CommonJS，因此必须后缀改为 `.cjs`，并在脚本指定配置文件路径。

### 2. 两端代码分工
- 共享模块：仅使用双端兼容第三方库（如 nunjucks），不使用 DOM / fs 等环境专属 API；
- 浏览器入口：使用 `document/window` 浏览器独有全局；
- Node 入口：使用 `process` 服务端独有 API，直接运行源码，**不需要 webpack 打包**。

### 3. webpack 两大脚本作用
- `npm start`：开发服务器 webpack-dev-server，热更新、实时预览，不生成 dist 静态文件；
- `npm run build`：生产构建，输出 dist 静态资源，自动哈希文件名实现缓存清除。

### 4. Cache Busting（缓存破坏）原理
打包文件名称绑定文件内容哈希：
文件不变 → 哈希不变，浏览器/CDN 复用缓存；
文件修改 → 哈希改变，生成全新文件，自动加载新版本，无需手动清缓存。

### 5. 同构库核心前提
共享模块**不能引入环境独有的 API**（浏览器 DOM / Node 文件系统、进程 API），否则一端会直接报错；如需差异化逻辑，后文会提供环境分支方案。

# 译文 + 核心知识点
## 译文
### 跨平台开发基础
在多平台开发场景中，最核心的难题是：**如何最大限度复用通用代码，同时针对各平台独有的特性提供专属实现**。本节我们会讲解应对该问题的核心原则与设计模式，包含运行时代码分支、模块替换两种主流方案。

## 核心知识点
### 核心矛盾
同构/跨平台开发的核心平衡：
1. 最大化复用通用逻辑（减少重复编码、降低维护成本）；
2. 区分平台专属逻辑（浏览器DOM/Node文件系统、API、第三方依赖不互通）。

### 两大核心解决方案
1. **Runtime code branching 运行时代码分支**
运行时判断当前执行环境，执行对应平台逻辑；代码仅维护一份，靠条件分支区分两端行为。
2. **Build-time module swapping 构建时模块替换**
打包阶段区分平台，浏览器打包流程加载浏览器专属模块，Node环境直接引入服务端模块，构建期完成模块切换，运行时无分支判断，性能更优。

### 两种方案优缺点简要对比
| 方案 | 优势 | 劣势 |
|------|------|------|
| 运行时分支 | 单套源码，构建流程简单 | 运行时存在判断开销，分支逻辑多时代码杂乱 |
| 构建时模块替换 | 运行时无多余判断，产物干净 | 需要维护两套平台专属模块，构建配置更复杂 |

# 译文 + 核心知识点
## 译文
### 运行时代码分支
最简单直观的跨平台方案就是**运行时动态分支**：程序运行时识别当前宿主环境，通过 `if...else` 切换不同平台的实现逻辑。通用实现思路是检测仅存在于 Node 或仅存在于浏览器的全局变量，以此区分环境。

举个例子，我们可以检测全局 `window` 对象是否存在。改造 `say-hello.js`，根据运行环境提供差异化逻辑：
```js
import nunjucks from 'nunjucks'
const template = '<h1>Hello <i>{{ name }}</i>'

export function sayHello (name) {
  // 判断是否为浏览器环境
  if (typeof window !== 'undefined' && window.document) {
    // 浏览器端逻辑：返回 HTML 字符串
    return nunjucks.renderString(template, { name })
  }
  // Node.js 服务端逻辑：返回带 ANSI 加粗格式的终端文本
  return `Hello \u001b[1m${name}\u001b[0m`
}
```
分别在 Node 和浏览器运行项目，就能看到效果差异：
- Node 终端不会输出 HTML，而是加粗格式的纯文本；
- 浏览器页面逻辑保持原样，不受影响。

转义序列说明：
`\u001b[1m` 是 ANSI 终端控制码，开启文本加粗；
`\u001b[0m` 用于重置终端样式。想了解更多可查阅 ANSI 转义序列相关资料。

## 核心知识点
### 1. 环境检测原理
浏览器独有全局：`window` / `document`
Node 无 `window`，因此通过 `typeof window !== 'undefined'` 可快速区分两端。
### 2. 方案优缺点
✅ 优点：
1. 只维护一份源码，无需拆分多套平台文件；
2. 构建配置零改动，开箱即用。
❌ 缺点：
1. 运行时每次调用都要执行判断，存在微小性能损耗；
2. 分支逻辑增多时代码臃肿；
3. 打包后所有平台代码都会打进 bundle，浏览器产物会包含 Node 无用逻辑，无法 tree-shake 剔除。
### 3. ANSI 转义序列
终端专用格式化标记，用于控制文字加粗、颜色、背景等样式，仅在 Node 终端生效，浏览器无效果。
### 4 适用场景
小型工具类共享函数、简单差异化逻辑；
大型复杂项目不推荐，优先使用**构建时模块替换**方案。

# 译文 + 核心难点总结
## 译文
### 运行时代码分支的缺陷
虽然运行时分支是区分 Node/浏览器最直观简单的方案，但它存在不少弊端：
1. **产物体积膨胀，存在安全风险**
两套平台的代码会被打包进同一个模块、最终产物 bundle 里。浏览器包会包含永远不会执行的 Node 冗余代码；更危险的是，这些废弃代码里可能存放密钥、API 等敏感信息，直接暴露给前端用户，引发安全隐患。

2. **代码可读性大幅下降**
如果项目大量使用环境分支，业务逻辑和跨平台兼容代码会混杂在一起，代码臃肿、难以维护。

3. 静态导入无法按需剔除依赖，所有模块全打入包
即使根据环境判断只调用其中一个模块，打包工具依然会把两套模块都打进 bundle。示例代码：
```js
import { clientFunctionality } from 'clientModule'
import { serverFunctionality } from 'serverModule'

if (typeof window !== 'undefined' && window.document) {
  clientFunctionality()
} else {
  serverFunctionality()
}
```
webpack 打包后，`clientModule` 和 `serverModule` 都会被包含在内。
造成该问题的两大底层原因：
- 打包构建阶段无法预知运行时变量的值，无法判断 `if` 分支哪一段会被执行，只能全部保留；
- ESM `import` 是静态顶层声明，不能根据运行环境动态过滤导入语句，打包工具会直接载入所有导入模块。

补充：动态 `import()` 变量形式有特殊规则
```js
moduleList.forEach(function(module) {
  import(module)
})
```
像上面这种完全动态变量导入，打包工具无法预判文件路径，不会把任何模块打入 bundle。
但 webpack 支持有限的静态字符串模板动态导入：
```js
function getControllerModule (controllerName) {
  return import(`./controller/${controllerName}`)
}
```
这种写法下，webpack 会自动把 `controller` 文件夹下所有模块全部打包。
更多动态导入规则建议查阅 webpack 官方文档。

## 核心知识点
### 1. 三大核心痛点
1. **体积问题**：无效代码无法 Tree-Shake，浏览器包混入 Node 代码，体积变大；
2. **安全隐患**：服务端密钥、私密逻辑暴露在前端静态资源中；
3. **依赖冗余**：静态 `import` 不受 `if` 判断控制，双端依赖全部打包。

### 2. 底层根本原因
1. 构建时 ≠ 运行时：打包阶段不知道 `window` 这类变量最终值；
2. ESM 静态导入限制：`import` 必须写在顶层，不支持条件导入。

### 3. 两种动态 import 打包区别
1. 完全动态变量 `import(module)`：无法预判路径，不打包任何对应模块；
2. 模板字符串 `import(`./dir/${name}`)`：webpack 扫描对应目录，全部打包。

### 4. 适用场景边界
仅适合**极简小型差异化逻辑**；中大型项目、涉及服务端敏感数据、大量平台专属依赖时，禁止使用该方案，改用**构建时模块替换**。

# 译文 + 核心知识点
## 译文
### 构建时代码分支
本节我们将学习借助 webpack 插件，在打包阶段剔除仅服务端运行的代码。该方案可以产出体积更小的浏览器包，同时避免密钥、密码、API 密钥等敏感服务端代码意外暴露给前端。

webpack 支持插件机制拓展打包能力。实现构建时分支需要两个核心工具：
1. **DefinePlugin**：webpack 内置插件，用于在打包时全局替换代码中的变量；
2. **terser-webpack-plugin**：第三方压缩插件，基于 Terser 实现代码压缩与**死代码消除**。

我们先改造 `say-hello.js`，引入全局标记变量 `__BROWSER__`：
```js
import nunjucks from 'nunjucks'
export function sayHello (name) {
  if (typeof __BROWSER__ !== 'undefined') {
    // 浏览器专属代码
    const template = '<h1>Hello <i>{{ name }}</i></h1>'
    return nunjucks.renderString(template, { name })
  }
  // Node 服务端代码
  return `Hello \u001b[1m${name}\u001b[0m`
}
```
`__BROWSER__` 是自定义全局标识，我们会通过 DefinePlugin 在打包时赋值替换。

### 配置步骤
1. 安装压缩插件开发依赖
```bash
npm install --save-dev terser-webpack-plugin
```
2. 修改 `webpack.config.cjs` 配置
```js
const TerserPlugin = require('terser-webpack-plugin')
module.exports = {
  mode: 'production',
  plugins: [
    new webpack.DefinePlugin({
      __BROWSER__: true
    })
  ],
  optimization: {
    minimize: true,
    minimizer: [new TerserPlugin()]
  }
}
```
配置说明：
- `mode: production`：开启全套生产优化（压缩、死代码剔除）；
- DefinePlugin：打包时将代码中所有 `__BROWSER__` 替换为字面量 `true`；
- optimization.minimize：开启代码压缩，使用 Terser 插件做代码精简。

DefinePlugin 配置项的值会在构建阶段求值后直接替换源码中的对应标识符，除布尔值外，还可注入环境变量、时间戳、Git 提交哈希等外部数据。

### 打包后代码处理流程
1. 全局替换：所有 `__BROWSER__` → `true`，判断逻辑变为 `if (true !== 'undefined')`；
2. webpack 静态推导该判断恒为 `true`，简化为 `if (true)`；
3. Terser 压缩工具执行死代码消除，直接删除 `else` 内全部 Node 服务端代码，最终打包产物仅保留浏览器逻辑：
```js
import nunjucks from 'nunjucks'
export function sayHello(name) {
  const template = '<h1>Hello <i>{{ name }}</i></h1>'
  return nunjucks.renderString(template, { name })
}
```
浏览器 bundle 中彻底剔除了服务端代码，解决体积与安全两大痛点。

### 该方案局限性
构建时分支优于运行时分支，但如果项目大量滥用 `if (__BROWSER__)` 判断，源码依然会充斥大量环境分支，可读性、调试难度变差。
当平台专属逻辑复杂时，更好的方案是**拆分独立平台模块**，下一节讲解该方案。

## 核心知识点
### 1. 核心两大插件分工
1. `DefinePlugin`：构建阶段注入全局常量，标记环境；
2. `TerserPlugin`：压缩 + 死代码消除（移除永远不会执行的分支）。

### 2. 完整优化链路
源码带环境判断 → 构建替换常量 → 静态推导恒真/恒假分支 → Terser 删除无效代码 → 仅保留目标平台逻辑。

### 3. 对比运行时分支优势
1. 包体积更小：无用服务端代码彻底从前端产物移除；
2. 安全：密钥、服务端逻辑不会暴露给浏览器；
3. 无运行时判断开销。

### 4. 缺陷
大量跨平台分支依然会让源码杂乱；平台逻辑复杂时推荐**模块置换（module swapping）** 方案。

### 5. 关键配置补充
- 必须开启 `mode: production`，开发模式默认不执行死代码剔除；
- DefinePlugin 传入的值会被直接解析为 JS 字面量，字符串需要手动加引号 `"\"xxx\""`。

对，你说得**完全正确**，这就是 `DefinePlugin` 最经典、最容易踩的坑。

### 核心规则
`DefinePlugin` 会把你传的值**当作代码片段直接替换**，而不是当作字符串变量。

所以：
```js
// 错误：会被当成变量名，而不是字符串
new webpack.DefinePlugin({
  'process.env.NODE_ENV': 'production'
})
```

```js
// 正确：手动包一层引号，变成字符串字面量
new webpack.DefinePlugin({
  'process.env.NODE_ENV': '"production"'
})
```

---

### 更安全的写法（推荐）
用 `JSON.stringify()` 自动加引号，避免手滑漏写：
```js
new webpack.DefinePlugin({
  'process.env.NODE_ENV': JSON.stringify('production'),
  'process.env.BASE_URL': JSON.stringify('/api'),
})
```

---

### 数字 / 布尔值不需要加引号
```js
// 数字、布尔可以直接写
IS_PROD: true,
VERSION: 1.0.0
```

---

如果你现在的报错就是因为这个导致编译异常，把字符串改成 `"xxx"` 或 `JSON.stringify` 就能解决。

# 译文 + 核心知识点
## 译文
### 模块置换（Module swapping）
多数场景下，我们在打包阶段就能明确区分哪些代码需要打入浏览器包、哪些不需要。因此可以在构建前就做好分流，让打包工具**整体替换整个模块文件**。
相比运行时/构建时代码分支，该方案打包产物体积更轻、源码可读性更高，代码里不会充斥大量 `if...else` 环境判断。

我们改造示例，演示 webpack 模块置换用法：
核心思路：拆分两套独立实现
1. 服务端专用：`src/say-hello.js`
2. 浏览器专用：`src/say-hello-browser.js`
打包时让 webpack 把所有导入 `say-hello.js` 的语句，自动替换为导入浏览器版本。

```js
// src/say-hello.js（Node服务端实现）
import chalk from 'chalk'
export function sayHello (name) {
  return `Hello ${chalk.green(name)}`
}
```
```js
// src/say-hello-browser.js（浏览器实现）
import nunjucks from 'nunjucks'
const template = '<h1>Hello <i>{{ name }}</i>'
export function sayHello (name) {
  return nunjucks.renderString(template, { name })
}
```
服务端代码引入了 `chalk` 终端着色库，以此体现该方案核心优势：
两端代码完全隔离，服务端专属依赖不会被打进浏览器包，不会增大前端体积。

### webpack 配置改造
移除之前的 `DefinePlugin`，改用 `NormalModuleReplacementPlugin` 实现模块替换：
```js
plugins: [
  new webpack.NormalModuleReplacementPlugin(
    /src\/say-hello\.js$/,
    path.resolve(__dirname, 'src', 'say-hello-browser.js')
  )
]
```
插件入参说明：
1. 正则表达式：匹配需要被替换的模块文件路径；
2. 绝对路径：替换后的目标浏览器模块。

构建时，所有匹配正则的模块导入，都会自动替换为浏览器专用文件。
该方案不仅适用于项目内部源码，`node_modules` 第三方依赖同样可以置换。

借助模块置换插件，我们能优雅处理两端代码结构差异：只需要维护多份平台独立模块，打包时自动替换 Node 专属模块为浏览器兼容版本。

## 核心知识点
### 1. 核心插件：NormalModuleReplacementPlugin
作用：构建阶段全局替换匹配路径的模块文件，**整个文件直接替换**，而非只删代码分支。
参数：
- 正则：匹配原模块路径；
- 绝对路径：替换后的浏览器模块。

### 2. 核心优势
1. **依赖隔离**
服务端专属库（如 chalk、fs）不会被打包进浏览器产物，彻底减小包体积；
2. **源码干净**
无大量 `__BROWSER__` 环境判断，两端逻辑完全拆分，易维护、易调试；
3. **天然安全**
服务端密钥、数据库逻辑、终端工具完全隔离，不会流入前端 bundle；
4. 适用范围广：项目内部文件 + node_modules 第三方包都支持置换。

### 3. 和前两种方案对比
| 方案 | 优点 | 缺点 | 适用场景 |
|------|------|------|---------|
| 运行时分支 | 配置最简单，单文件 | 冗余代码全打进包，有安全风险 | 超简单小工具函数 |
| 构建时Define分支 | 能删无效代码，体积优化 | 文件内仍充斥环境if判断 | 少量简单平台逻辑 |
| 模块置换 | 两端完全隔离，依赖分离，代码整洁 | 需要维护两份模块文件 | 中大型跨平台项目、存在专属依赖 |

### 4. 拓展用法
不仅限于业务源码，可置换 node_modules 里的库：
例：Node 原生 `fs` 库打包时替换为浏览器兼容的内存文件模拟库。

### 5. 执行时机
模块替换发生在依赖解析阶段，打包器读取导入路径时就完成替换，从根源排除服务端模块，不会加载服务端依赖。

# 译文 + 核心知识点
## 译文
### 跨平台开发设计模式
我们回顾前面章节讲过的经典设计模式，讲解如何将它们应用于同构/跨平台代码开发：
1. **策略模式 & 模板方法模式**
二者是浏览器+Node共享代码最实用的模式。核心思想：定义一套通用算法主干，仅开放局部逻辑供外部替换，完美适配跨平台场景。
我们可以抽取出与平台无关的通用核心逻辑，把平台差异化部分做成可替换策略/模板方法，搭配运行时分支、构建时分支、模块置换三种方案切换不同平台实现。

2. **适配器模式**
适合整套组件跨平台替换。第8章结构模式中已有大量案例：
例如服务端使用 SQLite 数据库，可通过适配器封装一套浏览器兼容存储层，底层对接 `localStorage` / IndexedDB，对外提供和服务端一致的调用接口，上层业务代码无需改动。

3. **远程代理模式**
服务端独有能力暴露给浏览器时非常实用。举例：浏览器无法直接操作服务器文件系统，可在客户端封装一个 `fs` 代理对象，所有文件操作通过 Ajax / WebSocket 转发到服务端真实 `fs` 模块执行，再将结果回传给前端。

4. **依赖注入 / 服务定位器模式**
二者都支持在模块注入阶段替换底层实现。前文打包章节中，打包工具内置 `require` 运行时本质就是服务定位器，统一收集、调度所有模块代码。

可以看到适配跨平台的设计工具十分丰富，但最关键的能力是开发者根据业务场景选择最合适的方案。
掌握打包工具原理与各类跨平台编码模式后，本章下半部分将介绍 React，并从零搭建一套完整同构 JavaScript 应用。

## 核心知识点
### 各模式跨平台适用场景总结
1. **策略/模板模式**
适用：算法、流程主干通用，仅少量分支逻辑平台不同；
优势：核心代码完全复用，差异点抽离独立实现。
2. **适配器模式**
适用：底层存储、IO 整套组件两端API完全不同，但上层调用接口希望统一；
优势：抹平底层API差异，业务层无感知。
3. **远程代理模式**
适用：浏览器无权限调用服务端原生能力（文件、数据库、本地硬件）；
思路：前端调用转发远程服务，远程执行后返回结果。
4. **依赖注入/服务定位器**
适用全局统一替换底层服务（日志、存储、网络客户端），大型同构项目架构首选。

### 四种跨平台技术分层
1. 简易层：运行时代码分支（小工具、极简差异）
2. 优化层：构建时DefinePlugin死代码剔除（少量平台逻辑）
3. 工程层：NormalModuleReplacementPlugin 模块置换（两端依赖完全隔离）
4. 架构层：策略/适配器/DI等设计模式（中大型同构项目，复杂分层架构）
