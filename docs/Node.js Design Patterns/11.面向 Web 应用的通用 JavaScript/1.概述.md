# 译文+核心知识点（仅聚焦本节：Sharing code with the browser）
## 正文翻译
### 在浏览器与服务端共享代码
Node.js 的一大核心优势，是它基于 JavaScript、搭载 V8 引擎——而这款引擎同时驱动 Chrome、Edge 等主流浏览器。我们或许会以为，既然共用一套 JS 引擎，前后端共享代码会是一件轻而易举的事；但本章会讲到：**除非只共享完全独立、通用的极简代码片段，否则跨环境共享代码并不简单**。

同时适配客户端与服务端的开发，需要投入不少工作量，来保证同一份代码能在两种本质完全不同的环境正常运行。举个例子：Node.js 中不存在 DOM、持久化视图；而浏览器里无法访问文件系统，也没有各类操作系统底层交互接口。

另一大难点是现代 JS 语法的兼容差异。服务端 Node 环境可控：我们能确定服务器运行的 Node 版本，只要线上是 Node 8+，就可以放心使用 `async/await` 这类新语法。但浏览器环境完全不可控：不同用户使用的浏览器版本千差万别，一部分人用现代浏览器完整支持新语法，另一部分老旧设备的浏览器则完全不兼容 `async/await`。

因此，跨平台开发的核心工作，就是尽可能抹平两类运行环境的差异。我们可以借助抽象层、设计模式、工程工具，在**运行时动态切换**或**构建时区分**浏览器/Node 两套逻辑。

好在同构开发的需求持续走高，生态里大量库、框架都开始同时兼容两端，配套构建工具也经过多年打磨日趋成熟。很多 npm 包在 Node 中使用后，能直接在浏览器无差别运行。但仅靠第三方库兼容，不足以保证我们自己的业务代码两端零故障，跨平台代码依然需要严谨的设计。

本节我们会梳理一套代码同时跑在 Node、浏览器时会遇到的核心问题，并给出配套工具与设计模式，解决这一开发难题。

## 本节核心要点
1. **共用 V8 ≠ 代码直接互通**
    引擎相同，但运行时 API、全局对象完全割裂：
    - Node：`fs`/`process`/`child_process`、无 DOM/BOM
    - 浏览器：`window`/`document`/DOM API、无操作系统底层接口
2. **ES 语法兼容鸿沟**
    Node 版本固定，可直接使用新标准语法；浏览器碎片化，老旧环境不支持新特性，必须转译。
3. 抹平差异两大方案
    - 运行时分支：代码执行中判断当前环境，执行对应逻辑
    - 构建时分支：打包阶段区分两套代码，浏览器包剔除 Node 专属 API
4. 生态现状
    多数通用 npm 包已双端兼容，但业务层自定义代码仍需专门设计，不能直接复用。

## 译文：跨平台场景下的 JavaScript 模块
想要在浏览器与服务端共享代码，第一个阻碍就是**模块体系不匹配**：Node 的模块规范，与浏览器五花八门的模块方案无法互通。另一个痛点是浏览器不存在 `require()` 函数，也没有本地文件系统用于解析模块。

当下主流现代浏览器虽已支持 ES Module（`import`），但仍有部分用户使用老旧浏览器，不兼容这套标准。

除此之外，服务端与浏览器的代码分发逻辑完全不同：
服务端直接从本地文件系统加载模块，文件读取性能很高，因此业界提倡将代码拆分为大量小型模块，拆分逻辑、提升可维护性。

而浏览器的脚本加载机制截然不同：流程始于浏览器从远程服务拉取 HTML，解析页面后发现外部脚本链接，再逐个下载、执行脚本。如果应用代码拆分得很零散，浏览器就要发起大量 HTTP 请求，下载并解析海量脚本文件，才能完成应用初始化。文件数量越多，性能损耗越严重，弱网环境下问题会被放大。
即便我们可以借助 HTTP/2 服务端推送、客户端缓存、预加载等手段缓解该问题，但核心矛盾依旧存在：加载、解析大量零散文件，远不如少量优化后的文件高效。

针对这个痛点，行业通用方案是为浏览器**打包构建（bundle）**：构建流程会把所有源码合并为少量打包产物（例如单页对应一个 JS 文件），用户访问页面时无需批量请求脚本。
打包流程不止合并文件，还能执行多种优化，最典型的是**代码压缩（minification）**：在不改变代码逻辑的前提下精简代码体积，比如删除注释、剔除未使用代码、缩短函数与变量名。

## 核心要点
### 1. 两端模块体系三大冲突
1. Node 端：原生支持 CommonJS + ESM，依靠本地文件系统、`require.resolve` 算法查找依赖；
2. 浏览器旧环境：无 `require`、无文件系统，仅支持 `<script>` 标签全局变量；
3. 现代浏览器：原生 ESM，但存量老旧浏览器不兼容 `import/export`。

### 2. 加载性能的本质矛盾
- Node：本地磁盘读取小文件成本极低 → 鼓励**细粒度拆分模块**；
- 浏览器：每个脚本对应一次网络请求，网络开销远大于磁盘IO → 禁止大量零散脚本，必须打包合并。

### 3. 浏览器打包核心作用
1. 合并文件：减少 HTTP 请求数量；
2. 代码压缩：删除注释、死代码、缩短标识符，降低传输体积；
3. 配套拓展能力：转译 ES6+、Tree Shaking、代码分割、资源内联等。

### 4. 缓解优化手段（仅治标，无法替代打包）
HTTP/2 Server Push、浏览器缓存、`<link rel="preload">` 预加载。
