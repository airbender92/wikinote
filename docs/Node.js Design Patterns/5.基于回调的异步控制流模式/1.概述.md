# 中文翻译
## 基于回调的异步控制流模式
从同步编程风格切换到 Node.js 这类以**续传风格（CPS）**和异步 API 为主的平台时，开发者往往会感到不适。异步代码会让语句的执行顺序变得难以预测。即使是一些简单问题，比如遍历一组文件、按顺序执行任务，或是等待一批操作全部完成，都需要开发者采用全新的思路和技巧，否则很容易写出低效且难以阅读的代码。

使用回调处理异步控制流时，最常见的错误就是陷入**回调地狱（callback hell）**：代码横向嵌套越来越深，而不是纵向延伸，这种嵌套结构会让哪怕简单的逻辑都变得难以阅读和维护。

在本章中，你会看到，只要遵循一定规范并借助一些设计模式，我们完全可以驾驭回调，写出清晰、易于管理的异步代码。掌握好回调的正确用法，也将为你后续学习 Promise、async/await 等现代方案打下坚实基础。

简单来说，本章你将学习：
- 异步编程面临的挑战
- 如何避免回调地狱，以及回调相关的最佳实践
- 常见的异步模式：顺序执行、顺序迭代、并行执行、受限并行执行

# 逐段精读解析：不可预测函数 Unpredictable Function（Zalgo 源头）
## 1. 核心定义
**不可预测函数**：同一个接口，**某些场景同步执行回调、另一些场景异步执行回调**。
这是 Node.js 异步代码最经典的高危反模式，作者把这种现象命名为 **Unleashing Zalgo（释放扎尔戈）**。

## 2. 示例代码完整拆解
```javascript
import { readFile } from 'fs'
const cache = new Map() // 全局缓存，保存已读取文件内容

function inconsistentRead (filename, cb) {
  // 分支1：缓存命中 → 同步调用回调
  if (cache.has(filename)) {
    cb(cache.get(filename))
  } 
  // 分支2：缓存未命中 → 异步调用回调
  else {
    readFile(filename, 'utf8', (err, data) => {
      cache.set(filename, data)
      cb(data)
    })
  }
}
```
### 两条执行分支对比
1. **首次读取文件（无缓存）**
   `readFile` 是标准异步 IO API，回调会被丢进事件队列，**当前函数执行完毕后，下一轮事件循环才会执行 `cb`**。
2. **重复读取同一文件（缓存存在）**
   直接同步调用 `cb()`，**代码还没走完当前函数，回调立刻执行**。

### 关键矛盾：回调执行时机不确定
调用方完全无法预判 `cb` 是**立刻同步执行**，还是**延迟异步执行**。

## 3. 致命 Bug 演示（原文配套案例）
```javascript
function createFileReader(filename) {
  const listeners = []
  inconsistentRead(filename, value => {
    listeners.forEach(listener => listener(value))
  })
  return {
    onDataReady: listener => listeners.push(listener)
  }
}

// 第一次读取（无缓存，异步）
const reader1 = createFile('data.txt')
reader1.onDataReady(data => console.log('第一次数据'))

// 第二次读取（已有缓存，同步）
const reader2 = createFile('data.txt')
reader2.onDataReady(data => console.log('第二次数据')) // 这条日志永远不打印
```
### Bug 原因拆解
1. `reader1`：缓存为空 → `cb` 异步执行。
   先创建对象、注册监听函数，等事件循环再触发回调，注册流程完整，日志正常打印。
2. `reader2`：缓存已存在 → `cb` 同步执行。
   `inconsistentRead` 内部立刻遍历空数组 `listeners`，此时代码还没走到 `onDataReady` 注册监听，监听函数永远无法被触发。

## 4. 为什么这种缺陷极难排查？
1. 表现不稳定：复现依赖**请求顺序、缓存状态、并发时机**，本地无法稳定复现；
2. 无报错、无堆栈，程序静默丢失逻辑；
3. 高并发服务中随机出现请求卡死、回调不执行，难以定位根源。

## 5. 两种标准修复方案（消除 Zalgo）
### 方案1：全程同步（仅程序启动初始化可用）
用同步读取 `readFileSync`，全程同步逻辑，执行时机统一。
缺点：会阻塞事件循环，业务运行时严禁使用。
```javascript
import { readFileSync } from 'fs'
const cache = new Map()

function consistentReadSync(filename, cb) {
  let data
  if (cache.has(filename)) {
    data = cache.get(filename)
  } else {
    data = readFileSync(filename, 'utf8')
    cache.set(filename, data)
  }
  cb(data) // 全程同步调用
}
```

### 方案2：全程异步（生产通用最佳方案）
使用 `process.nextTick()` 强制把同步分支的回调推入微任务队列，保证**所有场景回调都延迟执行**，统一异步行为。
```javascript
import { readFile } from 'fs'
const cache = new Map()

function consistentReadAsync(filename, cb) {
  if (cache.has(filename)) {
    // 强制推迟到下一轮事件循环，统一异步行为
    process.nextTick(() => cb(cache.get(filename)))
  } else {
    readFile(filename, 'utf8', (err, data) => {
      cache.set(filename, data)
      cb(data)
    })
  }
}
```
补充：
- `process.nextTick` 优先级高于普通 IO 回调；
- 若担心无限微任务阻塞，可替换 `setImmediate`。

## 6. 核心设计准则（Node 异步编码铁律）
> 一个 API 的回调，要么**永远同步执行**，要么**永远异步执行**，不能两种行为混杂。

## 7. 补充原文注释的两个缺陷（示例简化，生产不能直接用）
1. 缺少错误处理：`readFile` 失败时没有把 `err` 传给回调，会静默吞异常；
2. 缓存逻辑简陋：未处理大文件、内存溢出、缓存过期，第11章会讲解工业级异步缓存方案。
