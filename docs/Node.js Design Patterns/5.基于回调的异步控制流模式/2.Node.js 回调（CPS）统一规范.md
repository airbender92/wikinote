# Node.js 回调（CPS）统一规范 完整解读
## 前言
Node 所有内置 API、社区主流库统一遵循一套**回调约定（Continuation-Passing Style，续传风格）**，是编写、阅读、排错异步代码的基础，自定义异步接口也必须遵守这套标准，保证生态一致性。

## 三大强制核心规范
### 1. 回调函数永远作为**最后一个参数**
#### 规则说明
函数入参列表里，普通业务参数在前，回调 cb 固定放在末尾；存在可选参数时也不例外。
#### 标准示例（fs.readFile）
```js
// 语法：readFile(path[, options], callback)
readFile('./a.txt', 'utf8', (err, content) => {})
```
- `path`、编码配置是前置参数；
- 回调永远是最后一位。
#### 反面错误设计（社区不会使用）
```js
// 糟糕：回调放中间，可读性极差
function badReadFile(cb, filename) {}
```

### 2. 回调第一个参数永远是错误对象：`(err, result, ...rest)`
#### 规则
1. 操作失败：第一个参数 `err` 是 `Error` 实例（禁止传字符串/数字报错）；
2. 操作成功：第一个参数 `err` 为 `null` / `undefined`；
3. 成功返回的数据从第二个参数开始传递，多返回值依次追加。
#### 标准正确写法
```js
readFile('test.txt', (err, text) => {
  if (err) {
    // 处理文件不存在、权限错误等
    return console.error(err)
  }
  // err 为 null，安全使用 text
  console.log(text)
})
```
#### 严重错误示范
```js
// 错误1：错误放第二个参数，破坏通用判断逻辑
readFile((content, err) => {})

// 错误2：报错不传 Error 对象，堆栈丢失无法排查
readFile((msg) => {
  if (msg === 'fail') {}
})
```

### 3. 错误必须沿回调链路传递（错误传播规范）
同步代码用 `throw` 抛异常；异步回调中**不能直接 throw**，只能把错误传给下一层回调。
#### 标准错误透传模板
```js
function readJSON(file, cb) {
  readFile(file, 'utf8', (err, raw) => {
    // IO 错误直接透传给上层回调
    if (err) return cb(err)

    try {
      const data = JSON.parse(raw)
      // 无错误，null 作为第一个参数
      cb(null, data)
    } catch (parseErr) {
      // 同步解析异常，捕获后传入回调
      cb(parseErr)
    }
  })
}
```
关键点：
- `return cb(err)` 提前终止函数，避免后续代码继续执行；
- 同步操作（JSON.parse、new 类）抛错必须用 `try/catch` 捕获再传给回调；
- 禁止在回调内部 `throw`，会直接导致进程崩溃。

## 补充配套规范：未捕获异步异常
如果异步回调内抛出异常，没有任何 `try/catch` 可以捕获，异常会直达事件循环，触发全局 `uncaughtException` 事件，进程会直接崩溃。
```js
readFile('xxx.txt', (err, data) => {
  if (err) return cb(err)
  // 无法被外层 try-catch 捕获
  JSON.parse(data) 
})
```
生产最佳实践：监听 `uncaughtException` 做日志、清理后主动退出进程，避免程序处于不一致脏状态。

## 一套规范带来的好处
1. **统一代码阅读习惯**：看到回调就知道 `err` 优先，不用记忆不同库自定义参数顺序；
2. **统一错误处理逻辑**：所有异步函数都能用 `if (err) return cb(err)` 模板；
3. **工具兼容**：`util.promisify`、async 等库依靠这套固定格式，自动把回调 API 转 Promise；
4. 降低协作沟通成本，团队自定义工具函数无需额外说明回调格式。

## 自定义异步接口的编码模板（标准范式）
```js
/**
 * 遵循Node回调规范的自定义异步函数
 * @param {string} filePath 入参
 * @param {Function} cb 回调放在最后 (err, fileData) => void
 */
function customRead(filePath, cb) {
  fs.readFile(filePath, 'utf8', (err, content) => {
    if (err) {
      // 错误优先传递
      return cb(err)
    }
    // 业务处理...
    const processed = content.toUpperCase()
    // 成功：err=null，返回结果
    cb(null, processed)
  })
}
```

# 原文精准逐段解析（只围绕 Uncaught exceptions，不额外发散）
## 核心概念：异步回调内抛出的未捕获异常
### 1 核心原理
异步回调函数内部执行同步代码时如果`throw`抛出错误，**外层同步`try/catch`完全捕获不到**。
原因：
`readFile`是异步API，文件读取完成后，回调函数是**全新调用栈**，在事件循环中执行，和调用`readJSONThrows`的代码不在同一执行堆栈。异常会一路冒泡到事件循环，Node 没有上层代码承接，判定为**未捕获异常**，程序直接退出。

### 2 错误示例代码拆解
```js
function readJSONThrows (filename, callback) {
  readFile(filename, 'utf8', (err, data) => {
    if (err) {
      return callback(err)
    }
    // JSON.parse 解析非法JSON会直接throw，没有try/catch包裹
    callback(null, JSON.parse(data))
  })
}
```
- 文件IO错误：能通过`callback(err)`传递给上层回调，属于**可控异步错误**；
- JSON解析语法错误：同步`throw`，无法传入callback，直接抛给事件循环。

调用代码：
```js
readJSONThrows('invalid_json.json', (err) => console.error(err))
```
这里的回调只会接收`readFile`的IO错误，**接收不到JSON.parse抛出的语法错误**，程序崩溃打印堆栈。
堆栈特征：报错起点是`FSReqCallback.readFileAfterClose`，证明异常发生在事件循环的异步回调栈里。

### 3 经典反模式：外层 try/catch 无效
```js
try {
  readJSONThrows('invalid_json.json', (err) => console.error(err))
} catch (err) {
  console.log('This will NOT catch the JSON parsing exception')
}
```
- `try/catch`包裹的是**发起异步请求的同步代码**；
- JSON解析的异常在很久以后、另一轮事件循环的独立堆栈抛出；
- 两个执行栈隔离，外层捕获器完全无法拦截。

### 4 兜底方案：`uncaughtException` 全局事件
当异常抵达事件循环且无任何捕获逻辑时，Node 会触发`process.uncaughtException`事件，是最后的拦截机会：
```js
process.on('uncaughtException', (err) => {
  console.error(`捕获到未捕获异常：${err.message}`)
  // 必须手动退出进程
  process.exit(1)
})
```
#### 关键警告（原文重点）
1. 未捕获异常出现后，程序**状态不可信**：可能存在未完成IO、闭包数据错乱、内存损坏等脏状态；
2. 生产环境禁止捕获后继续运行程序，必须执行清理并调用`process.exit(1)`；
3. 最佳实践（快速失败 fail-fast）：进程退出后，由外部守护进程（如pm2、systemd）重启服务。

### 5 正确修复写法（对应书中前文规范）
给回调内的同步解析加`try/catch`，把同步异常转成回调错误，遵循Node回调规范：
```js
function readJSONSafe (filename, callback) {
  readFile(filename, 'utf8', (err, data) => {
    if (err) return callback(err)
    try {
      const json = JSON.parse(data)
      callback(null, json)
    } catch (parseErr) {
      // 同步异常转异步回调错误
      callback(parseErr)
    }
  })
}
```

### 本段总结
1. 异步回调内部同步代码`throw`，外层`try/catch`无效；
2. 这类异常会直达事件循环，触发`uncaughtException`，进程默认崩溃；
3. 兜底事件仅用于日志+清理，不能恢复业务；
4. 标准解法：回调内同步逻辑一律用`try/catch`捕获，转成回调第一个Error参数传递。
