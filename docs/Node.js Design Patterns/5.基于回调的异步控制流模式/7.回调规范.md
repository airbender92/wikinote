# 原文完整解读：回调规范（消灭回调地狱三大准则 + 爬虫重构实战）
## 一、核心定位
无需第三方库、不换Promise，仅靠编码规范就能抹平多层嵌套，从根源解决回调地狱；同时是手写各类异步控制流的前置基础。
## 二、三大回调编码铁律（Callback discipline）
### 1. 尽早返回（Early return，最重要）
**核心：用return提前终止函数，消除else分支，直接减少缩进层级**
反面丑陋写法（多一层else嵌套）
```js
if (err) {
  cb(err)
} else {
  // 正常业务代码，多一层缩进
}
```
优化标准写法：出错直接`return cb(err)`，删掉else
```js
if (err) {
  return cb(err)
}
// 无缩进，直接写正常逻辑
```
关键易错点：只写`cb(err)`不加return，函数不会终止，报错后还会继续执行后续正常代码，产生双重回调、逻辑错乱。两种等价写法：
```js
// 简写（推荐）
return cb(err)
// 完整写法
cb(err)
return
```

### 2. 抽取具名函数，禁止无限内联匿名回调
不要把所有逻辑塞在回调内部，把独立功能抽成单独命名函数；
好处：栈追踪报错时能看到函数名、代码可复用、缩进自然变少。

### 3. 模块化拆分，单一职责
把通用IO、业务逻辑拆成独立工具函数，抽离出文件写入、网络请求等公共逻辑，多处可复用，支持单独单元测试。

## 三、爬虫完整重构流程（原四层嵌套 → 扁平化干净代码）
### 步骤1：抽离写入文件工具 saveFile
封装「创建目录+写入文件」逻辑，消除两层嵌套
```js
function saveFile(filename, contents, cb) {
  mkdirp(path.dirname(filename), err => {
    if (err) return cb(err)
    fs.writeFile(filename, contents, cb)
  })
}
```

### 步骤2：抽离下载工具 download
封装HTTP请求+调用saveFile，网络逻辑独立
```js
function download (url, filename, cb) {
  console.log(`Downloading ${url}`)
  superagent.get(url).end((err, res) => {
    if (err) return cb(err)
    saveFile(filename, res.text, err => {
      if (err) return cb(err)
      console.log(`Downloaded and saved: ${url}`)
      cb(null, res.text)
    })
  })
}
```

### 步骤3：改造主spider函数，反转判断条件，使用早返回
原逻辑：文件不存在才下载（else分支嵌套）
重构：文件已存在直接return，删除else，缩进彻底消失
```js
export function spider (url, cb) {
  const filename = urlToFilename(url)
  fs.access(filename, err => {
    // 文件存在，直接回调，return终止
    if (!err || err.code !== 'ENOENT') {
      return cb(null, filename, false)
    }
    // 仅文件缺失才执行下载，无嵌套
    download(url, filename, err => {
      if (err) return cb(err)
      cb(null, filename, true)
    })
  })
}
```

# 原文解读：串行执行（Sequential Execution）异步模式
## 一、串行执行核心定义
串行 = 任务**逐个依次执行**，上一个任务完全完成后，才启动下一个；执行顺序严格固定，前序任务的输出可以作为后序任务的输入，存在依赖关系。

## 二、串行三大分类（三种业务场景）
1. **固定任务串行（无数据传递）**
提前写死固定几个异步任务，依次执行，任务之间不交换数据。
例：先创建文件夹 → 再打印日志，两者无数据交互。

2. **流水线/瀑布流（Waterfall，带数据传递）**
前一个任务的返回结果，作为下一个任务的入参，强依赖。
对应之前爬虫：检查文件 → 下载页面 → 建目录 → 写入文件，每一步依赖上一步结果。

3. **集合异步串行迭代**
遍历数组，对每个元素依次执行异步操作，处理完当前元素再处理下一个。
例：循环抓取页面链接，一个页面爬完，再爬下一个链接。

## 三、核心痛点对比
同步阻塞代码中串行逻辑非常简单，自上而下线性书写；
但纯回调CPS写法下，串行极易产生多层嵌套，是**回调地狱的主要诱因**。
后续会给出纯JS递归实现的无嵌套串行迭代通用模板。

# 原文解读：固定任务串行执行通用模式
## 1. 模式核心思路
把每一步异步逻辑**拆分为独立具名函数**，单个任务完成后直接调用下一个任务，全程不使用多层内联匿名闭包，彻底规避回调金字塔。
适用场景：提前确定固定数量、固定执行顺序的异步任务。

## 2. 模板代码拆解
```js
// 任务1完成后执行task2
function task1 (cb) {
  asyncOperation(() => {
    task2(cb)
  })
}

// 任务2完成后执行task3
function task2 (cb) {
  asyncOperation(() => {
    task3(cb)
  })
}

// 最后一个任务，全部完成后执行顶层回调
function task3 (cb) {
  asyncOperation(() => {
    cb()
  })
}

// 入口：启动整条串行链路
task1(() => {
  console.log('所有任务全部执行完毕')
})
```
### 执行流程
1. 调用`task1`开启流程；
2. `task1`内部异步操作结束，触发回调，执行`task2`；
3. `task2`异步完成，执行`task3`；
4. `task3`结束，调用最外层传入的总回调，代表整条串行任务完成。

## 3. 模式优势
1. **无嵌套**：所有任务都是平级独立函数，不存在多层缩进，完美解决回调地狱；
2. **模块化复用** `task1/task2/task3` 可单独调用、单独测试；
3. 无需依赖第三方库，原生JS实现；
4. 消除深层闭包，减少内存泄漏风险。

## 4. 和爬虫重构代码对应关系
上一节重构后的`spider`、`download`、`saveFile`就是该模式的真实落地：
- `spider` = task1
- `download` = task2
- `saveFile` = task3
每一个函数执行完异步操作，直接调用下一个任务，逻辑完全匹配这套通用模板。

## 5. 补充局限
这套写法仅适用于**任务数量固定**的场景；
如果需要动态遍历数组、不确定任务数量（比如遍历链接列表），则需要下一节「串行迭代」递归模式。

# 原文精读：串行迭代（Sequential Iteration）
## 一、场景区分：固定串行 vs 串行迭代
上一节模式只能**硬编码固定个数任务**（提前知道有 task1/task2/task3）。
但业务经常需要：数组/集合长度不确定，对每个元素依次执行异步操作，**无法硬编码调用链**，这时要用「串行迭代递归模板」。
典型案例：爬虫解析页面所有链接，逐个串行爬取，链接数量不固定。

## 二、爬虫v2新需求说明
1. 新增递归爬取页面内全部链接，每个链接串行抓取；
2. 优化断点续传逻辑：不再只判断文件是否存在，而是直接读取本地文件；
   - 文件存在：直接读取内容、解析链接继续爬；
   - 文件不存在：先下载页面，再解析链接；
3. 新增`nesting`递归深度参数，防止无限递归爬全站；
4. 新增核心函数`spiderLinks`：接收页面内容，提取链接并**串行迭代爬取**。

## 三、重构后 `spider()` 代码逐段解析
```js
export function spider (url, nesting, cb) {
  const filename = urlToFilename(url)
  fs.readFile(filename, 'utf8', (err, fileContent) => {
    // 读取文件报错，且不是「文件不存在」错误 → 直接抛出异常
    if (err) {
      if (err.code !== 'ENOENT') {
        return cb(err)
      }
      // 文件缺失：先下载页面
      return download(url, filename, (err, requestContent) => {
        if (err) return cb(err)
        // 下载完成，解析页面链接串行爬取
        spiderLinks(url, requestContent, nesting, cb)
      })
    }
    // 文件已存在，直接解析现有页面内链接
    spiderLinks(url, fileContent, nesting, cb)
  })
}
```
### 逻辑分支
1. 读文件报错且非ENOENT（权限/路径错误）：回调抛出错误；
2. ENOENT 文件不存在：执行`download`下载页面，下载完调用`spiderLinks`；
3. 文件正常读取成功：直接传入已有页面内容给`spiderLinks`；
### 关键新增参数
`nesting`：递归层级，每爬一层链接数值-1，到达0停止递归，避免死循环。

# 原文解读：链接串行爬取核心逻辑
这一节是**异步串行迭代的经典递归模板**，也是 Node.js 回调式异步编程的核心写法，必须掌握。

## 一、核心函数：`spiderLinks` 完整解析
```js
function spiderLinks(currentUrl, body, nesting, cb) {
  // 达到最大深度，直接结束（用 nextTick 保证异步）
  if (nesting === 0) {
    return process.nextTick(cb)
  }

  // 解析页面内所有同域链接
  const links = getPageLinks(currentUrl, body)
  // 没有链接，直接结束
  if (links.length === 0) {
    return process.nextTick(cb)
  }

  // 迭代器函数：控制串行执行
  function iterate(index) {
    // 全部爬完 → 调用最终回调
    if (index === links.length) {
      return cb()
    }

    // 爬当前链接
    spider(links[index], nesting - 1, err => {
      if (err) return cb(err)
      // 完成后爬下一个
      iterate(index + 1)
    })
  }

  // 启动迭代：从第 0 个开始
  iterate(0)
}
```

---

## 二、关键步骤拆解
1. **深度控制**
   `nesting === 0` 时停止递归，避免无限爬取。
   用 `process.nextTick(cb)` 确保**统一异步返回**，防止 Zalgo 问题（同步/异步行为不一致）。

2. **解析链接**
   `getPageLinks` 提取页面内的**同域链接**，避免爬到外部网站。

3. **串行迭代核心：`iterate(index)`**
   这是**通用串行迭代模式**：
   - 接收当前要处理的下标
   - 下标等于数组长度 → 全部完成，调用最终 `cb`
   - 否则调用 `spider` 爬当前链接
   - 爬完后递归调用 `iterate(index + 1)` 处理下一个

4. **启动迭代**
   `iterate(0)` 从第一个链接开始执行。

---

## 三、这个模式的本质
这是**回调式异步串行遍历的标准实现**：
- 没有循环 `for/forEach`，因为它们不等待异步完成
- 用**递归 + 下标计数**模拟循环
- 严格保证：**一个链接爬完，再爬下一个**

# 原文解读：串行迭代通用模式
## 一、通用化模式（核心模板）
这是**所有异步串行遍历的底层写法**，适用于数组、任务列表、异步循环：

```js
function iterate(index) {
  // 迭代结束条件
  if (index === tasks.length) {
    return finish()
  }

  // 取出当前任务并执行
  const task = tasks[index]
  task(() => iterate(index + 1))
}

function finish() {
  // 全部完成
}

// 启动迭代
iterate(0)
```

### 核心思想
- 用**递归**代替 `for/while`，因为循环不等待异步完成
- 用**下标 index**控制进度
- 上一个任务完成 → 调用下一个 `iterate(index + 1)`
- 完全扁平，无回调地狱

---

## 二、这个模式能实现的扩展能力
- **异步 map**：遍历并对每个元素做异步处理，收集结果
- **异步 reduce**：把前一个异步结果传给下一个
- **异步 break**：满足条件就提前退出循环
- **无限迭代**：动态生成任务，持续执行

---

## 三、重要警告
### 1. 爬虫使用规范
不要爬太深、不要长时间跑，不要对服务器发起大量请求，可能违法或被封。

### 2. 同步任务会导致爆栈风险
如果 `task` 是**同步操作**，`iterate` 会变成**深度同步递归**，可能超出最大调用栈。
只有任务是**异步**时，每轮都会释放调用栈，才安全。

---

## 四、更进一步：封装成通用工具函数

```js
iterateSeries(collection, iteratorFn, finalCallback)
```

- `collection`：要遍历的数组
- `iteratorFn`：对每个元素执行的异步函数
- `finalCallback`：全部结束/出错时调用

这是类似 `async.series` 的原生实现，课后练习可自行封装。

# 原文解读：并行执行模式（Parallel Execution）
## 一、核心概念
并行执行 = **同时启动多个异步任务**，不等待前一个完成，**所有任务结束后统一通知**。
任务之间无依赖、顺序无关，目的是**缩短总耗时**。

---

## 二、关键澄清：Node.js 的“并行”其实是 **并发（Concurrency）**
Node 是**单线程**，没有真正的多核并行。
但异步 IO 操作（网络、文件）由底层非阻塞 API 并行处理，事件循环负责调度回调，实现**并发执行**。

简单流程：
1. 主线程**同时发起**多个异步操作（读文件、发请求）
2. 主线程立刻返回，不阻塞
3. 某个 IO 完成 → 事件循环执行其回调
4. 全部完成 → 执行最终回调

---

## 三、并行执行的特点
- 任务启动顺序 ≠ 完成顺序
- 总耗时 ≈ **最慢的那个任务**，而不是所有任务时间之和
- 只对**异步 IO 任务**有效
- **同步阻塞代码无法并行**，必须靠 `setTimeout`/`setImmediate` 让出线程

---

## 四、与串行执行对比
- **串行**：一个做完 → 再做下一个
- **并行**：一起开始 → 全部做完统一收尾

---

## 五、下一节内容预告
会给出**并行执行的通用回调模式**：
用一个计数器跟踪完成数，全部完成后调用最终回调，这是 Node.js 最经典的并发控制模式。

# 原文解读：并行爬虫（v3）+ 并行执行通用模式
## 一、核心改动思路
把原来**串行爬链接**改成**同时发起所有下载**，利用 Node 异步 IO 并发能力，大幅提速。

## 二、并行版 `spiderLinks` 完整解析
```js
function spiderLinks(currentUrl, body, nesting, cb) {
  if (nesting === 0) {
    return process.nextTick(cb)
  }

  const links = getPageLinks(currentUrl, body)
  if (links.length === 0) {
    return process.nextTick(cb)
  }

  // 并行控制核心变量
  let completed = 0
  let hasErrors = false

  // 每个任务完成后的统一回调
  function done(err) {
    // 一旦出错，立即终止，只回调一次
    if (err) {
      hasErrors = true
      return cb(err)
    }

    // 全部完成且无错误 → 结束
    if (++completed === links.length && !hasErrors) {
      cb()
    }
  }

  // 🔥 一次性启动所有爬虫任务（并行核心）
  links.forEach(link => spider(link, nesting - 1, done))
}
```

---

## 三、并行模式的两个关键点
### 1. 同时启动所有任务
```js
links.forEach(link => spider(..., done))
```
不等待、不排队，直接全部发起，这就是并行。

### 2. 用计数器 + 完成回调统一收尾
- `completed`：记录已完成任务数
- `done()`：每个子任务结束时调用
- 当 `completed === links.length`：全部完成

---

## 四、错误处理逻辑（非常重要）
- 任意一个任务出错 → 立即调用 `cb(err)`
- `hasErrors` 标记防止**多次回调**
- 其他仍在运行的任务会继续执行，但结果不再处理

这是并行回调模式的标准错误处理方式。

---

## 五、效果
- 下载速度**显著提升**
- 总时间 ≈ 最慢的那个页面下载时间
- 不再是所有下载时间相加

---

## 六、通用并行执行模式（可直接套用）
```js
const tasks = [...]
let completed = 0

function done(err) {
  if (err) return finalCb(err)
  if (++completed === tasks.length) {
    finalCb()
  }
}

tasks.forEach(task => task(done))
```

这是 Node.js 最经典、最基础的**并行异步控制模式**：
**同时启动 → 计数器收尾 → 统一回调**

# 并行执行通用模式（完整版）

## 一、最简并行模板
```js
const tasks = [/* 异步任务列表 */]

let completed = 0

tasks.forEach(task => {
  task(() => {
    if (++completed === tasks.length) {
      finish()
    }
  })
})

function finish() {
  // 所有任务执行完毕
}
```

### 核心原理
- 一次性**全部启动**所有异步任务
- 用 `completed` 计数器记录完成数
- 计数器达标 → 调用 `finish`

---

## 二、可扩展的变种
这本书明确指出这个简单模式可以轻松改造成：

1. **带结果收集的并行 map**
   每个任务回调把结果存入数组，最后一起返回。

2. **并行 filter**
   异步判断条件，最后过滤出符合条件的项。

3. **竞争模式（Race）**
   任一任务完成就立即调用 `finish`，实现“竞速”。

4. **指定数量完成即返回**
   比如 10 个任务里完成 5 个就触发回调。

---

## 三、引出新问题：竞态条件（Race Conditions）
并行执行会带来新坑：**多个异步任务同时读写同一个外部资源**，比如：
- 同一个文件
- 同一个数据库记录
- 同一个共享变量

可能导致：
- 数据覆盖
- 状态错乱
- 结果不符合预期

下一节就会专门讲 **Node.js 中的竞态问题与解决方法**。

# 原文解读：用并发控制修复竞态条件
## 一、Node 单线程下为什么还会有竞态？
关键点：
**单线程 ≠ 无竞态**
竞态不是来自多线程冲突，而是来自：
**异步操作发起 → 结果返回之间的时间差**
在这段空隙里，另一个同逻辑的任务可以同时启动。

---

## 二、爬虫里的真实竞态问题
两个并行任务同时爬同一个 URL：
1. 任务A：`fs.readFile` 发现文件不存在
2. 任务B：同时也 `fs.readFile`，同样发现不存在
3. 两个任务**同时开始下载同一个文件**
→ 重复下载、浪费带宽、可能写文件冲突

这是典型的 **check-then-act 竞态**。

---

## 三、最简修复方案：一个 Set 做“锁”
```js
// 全局记录正在爬的 URL
const spidering = new Set()

function spider(url, nesting, cb) {
  // 正在爬 → 直接返回，不再重复爬
  if (spidering.has(url)) {
    return process.nextTick(cb)
  }

  // 标记为正在爬
  spidering.add(url)

  // 后续正常逻辑...
}
```

### 原理
- 用一个 `Set` 记录**正在处理的 URL**
- 检查 + 标记 是同步操作，在单线程下**原子性**，不会被打断
- 从根本上避免重复下载

这就是 Node 里最常用的**轻量级并发控制**，不需要锁、信号量。

---

## 四、为什么这个方案在 Node 里有效？
- 所有同步代码（if 判断 + add）**原子执行**
- 单线程下不会被中断
- 异步操作才会让出事件循环

所以一个简单的集合就能实现**互斥**。

---

## 五、扩展优化
如果爬海量页面，可以在下载完成后移除：
```js
spidering.delete(url)
```
避免 Set 无限膨胀占内存。

---

## 六、本节重要结论
1. 单线程 Node 仍然会出现**竞态条件**
2. 根源是异步操作的延迟
3. 不需要复杂锁机制，用**变量/集合标记状态**即可解决
4. 竞态很难复现、很难调试，写并行逻辑时必须提前预防

---

## 七、下一节预告
无限制并行很危险：
- 瞬间几百个请求会打崩目标服务器
- 本地网络、文件句柄耗尽

所以要学习：
**有限并行模式（Limited Parallel Execution）**
限制同时运行的任务数量。

# 原文解读：有限并行执行（限流并发）

## 一、为什么要限制并行数
无限并行会直接引发一系列问题：
- 瞬间发起大量请求 → 目标服务器拒绝连接（`ECONNREFUSED`）
- 耗尽文件描述符、网络端口、内存
- 极易被判定为 DoS 攻击，导致程序直接崩溃
- 生产环境中是**稳定性大忌**

所以必须控制**最大并发数**。

## 二、限流并发核心思路
1. 一开始最多启动 **N 个任务**（N = 并发上限）
2. 每完成一个任务，**立即补一个新任务**
3. 始终保持同时运行的任务数不超过上限

这就是**有限并行执行模式**。

## 三、典型流程（并发上限 = 2）
- 启动任务1、任务2
- 任务1完成 → 启动任务3
- 任务2完成 → 启动任务4
- 任务3完成 → 启动任务5
- 全部结束

始终保持 **≤2 个任务同时运行**。

# 原文解读：有限并发执行模式（通用限流模板）

这是 Node.js 异步编程**最实用、最核心**的并发控制模式，直接背下来都不过分。

## 一、完整限流模板
```js
const tasks = [/* ... */]
const concurrency = 2  // 最大同时运行任务数

let running = 0
let completed = 0
let index = 0

function next() {
  // 🔥 核心：在并发限制内尽可能多启动任务
  while (running < concurrency && index < tasks.length) {
    const task = tasks[index++]

    // 执行任务，任务完成后触发回调
    task(() => {
      completed++
      // 全部完成 → 结束
      if (completed === tasks.length) {
        return finish()
      }
      // 减少运行计数，继续启动下一个
      running--
      next()
    })

    running++
  }
}

// 启动
next()

function finish() {
  // 全部任务执行完毕
}
```

---

## 二、核心逻辑拆解
### 1. `next()` 负责启动任务
- 循环判断：`正在运行数 < 并发上限`
- 能启动多少就启动多少
- 用 `index` 记录下一个要执行的任务

### 2. 任务完成回调
- 计数 `completed++`
- `running--` 腾出并发位
- 再次调用 `next()` 补上一个新任务

### 3. 整体行为
- 始终**最多同时跑 concurrency 个任务**
- 一个结束 → 立即补一个
- 既快又安全，不会爆资源

---

## 三、模式本质
= **并行执行 + 串行迭代** 的结合体
- 上限内并行
- 超上限排队
- 完成一个再进一个

---

## 四、用在爬虫上的效果
- 限制同时下载数（比如 2~5）
- 不会被服务器封 IP
- 不会耗尽文件描述符
- 程序稳定不崩溃

这就是最终版**健壮型爬虫**的核心逻辑。

# 原文精读：全局并发限制 + 任务队列（TaskQueue）

## 一、为什么页面级限流不够用？
如果只在 `spiderLinks` 里限制每页并发 2：
- 每页最多下 2 个链接
- 但递归爬取时，**子页面又会各开 2 个**
- 最终总下载数会**指数级爆炸**
- 无法实现真正的**全局最大并发控制**

所以需要：
**一个全局共享的队列，统一管理所有下载任务**

---

## 二、核心解决方案：TaskQueue 类
这是 Node.js 异步限流的**经典工程模式**，直接复用即可。

```js
export class TaskQueue {
  constructor(concurrency) {
    this.concurrency = concurrency  // 全局最大并发
    this.running = 0                // 当前正在跑的任务数
    this.queue = []                 // 等待队列
  }

  pushTask(task) {
    this.queue.push(task)
    process.nextTick(this.next.bind(this))  // 异步触发下一轮
    return this
  }

  next() {
    // 一边有空位，一边有任务 → 一直跑
    while (this.running < this.concurrency && this.queue.length) {
      const task = this.queue.shift()  // 取队首

      // 执行任务，完成后自动继续队列
      task(() => {
        this.running--
        process.nextTick(this.next.bind(this))
      })

      this.running++
    }
  }
}
```

---

## 三、核心逻辑拆解
### 1. 构造函数
- `concurrency`：全局最大并行下载数
- `running`：正在执行的任务数
- `queue`：所有待执行的任务排队

### 2. pushTask(task)
- 把任务加入队列
- 用 `process.nextTick` 异步触发 `next()`，开始消费

### 3. next() 消费逻辑
- 循环判断：**没超过并发上限 + 队列不为空**
- 从队列头取任务执行
- 任务完成后：
  - `running--`
  - 再次异步调用 `next()`，继续消费下一个

这就实现了：
**全局最多 N 个任务并行，一个结束，一个补上**

---

## 四、为什么这个方案适合递归爬虫？
- 队列是**全局共享**的
- 无论哪个页面、哪个层级产生的下载任务，都进同一个队列
- 真正实现**全局并发数严格可控**
- 不会指数级增长
- 稳定、可预测、不会被封、不会崩溃

---

## 五、模式总结
- 有限并行 → 适合固定任务列表
- **TaskQueue 全局队列 → 适合动态、递归、无限新增任务**
- 这是构建稳定爬虫、批量下载、批量 API 调用的**标准工程实践**

# 原文解读：增强版 TaskQueue（EventEmitter + 错误 + 完成事件）
## 一、为什么要升级 TaskQueue？
原版队列缺少两个工程必备能力：
1. 感知**任务失败**（报错没人知道）
2. 感知**队列全部空了**（所有任务完成）

解决方法：继承 `EventEmitter`，通过**事件**对外通知。

## 二、升级后核心代码
```js
import { EventEmitter } from 'events'

export class TaskQueue extends EventEmitter {
  constructor(concurrency) {
    super()
    this.concurrency = concurrency
    this.running = 0
    this.queue = []
  }

  pushTask(task) {
    this.queue.push(task)
    process.nextTick(this.next.bind(this))
    return this
  }

  next() {
    // ✅ 1. 队列为空且没有运行任务 → 触发 empty 事件
    if (this.running === 0 && this.queue.length === 0) {
      return this.emit('empty')
    }

    while (this.running < this.concurrency && this.queue.length) {
      const task = this.queue.shift()

      // ✅ 2. 任务回调现在支持 err 参数
      task((err) => {
        if (err) {
          this.emit('error', err) // 任务出错 → 触发 error 事件
        }
        this.running--
        process.nextTick(this.next.bind(this))
      })

      this.running++
    }
  }
}
```

## 三、两个关键增强
### 1. 队列排空事件：`empty`
当：
- 运行数 `running === 0`
- 且队列 `queue.length === 0`

触发 `empty`，表示**所有任务全部结束**。

### 2. 任务错误事件：`error`
任务回调传入 `err` 时，直接 `emit('error', err)`，
不会中断队列，其他任务继续跑。

## 四、设计思想（重要）
- 出错**不停止队列**，不崩溃
- 错误通过事件上报，外部决定重试/忽略/记录
- 适合长期运行的系统（爬虫、批量任务、服务）

## 五、外部使用方式
```js
const queue = new TaskQueue(2)

queue.on('empty', () => {
  console.log('全部任务完成！')
})

queue.on('error', (err) => {
  console.error('任务失败：', err)
})
```

这就是生产可用的**通用异步限流队列**，也是 Node 批量并发任务的标准写法。

function spiderLinks(currentUrl, body, nesting, queue) {
