# 原文逐段精准解读 EventEmitter
## 一、核心背景：传统OOP观察者 vs Node EventEmitter
传统面向对象实现观察者模式，需要定义接口、父类、继承层级，代码繁琐；
Node 直接在核心模块内置 `EventEmitter` 类，开箱即用，极简实现观察者模式：
- `EventEmitter` = 观察者模式的标准实现（发布者/主体subject）
- `on/once` 注册的函数 = 观察者/监听器listener
- `emit` 触发事件 = 主体状态变更，批量通知所有观察者

## 二、基础引入方式
`events` 是 Node 内置核心模块，无需安装依赖：
```js
import { EventEmitter } from 'events'
// 创建发布者实例
const emitter = new EventEmitter()
```

## 三、四大核心API（支持链式调用，返回自身实例）
1. **`.on(eventName, listener)`**
持续注册监听器；每次触发对应事件都会执行该函数，永久生效，不手动移除则一直存在。
2. **`.once(eventName, listener)`**
一次性监听器：事件第一次触发执行完毕后，自动解绑，只会运行一次。
3. **`.emit(eventName, ...args)`**
主动派发事件，可传递任意数量参数给所有绑定的监听器。
4. **`.removeListener(eventName, listener)`**
手动移除指定事件的指定监听器；**必须传入原始函数引用**，匿名函数无法移除。

### 链式调用示例
```js
emitter
.on('data', msg => console.log(msg))
.once('finish', () => console.log('结束'))
.emit('data', '测试消息')
```

## 四、监听器 与 Node 标准回调的关键差异（原文重点）
Node 普通异步回调强制规范：`(err, result)`，**第一个参数固定为错误**
EventEmitter 的监听器无此约束：
- 监听器入参完全由 `emit` 传递的参数决定，第一个参数可以是任意业务数据；
- 只有约定的 `error` 事件才会把错误对象作为参数，普通事件无统一错误规范。

### 对比示例
1. 标准回调（IO操作）
```js
readFile('a.txt', (err, content) => {}) // 首参数固定err
```
2. EventEmitter 普通事件
```js
emitter.on('data', (text, time) => {}) 
emitter.emit('data', '文本内容', Date.now()) 
// 参数完全自定义，不存在err强制首位
```

## 五、补充概念对应
观察者模式标准定义：
主体(subject)：`EventEmitter` 实例
观察者(observer/listener)：`on/once` 绑定的回调函数
事件触发通知：调用 `emit()`，批量执行同类型全部监听器（一对多）

# 原文代码逐段解析：EventEmitter 实战 findRegex
## 一、函数功能说明
`findRegex(files, regex)`：批量读取一组文件，匹配正则，通过`EventEmitter`实时向外推送三类事件，**无需等待全部文件读完才返回结果**，实现流式通知。
## 二、代码拆解
### 1. 依赖与函数主体
```js
import { EventEmitter } from 'events'
import { readFile } from 'fs'

function findRegex (files, regex) {
  // 1. 创建EventEmitter实例（发布者）
  const emitter = new EventEmitter()

  // 2. 循环异步读取每个文件
  for (const file of files) {
    readFile(file, 'utf8', (err, content) => {
      // 文件读取失败：触发error事件，参数为错误对象
      if (err) {
        return emitter.emit('error', err)
      }
      // 文件读取成功：触发fileread事件，传递文件名
      emitter.emit('fileread', file)
      // 正则匹配文件内容
      const match = content.match(regex)
      if (match) {
        // 每匹配到一个结果，触发found事件，传文件名+匹配文本
        match.forEach(elem => emitter.emit('found', file, elem))
    })
  }
  // 3. 直接返回emitter，外部可以链式绑定监听
  return emitter
}
```
### 2. 函数会抛出3类事件
1. `error`：文件读取报错（不存在/权限不足等），emit传`Error`对象；
2. `fileread`：单个文件读取完成，emit传文件名；
3. `found`：文件内匹配到正则片段，emit传**文件名、匹配到的字符串**两个参数。

## 三、外部调用示例（链式绑定监听器）
```js
findRegex(
  ['fileA.txt', 'fileB.json'],
  /hello \w+/g // 匹配 hello+单词
)
.on('fileread', file => console.log(`${file} was read`))
.on('found', (file, match) => console.log(`Matched "${match}" in ${file}`))
.on('error', err => console.error(`Error emitted ${err.message}`))
```
### 执行逻辑
1. 调用`findRegex`立刻拿到`emitter`，同步绑定所有监听；
2. 文件是异步读取，哪个文件先读完，就立刻触发对应事件；
3. 一对多特性：一个`fileread/found/error`事件可绑定任意多个监听函数。

## 四、关键知识点（贴合原文重点）
1. `emit(事件名, 参数1, 参数2...)`可以传递任意数量参数给监听器，`found`事件传递两个参数；
2. `error`是EventEmitter特殊事件：**不注册监听会直接让进程崩溃**，业务必须监听`error`；
3 该API设计是经典「回调+EventEmitter混合模式」：函数返回事件发射器，持续推送实时进度，适合流式、多阶段任务（爬虫、文件扫描、日志解析）。

# 原文解读：EventEmitter 的错误传递规范
## 核心规则
EventEmitter 发生错误时**不能直接 throw 抛出异常**，统一约定：触发专属 `error` 事件，并把 `Error` 实例作为入参传给监听器。
## 原因对比
1. 普通同步代码：出错用 `throw` + `try/catch` 捕获；
2. 回调函数：错误通过回调首个参数 `err` 传递；
3. EventEmitter 场景：事件触发是一对多广播，没有统一回调接收错误，因此设计专用 `error` 事件统一分发异常。

## 规范实操（对应上文 `findRegex` 示例）
文件读取失败时，不抛出异常，调用 `emitter.emit('error', err)`：
```js
readFile(file, 'utf8', (err, content) => {
  if (err) {
    // 遵循规范：发射error事件，携带错误对象
    return emitter.emit('error', err)
  }
})
```

## 致命特性（重点）
`error` 事件是特殊事件：
如果一个 EventEmitter 触发 `error`，但程序**没有通过 `.on('error', ...)` 注册任何监听器**，Node.js 会直接抛出未捕获异常，导致整个应用进程崩溃。
因此所有 EventEmitter 实例，业务代码必须监听 `error` 事件。

## 正确使用模板
```js
const emitter = findRegex(['test.txt'], /test/)
// 必须注册error监听器，防止进程崩溃
.on('error', err => console.error('读取文件失败：', err.stack))
.on('fileread', file => console.log(file))
```

# 原文完整解读：让任意对象具备可观测能力（继承EventEmitter模式）
## 一、核心思想
直接新建`EventEmitter`实例单独使用很少见，行业主流写法是**类继承EventEmitter**：
子类自动获得`on/once/emit/removeListener`全部事件能力，自身业务逻辑 + 事件广播能力合为一体，这个类生成的实例就是**可观测对象（observable）**。

## 二、代码拆解：FindRegex 完整实现
```js
import { EventEmitter } from 'events'
import { readFile } from 'fs'

// 继承EventEmitter，自动拥有事件能力
class FindRegex extends EventEmitter {
  constructor (regex) {
    super() // 必须调用父类构造，初始化EventEmitter内部存储监听器的数据结构
    this.regex = regex
    this.files = []
  }

  // 链式添加待扫描文件
  addFile (file) {
    this.files.push(file)
    return this // 支持链式调用
  }

  // 启动文件异步扫描
  find () {
    for (const file of this.files) {
      readFile(file, 'utf8', (err, content) => {
        // 错误统一emit error事件（规范）
        if (err) {
          return this.emit('error', err)
        }
        this.emit('fileread', file)
        const match = content.match(this.regex)
        if (match) {
          match.forEach(elem => this.emit('found', file, elem))
        }
      })
    }
    return this // 链式调用支持
  }
}
```
### 关键要点
1. `extends EventEmitter`：继承后实例自带所有事件API；
2. 构造函数必须执行`super()`，否则父类内部监听器容器未初始化，调用`on/emit`会报错；
3. `addFile()`、`find()`都返回`this`，实现流畅链式写法。

## 三、实例调用演示
```js
const findRegexInstance = new FindRegex(/hello \w+/)
findRegexInstance
  .addFile('fileA.txt')
  .addFile('fileB.json')
  .find()
  .on('found', (file, match) => console.log(`匹配到${match}：${file}`))
  .on('error', err => console.error('出错：', err.message))
```
实例`findRegexInstance`既是业务工具类（管理文件、扫描逻辑），又是事件发布者，可监听`found`/`error`/`fileread`事件。

## 四、Node生态大量同类内置案例（原文举例）
1. **http.Server**
   继承EventEmitter，可监听`request`、`connection`、`close`等网络事件；
2. **所有Stream流（可读/可写/转换流）**
   全部继承EventEmitter，支持`data`、`end`、`error`事件，第6章会深入讲解。

## 五、重复强调error事件特殊规则
若调用`this.emit(err)`，但当前实例**没有注册`.on('error', ()=>{})`监听器**，Node会直接抛出未捕获异常，进程退出。
所有继承EventEmitter的业务实例，都必须监听`error`事件兜底。

## 六、该模式优势
1. 高内聚：业务数据/操作 + 事件通知能力封装在同一个类，不用额外单独创建emitter；
2. 符合Node原生设计范式，阅读、维护成本更低；
3. 天然支持链式调用，API简洁易读。

# 原文精读：EventEmitter 与内存泄漏
## 一、核心结论
**未销毁的监听器是 Node/JS 最主要的内存泄漏来源**。长期存活的 EventEmitter（全局服务、HTTP Server、全局消息总线等）上注册的监听器，如果不再使用却不解绑，会持续占用内存，程序内存持续上涨直至崩溃。

### 内存泄漏底层原理
JS 垃圾回收机制：对象只要存在**可达引用**，就不会被回收。
```js
const thisTakesMemory = '超大长字符串/大数组/大型对象'
// 监听器闭包捕获外部变量
const listener = () => {
  console.log(thisTakesMemory)
}
emitter.on('an_event', listener)
```
1. `emitter` 内部保存了 `listener` 的引用；
2. `listener` 闭包持有 `thisTakesMemory`；
3. 只要 `emitter` 全局一直可达（比如全局HTTP服务），`listener` 和它捕获的大内存变量永远无法被GC回收。

### 高危场景示例
每一次HTTP请求都给全局EventEmitter注册监听器，请求结束不执行解绑：
请求越来越多，监听器无限累积，内存持续膨胀，最终OOM崩溃。

## 二、手动解绑方案：`removeListener`
语法要求：必须传入**完全相同的函数引用**，匿名函数无法解绑。
```js
// 正确：保存函数引用，后续可移除
function listener() {}
emitter.on('an_event', listener)
// 销毁监听器，释放闭包占用内存
emitter.removeListener('an_event', listener)

// 错误：匿名函数无法移除
emitter.on('test', () => {})
emitter.removeListener('test', () => {}) // 无效，两个是不同函数
```

## 三、内置内存泄漏预警机制
Event 默认规则：**单个事件注册监听器超过10个，控制台打印内存泄漏警告**，提示开发者可能忘记清理监听。
### 调整监听上限：`setMaxListeners(n)`
如果业务确实需要超过10个合法监听器（多模块日志监听等），手动调高阈值：
```js
emitter.setMaxListeners(20) // 单事件最多20个监听器，不再告警
emitter.setMaxListeners(0) // 无上限，永久关闭警告（不推荐生产）
```

## 四、补充规避手段（原文隐含最佳实践）
1. **一次性监听 `once`**
事件触发后自动解绑，天然无泄漏风险，适合只执行一次的逻辑；
2. 临时生命周期匹配：局部EventEmitter，实例销毁后自动释放所有监听；
3. 请求级监听：请求结束必须调用 `removeListener` 清理；
4. 全局长生命周期Emitter严格管控监听器注册与销毁配对。

# 原文完整解读：同步事件 vs 异步事件（Zalgo 问题延伸）
## 核心总原则
同一个 `EventEmitter` 下，**同一种事件不能一部分同步触发、一部分异步触发**，否则会出现和「不可预测函数 Unleashing Zalgo」完全一样的隐蔽 Bug。
两者最大差异：**监听器注册时机是否能晚于任务启动**。

## 1. 异步 emit（推荐，Node 主流写法）
### 代表案例：原版 `FindRegex.find()`
内部使用异步 `readFile`，文件读取完成后才调用 `this.emit()`
- `emit` 执行时机：**下一轮事件循环**，当前同步代码执行完毕后才广播事件
- 优势：任务启动后再绑定监听器也不会丢失事件
```js
findRegexInstance
  .addFile('fileA.txt')
  .find() // 启动异步读取，emit 延迟到下一轮循环
  .on('found', msg => console.log(msg)) // 后置监听依然能收到事件
```
原理：调用 `find()` 只是发起文件读取操作，同步代码立刻走完，后续 `on` 注册监听器；等 IO 完成进入下一轮事件循环才触发 `emit`，所有已注册监听都能收到。

## 2. 同步 emit（不推荐）
### 修改后的同步版本：`readFileSync`
`find()` 内部同步读取文件，循环执行过程中**立刻同步调用 `emit()`**
```js
find () {
  for (const file of this.files) {
    const content = readFileSync(file, 'utf8')
    this.emit('fileread') // 同步立即触发事件
  }
  return this
}
```
- `emit` 执行时机：执行到该行代码瞬间同步广播，阻塞当前循环
- 致命问题：**`find()` 调用后再注册的监听器完全收不到事件**

### 错误示例演示
```js
findRegexSyncInstance
  .addFile('fileA.txt')
  // 前置监听：执行时emit还没触发，可以收到
  .on('found', (m) => console.log(`前置匹配：${m}`))
  .find() // 同步循环+同步emit，事件立刻全部派发完毕
  // 后置监听：注册时机晚于emit，永远不会执行
  .on('found', (m) => console.log(`后置匹配：${m}`))
```
输出只会打印「前置匹配」，后置监听完全失效。

## 3. 混用同步/异步事件 = Zalgo 陷阱
若同一个事件名（比如`data`），一部分场景同步`emit`、一部分异步`emit`：
- 开发无法预判监听注册是否需要提前；
- 代码行为不稳定，时而能收到事件、时而丢失，Bug 极难复现排查；
这和前文「有时同步、有时异步的不可预测回调」属于同类设计缺陷。

## 4. once 方法的内存泄漏补充提醒
`emitter.once('evt', fn)` 仅在事件触发后自动解绑，但如果该事件**永远不会被 emit**，监听器会永久驻留，造成内存泄漏。
## 5. 业务设计建议
1. 绝大多数场景统一使用异步 emit，保持 API 行为稳定；
2. 若必须同步 emit，所有监听器必须**在执行任务前全部注册**；
3. 禁止同一个事件混合同步、异步两种派发方式；
4. 同步 emit 一般是代码异味，优先改用异步方案。

# 原文完整解读：EventEmitter vs 普通回调（选型区分标准）
## 一、核心语义区分（最根本判断依据）
1. **Callback（回调）**
适用场景：异步操作**产出单一最终结果**，只执行一次，语义是「返回结果」。
一次操作对应一个回调，只会触发一次（成功/失败仅一回）。

2. **EventEmitter（事件）**
适用场景：程序中**发生某件事**，可多次触发，语义是「通知事件发生」。
同一消息可以反复广播，支持多处监听。

## 二、等效示例对比
```js
// 方案1：EventEmitter 版本
function helloEvents () {
  const emitter = new EventEmitter()
  setTimeout(() => emitter.emit('complete', 'hello world'), 100)
  return emitter
}
helloEvents().on('complete', msg => console.log(msg))

// 方案2：纯回调版本
function helloCallback (cb) {
  setTimeout(() => cb(null, 'hello world'), 100)
}
helloCallback((err, msg) => console.log(msg))
```
两段代码功能完全一致：延迟100ms输出文本。
但**设计语义、扩展能力、适用场景完全不同**，不能随意互换。

## 三、三条选型判断准则（原文给出核心参考）
### 1. 多类消息/多种状态通知 → 选 EventEmitter
回调很难优雅区分多种事件；如果操作会产生「进度、完成、报错、中断」等多种通知，回调会变得臃肿。
举例：文件扫描会触发`fileread`/`found`/`error`三类消息，用EventEmitter分事件监听更清晰；如果只用回调只能靠参数区分类型，代码可读性极差。

### 2. 消息会重复触发 → 选 EventEmitter
回调约定**只能执行一次**（无论成功失败）；
若事件可能多次发生（数据流持续输出数据、HTTP多次请求、日志持续打印），必须用EventEmitter。
反例：单次文件下载、单次接口请求，只返回一次结果，用回调/Promise更简洁。

### 3. 需要多处同时监听同一条消息 → 选 EventEmitter
回调只能一对一传递结果；
EventEmitter一对多，同一个事件可以注册N个监听器（日志、鉴权、业务逻辑分开监听同一请求事件）。

## 四、补充反向场景：优先用回调的情况
操作只会执行一次、仅产出一个最终结果，无需多次通知、多监听：
文件一次性读取、单次网络请求、一次性计算任务，回调（或Promise/async await）更轻量，不需要引入EventEmitter额外开销。

## 五、补充原文小字提示
如果必须同步触发事件，可用`process.nextTick()`推迟`emit`调用，强制转为异步派发，避免Zalgo同步异步混杂问题。

# 原文解读：回调 + EventEmitter 混合设计模式
## 一、模式核心思想
单个异步API同时提供两套交互方式：
1. **回调 callback**：简单场景使用，等全部流程结束后一次性拿到最终结果；
2. **返回 EventEmitter**：复杂、精细化场景，实时监听过程中的每一步事件（进度、单条匹配、中断等）。
兼顾新手简易使用和高级细粒度监控需求，是Node生态经典兼容设计。

## 二、实战示例：glob 文件匹配库
### API 签名
```js
const emitter = glob(pattern, [options], callback)
```
- 入参末尾传入标准Node回调：扫描全部完成后，一次性返回所有匹配文件；
- 函数返回`EventEmitter`实例，可监听过程事件，实时获取每一条匹配结果。

### 使用代码演示
```js
import glob from 'glob'

glob('data/*.txt', (err, files) => {
  // 回调：全部扫描完成才执行，拿到完整文件列表
  if (err) return console.error(err)
  console.log('全部匹配文件：', files)
})
.on('match', match => {
  // EventEmitter：实时捕获每一个匹配到的文件（过程事件）
  console.log('实时命中文件：', match)
})
```
### 支持的事件（细粒度流程通知）
- `match`：找到单个匹配文件，实时触发；
- `end`：全部扫描结束，和回调时机一致；
- `abort`：手动终止扫描时触发。

## 三、两种使用场景分工
1. **简单业务**：只传回调，不需要过程进度，等待最终结果即可，代码极简；
2. **高级场景**：监听事件，实时处理中间数据、打印进度、中途中断扫描等。

## 四、模式优势
1. 一套API兼容两种开发习惯，降低学习成本；
2. 兼顾简洁性与灵活性：简单场景不用处理事件，复杂场景拥有完整流程监控能力；
3. 统一业务逻辑底层，对外提供分层交互接口，是成熟Node工具库主流设计方案。
