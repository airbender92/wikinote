# 翻译+精读解析
## 中文翻译
### 回调模式
回调是上一章介绍的反应器模式中处理器的实际载体，也是造就 Node.js 独特编程风格的标志性特性。

回调是一类用于传递操作执行结果的函数，这正是异步编程场景下我们所需要的机制。同步代码依靠 return 语句返回结果，但在异步环境中，return 不再适用，取而代之的就是回调。
JavaScript 天生适配回调机制：函数属于一等对象，可以赋值给变量、作为参数传递、被其他函数返回，或是存入各类数据结构。
闭包是实现回调的另一重要特性，借助闭包，函数可以捕获定义时所处的环境。无论回调在何时、何地被执行，都能保留异步操作发起时的上下文信息。

本节我们会详细分析这种舍弃 return、依靠回调传递结果的编程范式。

## 段落核心解读
1. **回调和反应器模式的关联**
Node 底层的事件调度依靠反应器模式，而回调就是反应器里所谓处理器在 JavaScript 层面的具体实现，底层IO事件就绪后，最终执行的业务代码就是我们写的回调。

2. **异步为什么不能用 return**
同步代码执行时会阻塞等待结果，能直接用 return 返回；但发起异步操作后主线程会立刻继续往下走，不会停下等待IO完成，没办法直接返回数据，只能提前传入一个函数，等操作结束再调用它把结果传进去。

3. JS 能写回调的两大根基
一是函数可以像普通变量一样随意传递；二是闭包会锁住函数定义时的局部变量，哪怕延迟很久执行回调，当初的临时数据也不会丢失，这让异步代码能正常保存业务上下文。

4. 本段作用
作为回调章节的开篇理论铺垫，讲清回调的底层来源、语言支撑逻辑，为后文同步/异步续传风格、回调陷阱、Node 回调规范等内容打好基础。

## 中文译文
## 续传风格（CPS）
在 JavaScript 中，回调是作为参数传给另一个函数的函数，等到操作完成后，该回调会被调用并传入执行结果。在函数式编程里，这种传递结果的写法被称作**续传风格（continuation-passing style，简称 CPS）**。

如果你需要复习闭包相关知识，可以访问 MDN 的相关文章：nodejsdp.link/mdn-closures。

这是一个通用概念，并非只和异步操作绑定。简单来说，CPS 的核心逻辑是：不通过 `return` 直接向调用方返回结果，而是把结果传给另一个函数（也就是回调）来完成传递。

## 核心解读
1. **CPS 的本质区分**
CPS 不分同步、异步，只要不用 `return` 返回，而是把结果交给传入的回调函数，就属于 CPS。同步代码也能写成 CPS 形式。
2. **和普通直写代码对比**
常规直写（Direct Style）：
```js
function add(a, b) {
  return a + b
}
```
CPS 写法：
```js
function addCps(a, b, cb) {
  cb(a + b)
}
```
3. **关键区分点**
- 直写：函数自身返回结果，调用方接收返回值；
- CPS：函数不返回有效数据，运算结果全部交给传入的回调函数处理。
4. 本段承上启下作用
先给出 CPS 标准定义，纠正“CPS=异步回调”的常见误区，下文中会分别讲解**同步CPS**和**异步CPS**两种场景。


# 中文翻译
## 同步续传风格（Synchronous CPS）
为把概念讲清楚，我们先看一个简单的同步函数：
```js
function add (a, b) {
  return a + b
}
```
这段代码逻辑十分直白，通过 `return` 将结果返回给调用者，这种写法称为**直接风格（direct style）**，也是同步编程中最常用的结果返回方式。

上面函数对应的 CPS 版本写法如下：
```js
function addCps (a, b, callback) {
  callback(a + b)
}
```
`addCps` 属于同步 CPS 函数。之所以说它是同步，是因为该函数会等待回调执行完毕后，自身才会结束运行。我们用下面代码验证这一点：
```js
console.log('before')
addCps(1, 2, result => console.log(`Result: ${result}`))
console.log('after')
```
由于是同步执行，代码输出顺序完全可以预判：
```
before
Result: 3
after
```
接下来我们再来了解异步 CPS 的运行机制。

# 核心解读
1. **直接风格 vs 同步CPS**
普通同步函数依靠 `return` 返回值；同步CPS 不返回数据，计算完成后立刻同步调用传入的回调，整个流程不会交出事件循环，代码顺序自上而下执行。
2. **执行顺序关键点**
调用 `addCps` 时，内部会立刻执行回调，打印结果后才会执行最后一行 `console.log('after')`，全程无任何异步延迟。
3. 本段作用
用最简单的同步加法示例区分两种编程范式，铺垫后文异步 CPS 的对比，直观体现同步/异步 CPS 在执行时序上的巨大差异。


# 中文翻译
## 异步续传风格（Asynchronous CPS）
我们改造一下 `addCps`，让它变成异步版本：
```js
function additionAsync (a, b, callback) {
  setTimeout(() => callback(a + b), 100)
}
```
上面代码中借助 `setTimeout` 模拟异步回调调用。`setTimeout` 会把任务推入事件队列，等待指定毫秒后再执行，属于标准异步操作。我们调用这个函数观察执行顺序的变化：
```js
console.log('before')
additionAsync(1, 2, result => console.log(`Result: ${result}`))
console.log('after')
```
输出结果：
```
before
after
Result: 3
```
`setTimeout` 会触发异步逻辑，但不会阻塞等待回调执行，函数会立刻结束，把执行权交还给调用方。这个特性对 Node.js 至关重要：发起异步请求后程序会立即交还控制权给事件循环，队列里其他事件就能被及时处理。

图3.1展示了异步函数的执行流程。
当异步操作真正完成时，才会从事件循环重启执行、运行回调函数，此时会生成全新的调用栈。JavaScript 的闭包机制在这里起到关键作用：即便回调延迟很久、在全新调用栈里执行，也能完整保留当初调用异步函数时的上下文环境。

总结：
同步函数会阻塞，直到内部所有逻辑执行完毕；
异步函数会立刻返回，操作完成后，会在下一轮事件循环中将结果传入回调处理器。

# 核心解读
1. **同步CPS与异步CPS核心时序差异**
同步CPS：回调原地同步执行，代码从上到下串行；
异步CPS：异步API不会阻塞主线程，主线程继续往下走，回调延迟到后续事件循环才执行，打印 `after` 先于计算结果。

2. 事件循环关键逻辑
调用 `setTimeout` 仅注册延时任务，不会卡住当前代码；主线程执行完所有同步代码后，再回头处理队列里的延时回调。

3. 闭包的价值
回调后续执行时调用栈已经完全清空，但闭包捕获了外层变量（a、b），因此回调依然能拿到数值完成计算。

4. 核心区分结论
- 同步：函数执行期间阻塞，回调同步运行；
- 异步：函数即刻退出，回调延后在事件循环中执行。

## 非CPS型回调
有些场景下，函数接收回调参数，很容易让人误以为它是异步函数、或是采用了CPS续传风格，但事实并非总是如此。

举个例子，数组的 `map` 方法：
```js
const result = [1, 5, 7].map(element => element - 1)
console.log(result) // [0, 4, 6]
```
这里的回调仅用于遍历数组元素，**并非用来传递运算最终结果**；整个运算结果是通过直接风格同步返回的。

从语法上，我们无法区分非CPS回调和CPS回调。因此，API文档必须清晰说明回调的实际用途。

下一节，我们会讲解所有Node开发者都必须警惕的、回调中最关键的陷阱之一。

# 核心解读
1. **CPS回调 vs 非CPS回调核心区别**
- CPS回调：函数自身不返回最终结果，运算结果全部交给回调处理；
- 非CPS回调：回调仅作为迭代/转换的中间逻辑，函数本身依旧通过`return`返回最终值，数组`map/forEach/filter`都属于这类。

2. 关键坑点
只凭“函数接收回调”无法判断它是不是异步、是不是CPS写法，不能主观臆断，必须查阅API说明。

# 中文翻译
## 行为不可预测的函数
最危险的一种情况是：同一个API，在某些条件下同步执行，另一些条件下又异步执行。我们来看下面这段示例代码：
```js
import { readFile } from 'fs'
const cache = new Map()

function inconsistentRead (filename, cb) {
  if (cache.has(filename)) {
    // 同步调用回调
    cb(cache.get(filename))
  } else {
    // 异步读取文件
    readFile(filename, 'utf8', (err, data) => {
      cache.set(filename, data)
      cb(data)
    })
  }
}
```
这个函数用 Map 缓存文件读取结果。请注意这仅为演示示例，缺少错误处理，缓存逻辑本身也不够完善（第11章高级实战会讲解规范的异步缓存实现）。

抛开这些缺陷不谈，这个函数最大的隐患是行为不稳定：首次读取文件时走异步逻辑；一旦文件内容存入缓存，后续所有调用都会同步执行回调。

# 核心解读
1. **核心问题**
首次读取文件：调用`readFile`异步IO，回调延迟到事件循环执行；
缓存命中时：直接同步执行回调，代码执行时序完全不一样。
2. **引发的严重bug（后文会展开Unleashing Zalgo）**
外部调用该函数时，无法预判回调是立刻执行还是延后执行，注册监听、事件订阅等逻辑极易失效，bug难以复现、排查。
3. 设计规范铺垫
引出核心编码准则：一个API必须**全程同步**或**全程异步**，不能两种行为混杂。

# 译文
## 释放扎戈（Unleashing Zalgo）
现在我们来分析，上文这种行为不可预测的函数，会如何轻易导致程序崩溃。请看下面这段代码：
```js
function createFileReader (filename) {
  const listeners = []
  inconsistentRead(filename, value => {
    listeners.forEach(listener => listener(value))
  })
  return {
    onDataReady: listener => listeners.push(listener)
  }
}
```
调用该函数会生成一个通知器对象，我们可以为文件读取操作注册多个监听器。文件读取完成、数据就绪时，所有监听器会一次性执行。
这个功能底层依赖我们刚才写的`inconsistentRead`函数。我们来演示调用逻辑：
```js
const reader1 = createFileReader('data.txt')
reader1.onDataReady(data => {
  console.log(`First call data: ${data}`)
  // 一段时间后，再次读取同一个文件
  const reader2 = createFileReader('data.txt')
  reader2.onDataReady(data => {
    console.log(`Second call data: ${data}`)
  })
})
```
程序实际输出仅为：
```
First call data: some data
```
第二个读取器的回调永远不会打印，下面解释根源：
1. 创建`reader1`时，缓存内没有文件数据，`inconsistentRead`走异步逻辑。回调会延迟到下一轮事件循环执行，因此我们有充足时间提前注册`onDataReady`监听器。
2. 创建`reader2`时，文件数据已经存入缓存，此时`inconsistentRead`会**同步执行回调**。回调立刻触发，但我们是在创建完`reader2`之后才注册监听器，监听器数组为空，回调执行时无任何逻辑触发。

`inconsistentRead`的回调执行时机完全不可控，取决于文件是否缓存、调用频率、文件加载耗时等多重条件。
这种Bug在真实Web服务中极难定位复现：并发请求场景下，部分请求会无报错永久挂起，排查成本极高，属于极其恶劣的缺陷。

npm创始人、前Node.js项目负责人Isaac Z. Schlueter在博客中将这种同步异步行为混杂的API比作**释放扎戈（Unleashing Zalgo）**。
扎戈是网络传说里一个不祥的存在，传说它会带来疯狂、毁灭与末日，感兴趣可以自行了解这个传说。

# 核心解读
## 1. Zalgo 核心定义
**Zalgo（扎戈）**：指代一套API在不同条件下时而同步、时而异步，回调执行时机无法预判，会产生隐蔽、难以复现的线上Bug。
行业铁律：任何接收回调的函数，必须**全程同步**或**全程异步**，不能两种行为混杂。

## 2. 示例Bug完整逻辑拆解
- 首次读取：无缓存 → `readFile`异步 → 回调延后执行 → 监听器先注册、后触发，正常打印；
- 二次读取：已有缓存 → 同步执行回调 → 注册监听器的代码还没运行，数组为空，逻辑彻底失效。

## 3. 线上真实危害
Web服务器并发请求场景下，缓存命中/未命中随机，一部分请求正常、一部分静默卡死，无报错日志，很难定位根因。

## 4. 标准解决方案（后文会讲解）
使用`process.nextTick`强制缓存命中场景的回调延后执行，保证API**永远异步**，消除时序不确定性：
```js
if (cache.has(filename)) {
  process.nextTick(() => cb(cache.get(filename)))
}
```

## 5. 补充小知识
Promise天然规避Zalgo问题：无论resolve是同步还是异步，`.then`回调永远进入微任务队列延迟执行，不存在同步触发的情况。

# 中文翻译
## 使用同步API
从「释放扎戈」的例子我们能得到一条核心教训：API必须明确定义自身是同步还是异步，二者不能混杂。
修复`inconsistentRead`的方案之一是将其改造为**完全同步**。Node为大部分基础IO都提供了同步直写API，比如我们可以用`fs.readFileSync`替代异步版`readFile`，改造后代码如下：
```js
import { readFileSync }
const cache = new Map()
function consistentReadSync (filename) {
  if (cache.has(filename)) {
    return cache.get(filename)
  } else {
    const data = readFileSync(filename, 'utf8')
    cache.set(filename, data)
    return data
  }
}
```
Isaac Z. Schlueter的原文博客地址：nodejsdp.link/unleashing-zalgo

可以看到整个函数都改成了**直接风格（direct style）**。纯同步函数完全没必要使用CPS续传风格，同步API优先采用直接返回值的写法是最佳实践，既能消除同步/异步混淆带来的隐患，执行效率也更高。

注意：如果把API从CPS回调风格改成同步直写，所有调用它的代码都需要同步改造。以我们的`createFileReader`为例，整套接口逻辑都要重写以适配同步逻辑。

同步API存在明显短板：
1. 部分功能没有提供同步版本；
2. 同步IO会阻塞事件循环，暂停所有并发请求，彻底破坏Node的并发模型，拖慢整个应用。

我们写的`consistentReadSync`中，每个文件只会执行一次同步读取，后续全部走缓存，因此阻塞风险会有所缓解。但如果需要一次性读取大量全新文件，事件循环阻塞的问题会立刻凸显。

绝大多数业务场景都不推荐使用同步IO，但少数场景下它是最简单高效的选择，需要结合场景权衡。
典型适用场景：应用启动初始化阶段读取配置文件。

### 设计范式1
纯同步函数，一律使用直接风格（return返回结果）。
### 设计范式
谨慎使用阻塞API，仅在不会影响应用并发处理能力的场景下使用。

# 核心解读
1. 彻底同步是解决Zalgo问题的第一种方案：全程`return`返回数据，不使用回调，执行时序完全稳定，不会出现时而同步回调、时而异步回调的分裂行为。
2. 同步API致命缺陷：`readFileSync`会卡住事件循环，所有HTTP请求、定时器、数据库操作全部停滞，服务并发能力归零。
3. 仅启动阶段允许同步阻塞：程序初始化时没有用户请求，短暂阻塞无负面影响；运行时业务逻辑严禁同步IO。
4. 配套规范：同步代码不用CPS回调，直接`return`，代码简洁、无歧义。

# 中文翻译
## 通过延迟执行保证异步特性
修复`inconsistentRead`的另一种方案，是让函数**完全异步**。核心技巧：即便命中缓存、本该同步执行回调，也要把回调推迟到后续事件循环周期再运行。
在 Node 中可以借助 `process.nextTick()` 实现延迟执行：它接收回调，将其插入事件队列最前端（优先级高于所有待处理IO事件），函数会立刻返回；等当前执行代码全部走完、交还执行权给事件循环后，再执行这个回调。

我们用该方法改造函数：
```js
import { readFile } from 'fs'
const cache = new Map()

function consistentReadAsync (filename, callback) {
  if (cache.has(filename)) {
    // 延迟执行回调
    process.nextTick(() => callback(cache.get(filename)))
  } else {
    // 原生异步文件读取
    readFile(filename, 'utf8', (err, data) => {
      cache.set(filename, data)
      callback(data)
    })
  }
}
```
借助`process.nextTick`，无论是否命中缓存，这个函数的回调永远是异步触发，彻底消除扎戈问题。

### 范式
使用`process.nextTick()`延迟执行回调，能保证回调一定异步调用。

另一个延迟执行API是`setImmediate()`，二者用途相近，但执行时机有本质区别：
1. `process.nextTick` 注册的是**微任务**，当前代码执行完毕后、任何IO事件处理前就会运行；
   缺点：递归调用时会持续抢占队列，造成IO饥饿，IO事件永久得不到处理。
2. `setImmediate` 的回调会放入IO处理完成后的专属阶段，不会阻塞IO，不存在饥饿问题。

`setTimeout(callback, 0)` 效果近似`setImmediate`，但执行时序更靠后：
事件循环分多个阶段，执行顺序为：定时器(setTimeout) → IO回调 → setImmediate。
如果在IO回调/微任务里调用`setImmediate`，会在本轮循环剩余阶段执行；
而`setTimeout(()=>{}, 0)`必须等到下一轮事件循环才会触发，速度更慢。

本书后续讲解CPU密集型任务分片时，会深入对比这几个API的差异。
下一节我们来学习 Node 统一的回调编码规范。

# 核心解读
## 1 根治Zalgo的标准方案
全程统一异步：缓存命中也不用同步回调，通过`nextTick`推入微任务队列，所有回调都延迟执行，调用方永远不用区分两种时序，不会出现监听器注册失效的bug。

## 2 nextTick / setImmediate / setTimeout(0) 优先级区别
执行先后顺序：`process.nextTick` > IO回调 > `setImmediate` > `setTimeout(fn, 0)`
- nextTick：微任务，无限递归会卡死IO；
- setImmediate：当前循环IO全部处理完再跑，无IO饥饿风险；
- setTimeout(0)：必须等完整一轮事件循环结束，延迟最高。

## 3 适用场景对比
- 只想尽快执行、无递归风险：`process.nextTick`
- 避免阻塞IO、批量延迟任务：`setImmediate`
- 需要让出整轮循环，延后较长时间执行：`setTimeout(fn, 0)`

## Node.js 回调规范
在 Node.js 中，CPS 续传风格的 API 与回调函数有一套统一规范。这套规范不仅适用于 Node 内置核心模块，绝大多数第三方库与业务项目也都会遵守。如果你需要设计基于回调的异步接口，务必吃透并遵循这套标准。

### 规范一：回调作为最后一个参数
Node 所有内置函数统一约定：如果函数接收回调，回调必须是形参列表最后一位。
以 `readFile(filename, [options], callback)` 为例：
即便存在可选配置参数，回调依然放在末尾。这么设计是为了内联定义回调时代码可读性更好。

### 规范二：错误对象永远是回调第一个入参
CPS 风格下错误也通过回调传递。Node 约定：回调第一个参数固定为错误对象；操作成功时该值为 `null` / `undefined`，返回数据从第二个参数开始传递。
示例标准写法：
```js
readFile('foo.txt', 'utf8', (err, data) => {
  if(err) {
    handleError(err)
  } else {
    processData(data)
  }
})
```
最佳实践：必须对 `err` 做判空处理，否则线上故障极难排查；同时错误只能是 `Error` 类实例，禁止直接传字符串、数字作为错误信息。

### 错误传递规范
同步代码依靠 `throw` 向上抛出异常；异步 CPS 不能用 throw，正确做法是把错误直接传入回调完成传递。
示例：读取文件并解析 JSON
```js
import { readFile } from 'fs'
function readJSON (filename, callback) {
  readFile(filename, 'utf8', (err, data) => {
    let parsed
    // 文件读取出错，直接把错误抛给上层回调
    if (err) {
      return callback(err)
    }
    try {
      parsed = JSON.parse(data)
    } catch (err)
      // JSON 解析同步异常，捕获后传给回调
      return callback(err)
    }
    // 无错误，第一个参数传null，返回解析结果
    callback(null, parsed)
  })
}
```
要点：
1. 底层 IO 报错时，`return callback(err)` 终止后续逻辑，向上传递错误；
2. `JSON.parse` 是同步函数，出错会直接抛出，必须用 `try/catch` 包裹捕获；
3. 不要在 `try` 内部调用回调，否则回调内部报错会被当前 `catch` 误捕获，干扰错误分层。

## 未捕获异常
异步回调内部如果抛出异常，外层同步 `try/catch` 完全捕获不到。
举个反面例子，去掉 JSON 解析的 `try/catch`：
```js
function readJSONThrows (filename, callback) {
  readFile(filename, 'utf8', (err, data) => {
    if (err) {
      return callback(err)
    }
    // 解析出错会直接抛出，无法被回调捕获
    callback(null, JSON.parse(data))
  })
}
```
执行错误 JSON 文件时：
```js
readJSONThrows('invalid_json.json', (err) => console.error(err))
```
程序会直接崩溃并打印堆栈：
```
SyntaxError: Unexpected token h in JSON at position 1
at JSON.parse (<anonymous>)
at FSReqCallback.readFileAfterClose [as oncomplete] (internal/fs/read_file_context.js:61:3)
```
原因：`JSON.parse` 的异常抛出在全新的事件循环执行栈，和调用 `readJSONThrows` 的同步代码栈完全隔离。
下面这段代码完全无效，外层 `catch` 永远捕获不到解析异常：
```js
try {
  readJSONThrows('invalid_json.json', (err) => console.error(err))
} catch (err) {
  console.log('这段捕获逻辑永远不会执行')
}
```

### uncaughtException 全局兜底事件
异步异常冒泡到事件循环后，Node 在进程退出前会触发 `uncaughtException` 事件。仅作为崩溃前的日志、清理兜底，**不能用来恢复业务继续运行**。
```js
process.on('uncaughtException', (err) => {
  console.error(`捕获到未处理异常：${err.message}`)
  // 必须主动退出进程，进程状态已不可信
  process.exit(1)
})
```
生产规范：触发该事件后必须退出进程。此时内存、IO、闭包等状态全部混乱，继续运行会引发数据损坏、连锁故障；采用「快速失败」策略，由进程管理工具（PM2、K8s）重启服务。

# 核心知识点梳理
## 一、两大回调强制规范
1. 回调放最后一个参数；
2. err 是回调第一个参数，成功传 `null`，错误必须是 Error 对象。

## 二、异步错误传递核心规则
1. IO 异步错误：`return callback(err)` 向上透传；
2. 回调内部同步运算（JSON.parse）：必须在回调内加 `try/catch`，捕获后丢给上层回调；
3. 禁止在 try 块中执行回调，避免错误捕获混乱。

调用 `readFile` 时外层同步代码执行完毕，栈已销毁；等文件读取完成，回调在事件循环新建栈执行，此时外层 try-catch 早已失效。

## 四、uncaughtException 生产红线
仅做日志记录、资源释放，执行后必须 `process.exit(1)`，绝对不能继续接收业务请求。进程出现未捕获异常代表内部状态已不一致，继续运行风险极高。

# 中文翻译
## EventEmitter 事件触发器
在传统面向对象编程里，实现观察者模式需要定义接口、实体类以及类继承体系；但在 Node.js 中这件事被大幅简化，核心内置了 `EventEmitter` 类，开箱即用。我们可以通过它注册一个或多个监听器，当对应事件被触发时，所有监听器函数都会执行。

观察者模式的标准定义：存在一个主体对象，当其内部状态发生变更时，可以通知一组观察者/监听器。

`EventEmitter` 由 `events` 核心模块导出，获取方式如下：
```js
import { EventEmitter } from 'events'
const emitter = new EventEmitter()
```
`EventEmitter` 核心方法：
1. `on(event, listener)`
为指定事件名（字符串类型）注册监听器函数。
2. `once(event, listener)`
注册一次性监听器，事件第一次触发后自动解绑。
3. `emit(event, [arg1], [...])`
触发指定事件，并可传入多个参数，所有对应监听器都会接收这些参数。
4. `removeListener(event, listener)`
移除指定事件绑定的某一个监听器。

以上所有方法都会返回 `EventEmitter` 实例，支持链式调用。
监听器函数的入参格式为 `function([arg1], [...])`，仅接收 `emit` 传递的自定义参数。

这里能明显看出监听器和 Node 标准回调的巨大区别：监听器的第一个参数**不一定是错误对象**，可以是任意业务数据。

# 核心解读
1. **与普通回调的核心区分**
Node 异步回调强制第一个参数为 `err`；但 `EventEmitter` 的自定义事件无此约束，参数完全由 `emit` 自由定义。
2. 链式调用特性
```js
emitter.on('data', () => {}).once('close', () => {})
```
3. `once` 适用场景：只需要监听一次的事件（服务首次启动、初次连接）
4. `removeListener` 注意点：只能移除具名函数，匿名函数无法解绑，内存泄漏高发坑点。
5. 核心本质：一对多通知，同一个 `emit` 可以同时触发多个绑定的监听器，是回调做不到的能力。

## EventEmitter 的创建与使用
下面我们通过实战示例演示 EventEmitter 的用法。示例函数会遍历一组文件，读取文件内容并匹配正则，每当匹配到内容时，通过 EventEmitter 实时通知订阅者：
```js
import { EventEmitter } from 'events'
import { readFile } from 'fs'

function findRegex (files, regex) {
  const emitter = new EventEmitter()
  for (const file of files) {
    readFile(file, 'utf8', (err, content) => {
      if (err) {
        return emitter.emit('error', err)
      }
      emitter.emit('fileread', file)
      const match = content.match(regex)
      if (match) {
        match.forEach(elem => emitter.emit('found', file, elem))
      }
    })
  }
  return emitter
}
```
该函数会返回一个 EventEmitter 实例，会触发三类事件：
1. `fileread`：文件读取完成时触发
2. `found`：匹配到正则内容时触发
3. `error`：读取文件出现错误时触发

调用示例：
```js
find(
  ['fileA.txt', 'fileB.json'],
  /hello \w+/g
)
.on('fileread', file => console.log(`${file} was read`))
.on('found', (file, match) => console.log(`Matched "${match}" in ${file}`))
.on('error', err => console.error(`Error emitted ${err.message}`))
```
代码中我们分别为三种事件绑定了对应的监听函数。

# 核心解读
1. **error 事件特殊规则**
EventEmitter 的 `error` 是特殊事件：如果触发 `error` 且没有绑定对应监听器，程序会直接崩溃退出。业务中必须统一监听 `error` 事件。
2. `emit` 传参规则
`emit(事件名, 参数1, 参数2...)` 可以传递任意数量参数，监听器会按顺序接收，如 `found` 事件传递了文件名、匹配内容两个参数。
3. 链式调用
`on()` 方法返回自身实例，因此可以连续链式绑定多个事件监听，代码更简洁。
4. 异步特性
内部 `readFile` 是异步操作，文件读取完成后才会触发对应事件，不会阻塞主线程。

## 让任意对象具备可监听能力
在 Node 开发中，很少会单独实例化使用 `EventEmitter`，更普遍的做法是让其他类继承它。类继承后就能获得事件发射、监听的全部能力，变成一个**可被观测（可订阅）**的对象。

补充规则：`error` 事件是 `EventEmitter` 的特殊事件。如果触发 `error` 却没有注册对应的监听器，程序会直接抛出异常并退出。因此开发规范要求：所有 `EventEmitter` 实例都必须监听 `error` 事件。

下面我们把前面 `findRegex` 的功能改写成继承 `EventEmitter` 的类：
```js
import { EventEmitter } from 'events'
import { readFile } from 'fs'

class FindRegex extends EventEmitter {
  constructor (regex) {
    super() // 必须调用父类构造器初始化事件内部逻辑
    this.regex = regex
    this.files = []
  }

  addFile (file) {
    this.files.push(file)
    return this // 支持链式调用
  }

  find () {
    for (const file of this.files) {
      readFile(file, (err, content) => {
        if (err) {
          return this.emit('error', err)
        }
        this.emit('fileread', file)
        const match = content.match(this.regex)
        if (match) {
          match.forEach(elem => this.emit('found', file, elem))
        }
      })
    }
    return this
  }
}
```
`FindRegex` 通过继承 `EventEmitter`，完整拥有事件能力。注意构造函数里一定要执行 `super()`，初始化父类内部数据。

使用示例：
```js
const findRegexInstance = new FindRegex(/hello \w+/)
findRegexInstance
  .addFile('fileA.txt')
  .addFile('fileB.json')
  .find()
  .on('found', (file, match) => console.log(`匹配到"${match}"，文件：${file}`))
  .on('error', err => console.error(`事件错误：${err.message}`))
```
可以看到实例直接拥有继承而来的 `.on()` 方法。
这是 Node 生态最主流的设计模式：
1. 内置 HTTP 服务 `http.Server` 继承 EventEmitter，会派发 `request`、`connection`、`closed` 等事件；
2. Node 中所有流（Stream）也全部继承 EventEmitter，第6章会详细讲解流相关内容。

# 核心解读
1. **继承 EventEmitter 标准写法**
`class X extends EventEmitter`，构造函数第一行必须 `super()`，否则事件内部状态未初始化，调用 `emit/on` 会报错。
2. 链式设计
`addFile()`、`find()` 都返回 `this`，支持连续调用，简化代码。
3. 真实生态落地案例
- HTTP 服务器：监听 `request` 接收请求；
- 各类读写流（文件流、网络流）：`data`、`end`、`error` 事件都是基于该模式。
4. 设计优势
把对象自身业务逻辑 + 事件通知能力整合在一起，对外统一接口，不用单独返回 emitter 实例，封装性更好。

# 中文翻译
## EventEmitter 与内存泄漏
如果给生命周期很长的可观测对象订阅监听器，一旦监听器不再使用，**必须及时取消订阅**，这是重中之重。这样才能释放监听器作用域内占用的内存，避免内存泄漏。未销毁的 EventEmitter 监听器，是 Node.js（乃至整个 JS 领域）最主要的内存泄漏源头。

内存泄漏指程序不再需要的内存没有被回收，导致应用内存占用持续无限上涨。举个例子：
```js
const thisTakesMemory = '一段占用大量长字符串....'
const listener = () => {
  console.log(thisTakesMemory)
}
emitter.on('an_event', listener)
```
变量 `thisTakesMemory` 被监听器函数引用，只要该监听器没有从 emitter 上移除，或是 emitter 对象本身还能被代码访问到，这段字符串占用的内存就永远无法被垃圾回收。

由此带来严重问题：如果一个全局常驻 EventEmitter，每来一条 HTTP 请求就注册一个监听器，且从不销毁，内存会持续膨胀，最终程序崩溃。
解决方式：调用 `removeListener` 解绑监听器：
```js
emitter.removeListener('an_event', listener)
```

EventEmitter 内置内存泄漏预警机制：同一个事件绑定的监听器数量超过默认阈值（10个）时，会打印警告日志。
如果业务场景确实需要绑定超过10个监听器，可以调用 `setMaxListeners()` 调整该上限。

# 核心要点
1. **闭包内存滞留原理**
监听器闭包会捕获外部变量，只要监听器还挂载在 emitter 上，闭包引用的大字符串、大数组、实例等对象都无法 GC。
2. **高危场景**
全局/服务级常驻 emitter + 每次请求动态新增监听器、不做清理，是线上高频内存泄漏场景。
3. 解绑限制
`removeListener` 只能移除**具名函数**，匿名监听器无法解绑，长期业务禁止直接传入匿名回调。
4. 预警机制作用
10个监听告警只是提示，不代表真的泄漏；合理多监听场景通过 `emitter.setMaxListeners(数字)` 关闭告警。
5. 替代方案
一次性监听 `once(event, listener)` 触发后自动解绑，天然规避长期滞留问题。

## 同步事件与异步事件
和回调一样，事件的触发也分同步、异步两种，区分标准是触发事件的时机与发起任务的执行时序。
**同一个 EventEmitter 内绝不允许混用同步、异步触发逻辑；同一类事件更不能一部分同步发射、一部分异步发射**，否则会出现和「释放扎戈」完全一样的隐患。二者最核心的区别是监听器的注册时机。

异步发射事件：任务发起后，我们依然可以继续注册监听器，不会丢失事件。因为事件会推迟到下一轮事件循环才触发，当前同步代码执行期间注册的监听都能捕获事件。

补充：可以用 `once(event, listener)` 替代 `on`，事件触发后自动解绑监听器；但如果该事件永远不会发射，这个监听函数会永久驻留，造成内存泄漏。
JS 垃圾回收与可达性概念参考：nodejsdp.link/garbage-collection

前面写的 `FindRegex` 类是**异步发射事件**，因此可以在调用 `.find()` 之后再绑定监听，不会丢失消息：
```js
findRegexInstance
  .addFile(...)
  .find()
  .on('found', ...)
```

如果是同步发射事件，必须在执行任务前完成所有监听器注册，任务执行后再绑定的监听会彻底丢失。我们改造 `find` 方法，改用同步 `readFileSync` 实现同步发射：
```js
find () {
  for (const file of this.files) {
    let content
    try {
      content = readFileSync(file, 'utf8')
    } catch (err) {
      this.emit('error', err)
    }
    this.emit('fileread', file)
    const match = content.match(this.regex)
    if (match) {
      match.forEach(elem => this.emit('found', elem))
    }
  }
  return this
}
```

调用测试：
```js
const findRegexSyncInstance = new FindRegexSync(/hello \w+/)
findRegexSyncInstance
  .addFile('fileA.txt')
  .addFile('fileB.json')

  .on('found', (file, match) => console.log(`[前置监听] 匹配${match}`))
  .find()
  // 执行后注册，永远不会执行
  .on('found', (file, match) => console.log(`[后置监听] 匹配${match}`))
```

输出结果只有前置监听的日志，后置监听完全失效。

极少数场景适合同步发射事件，但 EventEmitter 设计初衷就是处理异步通知。如果大量同步发射事件，往往意味着设计不合理：要么根本不需要 EventEmitter，要么同一实例存在异步事件，极易引发 Zalgo 时序混乱问题。

- EventEmitter：需要多次、持续通知状态变更时使用。

# 核心解读
## 1. 同步emit致命问题
同步调用 `this.emit()` 会在当前同步执行流里立刻执行所有监听函数，任务执行完再注册的监听完全捕获不到事件，时序错乱。
## 2. 异步emit优势
异步IO（`readFile`）会把事件发射推迟到事件循环，执行 `.find()` 后再绑定监听也能正常接收，业务编码更灵活。
## 3. Zalgo 延伸风险
同一事件时而同步emit、时而异步emit，监听注册逻辑会时而生效时而失效，Bug 极难复现。
## 4. once 隐藏内存坑
`once` 仅事件触发后自动释放；若事件永不触发，监听函数永久持有闭包变量，造成内存泄漏。
## 5. API选型标准
单次一次性结果（单次文件读取、单次HTTP请求）→ 回调；
多次持续推送消息（数据流、连接、定时推送）→ EventEmitter。

# 中文翻译
## EventEmitter 与回调如何选择
设计异步API时，常常会纠结选用 EventEmitter 还是单纯回调函数。核心区分依据是语义：
**回调适用于异步操作仅需返回最终结果的场景；事件触发器适用于需要持续通报「某件事发生」的场景。**

抛开这条核心准则，两种方案大多能实现相同功能，很容易让人混淆。请看示例对比：
```js
import { EventEmitter } from 'events'

function helloEvents () {
  const eventEmitter = new EventEmitter()
  setTimeout(() => eventEmitter.emit('complete', 'hello world'), 100)
  return eventEmitter
}

function helloCallback (cb) {
  setTimeout(() => cb(null, 'hello world'), 100)
}

// 事件方式调用
helloEvents().on('complete', message => console.log(message))
// 回调方式调用
helloCallback((err, message) => console.log(message))
```
补充：同步发射的事件也可以借助 `process.nextTick` 延后执行，保证事件一定异步触发。

`helloEvents` 和 `helloCallback` 功能完全等价：前者通过事件告知任务完成，后者依靠回调返回结果。但二者在代码可读性、语义、实现复杂度上差异明显。

虽然没有一套绝对死板的判定标准，但以下几条参考准则能帮你快速选型：
1. 多类型消息区分时优先 EventEmitter
如果操作会产生多种不同通知，仅用回调实现会非常臃肿（要么把事件类型当参数传入回调，要么定义多个回调入参），API 设计很难优雅；EventEmitter 可按事件名拆分监听，代码更简洁清晰。

2. 事件可能多次触发/也可能永不出现时，选用 EventEmitter
回调的设计预期是**只会执行一次**（成功或失败各调用一回）；如果消息会反复推送（数据流、连接心跳、实时日志），本质是持续发生的事件，而非一次性结果，更适合 EventEmitter。

3. 需要多处同时监听同一条消息，选用 EventEmitter
回调只能绑定一个处理函数；EventEmitter 支持给同一个事件注册多个监听器，一对多通知能力是回调不具备的。

# 核心总结
## 回调适用场景
单次异步操作，仅有一次成功/失败结果，仅需一处处理逻辑（文件单次读取、单次接口请求）。
优点：API 简洁、轻量；缺点：无法多次触发、不能多订阅。

## EventEmitter 适用场景
1. 会多次触发的通知（数据流、HTTP 请求、定时消息）；
2. 存在多种不同类型的状态变更（成功、进度、错误、关闭）；
3. 程序多处代码需要同时接收同一份通知。

## 关键本质区别
回调：一对一、一次性返回结果；
EventEmitter：一对多、可无限次派发各类状态通知。

## 回调与事件的结合使用
在一些特定场景下，可以将 EventEmitter 与回调函数**结合使用**。这种模式非常强大：既可以通过传统回调异步返回最终结果，同时又返回一个 EventEmitter，用来更细粒度地同步异步任务的执行状态。

典型例子是 `glob` 包（用于按通配符批量匹配文件），它的主函数签名如下：
```js
const eventEmitter = glob(pattern, [options], callback)
```
该函数接收匹配规则、可选配置项，以及一个回调函数——任务结束后回调会返回所有匹配到的文件列表。
与此同时，函数还返回一个 EventEmitter，用于实时推送搜索过程中的状态：
- `match` 事件：每找到一个匹配文件就触发一次
- `end` 事件：搜索结束，返回全部文件列表
- `abort` 事件：任务被手动中止时触发

使用示例：
```js
import glob from 'glob'

glob('data/*.txt', (err, files) => {
  if (err) {
    return console.error(err)
  }
  console.log(`找到全部文件：${JSON.stringify(files)}`)
})
.on('match', match => {
  console.log(`实时匹配到：${match}`)
})
```

将 EventEmitter 与回调结合，是一种优雅的 API 设计思路：
- 回调提供简单、直接、一次性的结果；
- 事件提供更精细、实时、可扩展的过程通知。

# 核心要点
1. **设计思路**
- 回调：给简单场景用，只关心**最终结果**；
- EventEmitter：给复杂场景用，关心**过程、进度、实时事件**。

2. **典型适用场景**
- 文件批量搜索、遍历
- 大文件上传/下载（进度通知 + 完成回调）
- 批量任务执行（逐个完成事件 + 最终汇总回调）

3. **为什么这种模式好用**
- 兼顾简单用户与高级用户
- 一次性结果用回调，语义清晰
- 过程性事件用 EventEmitter，支持多监听、多事件类型
- 符合 Node.js 社区一贯的风格（ you get both simplicity and power ）
