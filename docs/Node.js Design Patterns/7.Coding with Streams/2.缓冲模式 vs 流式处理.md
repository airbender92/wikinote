# 翻译
## 缓冲模式 vs 流式处理
本书到目前为止介绍的几乎所有异步API都采用缓冲模式。对于输入操作，缓冲模式会把来自资源的全部数据存入缓冲区，等读取操作完成后，再将整块完整数据一次性返回给调用方。
图6.1展示了该模式的流程：
在图6.1中，t1时刻从资源读取一部分数据存入缓冲区；t2时刻收到最后一段数据，读取操作完成；到t3时，整块缓冲数据才会交付给使用者。

而流机制则可以在数据抵达资源的瞬间就开始处理，对应流程见图6.2：
图6.2中，每一段数据分片一抵达，就会立刻交给使用者处理，无需等待全部数据缓存完毕。

这两种方式有什么区别？单从性能角度看，流在**内存占用（空间）**和**处理耗时（时间）**上效率更高。除此之外，Node.js的流还有一大关键优势：可组合性。下面我们就分析这些特性对应用设计与编码带来的影响。

# 核心解读
1. **缓冲模式**：完整数据先存入内存，全部接收完才交付，大文件/大流量场景易占用大量内存；
2. **流式处理**：数据分块传输，分片到达即处理，无需缓存全部内容，内存开销极低；
3. 流两大核心优势：时空双高效、支持任意流拼接组合，是Node处理大IO的标准方案。

# 翻译
## 空间效率
首先，借助流可以实现缓冲模式无法做到的业务场景。举个例子，假设需要读取数百兆甚至GB级别的超大文件，如果采用读取完整文件后返回缓冲区的API，显然不是好方案。如果并发读取多个这类大文件，程序极易耗尽内存。
除此之外，V8引擎对缓冲区的大小本身存在硬性上限，我们无法分配数GB大小的缓冲区，往往还没耗尽物理内存就会触发限制。
缓冲区的最大容量随操作系统、Node版本变化。如果你想查看当前环境的字节上限，可以运行以下代码：
```js
import buffer from 'buffer'
console.log(buffer.constants.MAX_LENGTH)
```

# 核心解读
1. **缓冲模式致命缺陷**：大文件一次性读入整块Buffer会大量占用内存，并发场景直接内存溢出；
2. **底层硬限制**：V8规定单个Buffer有最大字节值`MAX_LENGTH`（32位系统约1GB，64位约2/4GB），超大文件无法生成完整缓冲区；
3. **流的空间优势**：数据分小块处理，全程无需存放完整文件，突破Buffer尺寸与内存双重限制。

## 翻译
### 使用缓冲式API实现Gzip压缩
举一个实际案例：我们开发一个使用GZIP格式压缩文件的简单命令行程序。在Node.js中用缓冲API实现的代码如下（为简洁省略错误处理）：
```js
import { promises as fs } from 'fs'
import { gzip } from 'zlib'
import { promisify } from 'util'
const gzipPromise = promisify(gzip)
const filename = process.argv[2]
async function main () {
  const data = await fs.readFile(filename)
  const gzippedData = await gzipPromise(data)
  await fs.writeFile(`${filename}.gz`, gzippedData)
  console.log('File successfully compressed')
}
main()
```
将上述代码保存为 `gzip-buffer.js`，执行命令：
```
node gzip-buffer.js <文件路径>
```
如果目标文件体积足够大（例如8GB左右），程序几乎一定会抛出报错：
```
RangeError [ERR_FS_FILE_TOO_LARGE]: File size (8130792448) is greater than possible Buffer: 2147483647 bytes
```
报错含义：文件大小超出Buffer允许的最大容量。这印证了缓冲方案并不适合大文件场景。

不同平台、Node版本下Buffer最大容量各不相同，可执行下方代码查看当前环境限制：
```js
import buffer from 'buffer'
console.log(buffer.constants.MAX_LENGTH)
```

## 核心解读
1. `fs.readFile` 是典型缓冲API：会把整个文件一次性读入内存Buffer，受V8 `MAX_LENGTH` 硬限制（示例上限约2GB）；
2. 超大文件会直接抛出文件过大异常，程序无法执行压缩；
3. 缓冲方案存在内存与Buffer尺寸双重瓶颈，处理大文件必须改用流式zlib API。

> 注：原文 `buffer.constansts` 为笔误，正确是 `buffer.constants`

# 翻译
## 时间效率
我们设想这样一套应用：客户端压缩文件并上传至远程HTTP服务端，服务端接收后解压并写入磁盘。
若客户端采用缓冲API，必须等完整文件读取、全部压缩完成后，才会发起上传；服务端同理，需要接收完所有数据，才能开始解压。
而流机制能给出更优方案：客户端每从磁盘读取一小段数据，就立刻压缩并发送；服务端每收到一段数据，就同步解压写入磁盘。我们先从服务端代码实现这套程序。

注：前文示例为简洁省略了异常处理，本章后续会详解流的标准错误捕获方案，接下来大部分示例也会简化异常逻辑。

新建文件 `gzip-receive.js`，代码如下：
```js
import { createServer } from 'http'
import { createWriteStream } from 'fs'
import { createGunzip } from 'zlib'
import { basename, join } from 'path'
const server = createServer((req, res) => {
  const filename = basename(req.headers['x-filename'])
  const destFilename = join('received_files', filename)
  console.log(`File request received: ${filename}`)
  req
    .pipe(createGunzip())
    .pipe(createWriteStream(destFilename))
    .on('finish', () => {
      res.writeHead(201, { 'Content-Type': 'text/plain' })
      res.end('OK\n')
      console.log(`File saved: ${destFilename}`)
    })
})
server.listen(3000, () => console.log('Listening on http://localhost:3000'))
```
示例中的 `req` 本身就是流对象，服务端通过它分块接收网络数据。借助Node流，每一段数据抵达时，都会立即执行解压并写入本地文件。

# 核心解读
1. **缓冲模式时间缺陷**：全量等待，读文件→压缩→上传串行阻塞，前后两端都存在长时间等待空窗，整体耗时更长；
2. **流式并行优势** 文件读取、压缩、网络传输、解压、写入磁盘同步流水线执行，各环节无需等待前置全部完成，大幅缩短总耗时；
3. 代码关键点：HTTP请求体`req`是原生可读流，链式`pipe`串联解压转换流、文件可写流，数据分片实时流水线处理。

# 翻译
客户端代码单独存放于 `gzip-send.js` 文件，代码如下：
```js
import { request } from 'http'
import { createGzip } from 'zlib'
import { createReadStream } from 'fs'
import { basename } from 'path'
const filename = process.argv[2]
const serverHost = process.argv[3]
const httpRequestOptions = {
  hostname: serverHost,
  port: 3000,
  path: '/',
  method: 'PUT',
  headers: {
    'Content-Type': 'application/octet-stream',
    'Content-Encoding': 'gzip',
    'X-Filename': basename(filename)
  }
}
const req = request(httpRequestOptions, (res) => {
  console.log(`Server response: ${res.statusCode}`)
})
createReadStream(filename)
  .pipe(createGzip())
  .pipe(req)
  .on('finish', () => {
    console.log('File successfully sent')
  })
```
这段代码同样基于流实现：从文件分块读取数据，每读取一小块就立刻执行压缩并发送。

运行整套程序步骤：
1. 先启动服务端
```
node gzip-receive.js
```
2. 再启动客户端，传入文件路径与服务端地址（示例为本地 localhost）
```
node gzip-send.js <文件路径> localhost
```
选用大文件测试，就能直观看到数据实时流转的效果。
为什么流式传输比缓冲API效率更高？图6.3会清晰对比两者差异。

处理文件一共分为6个串行阶段：
1. 【客户端】读取本地文件
2. 【客户端】压缩数据
3. 【客户端】发送数据
4. 【服务端】接收网络数据
5. 【服务端】解压数据
6. 【服务端】写入磁盘

缓冲模式下，所有阶段必须完整串行执行：必须读完整个文件才能压缩；完整读取+全部压缩完成后才能上传，每一步都要等待前置全量数据就绪。

而流模式下，读取到第一块数据就启动整条处理流水线；下一分块就绪后无需等待上一分块全部处理完毕，即可并行处理。所有操作都是异步，Node 天然支持并行分块处理，且流内部机制会严格保证数据分片顺序不乱，无需开发者手动处理。

由对比图可见，流式处理省去了等待完整文件加载的空闲时间，整体耗时大幅缩短。

# 核心解读
1. 缓冲模式：全流程阻塞串行，每个步骤必须等前一步处理完所有数据才开始，存在大量等待空窗；
2. 流流水线：分块并行流水线，读到第一片数据就开始全链路处理，多块数据异步并发加工；
3. 内置保障：流自动维护分片顺序，不会出现文件内容错乱；
4. 双重收益：既解决大文件内存溢出（空间效率），又减少整体处理耗时（时间效率）。

# 翻译
## 可组合性
前面示例代码已经展示了借助`pipe()`方法组合流的方式，它能把各个独立处理单元串联起来，完全贴合Node的设计风格。流能够互相拼接，核心原因是所有流都拥有统一标准接口，互相兼容。唯一要求是流水线中下一个流能够接收上游产出的数据类型（二进制、文本、对象流都支持，本章后续会介绍）。

我们给之前的压缩上传程序新增一层加密逻辑，以此直观展示流可组合的优势，只需小幅修改客户端与服务端代码。

### 客户端增加加密逻辑
先改造客户端代码：
```js
// ...
import { createCipheriv, randomBytes } from 'crypto' // (1)
const filename = process.argv[2]
const serverHost = process.argv[3]
const secret = Buffer.from(process.argv[4], 'hex') // (2)
const iv = randomBytes(16) // (3)
// ...
```
改动说明：
1. 从`crypto`模块引入加密转换流`createCipheriv`和随机字节生成工具`randomBytes`；
2. 从命令行读取加密密钥，密钥为十六进制字符串，转成Buffer存储；
3. 生成16字节随机初始向量（iv），用于AES加密。

接着修改HTTP请求相关代码：
```js
const httpRequestOptions = {
  hostname: serverHost,
  headers: {
    'Content-Type': 'application/octet-stream',
    'Content-Encoding': 'gzip',
    'X-Filename': basename(filename),
    'X-Initialization-Vector': iv.toString('hex') // (1)
  }
}
// ...
const req = request(httpRequestOptions, (res) => {
  console.log(`Server response: ${res.statusCode}`)
})
createReadStream(filename)
  .pipe(createGzip())
  .pipe(createCipheriv('aes192', secret, iv)) // (2)
  .pipe(req)
// ...
```
两处核心修改：
1. 将加密初始向量iv转为十六进制字符串，通过自定义HTTP请求头传给服务端；
2. 在gzip压缩流之后，串联AES192加密转换流，对压缩后的数据加密。

客户端改造完成。

# 核心解读
1. **可组合性本质**：所有流统一接口，通过`pipe`链式拼接，每个流只负责单一职责（读/压缩/加密/网络发送），符合「单一职责」；
2. 扩展零侵入：原有文件读取、gzip压缩逻辑完全不动，仅新增一行加密流即可叠加加密能力，无需重写原有IO逻辑；
3. 流水线顺序可控：数据流顺序：文件读取 → gzip压缩 → AES加密 → HTTP上传，按需调整拼接顺序即可改变处理流程。

# 翻译
## 服务端新增解密逻辑
接下来改造服务端代码。首先从内置`crypto`模块引入工具函数，用于生成加密密钥：
```js
// ...
import { createDecipheriv, randomBytes } from 'crypto'
const secret = randomBytes(24)
console.log(`Generated secret: ${secret.toString('hex')}`)
```
程序会把生成的密钥以十六进制字符串打印到控制台，我们需要将这个密钥提供给客户端使用。

然后修改文件接收处理逻辑：
```js
const server = createServer((req, res) => {
  const filename = basename(req.headers['x-filename'])
  const iv = Buffer.from(
    req.headers['x-initialization-vector'], 'hex') // (1)
  const destFilename = join('received_files', filename)
  console.log(`File request received: ${filename}`)
  req
    .pipe(createDecipheriv('aes192', secret, iv)) // (2)
    .pipe(createGunzip())
    .pipe(createWriteStream(destFilename))
  // ...
```
两处关键修改：
1. 读取请求头中客户端传来的加密初始向量（iv），并转为Buffer；
2. 在整条流流水线最前端新增解密转换流`createDecipheriv`，先对网络传输的数据解密。

仅新增少量代码，我们就为整套程序新增了加密解密层。我们只需要复用内置的转换流`createCipheriv`、`createDecipheriv`，将其接入客户端、服务端的流水线即可。我们可以像拼接乐高积木一样，自由增减、组合各类流。

这种写法最大优势是代码可复用，同时让代码结构更整洁、模块化。因此流不只是用来处理IO，更是简化、拆分业务代码的绝佳工具。
介绍完流的核心优势后，我们将系统讲解Node中各类流的分类。

# 核心解读
1. **流模块化积木特性**：各类转换流（压缩、加密、解密）完全解耦，新增功能无需改动原有读写逻辑，仅插入一段`.pipe()`即可；
2. 流水线顺序约束：客户端顺序「读文件→压缩→加密→上传」，服务端必须反向「接收→解密→解压→写入文件」；
3. 工程价值：单一功能流可复用在任意项目，代码解耦、易维护、方便单元测试。
