# 翻译
## 懒加载流（Lazy streams）
有时我们需要**一次性创建大量流**，传给某个函数统一处理。
典型场景：使用 `archiver` 批量打包大量文件为 ZIP/TAR。

问题在于：
像 `fs.createReadStream()` 这类方法，**在创建流的瞬间就会打开文件描述符**，哪怕还没开始读。
如果同时创建成百上千个文件流，很容易抛出：
**EMFILE: too many open files**（打开文件数过多）。

更通用地说：
创建流实例时，可能会**立即执行昂贵的初始化操作**（打开文件、建立网络连接、连接数据库等），即使你暂时还不用这个流。
批量创建时这会造成资源浪费甚至报错。

解决方案：
**把流的初始化延迟到真正开始消费数据时再执行**，这就是懒加载流。

---

## 实现方式：lazystream
可以用 `lazystream` 库轻松实现。
它会创建一个**流代理**，直到有人真正开始读/写数据时，才调用工厂函数创建真实流。

示例：创建一个懒加载的 `/dev/urandom` 可读流
```js
import lazystream from 'lazystream'
import fs from 'fs'

const lazyURandom = new lazystream.Readable(function (options) {
  // 这个函数只有在流第一次被消费时才会执行
  return fs.createReadStream('/dev/urandom')
})
```

这里传入的是一个**工厂函数**，负责在需要时生成真实流。

---

## 内部原理（基于 PassThrough）
`lazystream` 底层就是用 **PassThrough** 实现的：
1. 先返回一个 PassThrough 代理流
2. 当第一次调用 `_read()` 开始消费数据时
3. 执行工厂函数，创建真实流
4. 把真实流 `pipe` 到 PassThrough
5. 对外完全透明，使用者无感

它也支持懒加载可写流 `lazystream.Writable`。

---

# 核心思想
- **懒加载 = 延迟昂贵资源初始化**
- 创建流对象 ≠ 打开文件/建立连接
- 真正开始读数据时，才执行真实操作
- 避免一次性打开大量文件描述符、网络连接

---

# 模式总结
**使用 PassThrough + 工厂函数，实现流的懒初始化。**
这是处理**批量流、打包、上传、遍历大文件目录**时非常实用的优化手段。

# 翻译
## 使用管道连接流
Unix 管道由 Douglas Mcllroy 发明，它可以把一个程序的输出连通到下一个程序的输入。示例命令：
```bash
echo Hello World! | sed s/World/Node.js/g
```
执行流程：`echo` 将 `Hello World!` 输出到标准输出，通过管道符 `|` 重定向为 `sed` 的标准输入；`sed` 完成字符串替换后，将结果打印到控制台。

Node.js 的流采用相似思想，通过**可读流的 `.pipe()` 方法**串联流，接口定义：
```js
readable.pipe(writable, [options])
```

### pipe 核心特性
1. 自动把可读流产出的数据推送至可写流；
2. **默认行为**：可读流触发 `end` 事件后，自动调用下游可写流的 `.end()`；
   若传入配置 `{ end: false }`，则不会自动关闭下游；
3. 返回传入的可写流实例。如果目标流同时属于可读流（Duplex / Transform），就可以链式调用；
4. 管道内部**自动处理背压**，无需手动监听 `drain`、判断 `write()` 返回值，不用手动驱动读写循环。

### 实战示例
新建 `replace.js`，读取标准输入，使用之前实现的 `ReplaceStream` 做字符串替换，最终输出到标准输出：
```js
// replace.js
import { ReplaceStream } from './replace-stream.js'

process.stdin
  .pipe(new ReplaceStream(process.argv[2], process.argv[3]))
  .pipe(process.stdout)
```

在终端配合 Unix 管道执行：
```bash
echo Hello World! | node replace.js World Node.js
```
输出结果：
```
Hello Node.js!
```

这个例子直观说明：流（尤其是文本流）是一套通用接口，管道机制可以无缝组装、串联各个流组件。

---

# 重点总结
1. **Unix | 管道 ≈ Node.js stream .pipe()**，设计思想同源；
2. `.pipe()` 最大优势：**内置背压控制**，是基础安全的流式串联方案；
3. 链式调用前提：下游必须同时是可读流（Transform / Duplex）；
4. 默认自动关闭下游流；长期持续通信场景，需要配置 `{end:false}`；

> ⚠️ 补充书中未展开的经典坑：
原生 `.pipe()` **不会自动转发错误**。管道中任意流发生 `error`，整条链路不会自动终止，极易造成内存泄漏。生产环境官方推荐使用 `stream.pipeline()` 替代裸 `pipe`。

# 翻译
## 管道与错误处理
使用 `pipe()` 时，**错误事件不会自动在管道链中传播**。

看这个例子：
```js
stream1
  .pipe(stream2)
  .on('error', () => {})
```
这里只会捕获来自 **stream2** 的错误。
如果 `stream1` 出错，这个监听器是收不到的。

所以要完整捕获错误，必须给每个流都单独监听：
```js
stream1
  .on('error', () => {})
  .pipe(stream2)
  .on('error', () => {})
```

### 问题很严重
1. **错误不跨流传播**
2. 出错时，Node 只会把失败的流 `unpipe` 移出管道
3. **不会自动销毁流**
   文件描述符、网络连接、内存资源可能一直悬挂，造成**内存泄漏**

### 更健壮（但不优雅）的写法
```js
function handleError(err) {
  console.error(err)
  // 手动销毁所有流，释放资源
  stream1.destroy()
  stream2.destroy()
}

stream1
  .on('error', handleError)
  .pipe(stream2)
  .on('error', handleError)
```

要点：
- 给链路上**每个流**都绑定同一个错误处理
- 出错时统一 `destroy()` 所有流
- 保证资源释放，避免泄漏

---

# 核心结论
- **`.pipe()` 不做错误转发**
- **`.pipe()` 不自动清理资源**
- 长管道、多步骤流时，这种写法非常繁琐易错

这也是为什么 Node.js 后来官方推出了
**`stream.pipeline()`**
来解决这一整套问题。

# 翻译
## 使用 `pipeline()` 实现更完善的错误处理
在管道中手动处理错误不仅繁琐，还很容易出问题，我们应当尽量避免。

幸运的是，Node.js 核心的 `stream` 模块提供了一个非常好用的工具函数：**`pipeline()`**，让构建流管道更安全、更易用。

### 基本用法
```js
pipeline(stream1, stream2, stream3, ..., callback)
```

作用：
- 自动把所有传入的流**依次 pipe 到下一个**
- 自动为每个流注册**错误监听和关闭监听**
- 无论管道**正常完成**还是**因错误中断**，都会**自动销毁所有流**，释放资源
- 最后一个参数是回调：成功时无参数，出错时会把错误作为第一个参数传入

---

## 实战示例
实现一个命令行工具：
1. 从标准输入读取 gzip 数据
2. 解压
3. 把所有文本转为大写
4. 再次 gzip 压缩
5. 输出到标准输出

文件：`uppercasify-gzipped.js`
```js
import { createGzip, createGunzip } from 'zlib'
import { Transform, pipeline } from 'stream'

// 转换流：转大写
const uppercasify = new Transform({
  transform (chunk, enc, cb) {
    this.push(chunk.toString().toUpperCase())
    cb()
  }
})

// 构建管道
pipeline(
  process.stdin,
  createGunzip(),
  uppercasify,
  createGzip(),
  process.stdout,
  (err) => {
    if (err) {
      console.error(err)
      process.exit(1)
    }
  }
)
```

### 测试运行
```bash
echo 'Hello World!' | gzip | node uppercasify-gzipped.js | gunzip
```

输出：
```
HELLO WORLD!
```

如果输入不是合法 gzip 数据，解压会报错，例如：
```
Error: unexpected end of file
```
这时 **`pipeline()` 会自动清理并销毁所有流**，不会留下悬挂资源。

---

# 核心优势总结
相比于手动 `.pipe()`：
1. **错误统一捕获**，不用给每个流加 `error` 事件
2. **自动销毁所有流**，避免文件描述符泄漏、内存泄漏
3. 代码更简洁，适合长管道
4. 是 Node.js 官方**推荐的生产环境用法**
