## 段落解读
引入消息代理Broker能够极大简化消息系统架构，但在部分场景下它并不是最优方案。
典型场景包括：对延迟指标要求极高、大规模复杂分布式集群、无法接受存在单点故障的系统。
对应的替代方案，就是搭建**点对点(P2P)架构的消息系统**，本节将使用ZeroMQ实现P2P模式下的发布订阅。

补充核心思路区分：
前面Redis Pub/Sub属于Broker中心化方案，所有消息经过中间件转发；而ZeroMQ可以做到无中心、节点直连的Pub/Sub，消除中间代理带来的延迟与单点风险。

# 段落核心解读（贴合原文，无发散）
## ZeroMQ基础介绍
1. 定位：适合搭建点对点架构的网络库，简称zmq，底层轻量化、速度极高，API简洁，自带构建消息系统的基础能力，支持原子消息、负载均衡、队列等核心组件。
2. 多传输协议支持：
    - inproc:// 进程内通信
    - ipc:// 本机进程间通信
    - pgm/epgm:// 组播传输
    - tcp:// 标准TCP网络传输
3. 和Redis Pub/Sub简单区分：Redis以字符串命名频道，支持通配符匹配多频道；ZeroMQ原生提供发布订阅套接字，可实现P2P发布订阅。
## 本段改造方案
之前聊天程序依靠Redis作为中间Broker中转消息，现在改用ZeroMQ重构：移除Redis消息代理，各服务节点直接点对点通信，依靠ZeroMQ自带的发布订阅套接字实现跨实例聊天互通。

# 段落原文解读
## 1 移除Broker后的架构变化
去掉Redis这类中间代理后，每一个聊天服务实例都需要主动和其他所有实例建立直连，才能接收对方发出的消息。

## 2 ZeroMQ PUB、SUB套接字工作规则
1. 套接字分工：PUB负责发布消息，SUB负责订阅消息；
2. 常规部署方式：PUB绑定本机端口，等待其他节点的SUB套接字发起连接；
3. 订阅过滤器：SUB可设置二进制/字符串过滤器，消息头部和过滤器前缀匹配才会推送给该客户端；
4. 过滤执行位置：TCP这类面向连接协议下，过滤逻辑在发布端执行；
5. 消息分发逻辑：PUB发送消息后，会把内容广播给所有已连接、且匹配订阅规则的SUB套接字。

## 3 ZeroMQ套接字定位
它是增强版网络套接字，封装了各类消息模式专用抽象，除PUB/SUB发布订阅外，还内置请求应答、单向推送等专用套接字。

## 4 多节点通信逻辑（以2台实例举例，可拓展至N台）
1. 每个节点必须知晓其余所有节点地址，才能完成全量连接；
2. 数据流方向相反：SUB向PUB发送订阅请求，消息从PUB反向流向SUB。

# 完整解读（仅围绕本段代码与说明，无额外拓展）
## 完整代码
```js
import { createServer } from 'http'
import staticHandler from 'serve-handler'
import ws from 'ws'
import yargs from 'yargs'
import zmq from 'zeromq'

// 静态文件服务
const server = createServer((req, res) => {
  return staticHandler(req, res, { public: 'www' })
})

let pubSocket

async function initializeSockets () {
  pubSocket = new zmq.Publisher()
  await pubSocket.bind(`tcp://127.0.0.1:${yargs.argv.pub}`)

  const subSocket = new zmq.Subscriber()
  const subPorts = [].concat(yargs.argv.sub)
  for (const port of subPorts) {
    console.log(`Subscribing to ${port}`)
    subSocket.connect(`tcp://127.0.0.1:${port}`)
  }
  subSocket.subscribe('chat')

  // 持续监听其他服务发来的消息
  for await (const [msg] of subSocket) {
    console.log(`Message from another server: ${msg}`)
    broadcast(msg.toString().split(' ')[1])
  }
}

initializeSockets()

const wss = new ws.Server({ server })
wss.on('connection', client => {
  console.log('Client connected')
  client.on('message', msg => {
    console.log(`Message: ${msg}`)
    broadcast(msg)
    pubSocket.send(`chat ${msg}`)
  })
})

// 广播给本机所有WebSocket客户端
function broadcast (msg) {
  for (const client of wss.clients) {
    if (client.readyState === ws.OPEN) {
      client.send(msg)
    }
  }
}

server.listen(yargs.argv.http || 8080)
```
## 代码5处改动逐点说明
1. 新增两个依赖包
`yargs`：解析命令行启动参数，方便指定http端口、发布端口、订阅端口；
`zeromq`：Node.js版ZeroMQ客户端，提供PUB/SUB套接字。

2. 创建PUB发布套接字
在`initializeSockets`函数里实例Publisher，通过启动参数`--pub`指定端口绑定，本机所有聊天消息都会从这个端口对外发布。

3. 创建SUB订阅套接字
读取所有`--sub`参数（其他实例的PUB端口），循环连接各个远端发布端口；调用`subscribe('chat')`设置过滤前缀，只接收以`chat`开头的消息。

4. 异步循环读取跨服务消息
SUB套接字是异步可迭代对象，用`for await`持续接收其他实例推送的消息；
消息格式是`chat 内容`，按空格分割，取出真正聊天内容，调用broadcast推送给本机全部在线网页客户端。

5. 客户端发消息的处理逻辑
用户通过网页发消息时：
① 先广播给当前实例所有WebSocket连接用户；
② 通过PUB套接字发送带`chat`前缀的完整消息，所有订阅该前缀的其他服务实例都能收到。

## 多实例启动命令说明
```bash
# 实例1：http8080，发布端口5000，订阅另外两台的发布端口5001、5002
node index.js --http 8080 --pub 5000 --sub 5001 --sub 5002
# 实例2：http8081，发布端口5001，订阅5000、5002
node index.js --http 8081 --pub 5001 --sub 5000 --sub 5002
# 实例3：http8082，发布端口5002，订阅5000、5001
node index.js --http 8082 --pub 5002 --sub 5000 --sub 5001
```
每个服务都兼具发布、订阅能力，主动直连其余所有实例，实现无中间件的点对点发布订阅。

## ZeroMQ内置容错特性
1. SUB连接不上远端PUB端口不会直接报错，内置自动重连机制；
2 远端节点下线、重启后会自动恢复连接；
3. 若PUB当前没有任何SUB客户端，消息会直接丢弃，程序不会崩溃。

## 整体效果
分别访问8080/8081/8082页面，任意窗口发送聊天内容，全部实例下的在线用户都能同步收到消息，完成无Broker分布式点对点聊天。

# 可靠消息队列与持久订阅者 核心精读笔记
## 一、消息队列(MQ)核心价值：解耦收发两端
ZeroMQ PUB/SUB 属于**发后即忘（fire-and-forget）**模型：发送方发消息时，订阅方必须在线、保持连接，离线期间的消息直接丢弃，两端必须同时在线才能通信。
而**消息队列**提供缓冲层，核心差异：
发送者、接收者无需同时在线；消息由队列持久存储，等待消费者上线后再投递。

## 二、关键概念：持久订阅者（durable subscriber）
定义：消息系统支持**至少一次 / 恰好一次**投递语义，消费者离线时消息会保存在队列，重启后完整接收离线期间所有消息，不会丢失。
实现前提：消息队列缓存消息，支持内存/磁盘持久化，Broker 崩溃重启后消息不丢失。

## 三、三种消息投递语义（行业标准分类）
### 1. At most once 至多一次（发后即忘，ZeroMQ PUB/SUB 默认）
- 无消息持久化、无接收确认（ack）
- 风险：消费者断线/崩溃，消息直接丢失；适合容忍丢包场景（实时聊天室、实时日志）
- 代表：原生 ZeroMQ PUB/SUB

### 2. At least once 至少一次（MQ 主流可靠方案）
- 消息落地存储，消费者处理完成后发送确认回执（ack）
- 逻辑：未收到 ack 则重发消息
- 副作用：网络延迟/消费者崩溃会产生**重复消息**，业务代码必须做幂等处理
- 代表：RabbitMQ(AMQP)、Redis Streams

### 3. Exactly once 恰好一次（最强可靠性，性能开销高）
- 底层结合持久存储、事务、唯一消息标识、去重机制
- 代价：协议复杂、存储与网络开销更大，极少通用中间件原生支持，多靠业务层幂等兜底

## 四、持久订阅者完整工作流程（配图逻辑拆解）
1. **正常在线阶段**
发布者发送消息 → 消息存入队列 → 实时推送给在线订阅者，消费完成发送 ack，队列删除已消费消息。
2. **订阅者离线/宕机**
发布者持续发消息，队列全部缓存保存（内存/磁盘持久化），不会丢弃。
3. **订阅者重新上线**
Broker 按顺序推送离线期间积压的全部消息，消费者逐条处理并确认，保证无消息丢失。

## 五、ZeroMQ 局限与扩展方案
前文 ZMQ P2P 聊天室无队列缓冲，不支持持久订阅：
1. 节点离线时消息直接丢失，无法缓存；
2. 集群拓扑写死，节点地址需提前配置。
改进方案：
- 引入**服务注册中心**（第12章内容）实现动态节点发现，不用硬编码端口；
- 基于 ZMQ 原语自行封装 Broker 中间件，实现队列持久化；
- 工业标准替代：采用 AMQP 协议（RabbitMQ）专用消息队列，原生支持持久订阅。

# AMQP 协议完整精读笔记（来自《Node.js Design Patterns》第13章）
## 一、AMQP 诞生背景
1. **传统企业消息中间件痛点**
早期商用MQ（Oracle、IBM）均使用私有闭源协议，厂商锁定（客户难以迁移），架构封闭、成本高昂，仅用于金融、航空、医疗等核心关键业务（零消息丢失硬性要求）。
2. **开源标准化协议兴起**
随着分布式系统普及，诞生三类主流开放消息协议：
- AMQP：企业级可靠队列标准（本章重点，RabbitMQ 核心协议）
- STOMP：轻量文本消息协议
- MQTT：物联网专用轻量协议
3. AMQP 定位：开放标准化企业级消息协议
不只是传输规范，完整定义**路由、过滤、队列、持久化、安全**一整套消息模型，所有兼容 Broker（RabbitMQ）遵循同一套标准，跨服务互通。

## 二、AMQP 三大核心组件：Exchange、Queue、Binding
### 1. Queue（消息队列，存储消息载体）
作用：持久/临时缓存消息，消费者从队列拉/取消息；多消费者绑定同一队列时，消息会**负载均衡分发**（竞争消费者模式）。
队列4种属性：
1. **Durable（持久队列）**
Broker 重启后队列元数据自动重建；**仅队列持久不代表消息持久**，消息必须手动标记`persistent`才会落盘保存。
2. **Exclusive（独占队列）**
仅当前连接可用，连接关闭则队列自动销毁，多用于临时私有会话。
3. **Auto-delete（自动删除队列）**
最后一个消费者断开连接，队列直接删除。

### 2. Exchange（交换机，消息分发路由中心）
发布者不会直接发送到队列，统一发送给 Exchange，由 Exchange 根据规则路由到绑定的队列。4种主流交换机类型：
1. **Direct 直连交换机**
完全匹配`routing-key`，精准一对一路由。
例：路由键`chat.msg`仅匹配绑定相同key的队列。
2. **Topic 主题交换机（最常用）**
通配符模糊匹配路由键，支持多话题订阅。
规则：`#`匹配多级任意字符、`*`匹配单段字符；
例：绑定`chat.#`，可接收`chat.login`、chat.msg 所有以 chat 开头的消息。
3. **Fanout 扇出交换机**
忽略路由键，广播消息到所有绑定队列，等价原生 PUB/SUB。

### 3. Binding（绑定关系）
交换机 ↔ 队列之间的桥梁，定义绑定使用的路由键/通配过滤规则；
一条 Exchange 可绑定多个队列，一个队列也可绑定多个 Exchange。

## 三、Broker & Channel 基础概念
1. **Broker（消息代理）**
完整AMQP服务实例（如RabbitMQ），管理所有交换机、队列、绑定，提供客户端交互接口，承担消息存储、路由、持久化、重发、确认全流程。
2. **Channel（信道）**
客户端与Broker连接后的轻量化抽象：
一条TCP物理连接可创建多条独立Channel，隔离不同业务消息流，减少多连接资源开销。

## 四、AMQP 对比 ZeroMQ / Redis 消息模型
1. 复杂度：AMQP > Redis Streams > ZeroMQ
2. 可靠性：AMQP 原生支持持久队列、消息ACK、至少一次投递、持久订阅；
   ZeroMQ 原生发后即忘、无存储；Redis 持久能力弱于AMQP。
3. 路由能力：AMQP 分层交换机模型，Topic/Direct/Fanout 多路由策略，灵活复杂业务过滤；
4. 适用场景：
   - AMQP：金融、医疗、航空等**不能丢消息**核心业务；
   - ZeroMQ：点对点实时通讯、临时分布式推送（容忍少量消息丢失）；
   - Redis Streams：缓存配套轻量消息、实时统计。

## 五、核心总结
AMQP 提供标准化、高可靠企业消息模型，分层设计（Exchange路由 + Queue存储 + Binding绑定）解决复杂消息分发需求，内置持久化、消费者负载均衡、消息确认等可靠机制，是构建无丢失分布式任务、事件系统的工业标准方案，底层能力是单纯PUB/SUB原语（ZeroMQ）无法简易实现的。
