# 历史服务 historySvc.js 完整代码逐行拆解 & AMQP持久逻辑讲解
## 一、整体服务两大核心职责
1. **AMQP消费者**：监听RabbitMQ `fanout` 交换机的所有聊天消息，写入LevelDB持久存储；
2. **HTTP接口服务（8090端口）**：对外提供接口，流式返回全部历史聊天记录给前端/聊天服务。

## 二、依赖包作用
| 依赖 | 用途 |
|------|------|
| `http` | 搭建历史查询HTTP服务 |
| `level` | LevelDB 嵌入式键值数据库，存储聊天消息 |
| `monotonic-timestamp` | 生成单调递增时间戳，作为DB主键，天然保证消息时序 |
| `JSONStream` | 数据库流式数据转为标准JSON数组输出给HTTP响应 |
| `amqplib` | Node.js RabbitMQ AMQP客户端 |

## 三、代码分步解析
```javascript
import { createServer } from 'http'
import level from 'level'
import timestamp from 'monotonic-timestamp'
import JSONStream from 'JSONStream'
import amqp from 'amqplib'

async function main () {
  // 1. 初始化本地消息数据库，目录 ./msgHistory
  const db = level('./msgHistory')

  // (1) 建立RabbitMQ TCP连接，默认地址 amqp://localhost
  const connection = await amqp.connect('amqp://localhost')
  // 创建信道Channel：复用单TCP连接，隔离多套消息逻辑
  const channel = await connection.createChannel()

  // (2) 声明fanout类型交换机 chat
  // assertExchange：不存在则自动创建；存在则直接复用
  await channel.assertExchange('chat', 'fanout')

  // (3) 声明持久队列 chat_history
  // 无额外参数时默认配置：durable=true、exclusive=false、autoDelete=false
  const { queue } = await channel.assertQueue('chat_history')

  // (4) 将队列绑定到chat交换机
  // fanout交换机无需routing-key参数，所有消息全转发到该队列
  await channel.bindQueue(queue, 'chat')

  // (5) 消费队列消息，手动ACK模式（amqplib默认手动ack）
  channel.consume(queue, async msg => {
    // 二进制消息转字符串
    const content = msg.content.toString()
    console.log(`Saving message: ${content}`)
    // 写入数据库：单调时间戳作为key，消息内容作为value
    await db.put(timestamp(), content)
    // 数据库写入成功后，手动发送ACK告知Broker
    channel.ack(msg)
  })

  // 启动HTTP服务，端口8090
  createServer((req, res) => {
    res.writeHead(200)
    // 读取DB所有值流，转JSON流式输出
    db.createValueStream()
      .pipe(JSONStream.stringify())
      .pipe(res)
  }).listen(8090)
}

main().catch(err => console.error(err))
```

## 四、AMQP关键逻辑详解（对应文中5个标注点）
### 1. Connection + Channel
- Connection：客户端与RabbitMQ的TCP长连接；
- Channel：连接内轻量会话，业务隔离，大量逻辑复用一条TCP，节省资源。

### 2. `assertExchange('chat', 'fanout')`
- 幂等操作：交换机已存在不会报错，不存在自动创建；
- Fanout交换机特性：无视路由键，所有绑定队列全量接收消息，完美适配全局聊天室。

### 3. `assertQueue('chat_history')` 持久队列核心
默认参数：
`durable: true`（队列元数据持久，Rabbit重启队列不消失）
`exclusive: false`（多服务可连接，不绑定单一连接）
`autoDelete: false`（无消费者也不删除队列）
完全满足**持久订阅者**要求，历史服务宕机消息不会丢失。

### 4. `bindQueue(queue, 'chat')`
建立交换机与队列的绑定关系，Fanout无需第三个路由键参数。

### 5. 消费+手动ACK（核心可靠保障）
1. 收到消息后**先落库，再发ack**；
2. 若写入数据库失败、服务崩溃，`channel.ack(msg)`不会执行；
3. RabbitMQ收不到ACK，消息会留在队列；服务重启后重新投递；
4. 实现**至少一次**投递语义，保证消息不会丢失。

## 五、HTTP查询接口逻辑
1. 访问 `http://localhost:8090`；
2. `db.createValueStream()` 流式读取全部历史消息；
3. `JSONStream.stringify()` 将逐条消息拼接为标准JSON数组；
4. 流式返回给请求方（前端/聊天服务），无需一次性加载全量数据，内存友好。

## 六、配套聊天服务的配合逻辑
1. 所有聊天服务发送消息到 `chat` Fanout交换机；
2. 交换机广播两路：
   - 各聊天实例**临时独占队列**：只接收实时在线消息；
   - `chat_history` 持久队列：全部消息留存，供历史服务存储；
3. 新客户端打开聊天室，请求 `8090` HTTP接口，拉取完整历史记录。

## 七、核心可靠性设计点
1. 队列持久 + 手动ACK，消息落库成功才确认；
2 单调时间戳做主键，天然保证聊天时序；
3. LevelDB本地持久存储，消息落盘永久留存；
4 服务宕机期间RabbitMQ缓存所有消息，重启自动补消费，无消息丢失。

## 八、前置依赖环境要求
本地必须运行RabbitMQ默认实例（`amqp://localhost`），否则连接报错；
数据库目录 `./msgHistory` 自动生成，无需手动创建。

# AMQP 聊天服务 index.js 完整代码拆解 & 与历史服务差异对比
## 一、整体功能
多实例 WebSocket 聊天服务，基于 RabbitMQ Fanout 交换机做分布式实时消息同步；
- 每个聊天实例创建**独占临时队列**，只消费在线实时消息；
- 客户端连接时自动请求历史微服务，推送全部历史聊天记录；
- 用户发消息推送到交换机，自动广播给所有聊天实例，实现跨端口互通。

## 二、依赖说明
`amqplib`：RabbitMQ AMQP 客户端
`superagent`：HTTP 请求库，调用历史服务接口
`JSONStream`：流式解析历史服务返回的 JSON 消息流

## 三、代码逐段核心标注解析
```javascript
import { createServer } from 'http'
import staticHandler from 'serve-handler'
import ws from 'ws'
import amqp from 'amqplib'
import JSONStream from 'JSONStream'
import superagent from 'http'

// 从命令行读取HTTP端口，默认8080
const httpPort = process.argv[2] || 8080

async function main () {
  // 1. 连接RabbitMQ，创建信道
  const connection = await amqp.connect('amqp://localhost')
  const channel = await connection.createChannel()

  // 声明全局fanout交换机chat
  await channel.assertExchange('chat', 'fanout')

  // (1) 创建独占临时队列，每个实例队列名称唯一：chat_srv_端口
  const { queue } = await channel.assertQueue(`chat_srv_${httpPort}`, {
    exclusive: true // 独占：当前连接销毁，队列自动删除
  })
  // 绑定到chat交换机
  await channel.bindQueue(queue, 'chat')

  // (2) 消费队列消息，开启noAck无确认模式
  channel.consume(queue, msg => {
    const content = msg.content.toString()
    console.log(`From queue: ${content}`)
    broadcast(content) // 推送给本地全部WebSocket客户端
  }, { noAck: true }) // 无需手动ack，收到即丢弃消息

  // 静态文件服务（前端聊天页面）
  const server = createServer((req, res) => {
    return staticHandler(req, { public: 'www' })
  })

  // WebSocket服务
  const wss = new ws.Server({ server })
  wss.on('connection', client => {
    console.log('Client connected')

    // (4) 新客户端接入：拉取历史服务全量消息并逐条下发
    superagent.get('http://localhost:8090')
      .on('error', err => console.error(err))
      .pipe(JSONStream.parse('*')) // 流式解析每条历史消息
      .on('data', msg => client.send(msg))

    // 客户端发送消息
    client.on('message', msg => {
      console.log(`Message: ${msg}`)
      // (3) 发布消息到fanout交换机，路由键填空
      channel.publish('chat', '', Buffer.from(msg))
    })
  })

  // 本地广播工具：发给当前服务所有在线客户端
  function broadcast (msg) {
    for (const client of wss.clients) {
      if (client.readyState === ws.OPEN) {
        client.send(msg)
      }
    }
  }

  server.listen(httpPort)
}
main().catch(err => console.error(err))
```

### 4个核心关键点详解
1. **独占临时队列 `{ exclusive: true }`**
    - 队列名称带当前HTTP端口，每个聊天实例独立队列；
    - 仅当前TCP连接可用，服务关闭/断开连接时队列自动销毁；
    - 设计目的：聊天服务只需要在线实时消息，离线丢失的消息不需要缓存，历史数据由持久化数据库兜底，不需要持久订阅。

2. **消费配置 `{ noAck: true }`**
    - 无手动确认机制：RabbitMQ 把消息推送给消费者后立刻删除；
    - 发后即忘模式，适用于实时消息，无需重试；
    对比历史服务：历史服务必须手动`channel.ack`，保证消息落地数据库才删除。

3. **消息发布 `channel.publish('chat', '', Buffer.from(msg))`**
    - Fanout交换机不需要路由键，第二个参数填空字符串；
    消息会广播给所有绑定队列（所有聊天实例 + 历史持久队列）。

4. 客户端连接自动拉取历史
    新浏览器接入WebSocket时，立刻HTTP请求 `8090` 历史服务，流式读取所有存档消息下发，实现上线加载完整聊天记录。

## 四、聊天服务 vs 历史服务 AMQP 配置对比
| 配置项 | 聊天服务(index.js) | 历史服务(historySvc.js) |
|--------|--------------------|------------------------|
| 队列属性 | exclusive 独占临时队列 | 默认durable持久队列 |
| 消费ack | noAck:true，自动丢弃 | 手动channel.ack，落库才确认 |
| 订阅类型 | 非持久订阅 | 持久订阅 |
| 宕机消息 | 服务下线期间消息全部丢失 | 消息持久保存在Rabbit，重启补发 |
| 适用场景 | 实时在线推送 | 全量消息持久存储 |

1. 本地启动 RabbitMQ 服务；
2. 终端1：`node index.js 8080`（8080端口聊天实例）
3. 终端2：`node index.js 8081`（8081端口聊天实例）

2. 在8080/8081页面发送多条消息；
3. 重启历史服务；
4. 历史服务会一次性消费停机期间所有消息，写入LevelDB，完美验证**持久订阅者模式**。

## 六、全系统消息流转链路
1. 用户在8080网页发消息；
2. 聊天服务调用`channel.publish`推送到`chat` Fanout交换机；
3. 交换机广播两路：
   - 分发给8080、8081两个聊天实例的独占队列，实时广播给所有在线网页；
   - 分发给`chat_history`持久队列，等待历史服务消费入库；
4. 新用户打开任意端口页面，WebSocket连接建立时，自动请求8090接口加载全部历史消息。

## 七、核心设计优势
1. 分布式多聊天实例互通，无需点对点ZMQ硬编码端口；
2. 实时消息与历史存储职责拆分，微服务解耦；
3 历史服务依靠Rabbit持久队列保证消息零丢失；
4. 实时聊天采用轻量发后即忘模型，减少Rabbit存储压力。

# Redis Streams 可靠消息流 完整解读（对比AMQP消息队列）
## 一、流(Stream)核心定义与底层特性
流是**仅追加、有序、持久化**日志型数据结构，核心区别于传统消息队列：
1. **消息不会自动删除**：队列消费后消息默认移除；流中记录写入后永久留存（可手动配置过期）；
2. **消费者主动拉取(Pull)模型**：Broker不主动推送，消费者按需拉取，可自主控制消费速度，不会被海量消息压垮；
3. **支持回溯重放**：可指定任意起始ID，重读历史全部消息，天然内置历史记录能力；
4. **宕机自愈**：消费者崩溃重启，仅需记录上次消费的最后ID，从断点继续读取，消息零丢失。

### 流 vs AMQP消息队列 核心取舍
|对比维度 | Redis Streams / Kafka 流 | RabbitMQ(AMQP)消息队列 |
|---------|--------------------------|------------------------|
|数据模型 | 持久日志，消息永久留存 | 消息消费后自动删除 |
|消费模型 | 客户端Pull拉取 | Broker Push推送 |
|历史能力 | 原生支持全量回溯，无需额外存储服务 | 无历史存储，需单独数据库微服务 |
|路由能力 | 无高级路由，全局单一流 | Direct/Topic/Fanout多交换机、复杂过滤 |
|适用场景 | 日志、聊天时序数据、事件回放、简单P2P订阅 | 微服务复杂集成、带优先级任务、多路由分发 |

## 二、基于Redis Streams改造聊天室 架构优势
原RabbitMQ方案需要**独立history历史微服务**存储聊天记录；
改用Redis Streams后：
1. 移除单独历史服务，Redis流本身存储所有聊天消息；
2. 客户端连接时直接`XRANGE`拉取全量历史消息，架构大幅简化；
3. 多聊天实例共用一条`chat_stream`流，天然分布式同步；
4. 服务宕机无需额外持久队列，仅保存最后读取ID即可断点续读。

## 三、代码逐段解析 Redis Streams 聊天室
### 依赖
`ioredis`：Redis Node客户端，支持`XADD/XREAD/XRANGE`流指令
```javascript
import { createServer } from 'http'
import staticHandler from 'serve-handler'
import ws from 'ws'
import Redis from 'ioredis'

// 双Redis连接：一个写消息，一个阻塞读流（读写分离避免阻塞干扰）
const redisClient = new Redis()
const redisClientXRead = new Redis()

const server = createServer((req, res) => {
  return staticHandler(req, { public: 'www' })
})
const wss = new ws.Server({ server })

// 记录当前实例读到的最后一条流ID，初始为$（流末尾）
let lastRecordId = '$'

// 循环阻塞读取流，实时同步其他实例消息
async function processStreamMessages () {
  while (true) {
    // 阻塞读取新记录
    const [[, records]] = await redisClientXRead(
      'BLOCK', '0', // 0=永久阻塞，无消息不返回
      'STREAMS', 'chat_stream', lastRecordId
    )
    // 遍历新消息，广播到本地所有客户端
    for (const [recordId, [, message]] of records) {
      console.log(`Message from stream: ${message}`)
      broadcast(message)
      lastRecordId = recordId // 更新断点ID
    }
  }
}

// 全局广播本地所有WebSocket客户端
function broadcast (msg) {
  for (const client of wss.clients) {
    if (client.readyState === ws.OPEN) {
      client.send(msg)
    }
  }
}

wss.on('connection', async client => {
  console.log('Client connected')

  // (2) 新客户端接入：读取全量历史消息下发
  const logs = await redisClient.xrange('chat_stream', '-', '+')
  for (const [, [, message]] of logs) {
    client.send(message)
  }

  // (1) 用户发送消息，追加到Redis流
  client.on('message', msg => {
    console.log(`Message: ${msg}`)
    redisClient.xadd('chat_stream', '*', 'message', msg)
  })
})

// 启动流消费循环
processStreamMessages().catch(err => console.error(err))
// 启动HTTP服务
server.listen(process.argv[2] || 8080)
```

### 三大核心Redis Stream指令详解
#### 1. `XADD chat_stream * message <msg>` 写入流
- `chat_stream`：流名称；
- `*`：让Redis自动生成**单调时序ID**（时间戳+序列号，保证全局有序）；
- 键值对 `message msg`：存储消息内容；
作用：用户发送聊天消息，追加到流尾部，所有实例均可读取。

#### 2. `XRANGE chat_stream - +` 读取全部历史记录
- `-`：流第一条最小ID；`+`：流最后一条最大ID；
- 返回流内所有历史消息；
- 客户端连接时执行，一次性下发完整聊天记录，替代独立history服务。
返回数据格式：
```
[
  ["1588590110918-0", ["message", "第一条消息"]],
  ["1588590130852-0", ["message", "第二条消息"]]
]
```
解构 `[, [, message]]` 直接提取消息文本，忽略ID与key字段。

#### 3. `XREAD BLOCK 0 STREAMS chat_stream lastRecordId` 阻塞消费流
- `BLOCK 0`：永久阻塞，无新消息时挂起连接，不轮询消耗CPU；
- `$` 初始ID：代表启动时只读取**之后新增**的消息，不重复回放历史；
- 循环持续拉取，每条消息处理完更新`lastRecordId`，保存消费断点；
- 服务重启后，从保存的ID继续读取，宕机期间消息不会丢失。

## 四、完整消息流转（多实例场景）
1. 用户在8080网页发送消息 → `XADD` 写入全局`chat_stream`；
2. 所有聊天实例的`XREAD`阻塞循环捕获新消息，调用`broadcast`推送给本地在线客户端；
3. 新浏览器连接服务 → `XRANGE` 读取流内全部历史消息，逐条下发展示；
4. 某聊天实例进程崩溃：重启后`lastRecordId`记录上次断点，自动读取宕机期间所有消息，无丢失。

## 五、Redis Streams 架构简化亮点（对比RabbitMQ方案）
1. **消除独立历史微服务**
RabbitMQ架构必须单独启动historySvc存储消息；Redis流自带持久时序存储，一套组件兼顾实时推送+历史查询。
2. 部署成本更低
无需额外RabbitMQ中间件，复用项目常用Redis；
3. 天然断点续传，无需ACK机制
依靠记录消费ID实现可靠消费，不用手动发送确认；
4. 全局单一流，无需管理多独占/持久队列，代码更简洁。

## 六、局限性
1. 无复杂路由、消息优先级；
2. 原生不支持多独立队列做任务分发；
3. 超大流量分布式集群场景不如Kinesis/Kafka成熟。
