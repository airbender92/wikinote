# 三大标准消息类型（EIP规范）完整解析
## 总述
消息的业务目标决定其结构、载荷与使用场景，业界标准分为**命令消息、事件消息、文档消息**三类，是设计消息体、区分业务通信逻辑的核心依据。

## 1. Command Messages 命令消息
### 核心语义
向接收方下发**执行指令**，强制要求对方完成指定操作，代表「我要你做某事」。
### 特征
1. 有明确执行动作、操作对象；
2. 发送方期望接收方完成对应行为；
3. 通常搭配请求-应答模式，可等待执行结果。
### 电商示例
```json
{
  "type": "command",
  "action": "reduceStock",
  "productId": 1001,
  "num": 2
}
```
含义：通知库存服务**扣减2件1001商品**，是主动操作指令。
### 适用场景
远程操作、变更业务状态、触发任务执行。

## 2. Event Messages 事件消息
### 核心语义
告知所有订阅者**某件业务事实已经发生**，仅做状态通知，不强制接收方执行操作；代表「刚刚发生了一件事，你们可以按需处理」。
### 特征
1. 描述已完成的历史行为；
2. 发送方不关心下游如何处理，无强制要求；
3. 适配发布订阅（Pub/Sub）单向异步模型，多服务可订阅消费。
### 电商示例
```json
{
  "type": "event",
  "eventName": "orderPaid",
  "orderId": 5678,
  "goodsList": [{"id":1001,"count":2}]
}
```
含义：订单已支付完毕，购物车、库存、积分服务可自行订阅处理。
### 适用场景
业务状态同步、多系统广播通知、数据更新推送。

## 3. Document Messages 文档消息
### 核心语义
完整传输一份**结构化业务数据集**，核心目的是同步完整实体数据，不携带动作指令、事件描述。
### 特征
1. 载荷是完整实体对象；
2. 侧重数据复制、全量/增量同步；
3. 无操作意图，仅传递数据本身。
### 电商示例
```json
{
  "type": "document",
  "dataType": "product",
  "data": {
    "id":1001,
    "name":"Node.js实战书籍",
    "price":59,
    "stock":120
  }
}
```
含义：同步商品完整信息给搜索服务做索引更新。
### 适用场景
数据同步、缓存刷新、第三方系统全量数据同步。

# 三类消息核心对比
| 消息类型 | 核心意图 | 动作属性 | 常用通信模式 | 核心关键词 |
|--------|---------|---------|------------|-----------|
| 命令消息 | 要求对方执行操作 | 待执行动作 | Request/Reply | 执行、修改、删除、触发 |
| 事件消息 | 告知已发生事实 | 已完成行为 | 单向Pub/Sub | 已完成、发生、变更 |
| 文档消息 | 传输完整业务数据 | 无动作，纯数据 | 单向推送 | 实体、完整数据、同步 |

# 关键区分要点
1. **命令 vs 事件**
命令：主动发起操作，需要对方执行；
事件：操作已结束，仅广播结果，不强制下游行为。
2. **事件 vs 文档**
事件侧重「发生了什么动作」；
文档侧重「完整实体数据是什么」。
3. 工程实践建议
同一消息队列/主题尽量统一消息类型，避免混合三类语义，防止消费逻辑混乱。

# 异步消息、队列、流核心要点（无发散，严格贴合原文）
## 一、同步通信 vs 异步通信类比
1. **同步通信（电话）**
通信双方必须同时在线、占用同一通道；同一时间只能进行一次会话，资源占用高。
2. **异步通信（短信）**
接收方无需实时在线；发送后可继续执行其他任务，回复延迟不定甚至无回复；支持批量多发、乱序回执，并行能力更强、资源消耗更低。
## 二、消息队列 Message Queue
1. 核心作用：作为生产者、消费者的中间存储，消息投递前持久缓存。
2. 故障容错：消费者宕机、断网、处理缓慢时，消息堆积在队列，消费者恢复后继续分发。
3. 队列部署位置三形态
    - 生产者本地；
    - P2P架构下两端拆分存储；
    独立中间件Broker（RabbitMQ等）。
4. 队列特性：消息被消费后一般移出队列，单条消息通常仅交付一个消费者。
## 三、数据流 Stream（日志结构）
1. 底层结构：仅追加（append-only）持久日志，别名数据流。
2. 和队列核心区别
    - 读取消息后**不会删除原数据**；
    - 支持实时消费新消息，也可回溯读取历史全量消息；
    - 多消费者可同时消费同一段消息，互不干扰。
3. 适用场景：多端数据同步、日志回放、批量数据回放。
## 四、队列 vs Stream 关键区分（原文核心）
1. 队列：消息消费即移除，单消息单一消费者；
2. 流：消息永久留存，支持多消费者重复读取历史数据。
## 五、收尾基础维度
消息系统最后一个核心要素：节点连接方式（直连P2P / 中介Broker转发）。

# P2P点对点 vs 基于Broker消息架构（严格贴合原文，无发散）
## 一、两种架构基础定义
1. **Peer-to-Peer（点对点直连）**
生产者与消费者直接建立网络连接，消息无中间中转，节点互相直推报文。
2. **Broker-based（消息代理中心化架构）**
引入独立中心化中间件（消息Broker）作为中转枢纽，所有生产者、消费者只和Broker通信，收发双方完全隔离。

## 二、P2P架构特点
1. 节点必须知晓对方地址、端口，提前约定统一协议与消息格式；
2. 消息投递逻辑完全由两端节点自行实现；
3. 优势：
   - 消除Broker带来的单点故障；
   - 无需单独扩容中间件，仅扩业务节点；
   - 省去中转网络开销，通信延迟更低；
   - 不受特定中间件技术、协议绑定，自由度更高；
4. 劣势：解耦能力弱，持久化、路由、监控、多订阅等能力需要业务自行开发，开发成本高。

## 三、Broker消息代理架构核心能力
1. **核心价值：彻底解耦收发双方**
生产者无需感知任何消费节点的地址、数量，只向Broker发送消息；消费者只从Broker拉取消息，彼此无感知。
2. **协议转换桥梁**
示例RabbitMQ同时支持AMQP、MQTT、STOMP多协议，不同协议的应用可通过Broker互通。
3. 内置开箱能力：持久队列、消息路由、报文转换、监控告警、原生支持各类消息模式；
4. 劣势：Broker为潜在单点故障，需要额外运维、集群扩容。

## 四、三大主流TCP消息协议（原文）
1. AMQP：功能完备复杂开源中间件标准协议，企业级消息中间件主流；
2. MQTT：轻量级协议，面向物联网、设备通信；
3. STOMP：文本类轻量协议，设计思路贴近HTTP。

# Publish/Subscribe 发布订阅模式（原文精简要点，无发散）
## 1 模式本质
Pub/Sub 是最主流的**单向消息模式**，本质是**分布式观察者 Observer 模式**。
角色划分：
- Publisher 发布者：产生消息，只发送主题消息；
- Subscriber 订阅者：预先注册关注的消息主题，仅接收自己订阅的消息。

## 2 两种实现架构
1. **P2P 点对点 Pub/Sub**
无中间代理，发布者直连所有订阅节点；发布者需要维护所有订阅方地址，耦合度更高。
2. **Broker 中心化 Pub/Sub（主流）**
所有发布、订阅动作都经过消息代理中转；发布者、订阅者互相完全无感知，解耦程度拉满。

## 3 核心核心特性：高度松耦合
发布者**完全不知道订阅者是谁、有多少个**：
1. 订阅方主动声明感兴趣的主题，而非发布者指定接收人；
2. 新增/下线消费服务，无需修改发布端代码；
3. 适配持续迭代、不断新增业务模块的分布式系统。

## 4 Broker 带来的额外优势
1. 彻底隔离发布与消费两端，双方互相不可见；
2. 内置消息队列持久化能力，网络断开、服务宕机场景下保障消息可靠投递；

## 5 典型业务场景
订单支付完成事件推送、商品变更同步搜索库、系统全局通知广播等多服务同步场景。
