# 三大标准消息类型（EIP规范）完整解析
## 总述
消息的业务目标决定其结构、载荷与使用场景，业界标准分为**命令消息、事件消息、文档消息**三类，是设计消息体、区分业务通信逻辑的核心依据。

## 1. Command Messages 命令消息
### 核心语义
向接收方下发**执行指令**，强制要求对方完成指定操作，代表「我要你做某事」。
### 特征
1. 有明确执行动作、操作对象；
2. 发送方期望接收方完成对应行为；
3. 通常搭配请求-应答模式，可等待执行结果。
### 电商示例
```json
{
  "type": "command",
  "action": "reduceStock",
  "productId": 1001,
  "num": 2
}
```
含义：通知库存服务**扣减2件1001商品**，是主动操作指令。
### 适用场景
远程操作、变更业务状态、触发任务执行。

## 2. Event Messages 事件消息
### 核心语义
告知所有订阅者**某件业务事实已经发生**，仅做状态通知，不强制接收方执行操作；代表「刚刚发生了一件事，你们可以按需处理」。
### 特征
1. 描述已完成的历史行为；
2. 发送方不关心下游如何处理，无强制要求；
3. 适配发布订阅（Pub/Sub）单向异步模型，多服务可订阅消费。
### 电商示例
```json
{
  "type": "event",
  "eventName": "orderPaid",
  "orderId": 5678,
  "goodsList": [{"id":1001,"count":2}]
}
```
含义：订单已支付完毕，购物车、库存、积分服务可自行订阅处理。
### 适用场景
业务状态同步、多系统广播通知、数据更新推送。

## 3. Document Messages 文档消息
### 核心语义
完整传输一份**结构化业务数据集**，核心目的是同步完整实体数据，不携带动作指令、事件描述。
### 特征
1. 载荷是完整实体对象；
2. 侧重数据复制、全量/增量同步；
3. 无操作意图，仅传递数据本身。
### 电商示例
```json
{
  "type": "document",
  "dataType": "product",
  "data": {
    "id":1001,
    "name":"Node.js实战书籍",
    "price":59,
    "stock":120
  }
}
```
含义：同步商品完整信息给搜索服务做索引更新。
### 适用场景
数据同步、缓存刷新、第三方系统全量数据同步。

# 三类消息核心对比
| 消息类型 | 核心意图 | 动作属性 | 常用通信模式 | 核心关键词 |
|--------|---------|---------|------------|-----------|
| 命令消息 | 要求对方执行操作 | 待执行动作 | Request/Reply | 执行、修改、删除、触发 |
| 事件消息 | 告知已发生事实 | 已完成行为 | 单向Pub/Sub | 已完成、发生、变更 |
| 文档消息 | 传输完整业务数据 | 无动作，纯数据 | 单向推送 | 实体、完整数据、同步 |

# 关键区分要点
1. **命令 vs 事件**
命令：主动发起操作，需要对方执行；
事件：操作已结束，仅广播结果，不强制下游行为。
2. **事件 vs 文档**
事件侧重「发生了什么动作」；
文档侧重「完整实体数据是什么」。
3. 工程实践建议
同一消息队列/主题尽量统一消息类型，避免混合三类语义，防止消费逻辑混乱。

# 异步消息、队列、流核心要点（无发散，严格贴合原文）
## 一、同步通信 vs 异步通信类比
1. **同步通信（电话）**
通信双方必须同时在线、占用同一通道；同一时间只能进行一次会话，资源占用高。
2. **异步通信（短信）**
接收方无需实时在线；发送后可继续执行其他任务，回复延迟不定甚至无回复；支持批量多发、乱序回执，并行能力更强、资源消耗更低。
## 二、消息队列 Message Queue
1. 核心作用：作为生产者、消费者的中间存储，消息投递前持久缓存。
2. 故障容错：消费者宕机、断网、处理缓慢时，消息堆积在队列，消费者恢复后继续分发。
3. 队列部署位置三形态
    - 生产者本地；
    - P2P架构下两端拆分存储；
    独立中间件Broker（RabbitMQ等）。
4. 队列特性：消息被消费后一般移出队列，单条消息通常仅交付一个消费者。
## 三、数据流 Stream（日志结构）
1. 底层结构：仅追加（append-only）持久日志，别名数据流。
2. 和队列核心区别
    - 读取消息后**不会删除原数据**；
    - 支持实时消费新消息，也可回溯读取历史全量消息；
    - 多消费者可同时消费同一段消息，互不干扰。
3. 适用场景：多端数据同步、日志回放、批量数据回放。
## 四、队列 vs Stream 关键区分（原文核心）
1. 队列：消息消费即移除，单消息单一消费者；
2. 流：消息永久留存，支持多消费者重复读取历史数据。
## 五、收尾基础维度
消息系统最后一个核心要素：节点连接方式（直连P2P / 中介Broker转发）。
