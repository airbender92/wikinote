# 极简实时聊天应用（Pub/Sub落地示例 核心要点）
## 整体实现三步思路
1. **基础单实例版本**：纯WebSocket实现单机聊天服务
   单台服务器维护所有客户端WebSocket连接，客户端发消息后，服务端广播给当前在线全部用户，是进程内简易发布订阅。
2. **单机局限**：多服务器多实例部署后，不同实例连接的用户互相收不到消息，实例间完全隔离，无法全局互通。
3. **引入消息系统扩容**：基于Pub/Sub打通多服务实例，实现全集群消息互通
   每个聊天服务实例同时作为发布者+订阅者：
   - 客户端消息 → 当前服务发布到全局消息主题；
   - 所有服务订阅该主题，收到消息后转发给自己连接的全部本地客户端。

## 架构逻辑（Broker型Pub/Sub）
1. 聊天服务多实例横向部署；
2. 统一消息Broker作为全局消息中转站；
3. 任意用户发送的聊天消息，由所在服务发布至聊天主题；
4. 全部聊天服务实例订阅同一聊天主题，收到消息后推送给本地在线客户端；
5. 最终所有服务器上的用户均可收到全局聊天消息，实现分布式实时聊天。

## 技术落地载体
原生WebSocket负责浏览器与服务端实时长连接；
消息中间件（Redis Pub/Sub / RabbitMQ Topic等）实现服务间分布式发布订阅，解决多实例数据隔离问题。

## 核心价值演示Pub/Sub
发布端（聊天实例）无需感知其他服务、在线用户数量；新增服务实例只需订阅主题即可自动加入全局聊天网络，天然适配分布式系统扩容迭代。

## 段落解读
接下来我们着手开发服务端，整体思路分两步走：先实现一个基础聊天程序，之后再改造支持多实例部署。
我们选用 `ws` 库实现实时通信，它是Node.js生态里纯正的WebSocket实现。用Node.js开发这类实时应用十分简洁，下面把服务端代码写在 index.js 文件中：
```js
import { createServer } from 'http'
import staticHandler from 'serve-handler'
import ws from 'ws'

const server = createServer((req, res) => {
  return staticHandler(req, res, { public: 'www' })
})
const wss = new ws.Server({ server })

wss.on('connection', client => {
  console.log('Client connected')
  client.on('message', msg => {
    console.log(`Message: ${msg}`)
    broadcast(msg)
  })
})

function broadcast (msg) {
  for (const client of wss.clients) {
    if (client.readyState === ws.OPEN) {
      client.send(msg)
    }
  }
}

server.listen(process.argv[2] || 8080)
```

以上就是完整的服务端代码，整体运行逻辑：
1. 新建HTTP服务，利用静态文件处理器托管www目录，提供前端页面、样式、脚本等资源访问；
2. 把WebSocket服务挂载在当前HTTP服务上，持续监听客户端连接；
3. 每当有客户端接入，就监听它发送的消息；收到消息后，向所有在线客户端广播；
4. 广播函数会遍历当前服务内所有客户端，只给连接状态正常的客户端推送消息。

Node.js开发实时程序的优势在此体现。虽然这套实现十分简陋，但基础聊天功能可以正常运行。
但要注意局限：消息广播范围仅限于当前服务实例。一旦启动多个服务实例，不同实例下的用户互相收不到消息，后面会借助消息发布订阅模式解决这个分布式难题。

## 段落解读
接下来实现聊天程序的客户端。代码同样十分简洁，就是一份简易HTML搭配少量JavaScript，新建`www/index.html`文件，代码如下：
```html
<!DOCTYPE html>
<html>
<body>
Messages:
<div id="messages"></div>
<form id="msgForm">
<input type="text" placeholder="Send a message" id="msgBox"/>
<input type="submit" value="Send"/>
</form>
<script>
const ws = new WebSocket(
`ws://${window.document.location.host}`
)
ws.onmessage = function (message) {
const msgDiv = document.createElement('div')
msgDiv.innerHTML = message.data
document.getElementById('messages').appendChild(msgDiv)
}
const form = document.getElementById('msgForm')
form.addEventListener('submit', (event) => {
event.preventDefault()
const message = document.getElementById('msgBox').value
ws.send(message)
document.getElementById('msgBox').value = ''
})
</script>
</body>
</html>
```

这份页面逻辑通俗易懂。代码借助浏览器原生WebSocket API和Node服务建立连接；持续监听服务端推送的消息，收到消息后新建div元素展示内容。页面内置表单，通过输入框和提交按钮完成消息发送。

整体流程：页面加载后自动和服务端建立WebSocket长连接；收到聊天消息就渲染到页面；用户填写内容提交表单，脚本阻止页面默认刷新行为，把文本通过WebSocket发送给服务端，随后清空输入框。
这套客户端配合前面的服务端，单实例场景可以正常聊天，依旧无法跨多个服务实例互通。

当前代码的缺陷：消息只会在当前服务实例内部广播，仅推送给接入这台服务的客户端。两个服务实例之间没有任何通信。想要实现跨实例互通，就需要把各个服务实例整合打通，这也是接下来要解决的核心问题。

## 段落整体解读
本节选用Redis充当简易消息代理，用来解决聊天服务多实例无法互通的问题。Redis常作为缓存、内存数据库，同时内置发布订阅能力。对比专业消息中间件，Redis的Pub/Sub功能比较轻量化，但优势十分突出：很多业务环境原本就部署了Redis，无需额外搭建、维护独立消息中间件，可以快速实现分布式消息分发。

整体改造思路：把Redis作为中心化消息总线。每一个聊天服务实例同时兼具发布者与订阅者身份。客户端发来消息后，实例将消息发布到Redis频道；所有服务实例订阅同一个频道，收到消息后再推送给本机连接的浏览器客户端。
完整消息流转路径：
1. 用户在网页输入消息，发送给自己所连接的聊天服务实例；
2. 服务实例把消息发布到Redis；
3. Redis把消息推送给所有订阅该频道的聊天服务实例；
4. 每一台实例收到消息后，广播给本机所有在线客户端。

> 前提条件：本地启动Redis服务，使用默认端口。

### 修改后的完整代码
```js
import { createServer } from 'http'
import staticHandler from 'serve-handler'
import ws from 'ws'
import Redis from 'ioredis' // (1)

const redisSub = new Redis()
const redisPub = new Redis()

// serve static files
const server = createServer((req, res) => {
  return staticHandler(req, res, { public: 'www' })
})
const wss = new ws.Server({ server })

wss.on('connection', client => {
  console.log('Client connected')
  client.on('message', msg => {
    console.log(`Message: ${msg}`)
    redisPub.publish('chat_messages', msg) // (2)
  })
})

redisSub.subscribe('chat_messages') // (3)
redisSub.on('message', (channel, msg) => {
  for (const client of wss.clients) {
    if (client.readyState === ws.OPEN) {
      client.send(msg)
    }
  }
})

server.listen(process.argv[2] || 8080)
```

### 代码改动逻辑说明
1. 引入ioredis客户端，创建两条独立Redis连接，一条用于订阅，一条用于发布。
Redis存在一个特性：一旦连接进入订阅模式，就只能执行订阅相关指令，不能执行publish，因此必须分开两个连接。
2. 收到客户端消息后，不再直接本地广播，而是发布至`chat_messages`频道。
当前服务实例同样订阅了这个频道，消息会原路返回本机，再统一广播。书中也提到，实际项目可以优化，过滤掉本机产生的消息，留给读者自行练习。
3. 服务启动时订阅`chat_messages`频道，监听频道消息。收到消息后遍历本机所有WebSocket连接，推送给在线客户端。

### 测试验证
启动多个服务实例
```bash
node index.js 8080
node index.js 8081
node index.js 8082
```
浏览器分别连接不同端口，此时任意客户端发送消息，所有实例上的用户都能收到消息。
至此，借助发布订阅模式，我们完成分布式实时应用多节点互通。
