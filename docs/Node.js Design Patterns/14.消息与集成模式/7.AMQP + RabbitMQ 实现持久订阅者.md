# AMQP + RabbitMQ 实现持久订阅者 核心解读
## 一、业务场景背景
微服务架构多服务数据同步场景，**消息绝对不能丢失**：
若服务离线期间产生的事件丢失，各服务本地数据会出现不一致，业务逻辑错乱。
因此必须基于 RabbitMQ（AMQP 标准 Broker）实现**持久订阅者**，保证服务重启后，离线积压的消息全部完整消费。

## 二、实现持久订阅的全套 AMQP 关键配置（缺一不可）
想要达成「At-Least-Once 至少一次投递、离线不丢消息」，四层持久配置必须同时开启：
### 1. 持久交换机 (Durable Exchange)
创建 Exchange 时设置 `durable: true`
Broker 重启后交换机定义不会丢失，路由规则保留。

### 2. 持久队列 (Durable Queue)
创建 Queue 时设置 `durable: true`
Broker 重启后队列本体依然存在；
⚠️ 仅队列持久不代表消息持久，消息本身需单独标记。

### 3. 持久消息 (Persistent Messages)
生产者发送消息时，设置投递模式 `persistent: true`
消息写入磁盘保存，Broker 崩溃重启后消息不会丢失；
若不设置，消息仅存内存，Broker 重启直接清空。

### 4. 持久消费者（持久订阅）
消费声明时设置 `durable: true` + 开启手动 ACK（手动确认）
1. **手动 ACK 机制**
自动 ACK：Broker 消息发出即标记完成，服务中途崩溃消息丢失；
手动 ACK：消费者业务处理完毕，主动发送确认；未确认消息会放回队列，服务重启后重新接收。
2. 持久订阅标识：RabbitMQ 会记录消费者绑定关系，离线期间消息全部缓存队列，上线后批量推送。

## 三、完整可靠消息流转流程
1. 生产者 → 持久 Exchange → 路由至持久队列，消息标记持久化落盘；
2. 消费者在线：接收消息，业务处理完成手动 ack，Broker 删除该消息；
3. 消费者下线/崩溃：未 ack 的消息留在磁盘队列；
4. 消费者重新连接：Broker 把离线全部积压消息依次推送，逐条消费确认，无丢失。

## 四、对比前文 ZeroMQ P2P 聊天室核心差异
1. ZeroMQ：无 Broker、无队列存储，离线消息直接丢弃，无法做数据同步；
2. RabbitMQ(AMQP)：中心化 Broker + 磁盘持久队列，天然适配微服务数据同步、任务分发等零丢失业务。

## 五、微服务同步业务价值
微服务多实例、多组件依赖事件同步时：
- 服务维护、宕机重启不会丢失变更事件；
- 所有服务最终能收到完整事件流，保证各模块数据最终一致性；
- 提供标准可靠投递语义（至少一次），只需业务层增加幂等逻辑处理重复消息。

## 六、前置章节关联
本章《消息与集成模式》前文提到**微服务集成模式**，AMQP 持久订阅正是该模式的标准落地实现，用中心化可靠消息中间件解耦微服务，保障跨服务事件可靠流转。

# 聊天应用-历史记录微服务 架构与设计完整解读
## 一、业务扩展目标
原有分布式聊天室只做实时消息推送，新增**消息历史微服务**：
1. 所有聊天消息持久存入数据库；
2. 客户端上线时可拉取完整历史聊天记录；
3. 通过 RabbitMQ（AMQP Fanout 交换机）解耦聊天服务与历史存储服务，实现微服务架构。

## 二、整体AMQP架构设计
### 1. 交换机选型：Fanout 扇出交换机
业务不需要复杂路由过滤（所有消息全量广播），因此选用最简单的 Fanout Exchange：
- 生产者（各聊天服务实例）发送消息到交换机；
- 交换机会把消息**无差别广播**给所有绑定的队列；
- 无需配置 routing-key，适配全局聊天消息分发场景。

### 2. 两类完全不同的消息队列（核心区分设计）
#### （1）每个聊天服务实例：独占临时队列
- 属性：`exclusive` 独占队列
- 特性：绑定当前聊天服务连接，连接断开（服务重启/崩溃）队列直接销毁；
- 设计原因：聊天服务只需要**实时在线消息**，离线期间丢失的消息不需要队列缓存，离线历史统一由历史服务提供，不需要队列持久化。
- 定位：实时消息推送通道，非持久订阅。

#### （2）历史记录服务：持久队列
- 属性：`durable` 持久队列 + 持久消息 + 手动ACK；
- 特性：历史服务下线/重启时，所有聊天消息会保存在RabbitMQ磁盘，服务恢复后完整补发；
- 设计必要性：历史服务核心职责是全量保存所有消息，**任何消息都不能丢失**，必须实现持久订阅。

## 三、各组件分工
1. **多实例聊天服务（Websocket服务）**
   - 用户发送消息 → 推送到RabbitMQ Fanout交换机；
   - 自身独占临时队列，接收其他聊天实例的实时消息，广播给本地在线浏览器；
   - 客户端上线时，主动请求历史服务接口，拉取全部历史消息展示。
2. **RabbitMQ Broker（AMQP中间件）**
   - 单一Fanout交换机；
   - 管理多组临时独占队列（聊天实例）、1个持久队列（历史服务）；
   实时消息分发给在线聊天服务，离线消息持久缓存给历史服务。
3. **History 历史微服务**
   - 绑定持久队列，消费所有聊天消息；
   - 存储引擎：LevelUP（本地键值数据库）持久落地每条聊天记录；
   - 对外提供查询接口，客户端连接时返回完整聊天历史；
   - 支持复杂历史查询（分页、时间段筛选等扩展能力）。

## 四、核心依赖工具
1. `amqplib`：Node.js AMQP 客户端，对接 RabbitMQ；
2. LevelUP：轻量嵌入式键值数据库，作为消息持久存储；
3. RabbitMQ：AMQP标准消息中间件，提供Fanout交换机、持久队列能力。

## 五、设计取舍逻辑
1. 聊天服务不用持久队列：
实时聊天只关心在线消息，断连丢失的消息不需要队列补发，由历史数据库兜底查询，降低RabbitMQ存储压力。
2. 历史服务必须持久队列：
一旦丢失任意一条消息，数据库记录残缺，历史查询功能完全失效，必须开启全套持久化（交换机/队列/持久消息/手动ACK）。
3. Fanout交换机适配全局聊天室：
不需要按用户/房间路由，所有消息全广播，架构极简，维护成本低。

## 六、数据流完整链路
1. 用户在8080端口网页发送消息；
2. 聊天实例1推送消息至RabbitMQ Fanout交换机；
3 交换机广播两路：
   - 分发至所有在线聊天实例的临时独占队列 → 实时推送给所有在线客户端；
   - 分发至历史服务持久队列 → 历史服务消费存入LevelUP；
4. 新客户端打开页面，调用历史服务接口，拉取全部存档消息渲染聊天记录。
5. 若历史服务宕机：消息全部存在RabbitMQ持久队列，重启后一次性消费全部积压消息补全数据库。
