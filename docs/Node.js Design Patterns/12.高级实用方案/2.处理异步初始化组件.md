## 译文
### 处理异步初始化组件
Node 核心模块与大量 npm 包提供同步 API，一大用途就是执行初始化逻辑。简单程序中，初始化阶段使用同步接口会大幅简化代码；且初始化仅执行一次，阻塞带来的负面影响可控。

但很多场景无法使用同步初始化：组件初始化需要网络交互（握手、拉取远程配置），典型如各类数据库驱动、消息队列客户端。

### 异步组件存在的问题
以数据库模块 `db.js` 举例：必须完成连接、握手后才能执行 SQL 查询；初始化未完成时调用接口会直接报错。
```js
import { EventEmitter } from 'events'
class DB extends EventEmitter {
  connected = false
  connect () {
    // 模拟网络连接延迟
    setTimeout(() => {
      this.connected = true
      this.emit('connected')
    }, 500)
  }
  async query (queryString) {
    if (!this.connected) {
      throw new Error('Not connected yet')
    }
    console.log(`Query executed: ${queryString}`)
  }
}
export const db = new DB()
```
这是典型的异步初始化组件。针对这类组件，书中提供两套基础落地方案：**本地初始化校验**、**延迟启动**，下面详细拆解。

## 核心知识点
### 1. 问题根源
组件初始化依赖网络 IO，只能异步执行；连接完成前调用业务方法，直接抛出异常，业务代码很难统一处理。
### 2. 示例组件逻辑拆解
- `connect()`：异步建立连接，500ms 后标记 `connected = true`，触发 `connected` 事件；
- `query()`：执行查询，未连接时直接抛错；
- 导出全局单例 db，项目各处共享实例。
### 3. 两大基础解决方案
1. **本地初始化校验**
每次调用组件方法前，手动判断初始化状态；未就绪则等待/抛错，适合调用点少的简单场景。
2. **延迟启动**
缓存所有未就绪的请求，等初始化完成后批量执行，业务侧无需手动判断，是高并发场景主流方案（后文会详细实现）。
### 4. 适用业务场景
数据库连接池、Redis/MQ 客户端、远程配置 SDK、第三方 RPC 客户端等需要异步握手初始化的工具类。

# 译文 + 核心知识点
## 译文
### 方案一：本地初始化校验
第一种方案思路：每次调用组件 API 前，主动校验组件是否初始化完成；若未就绪，则等待初始化完成再执行操作。每次调用接口都要加这段判断逻辑。
```js
import { once } from 'events'
import { db } from './db.js'

db.connect()

async function updateLastAccess () {
  // 每次调用前校验连接状态
  if (!db.connected) {
    // 阻塞等待connected就绪事件
    await once(db, 'connected')
  }
  await db.query(`INSERT (${Date.now()}) INTO "LastAccesses"`)
}

updateLastAccess()
// 延迟600ms再次调用（此时连接早已完成，无需等待）
setTimeout(() => {
  updateLastAccess()
}, 600)
```
只要调用 `db.query`，就必须先判断连接状态；未就绪时通过 `events.once` 监听 `connected` 事件，挂起当前异步函数等待初始化结束。

该方案有变种实现：把状态校验逻辑封装进 `query` 方法内部，将重复模板代码的负担从调用方转移到组件内部，不用每个业务函数都写判断。

## 核心知识点
### 1. 核心工具：events.once
`once(emitter, event)` 返回 Promise，仅监听一次目标事件，事件触发后 Promise 决议，完美适配 async/await 等待初始化场景。
### 2. 方案优缺点
✅ 优点：实现简单，无需额外队列、缓存逻辑，小型低并发项目够用；
❌ 缺点：
1. 调用方需要到处写状态判断模板代码，大量业务函数会产生冗余重复代码；
2. 并发大量调用时，会创建大量监听事件，有轻微内存开销；
3. 无法统一管控所有等待中的请求。

### 3. 优化变种（组件内部封装校验）
改造 db 的 query 方法，把 `connected` 判断内置，业务调用时无需手动等待：
```js
async query (queryString) {
  if (!this.connected) {
    await once(this, 'connected')
  }
  console.log(`Query executed: ${queryString}`)
}
```
改造后业务代码简化，不用每次手动判断，是该方案更实用的改良版本。

### 4. 适用场景
项目调用数据库/SDK 的地方很少、并发量低、对代码简洁度要求不高的小型脚本。高并发服务推荐后文「预初始化队列」方案。

## 译文
### 方案二：延迟启动（Delayed startup）
第二种简易解决思路：把所有依赖该异步组件的业务代码延后执行，等组件初始化全部完成后再运行。示例代码：
```js
import { db } from './db.js'
import { once } from 'events'

// 统一初始化函数
async function initialize () {
  db.connect()
  await once(db, 'connected')
}

async function updateLastAccess () {
  await db.query(`INSERT (${Date.now()}) INTO "LastAccesses"`)
}

// 先完成初始化，再执行业务逻辑
initialize()
.then(() => {
  updateLastAccess()
  setTimeout(() => {
    updateLastAccess()
  }, 600)
})
```
逻辑流程：先执行组件初始化，等待连接就绪后，才执行所有调用 `db` 的业务函数。

#### 该方案缺陷
需要提前梳理所有使用该组件的业务代码，全部包裹在初始化完成的回调内，代码十分脆弱，极易漏写调用逻辑引发报错。
衍生改良思路：**延迟整个应用启动**，等全部异步服务初始化完毕再执行业务入口。
优点：实现简单、不会出现未初始化就调用的错误；
缺点：
1. 拉长应用整体启动耗时；
2. 无法应对组件断线重连、二次初始化的场景。

下文会介绍第三种更完善的方案，可无感知缓存所有待执行操作，自动等初始化完成后批量执行，高效透明。

## 核心知识点
### 1. 核心思路
将所有依赖异步组件的逻辑后置，依托初始化 Promise 串行执行，从根源规避「未就绪调用」报错。
### 2. 两种落地形式
1. 局部延迟：仅延迟使用该组件的部分业务代码（示例写法）；
2. 全局延迟：应用主入口阻塞，所有服务（数据库、MQ 等）初始化完毕后才启动服务监听端口。

### 3. 优缺点总结
✅ 优点
1. 业务代码无需到处写状态判断，无重复样板代码；
2. 启动阶段即可捕获初始化失败（如数据库连接失败），提前抛出致命错误。
❌ 缺点
1. 代码耦合度高，新增业务调用时必须放入初始化回调，极易遗漏；
2. 全局延迟会拉长服务冷启动时间；
3. 不支持运行时组件重连、二次初始化（断线后新请求无等待机制）。

### 4. 适用场景
小型脚本、一次性离线任务；长驻后端服务不推荐，推荐下一节「初始化等待队列」方案。

# 第三种方案：预初始化队列 Pre‑Initialization Queues
> 书本第三种方案：**命令模式 + 等待队列**，对调用方完全透明。
组件未就绪时，把方法调用封装成命令函数存入队列；初始化完成，批量执行队列里全部任务。业务代码完全不需要写任何等待、判断逻辑。

改造后的 db.js：
```js
import { EventEmitter } from 'events'
class DB extends EventEmitter {
  connected = false
  // 存放待执行命令的队列
  commandsQueue = []

  connect () {
    // 模拟网络握手延迟
    setTimeout(() => {
      this.connected = true
      this.emit('connected')
      // 初始化完成，批量执行所有排队命令
      this.commandsQueue.forEach(command => command())
      this.commandsQueue = [] // 清空队列
    }, 500)
  }

  async query (queryString) {
    if (!this.connected) {
      console.log(`Request queued: ${queryString}`)
      // 返回Promise，把调用封装为命令推入队列
      return new Promise((resolve, reject) => {
        const command = () => {
          this.query(queryString).then(resolve, reject)
        }
        this.commandsQueue.push(command)
      })
    }
    console.log(`Query executed: ${queryString}`)
  }
}
export const db = new DB()
```

业务调用代码变得非常干净，**不需要任何 `await once`、不需要包裹初始化回调**：
```js
import { db } from './db.js'

db.connect()

// 组件还没连接成功就直接调用，会自动排队
db.query('SELECT * FROM users')
db.query('SELECT * FROM posts')

setTimeout(async () => {
  // 500ms之后连接已就绪，直接执行
  await db.query('SELECT * FROM logs')
}, 600)
```

## 核心原理拆解
1. **未初始化状态**：调用 `query`，不直接抛错；构造一个闭包命令函数存入 `commandsQueue`，返回 pending 的 Promise 挂起调用方。
2. **初始化完成**：`connect` 的定时器回调触发，遍历队列，依次执行每一条命令；命令内部再次调用真实 `query`，把结果/异常透传给原始 Promise。
3. **已经就绪**：后续调用直接执行业务逻辑，不走队列。

## ✅ 优点
1. **调用方零侵入**：业务完全感知不到内部有异步初始化，写法和普通同步 API 一模一样；
2. 高并发场景下，短时间大量请求不会报错，全部自动排队；
3. 不需要提前收集所有业务入口，新增业务代码直接调用即可，不会漏写；
4. 支持断线重连场景：断开后重新置 `connected=false`，新请求会再次进入队列等待重连。

## ❌ 现存缺陷（原生简易版本）
1. **缺少初始化失败处理**：如果连接失败（网络报错），队列里所有 Promise 会永远 pending，造成请求卡死、内存泄漏。真实项目必须处理失败，把队列全部 reject。
2. **无超时机制**：如果一直初始化不成功，排队请求永久挂起。
3. 只适合简单方法；组件 API 一多，每个异步方法都要写这套队列模板，重复代码多。

## 三种方案横向对比表
|方案|核心思路|业务方是否要写样板代码|支持断线重连|缺点|适用场景|
|---|---|---|---|---|---|
|本地初始化校验|每次调用前 await once|是，每处调用都要判断|可以|大量重复代码|小型脚本，调用点很少|
|延迟启动|全部业务逻辑放在初始化完成之后|是，业务入口要包裹|不支持，重连无等待|容易漏写调用，拖慢启动|一次性离线脚本|
|预初始化队列（命令队列）|组件内部缓存待执行调用，就绪自动放行|**不需要**|支持|要额外处理失败、超时|Node常驻服务（数据库/MQ客户端首选）|

## 拓展：无法修改第三方组件源码怎么办
如果是外部 npm 包，不能修改源码，可以用**代理模式（Proxy）**，在外层包装一层代理对象拦截所有方法，实现相同排队逻辑，不侵入原始组件代码。
