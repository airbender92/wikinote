# 🚨 项目高风险代码分析报告

根据对项目源代码的全面审查，以下按严重程度列出高风险代码位置及原因：

---

## 🔴 严重级别（可能导致崩溃、数据丢失、安全漏洞）

### 1. 401 处理中的 `isHandlingUnauthorized` 状态变量永不重置

**文件**：`src/axios/service.ts` — `handleUnauthorized()` 函数

```typescript
let isHandlingUnauthorized = false  // 模块级全局变量

export const handleUnauthorized = (url?: string) => {
  if (isHandlingUnauthorized) {
    return true  // 🚨 设置后永远返回 true，永远不会再执行真正的处理逻辑
  }
  isHandlingUnauthorized = true
  // ...执行清理和跳转...
}
```

**风险**：
- `isHandlingUnauthorized` 被设为 `true` 后**从未被重置为 `false`**
- 第一次 401 正常处理；**之后所有 401 请求都直接 return true，不会执行任何跳转**
- 如果第一次 401 的跳转没有成功（比如 `window.location.href = ...` 被浏览器拦截），后续所有 401 都无法触发跳转，用户被困在空白页

---

### 2. 响应拦截器调用 `handleUnauthorized` 后未阻止后续拦截器继续执行

**文件**：`src/axios/service.ts` 第72-73行

```typescript
axiosInstance.interceptors.response.use(
  (res: AxiosResponse) => {
    // ...syncRefreshToken...
    if (isUnauthorizedResponse(res)) {
      handleUnauthorized(url)  // 🚨 调用了但没 return 或 reject
    }
    // 继续执行到 defaultResponseInterceptors
    return res
  },
```

**风险**：
- 第一层响应拦截器检测到 401，调用了 `handleUnauthorized()` 触发跳转
- 但**函数未返回 Promise.reject**，继续执行 `defaultResponseInterceptors`
- `defaultResponseInterceptors` 在 `config.ts` 中会再次检测 `isUnauthorizedResponse` → `config.ts` 第42行又会 `return Promise.reject`
- **重复处理同一 401**，`handleUnauthorized` 在成功（success）和失败（error）两个拦截器路径中可能都被调用

---

### 3. 路由守卫中的 `ensureUserInfo()` 循环调用风险

**文件**：`src/main.ts` 第44行 + `src/permission.ts` 第36行

```typescript
// main.ts: 启动时调用
await userStore.ensureUserInfo(true).catch(() => {})

// permission.ts: 路由守卫中再次调用
const hasRemoteSession = !hasLocalUserInfo && !shouldSkipRedirect 
  ? await userStore.ensureUserInfo() : false
```

**风险**：
- `ensureUserInfo` 内部有 `ensureUserInfoPromise` 缓存（单例）：
  ```typescript
  let ensureUserInfoPromise: Promise<boolean> | undefined
  ```
- 如果 `ensureUserInfo()` 返回 `false`（后端无登录态），路由守卫仍然会走到 `else` 分支跳转 `/login`
- 但 `ensureUserInfo` 的 promise 缓存（单例模式）没有考虑竞态——`main.ts` 的 `.catch(() => {})` 会吞掉错误，但 promise 实例仍然存在，后续守卫中再次调用会复用同一个已 settled 的 promise，可能拿到过期的结果

---

### 4. 开发环境变量加载使用 `argv[3]` 而非 `ConfigEnv.mode`

**文件**：`vite.config.ts` 第28-31行

```typescript
export default ({ command, mode }: ConfigEnv): UserConfig => {
  let env = {} as any
  const isBuild = command === 'build'
  if (!isBuild) {
    // 🚨 开发模式手动解析 process.argv
    env = loadEnv(process.argv[3] === '--mode' ? process.argv[4] : process.argv[3], root)
  } else {
    env = loadEnv(mode, root)  // 构建模式正常使用 ConfigEnv.mode
  }
```

**风险**：
- 开发模式**忽略**了 Vite 框架传入的 `ConfigEnv.mode`，而是手动解析 `process.argv`
- 如果启动命令是 `pnpm vite --mode dev`，`argv[3] = 'dev'` OK
- 但如果通过其他方式启动（如 IDE 配置的 `vite` 命令不带 `--mode` 参数），`argv[3]` 可能是 `undefined`，`loadEnv(undefined, root)` **会加载 `.env` 文件但不加载 `.env.dev`**
- 注释中也特别写了 `process.argv[3]`，说明这是故意为之的"hack"，但对后来者极度不透明

## 🟠 高风险（可能导致功能异常、数据不一致）

### 5. `resetAllStores` 暴力遍历所有 Pinia Store

**文件**：`src/axios/service.ts` 第62-64行

```typescript
export const resetAllStores = () => {
  ;(store as any)._s.forEach((piniaStore: { $reset?: () => void }) => {
    piniaStore.$reset?.()  // 🚨 暴力调用所有 store 的 $reset
  })
}
```

**风险**：
- 遍历所有 pinia store 并调用 `$reset()`，包括**没有定义 `$reset` 方法的 store**（那些使用 setup 语法 `defineStore('xxx', () => { ... })` 的 store 没有 `$reset` 方法）
- 大部分 store 用的是 options API 定义（有 `$reset`），但如果有任何 store 是 setup 模式，会静默跳过，导致**该 store 不会被重置**
- 紧接着 `window.localStorage.clear()` 和 `window.sessionStorage.clear()` 会清除所有持久化数据，如果其他应用在同一个域下共享 localStorage，会造成数据丢失

---

### 6. `abortControllerMap` 在 Mock 模式下的 key 别名逻辑

**文件**：`src/axios/service.ts` 第88-93行

```typescript
axiosInstance.interceptors.request.use((res: InternalAxiosRequestConfig) => {
  const controller = new AbortController()
  const url = res.url || ''
  res.signal = controller.signal
  abortControllerMap.set(
    import.meta.env.VITE_USE_MOCK === 'true' ? url.replace('/mock', '') : url,
    // 🚨 Mock 模式下把 /mock 去掉作为 key
    controller
  )
```

**风险**：
- 仅在存储 key 时加了一次 `replace('/mock', '')`，但在 `cancelRequest` 和 `deleteAbortController` 中**没有对应的反向处理**
- 删除时 key 是原始 URL（带 `/mock`），但存储时 key 是不带 `/mock` 的 → **永远匹配不上**，Map 内存泄漏

---

### 7. 路由冲突：`fullscreen` 路径与动态路由路径未隔离

**文件**：`src/router/index.ts` 第82-95行

```typescript
// 在 constantRouterMap 中定义的
{
  path: '/fullscreen/graphView/:commandProcessId?',
  name: 'GraphViewFullscreen',
  // ...
},
{
  path: '/fullscreen/masterControl/:commandProcessId?',
  name: 'MasterControlFullscreen',
  // ...
}
```

**风险**：
- 这些全屏路由在动态路由模块中也可能有类似的路径（`drillCommander.ts` 中有 `/drillCommander/commandProcess/graphView/..`）
- 如果动态路由添加后与 `constantRouterMap` 中的路由产生路径重叠，vue-router 的匹配优先级可能导致**渲染了错误的组件**
- 特别是 `/:path(.*)*` 404 兜底是在动态路由生成时才追加到 `addRouters` 中的

### 8. 登录页 `redirect` 参数解码逻辑不安全

**文件**：`src/permission.ts` 第7-22行

```typescript
const getRouteGuardRedirectPath = (from, to) => {
  const fallbackPath = to.path === '/' ? '/home' : to.path
  const redirectPath =
    from.path === '/login' && typeof from.query.redirect === 'string'
      ? decodeURIComponent(from.query.redirect)
      : ''
```

**风险**：
- `decodeURIComponent` 可能抛出 `URIError`（Malformed URI），且**未被 try/catch 包裹**
- 如果用户在 URL 中手动构造 `#/login?redirect=%E0%A4%A`（不完整 UTF-8），整个路由守卫会抛异常
- 没有验证 `redirectPath` 是否是合法的站内路径，允许传入外部 URL 导致开放重定向

### 9. WebSocket 重连的 `maxAttempts: Infinity` 导致无限重连

**文件**：`src/views/DrillCommander/CommandProcess/components/GraphRel/ws.vue` + `src/components/ExecutionViewer/useSwitchRunViewSocket.ts`

```typescript
reconnect: {
  enabled: true,
  maxAttempts: Infinity,  // 🚨 无限重连
  baseDelayMs: 1000,
  maxDelayMs: 10000,
}
```

**风险**：
- `maxAttempts = Infinity` + 指数退避（最大10s）+ 心跳每30s发一次
- 如果后端 WebSocket 服务挂了且一直不恢复，前端会**永远重连**，每秒 → 2s → 4s → 8s → 10s → 10s…
- `useWebSocket` hook 只在组件 `onBeforeUnmount` 时清理，如果组件一直挂载中，后台会永远重连
- 心跳是 `setInterval`，如果页面处于**后台标签页**（浏览器会节流定时器），心跳可能不准时，导致连接被误判断开

---

### 10. `normalizeStoredUserInfo` 过滤数值 key 导致字段丢失

**文件**：`src/store/modules/user.ts` 第90-92行

```typescript
const normalizedUserInfo = Object.fromEntries(
  Object.entries(userInfo as Record<string, unknown>).filter(
    ([key]) => !NUMERIC_KEY_REGEXP.test(key)  // 🚨 过滤掉所有数值 key
  )
)
```

**风险**：
- `NUMERIC_KEY_REGEXP = /^\d+$/`，会过滤掉所有全数字 key
- 如果后端返回的用户信息中有数字 key 的字段（如 `0`, `1` 这种数组残留或用数字做 key 的对象），这些数据会被**静默丢弃**
- `permissions` 字段虽然通过 `normalizePermissions` 单独处理了，但其他数字 key 字段都会丢失

## 🟡 中风险（潜在逻辑缺陷、边界条件）

### 11. `syncRefreshToken` 在响应成功和失败的拦截器中被调用了两次

**文件**：`src/axios/service.ts` 第68行 + 第100行

```typescript
// 响应成功拦截器
(res) => {
  syncRefreshToken(res)    // 第1次
  // ...
}

// 响应失败拦截器
(error) => {
  syncRefreshToken(error.response)  // 第2次
  // ...
}
```

业务逻辑上没错（成功和失败都想刷新 token），但要注意：**如果请求成功但业务 code ≠ 200，会走 `defaultResponseInterceptors` 的 `Promise.reject`，此时两个路径都会触发 token 刷新**（但好在是幂等操作）。

---

### 12. `ensureUserInfoPromise` 单例没有超时机制

**文件**：`src/store/modules/user.ts`

```typescript
if (!ensureUserInfoPromise) {
  ensureUserInfoPromise = getCurrentUserInfoApi()
    .then(...)
    .finally(() => { ensureUserInfoPromise = undefined })
}
```

- 如果 `getCurrentUserInfoApi()` 请求**卡住不返回**（网络问题），`ensureUserInfoPromise` 永远不会被重置
- 所有后续需要用户信息的操作都会**永远等待这个 pending 的 promise**
- 建议增加超时机制或请求取消

---

### 13. `service.ts` 的 `cancelAllRequest` 使用了模块级变量

`abortControllerMap` 是模块级变量，但 `service.cancelRequest(url)` 被 export 后可以被任意地方调用。多个组件同时请求同一个 url 时，后一个请求的 `AbortController` 会覆盖前一个，导致前一个请求无法被正确取消。

---

### 14. `vite.config.ts` 中 API 代理目标硬编码

```typescript
proxy: {
  [`^${apiProxyPath}(?!/mock)`]: {
    target: 'http://10.1.130.93:8080/',  // 🚨 硬编码 IP
  },
  '^/ws': {
    target: 'http://10.1.130.93:8080/',  // 🚨 同样的硬编码
  }
}
```

- 代理目标写死在 `vite.config.ts` 中，没有通过环境变量控制
- 不同开发者需要各自修改这里的 IP，容易互相覆盖
- 测试环境和生产环境的 Nginx 代理目标也是硬编码

## 核心高危总结

| 优先级 | 问题 | 文件 | 后果 |
|--------|------|------|------|
| 🔴 P0 | `isHandlingUnauthorized` 永不重置 | `src/axios/service.ts` | 第二次 401 后完全无法跳转登录页 |
| 🔴 P0 | `handleUnauthorized` 在 success 拦截器中不阻止后续执行 | `src/axios/service.ts` | 401 后仍执行业务解包逻辑 |
| 🔴 P1 | 开发模式 env 加载用 `argv[3]` 而非 `ConfigEnv.mode` | `vite.config.ts` | 特定启动方式下环境变量错乱 |
| 🔴 P1 | `abortControllerMap` Mock key 别名不一致 | `src/axios/service.ts` | 请求取消功能在 Mock 模式下失效 |
| 🟠 P2 | `resetAllStores` 暴力遍历 + 清空整个 localStorage | `src/axios/service.ts` | 同域下其他应用数据丢失 |
| 🟠 P2 | WebSocket `maxAttempts: Infinity` | `ws.vue` / `useSwitchRunViewSocket.ts` | 后端挂掉时前端无限重连 |
| 🟠 P2 | `ensureUserInfoPromise` 单例无超时 | `src/store/modules/user.ts` | 请求卡住后所有操作永远等待 |
| 🟠 P2 | `decodeURIComponent` 无 try/catch | `src/permission.ts` | 畸形 URL 导致路由守卫崩溃 |
