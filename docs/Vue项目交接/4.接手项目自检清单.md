## 🟥 一、启动与构建阶段（必踩坑区）

### □ 1.1 开发环境变量检查

| 检查项 | 期望值 | 当前值（以仓库为准） |
|--------|--------|-------------------|
| `VITE_API_BASE_PATH` | `/dr/front/api` | dev=`/dr/front/api` / test=**空** / pro=`/dr/front/api` |
| `VITE_WS_BASE_PATH` | `/ws` 或 `/dr/ws` | dev=`/ws` / test=`/ws` / pro=`/dr/ws` |
| `VITE_BASE_PATH` | `/` 或 `/dr/` | dev=无 / test=无 / **pro=`/dr/`** |
| `VITE_USE_MOCK` | 开发开启 | dev=true / test=false / pro=true |
| `VITE_USE_PERMISSION` | 开发关闭 | dev=false / test=true / pro=true |
| `VITE_USE_LEGACY` | pro开启 | dev=false / test=false / pro=true |

> **🔥 最高频踩坑 #1**：test 环境的 `VITE_API_BASE_PATH` 为**空字符串**，这意味着本地构建 `pnpm build:test` 后的产物中 API 前缀为空。接手后**必须先与后端/运维确认** test 环境是否依赖网关重写路径，否则所有接口请求会发到同域根路径，导致 404。

### □ 1.2 首次启动验证
- [ ] 执行 `pnpm i`（注意 Node >= 18，pnpm >= 8.1）
- [ ] 执行 `pnpm dev`（确认能启动且无 Vite 报错）
- [ ] 打开 `http://localhost:4000` 确认页面渲染（Hash 路由自动带 `#/`）
- [ ] 确认 API 代理生效（打开浏览器 DevTools Network，看请求发往 `/dr/front/api/...`）
- [ ] 确认 Mock 数据正常返回（VITE_USE_MOCK=true 时）

> **🔥 高频踩坑 #2**：`vite.config.ts` 第28-31行，开发模式的环境变量加载采用**解析 `process.argv[3]`** 而非 Vite 传入的 `ConfigEnv.mode`。如果你用 `npx vite --mode dev` 或 IDE 带参数启动，`argv[3]` 的值可能不同，导致环境文件加载错误。**建议改用 `pnpm dev` 脚本启动**。

## 🟧 二、权限与路由阶段（逻辑坑区）

### □ 2.1 动态路由机制确认
- [ ] 确认 `appStore.getDynamicRouter` 和 `appStore.getServerDynamicRouter` 的配置值
- [ ] 确认 `VITE_USE_PERMISSION` 环境变量是否对齐期望

| 权限模式 | 触发条件 | 行为 |
|---------|---------|------|
| `static` | `dynamicRouter=false` | 直接加载所有动态路由模块 |
| `frontEnd` | `dynamicRouter=true` + `serverDynamicRouter=false` | 按 `userStore.getPermissions` 前端过滤 |
| `server` | `dynamicRouter=true` + `serverDynamicRouter=true` | 按后端返回的 `roleRouters` 动态生成 |

> **🔥 高频踩坑 #3**：`dev` 环境 `VITE_USE_PERMISSION=false`，所以权限控制**完全关闭**，所有菜单对所有用户可见。但 `test` / `pro` 环境开启后，如果后端返回的 `roleIds` 权限码与路由 `meta.permission` 不匹配，**整个菜单和页面都会消失**。建议先在 dev 确认完整路由，再切 test 排查权限。

### □ 2.2 路由守卫流程验证
- [ ] 无登录态访问首页 → 应跳转到 `#/login?redirect=/home`
- [ ] 登录后 → 应正确跳转到 `#/home`
- [ ] 退出登录后 → 应重置所有状态并跳转到 `#/login`
- [ ] 刷新页面 → 应保持登录态（pinia 持久化恢复）

> **🔥 高频踩坑 #4**：`src/main.ts` 第44行，启动时 `userStore.ensureUserInfo(true)` 会调后端接口验证登录态。如果**后端没启动或接口地址不对**，这个 `.catch(() => {})` 会静默吞掉错误，然后路由守卫中再次调用 `ensureUserInfo()` 复用同一个失败的 Promise，导致误判「有用户信息」或「无用户信息」→ **一直卡在空白页或无限重定向**。

### □ 2.3 路由冲突排查
- [ ] 打开 `#/fullscreen/graphView/xxx` → 确认渲染全屏组件
- [ ] 打开 `#/fullscreen/masterControl/xxx` → 同上
- [ ] 确认这些全屏路由与 `drillCommander` 模块中的路由**没有路径重叠**

> **🔥 高频踩坑 #5**：`constantRouterMap` 中定义的全屏路由和动态路由模块中的嵌套路由，如果 url path 有相似模式（比如都包含 `graphView`），Vue Router 的匹配优先级可能导致渲染错误的组件。

## 🟨 三、接口与请求阶段（网络坑区）

### □ 3.1 API 基础路径对齐
- [ ] 打开任何页面 → 确认发起的 API 请求 URL 前缀正确
- [ ] 检查 `VITE_WS_BASE_PATH` 在三个环境的值（dev=`/ws`, test=`/ws`, pro=`/dr/ws`）

> **🔥 高频踩坑 #6**：pro 环境的 WebSocket 路径是 `/dr/ws` 而非 `/ws`，而 Nginx 中全部都是用 `location ^~ /ws` 代理。如果 prod 实际部署时没有对应的 `/dr/ws` → `/ws` 重写规则，**WebSocket 连接会失败**。排查时检查 Nginx 的 proxy_pass 路径是否需要加上 rewrite。

### □ 3.2 Mock 模式验证
- [ ] VITE_USE_MOCK=true 时确认所有接口走 Mock
- [ ] VITE_USE_MOCK=false 时确认所有接口走真实后端
- [ ] 特别注意 `VITE_ENABLE_BUILD_MOCK` 控制生产构建中是否包含 Mock 服务

### □ 3.3 Token 续签流程验证
- [ ] 登录后看接口响应头是否包含 `x-refresh-token`
- [ ] 确认 `syncRefreshToken` 在响应成功/失败拦截器中都正常执行
- [ ] 模拟 401 返回 → 确认触发 `handleUnauthorized` 并跳转登录页

> **🔥 高频踩坑 #7**：`src/axios/service.ts` 的 `isHandlingUnauthorized` 状态变量**设为 true 后永不重置**。这意味着第一次 401 处理后，**后续的所有 401 请求都不会再触发跳转**。如果第一次跳转被浏览器拦截（弹窗拦截），用户会困在当前页无法登录。可在控制台手动 `isHandlingUnauthorized = false` 临时解决。

## 🟫 四、WebSocket 阶段（实时坑区）

### □ 4.1 指挥流程图 WebSocket 验证
- [ ] 进入指挥流程页面 → 确认 WebSocket 连接 `/ws/command/flow/view/{id}` 建立
- [ ] 确认心跳包每30s发送
- [ ] 后端重启 → 确认前端自动重连（指数退避 1s→2s→4s→...→10s）
- [ ] 网络断开再恢复（F12 Network Offline）→ 确认自动重连

### □ 4.2 切换运行视图 WebSocket 验证
- [ ] 进入切换运行页面 → 确认 WebSocket 连接 `/ws/switch/run/view/{id}` 建立
- [ ] 确认数据推送格式为 `{ type: 'SWITCH_RUN_VIEW_SNAPSHOT', data: {...} }`

> **🔥 高频踩坑 #8**：两个 WebSocket 的 `maxAttempts` 都设为 `Infinity`，且页面没有显式的「断开连接」按钮。如果页面被放在后台标签页（浏览器节流定时器），**心跳不准时可能导致 WebSocket 被服务端断开**，然后会无限重连。需要确认服务端是否会大量记录这种"连接-断开"日志。**建议在开发环境下暂时设置 `maxAttempts: 10` 或更小值进行验证**。

### □ 4.3 Token 查询参数确认
- [ ] 检查 `VITE_WS_TOKEN_QUERY_KEY` 环境变量是否配置
- [ ] 确认 WebSocket URL 中携带了正确的 token 参数

## 🟩 五、Nginx 部署阶段（发布坑区）

### □ 5.1 三个环境 Nginx 配置差异检查
- [ ] dev: 端口 8081，API 前缀 `/dr/front/api/`，部署目录 `/var/www/html/dev`
- [ ] test: 端口 8082，API 前缀 `/front/api/`，部署目录 `/var/www/html/test`
- [ ] prod: 端口 8083，API 前缀 `/dr/front/api/`，部署目录 `/var/www/html/prod`

> **🔥 高频踩坑 #9**：test 环境的 Nginx API 代理路径是 `/front/api/` 而非 `/dr/front/api/`，而 dev/pro 都是 `/dr/...`。同时 `VITE_API_BASE_PATH` test 环境是**空**。这意味着 test 部署时，前端请求发到 `/front/api/xxx`，Nginx 要匹配到 `location ^~ /front/api/` 才能正确代理。如果运维改了路径但忘了同步 `nginx/conf.d/test.conf`，**接口全挂**。

### □ 5.2 Hash 路由兜底确认
- [ ] 确认 `location / { try_files $uri $uri/ /index.html; }` 存在（虽然 Hash 路由不需要，但保持兼容）
- [ ] 确认静态资源缓存配置 `expires 1y` + `Cache-Control: public, immutable`
- [ ] 确认 `VITE_BASE_PATH` = `/dr/` 时，`index.html` 中资源路径正确

### □ 5.3 WebSocket Nginx 代理确认
- [ ] 确认 `proxy_read_timeout 86400s`（24h，超长 WebSocket 连接）
- [ ] 确认 `proxy_set_header Upgrade $http_upgrade` 和 `Connection "upgrade"` 存在

### □ 6.1 构建参数确认
- [ ] 确认 Jenkins 参数 `BUILD_ENV` 对应正确环境文件

### □ 6.2 Node/pnpm 版本差异排查

- [ ] Docker dev 镜像: **Node 18** + **pnpm 8.1.0**
- [ ] 本机推荐: Node >= 18, pnpm 9.x

> **🔥 高频踩坑 #10**：Jenkins 用 Node 24 + pnpm 9，但 `Dockerfile.dev` 是 Node 18 + pnpm 8。如果 `package.json` 中 `engines` 限制了 `"pnpm": ">=8.1.0"`，但某些 pnpm 9 行为或 lockfile 格式与 pnpm 8 不兼容，可能出现"本地能跑、CI 报错"的问题。**建议统一本地和 CI 的版本**。

## 🚑 紧急故障排查速查

| 症状 | 可能原因 | 快速修复路径 |
|------|---------|------------|
| 白屏/404，URL 是 `#/home` | 路由未注册 / 动态路由未生成 | 检查 `permission.ts` → `isAddRouters` |
| API 请求发到根路径 | `VITE_API_BASE_PATH` 为空 | 检查 `.env.{env}` 文件 |
| 页面一直 loading，不走路由 | `ensureUserInfo` 卡住 | F12 看 `/auth/getCurrentUserInfo` 接口 |
| 菜单和页面消失 | 权限过滤掉了 | 设置 `VITE_USE_PERMISSION=false` 临时验证 |
| WS 连接失败 | 路径不对或 Nginx 没配 Upgrad | 检查 `VITE_WS_BASE_PATH` + Nginx |
| 第二次 401 后不跳转登录 | `isHandlingUnauthorized` 永不重置 | 控制台手动设为 false 或刷新页面 |
| 登录后无限跳转 | 路由守卫中 `ensureUserInfo` 返回 false | 检查 `/auth/getCurrentUserInfo` 接口返回结构 |
| 构建产物中资源路径错误 | `VITE_BASE_PATH` 配置不正确 | 构建后检查 `index.html` 中资源路径前缀 |
