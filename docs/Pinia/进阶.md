## 组合式 API 中的高级模式：跨 Store 调用、工厂模式、依赖注入、动态注册与 SSR 隔离

Pinia 在组合式 API（Setup Store）中提供了一些高级模式，用于处理复杂场景：跨 Store 通信、非单例 Store、依赖注入、动态注册以及 SSR 中的状态隔离。掌握这些模式能让你的架构更灵活、可测试。

---

### 一、Store 间调用（互相引用）

#### 基本用法
在一个 Store 中可以调用另一个 Store 的 action、读取其 state 或 getter，实现跨模块协作。

```ts
// stores/cart.ts
import { defineStore } from 'pinia'
import { ref } from 'vue'

export const useCartStore = defineStore('cart', () => {
  const items = ref([])
  const total = ref(0)
  
  function addItem(item: any) {
    items.value.push(item)
    total.value += item.price
  }
  
  async function checkout() {
    // 调用 user store 获取当前用户
    const userStore = useUserStore()
    if (!userStore.isLoggedIn) {
      throw new Error('请先登录')
    }
    await api.checkout({ userId: userStore.userId, items: items.value })
    items.value = []
    total.value = 0
  }
  
  return { items, total, addItem, checkout }
})

// stores/user.ts
export const useUserStore = defineStore('user', () => {
  const userId = ref(null)
  const isLoggedIn = computed(() => !!userId.value)
  
  function setUser(id: string) {
    userId.value = id
  }
  
  return { userId, isLoggedIn, setUser }
})
```

#### 注意点
- **直接调用**：在 Setup Store 中，直接调用 `useOtherStore()` 即可，因为函数会在当前 `setup` 上下文中执行。
- **循环依赖**：如果 Store A 与 Store B 互相调用，可能导致初始化时无限递归或获取到未初始化的状态。

#### 常见坑点 ⚠️

| 坑点 | 说明 | 解决 |
|------|------|------|
| **循环调用导致死循环** | `storeA.action` 调 `storeB.action`，而后者又调回 `storeA` | 避免设计上的循环依赖；可提取公共逻辑到第三个 Store；或使用 `setTimeout` / `nextTick` 打破同步链条 |
| **在 getter 中调用其他 Store 的 action** | getter 应该是纯的，不应有副作用 | 将调用放到 action 中 |
| **跨 Store 订阅导致内存泄漏** | 在 Store A 中订阅 Store B 的变化，但未在 A 销毁时取消 | 使用 `onUnmounted` 或 `effectScope` 管理订阅 |
| **TypeScript 类型循环引用** | 两个 Store 互相导入类型可能造成 TS 错误 | 使用 `import type` 或提取共享类型到单独文件 |

### 二、工厂模式 Store（非单例）

#### 基本用法
默认 Pinia Store 是**单例**的（全局唯一）。但有时需要创建独立的 Store 实例，比如：
- 多个相同类型的组件各自维护独立状态（如表单校验、分页控件）。
- 每个对话（chat session）拥有自己的消息列表。

通过**返回一个函数**而不是直接导出 Store，每次调用该函数会创建一个全新的 Store 实例。

```ts
// stores/createCounter.ts
import { defineStore } from 'pinia'
import { ref, computed } from 'vue'

export function createCounterStore(initialCount = 0) {
  return defineStore(`counter_${Date.now()}_${Math.random()}`, () => {
    const count = ref(initialCount)
    const double = computed(() => count.value * 2)
    function increment() { count.value++ }
    return { count, double, increment }
  })
}
```

#### 使用
```vue
<!-- ComponentA.vue -->
<script setup>
import { createCounterStore } from '@/stores/createCounter'

// 每次调用都生成一个独立 store
const useLocalCounter = createCounterStore(10)
const counter = useLocalCounter()  // 注意：需要调用两次？上面的函数返回 defineStore 的结果，还需要再执行一次获得 store 实例。
</script>
```

更简洁的工厂写法（直接返回 store 实例，而不是 store 构造函数）：
```ts
import { defineStore } from 'pinia'
import { ref } from 'vue'

export function createCounter(initial = 0) {
  const store = defineStore(`counter_${Date.now()}_${Math.random()}`, () => {
    const count = ref(initial)
    function inc() { count.value++ }
    return { count, inc }
  })
  return store()  // 直接返回 store 实例
}
```

```vue
<script setup>
import { createCounter } from '@/stores/createCounter'
const counter = createCounter(5)  // 直接获得实例
</script>
```

#### 常见坑点 ⚠️

| 坑点 | 说明 | 正确做法 |
|------|------|----------|
| **忘记唯一 ID** | 多次调用使用相同 ID 会导致后面的调用返回同一个 store 实例（单例） | 动态生成 ID（如 `Date.now() + Math.random()`） |
| **内存泄漏** | 创建的动态 Store 不会自动销毁，组件卸载后实例仍然存在 | 在组件 `onUnmounted` 中调用 `store.$dispose()` 手动销毁 |
| **SSR 中客户/服务端 ID 不一致** | 动态 ID 在服务端和客户端生成不同，导致 hydration 错误 | 避免在 SSR 中使用工厂 Store，或确保 ID 稳定（如使用 `Symbol()` 并序列化） |
| **TypeScript 类型推断复杂** | 工厂函数返回的 store 实例类型可能丢失 | 显式返回类型：`return store() as ReturnType<typeof defineStore<...>>` |
| **在同一个组件中多次调用工厂生成多个实例** | 每个实例都是独立的，符合预期但需注意性能 | 确保确实需要多个独立实例 |

### 三、依赖注入 Store（可测试性）

#### 基本用法
将外部依赖（如 API 客户端、日志服务、配置对象）作为参数传入 Store，而不是在 Store 内部硬编码。这样做可以方便地替换依赖进行单元测试。

```ts
// stores/userWithDI.ts
import { defineStore } from 'pinia'
import { ref } from 'vue'

// 定义依赖接口
interface UserApi {
  fetchUser: (id: string) => Promise<{ name: string; email: string }>
  updateUser: (id: string, data: any) => Promise<void>
}

export function createUserStore(api: UserApi, defaultUserId = '') {
  return defineStore('user_di', () => {
    const user = ref(null)
    const loading = ref(false)
    
    async function loadUser(id: string = defaultUserId) {
      loading.value = true
      try {
        const data = await api.fetchUser(id)
        user.value = data
      } finally {
        loading.value = false
      }
    }
    
    async function update(data: any) {
      if (!user.value) return
      await api.updateUser(user.value.id, data)
      Object.assign(user.value, data)
    }
    
    return { user, loading, loadUser, update }
  })()
}
```

#### 使用
```vue
<script setup>
import { createUserStore } from '@/stores/userWithDI'
import { realUserApi } from '@/api/user'

const userStore = createUserStore(realUserApi, '123')
await userStore.loadUser()
</script>
```

#### 单元测试
```ts
// 测试中用 mock API
const mockApi = {
  fetchUser: async (id: string) => ({ name: 'Test', email: 'test@example.com' }),
  updateUser: async () => {}
}
const testStore = createUserStore(mockApi)
await testStore.loadUser()
expect(testStore.user.name).toBe('Test')
```

#### 常见坑点 ⚠️

| 坑点 | 说明 | 正确做法 |
|------|------|----------|
| **依赖注入与全局 Pinia 实例冲突** | 注入的依赖可能被 Pinia 插件修改 | 确保依赖是纯对象，不依赖注入上下文 |
| **在 SSR 中依赖注入导致状态泄漏** | 每个请求应创建独立 Store 实例，但依赖可能是单例的 | 同时结合工厂模式，每个请求重新创建 Store 和依赖 |
| **类型复杂** | 依赖接口定义需要手动维护 | 使用 TypeScript 严格定义接口 |
| **与组合式函数（composable）的取舍** | 依赖注入 Store 本质上是高阶函数，也可用 composable 替代 | 如果不需要全局单例且只需局部状态，使用 composable 可能更简单 |

### 四、动态 Store 注册

#### 基本用法
某些场景需要在运行时动态创建 Store（如插件系统、动态模块加载）。可以通过 `useStore` 配合 `store.$id` 动态获取或创建。

```ts
// 动态注册一个 Store
import { useStore } from 'pinia'
import { defineStore } from 'pinia'

const dynamicId = 'dynamic_' + Date.now()
const dynamicStore = defineStore(dynamicId, {
  state: () => ({ data: null })
})

// 注册到 pinia 实例（由 app.use(pinia) 创建）
// defineStore 会自动注册，也可以手动：
// pinia._s.set(dynamicId, dynamicStore(pinia))

// 在组件中动态获取（即使未显式调用 defineStore，只要 id 已注册）
const store = useStore(dynamicId)  // 注意：useStore 接收 store id 作为参数
```

#### 更常用的模式：根据条件获取不同的 Store
```ts
// stores/factory.ts
export function useDynamicStore(storeName: 'user' | 'cart') {
  switch (storeName) {
    case 'user':
      return useUserStore()
    case 'cart':
      return useCartStore()
    default:
      throw new Error('Unknown store')
  }
}
```

> Pinia 官方提供了 `useStore(storeId)` 的签名（需要导入 `useStore` from `pinia`），但它主要用于测试或高阶用法。

#### 常见坑点 ⚠️

| 坑点 | 说明 | 解决 |
|------|------|------|
| **动态 Store 未提前定义** | 使用 `useStore(id)` 时，如果该 id 从未通过 `defineStore` 定义，会抛出错误 | 确保先调用 `defineStore` 注册 |
| **动态 Store 不会自动卸载** | 即使不再需要，也会一直占用内存 | 调用 `store.$dispose()` 并手动从 `pinia._s` 中删除（不推荐，需要谨慎） |
| **TypeScript 类型丢失** | `useStore(id)` 返回的是 `StoreGeneric`，无法知道具体类型 | 使用类型断言：`useStore(id) as ReturnType<typeof useUserStore>` |
| **SSR 中动态 ID 不一致** | 客户端和服务端生成的 ID 不同，导致 hydration 失败 | 避免在 SSR 中动态生成 ID，或使用稳定 ID（如基于路由参数） |

### 五、跨请求状态隔离（SSR）

#### 基本用法
在服务端渲染（SSR）中，**每个请求应当拥有独立的 Pinia 实例和 Store 状态**，避免用户 A 的数据泄漏给用户 B。默认 `createPinia()` 是单例的，需要在每个请求中重新创建。

```ts
// server entry (比如 express + vue ssr)
import { createPinia } from 'pinia'
import { createApp } from 'vue'
import App from './App.vue'

app.use((req, res) => {
  // 每个请求创建一个新的 pinia 实例
  const pinia = createPinia()
  const app = createApp(App)
  app.use(pinia)
  
  // 可以预先获取数据填充 store
  const userStore = useUserStore(pinia)  // 传入 pinia 实例
  await userStore.fetchUser(req.userId)
  
  // 渲染应用...
  const html = await renderToString(app)
  // 将 pinia 状态序列化并注入到 HTML
  const state = JSON.stringify(pinia.state.value)
  // 返回 HTML 和 state
})
```

在客户端，你需要**使用服务端注入的 state 初始化 Pinia**：
```ts
// client entry
import { createPinia } from 'pinia'

const pinia = createPinia()
// 从 window.__INITIAL_STATE__ 恢复状态
if (window.__INITIAL_STATE__) {
  pinia.state.value = JSON.parse(window.__INITIAL_STATE__)
}
app.use(pinia)
```

#### 高级模式：使用 `createPinia` 工厂
```ts
// utils/createServerPinia.ts
import { createPinia, setActivePinia } from 'pinia'

export function createServerPinia() {
  const pinia = createPinia()
  setActivePinia(pinia)  // 设置当前活跃 pinia，使得 useStore 无需显式传入
  return pinia
}
```

#### 常见坑点 ⚠️

| 坑点 | 说明 | 解决 |
|------|------|------|
| **忘记为每个请求创建新 Pinia** | 使用全局单例，导致状态泄漏 | 在请求处理器中调用 `createPinia()` |
| **未正确序列化/反序列化 state** | 客户端 hydration 后状态与服务端不一致 | 确保 `pinia.state.value` 可序列化（不含函数、Symbol 等） |
| **在服务端使用工厂 Store 时未清理** | 动态创建的 Store 会累积，导致内存泄漏 | 每次请求结束后调用 `pinia._s.forEach(store => store.$dispose())` 或使用 `effectScope` |
| **useStore 在服务端找不到 pinia 实例** | 未调用 `setActivePinia(pinia)` 或未传入 pinia 参数 | 显式传入：`useStore(pinia)` 或调用 `setActivePinia` |
| **getActivePinia() 为 null** | 由于异步操作丢失了上下文 | 在异步操作前保存 pinia 实例，或使用 `runWithContext`（Vue 3.3+） |

#### SSR 最佳实践
- 为每个请求创建独立的 Pinia 实例。
- 在请求结束时 `$dispose` 所有 store 或直接丢弃整个 pinia 实例（Node.js 中等待 GC）。
- 使用 `setActivePinia` 简化代码，但注意异步回调中可能丢失；推荐显式传递 pinia 参数。
- 不要在生产 SSR 中使用动态 ID 的工厂 Store，除非你能确保 ID 稳定。

---

### 总结对比

| 模式 | 核心 API | 主要解决场景 | 关键坑点 |
|------|----------|--------------|----------|
| Store 间调用 | `useOtherStore()` | 跨模块通信 | 循环依赖、类型循环 |
| 工厂模式 | 动态 ID + `defineStore` | 非单例、多实例 | ID 唯一性、内存泄漏 |
| 依赖注入 | 高阶函数参数 | 可测试性、解耦 | 与 Pinia 生命周期结合 |
| 动态注册 | `useStore(id)` | 运行时加载、插件系统 | 注册时机、类型丢失 |
| SSR 隔离 | 每请求新建 `createPinia()` | 状态隔离 | 序列化、清理、上下文丢失 |

### 记忆口诀

> **跨 Store 调用防循环，工厂模式 ID 要唯一；**
> **依赖注入好测试，动态注册先定义；**
> **SSR 隔离每请求新建，序列化清理记心间。**

掌握这些高级模式，你就能在复杂项目（大型应用、组件库、SSR 插件）中充分发挥 Pinia 的威力。
