## Pinia 性能优化：七个核心策略详解

随着应用规模增长，Pinia Store 的性能优化变得重要。以下七个策略能有效减少响应式开销、降低内存占用、提升运行时效率。

---

### 一、懒加载 Store（代码分割）

#### 原理
默认 Pinia Store 会在应用启动时全部加载（如果被静态 import）。通过动态 `import()`，可以让 Store 只在需要时才加载对应模块的代码。

#### 实现
```ts
// 路由配置中动态加载 Store
const routes = [
  {
    path: '/user',
    component: () => import('./views/User.vue'),
    // 在组件加载后再动态引入 Store
  }
]

// 在组件内动态使用 Store
<script setup>
import { onMounted } from 'vue'

onMounted(async () => {
  const { useUserStore } = await import('@/stores/user')
  const userStore = useUserStore()
  // 使用 userStore...
})
</script>
```

#### 坑点 ⚠️
- 动态导入后，store 的 `$subscribe` 和 `$onAction` 订阅需要在组件卸载时手动清理。
- 如果多个组件依赖同一个动态 Store，可能重复加载（但 webpack/vite 会自动合并）。
- 在路由守卫中无法直接使用未加载的 Store，需要配合异步守卫。

---

### 二、$patch 批量更新

#### 原理
连续多次直接修改 state（如 `store.count++`、`store.name = 'x'`）会触发多次响应式更新和视图重渲染。使用 `$patch` 将多次修改合并为一次，减少性能开销。

#### 对比
```ts
// ❌ 低效：三次更新
store.count++
store.name = 'Bob'
store.age = 30

// ✅ 高效：一次更新
store.$patch({
  count: store.count + 1,
  name: 'Bob',
  age: 30
})

// ✅ 更复杂逻辑：$patch 函数形式
store.$patch((state) => {
  state.count++
  state.name = 'Bob'
  state.list.push(newItem)
})
```

#### 坑点 ⚠️
- `$patch` 对象形式会**替换**嵌套对象，而不是合并。例如 `$patch({ user: { name: 'Bob' } })` 会删除原有的 `user.age`。
- 函数形式中不要进行异步操作，否则 patch 事件不完整。
- 对于少量字段（1-2个），直接修改的性能差异可忽略，不必过度优化。

---

### 三、避免不必要的订阅（及时取消）

#### 原理
`$subscribe` 和 `$onAction` 默认会绑定到当前组件，组件卸载时会自动取消。但如果设置了 `{ detached: true }` 或手动注册了全局监听，必须手动清理，否则会造成内存泄漏和多余回调。

#### 实现
```ts
// 组件内使用，默认自动清理（无需手动）
const unsubscribe = store.$subscribe((mutation, state) => {
  // ... 
})
// 组件卸载时自动调用 unsubscribe，但若手动调用也可

// 全局持久订阅（组件外）
const stop = store.$subscribe((mutation, state) => {
  localStorage.setItem('state', JSON.stringify(state))
}, { detached: true })  // detached 为 true 时不会自动清理

// 在合适时机手动清理（如 app 销毁前）
stop()
```

#### 坑点 ⚠️
- 忘记清理 `detached: true` 的订阅会导致回调一直执行，即使 store 已被 `$dispose`。
- 在 `setup` 函数中直接使用 `store.$subscribe` 而没保存返回函数，无法手动取消（但依赖自动清理也可以）。
- 多次订阅同一个 store 会累积，每个回调都会执行。

---

### 四、使用 shallowRef 处理大数据

#### 原理
`shallowRef` 只跟踪 `.value` 的变化，不对其内部属性进行深层响应式转换。对于大型数组或对象（如列表数据、日志记录），使用 `shallowRef` 可显著减少响应式代理的开销。

#### 使用场景
- 数据量很大（数千条以上），且不会频繁修改内部属性。
- 整体替换数据（如重新请求列表时直接赋值 `store.list = newArray`）。
- 展示只读数据，不需要深度响应式。

#### 实现
```ts
// Setup Store 中
import { shallowRef } from 'vue'

const useLargeDataStore = defineStore('largeData', () => {
  const items = shallowRef([])  // 只有 .value 变化时才触发更新
  
  function setData(newItems) {
    items.value = newItems  // ✅ 触发更新
  }
  
  function updateItem(index, newValue) {
    // ❌ 不会触发更新（因为内部属性改变，ref 未变）
    items.value[index] = newValue
    // ✅ 需要整体替换或使用 triggerRef
    items.value = [...items.value]
    items.value[index] = newValue
  }
  
  return { items, setData, updateItem }
})
```

#### 坑点 ⚠️
- `shallowRef` 的内部属性变更不会触发响应式更新，容易遗漏。
- 与 `storeToRefs` 配合时，仍会得到 `shallowRef`，行为一致。
- 在模板中遍历 `shallowRef` 数组时，若只修改数组元素而不改引用，视图不会更新。

---

### 五、合理拆分 Store（按业务域垂直拆分）

#### 原理
避免创建“上帝 Store”（如 `useAppStore` 包含用户、主题、购物车、通知等所有状态）。按业务模块拆分为多个独立 Store，每个 Store 只管理自己的状态，减少不必要的响应式依赖和变更范围。

#### 对比
```ts
// ❌ 坏实践：一个巨大的 Store
const useAppStore = defineStore('app', {
  state: () => ({
    user: {},
    theme: 'light',
    cart: [],
    notifications: []
  })
})

// ✅ 好实践：垂直拆分
const useUserStore = defineStore('user', ...)
const useThemeStore = defineStore('theme', ...)
const useCartStore = defineStore('cart', ...)
const useNotificationStore = defineStore('notification', ...)
```

#### 优点
- 每个 Store 的响应式依赖更清晰，修改一个模块不会引起其他模块的重新计算。
- 更容易进行代码分割和懒加载。
- 提高可维护性和测试性。

#### 坑点 ⚠️
- 注意 Store 之间的循环依赖，可通过提取公共逻辑或使用 `watch` 解耦。
- 不要过度拆分（如每个字段一个 Store），按业务域（用户、商品、订单）划分即可。

---

### 六、store.$state 整体替换

#### 原理
当你需要完全重置或替换整个 state 时，直接赋值 `store.$state = newState` 会丢失响应式（因为 `$state` 是只读代理）。正确方式是使用 `Object.assign` 合并属性，或者用 `$patch` 批量更新。

#### 正确用法
```ts
// ✅ 方式1：Object.assign 保留响应式
const newState = { count: 10, name: 'new' }
Object.assign(store.$state, newState)

// ✅ 方式2：$patch 批量更新
store.$patch(newState)

// ❌ 错误：直接替换 $state 会破坏响应式
store.$state = newState  // 虽然某些情况可行，但官方不推荐
```

#### 场景
- 从服务端拉取完整数据替换本地 state。
- 用户登出后重置所有状态（但 `$reset` 更适合 Options Store）。
- 实现撤销/重做功能时恢复历史快照。

#### 坑点 ⚠️
- `Object.assign` 是浅拷贝，如果 state 中有嵌套对象，只会替换顶层引用，内层对象可能与旧对象共享。
- 对于深层结构，需要递归合并或使用 `lodash.merge`。
- 使用 `$patch` 函数形式可以更安全地处理深层替换。

### 七、其他性能建议

| 建议 | 说明 |
|------|------|
| **避免在 getter 中返回新对象** | 每次访问 getter 都会创建新对象（如 `return [...state.list]`），破坏缓存。尽量返回计算后的派生值，或使用 `computed` 的缓存特性。 |
| **使用 computed 缓存计算结果** | 复杂的派生逻辑放在 getter 中，避免在模板或方法中重复计算。 |
| **合理使用 $onAction 的 after/onError** | 不要在 after 回调中执行重计算或深拷贝，保持轻量。 |
| **对大型数组使用 `shallowReactive`** | 比 `shallowRef` 更适合对象集合，但原理类似。 |
| **使用 Pinia devtools 分析性能** | 查看 mutation 频率、getter 重计算次数，定位瓶颈。 |

---

## 性能优化总结表

| 策略 | 核心 API | 主要收益 | 适用场景 |
|------|----------|----------|----------|
| 懒加载 Store | `import()` | 减少首屏 JS 体积 | 大型模块、非首屏功能 |
| $patch 批量更新 | `store.$patch` | 减少响应式触发次数 | 同时修改多个字段 |
| 及时取消订阅 | 返回的 `unsubscribe` | 防止内存泄漏 | 全局监听、detached 订阅 |
| shallowRef | `shallowRef` | 降低深度响应式开销 | 大型数组/对象、只读列表 |
| 合理拆分 Store | 多 Store 实例 | 减少依赖链，提高可维护性 | 复杂业务系统 |
| $state 整体替换 | `Object.assign` | 快速重置/替换 | 批量拉取数据、撤销重做 |

---

### 记忆口诀

> **懒加载减体积，批量 patch 少更新；**
> **订阅用完要取消，大数 shallow 省性能；**
> **拆分 store 防膨胀，整体替换 assign 行。**

遵循这些优化策略，你的 Pinia 应用将保持流畅高效。但切记：**不要过早优化**，优先保证代码清晰，遇到性能问题再针对性地应用上述技巧。
