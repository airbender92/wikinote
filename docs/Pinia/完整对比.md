## Pinia Store 定义：Options Store vs Setup Store (完整对比与坑点)

Pinia 提供两种定义 Store 的方式：**Options Store** 和 **Setup Store**。前者与 Vuex 风格类似，后者完全拥抱组合式 API。官方**推荐 Setup Store**，但在特定场景（如快速迁移）下 Options Store 也有价值。

---

### 一、Options Store（选项式）

#### 1. 定义方式
```ts
import { defineStore } from 'pinia'

const useCounterStore = defineStore('counter', {
  state: () => ({ count: 0, name: 'pinia' }),
  
  getters: {
    doubleCount: (state) => state.count * 2,
    // 使用 this 访问其他 getter/state 必须用普通函数
    greeting(): string {
      return `Hello, ${this.name}! Count is ${this.count}`
    }
  },
  
  actions: {
    increment() {
      this.count++
    },
    async asyncIncrement() {
      await delay(1000)
      this.count++
    }
  }
})
```

#### 2. 核心知识点
- **`state`**：必须是一个**返回对象的函数**，确保 SSR 和多个实例之间的隔离。
- **`getters`**：类似 Vue 的计算属性，有缓存。第一个参数是 `state`，可以使用 `this` 访问整个 store（此时不能使用箭头函数）。
- **`actions`**：可以是同步或异步方法，通过 `this` 直接修改 state、调用其他 action。
- **优点**：结构清晰，类似 Vuex，迁移成本低。
- **缺点**：类型推断稍弱（需要手动标注），逻辑复用不便。

#### 3. 常见坑点 ⚠️

| 坑点 | 错误示例 | 后果 | 正确做法 |
|------|----------|------|----------|
| **state 不是函数** | `state: { count: 0 }` | SSR 时状态污染，热更新异常 | `state: () => ({ count: 0 })` |
| **getter 中使用箭头函数导致不能访问 this** | `greeting: (state) => this.name` | `this` 为 undefined，报错 | 使用普通函数：`greeting(state) { return this.name }` |
| **解构 store 丢失响应式** | `const { count, doubleCount } = useStore()` | 变成普通值，不再更新 | 使用 `storeToRefs` 解构 |
| **在 getter 中修改 state** | `doubleCount(state) { state.count++ }` | 副作用，调试困难 | getter 只读，修改放到 action |
| **action 中使用箭头函数导致 this 丢失** | `increment: () => { this.count++ }` | `this` 指向 undefined | 使用普通函数 |
| **异步 action 中未正确处理 this 上下文** | `setTimeout(function() { this.count++ }, 100)` | 回调中 `this` 丢失 | 使用箭头函数或提前保存 `const store = this` |

### 二、Setup Store（组合式）

#### 1. 定义方式
```ts
import { defineStore } from 'pinia'
import { ref, computed } from 'vue'

const useCounterStore = defineStore('counter', () => {
  // state
  const count = ref(0)
  const name = ref('pinia')
  
  // getters
  const doubleCount = computed(() => count.value * 2)
  const greeting = computed(() => `Hello, ${name.value}! Count is ${count.value}`)
  
  // actions
  function increment() {
    count.value++
  }
  
  async function asyncIncrement() {
    await delay(1000)
    count.value++
  }
  
  // 必须返回所有要暴露的内容
  return { count, name, doubleCount, greeting, increment, asyncIncrement }
})
```

#### 2. 核心知识点
- **完全组合式 API**：使用 `ref` / `reactive` 定义 state，`computed` 定义 getter，普通函数定义 action。
- **返回值**：返回的对象成为 store 实例的属性和方法。注意：`ref` 会被自动解包，模板中直接 `store.count` 即可（无需 `.value`）。
- **优点**：更好的 TypeScript 推断，逻辑复用性强（可以把 state/getter/action 抽离成 composable），支持生命周期钩子，热更新友好。
- **缺点**：需要手动实现 `$reset`；初学者可能忘记 `.value` 或忘记返回。

#### 3. 常见坑点 ⚠️

| 坑点 | 错误示例 | 后果 | 正确做法 |
|------|----------|------|----------|
| **忘记返回属性** | `defineStore('id', () => { const count = ref(0) })` | store 为空对象 | 显式 `return { count }` |
| **在 action 中忘记 `.value`** | `function inc() { count++ }`（应为 `count.value++`） | 无法修改，失去响应式 | 牢记 `.value` |
| **使用 `reactive` 包装整个 state 却直接返回** | `const state = reactive({ count:0 }); return { state }` | 访问时多一层 `store.state.count` | 返回展开对象：`return { ...state }` 或分别用 ref |
| **解构 store 丢失响应式**（同 Options） | `const { count } = useStore()` | `count` 不再是响应式的 | 使用 `storeToRefs(useStore())` |
| **没有提供 `$reset`** | 调用 `store.$reset()` 报错 | 无法快速重置 | 手动实现 `$reset`（见下） |
| **在 action 中使用 `this`** | `this.count`（误以为和 Options 一样） | `this` 可能是 undefined | 直接使用变量名：`count.value++` |
| **在 store 外部使用 `ref` 的 `.value` 混淆** | `store.count`（正确）vs `store.count.value`（错误） | 后者会报错或得到 undefined | 组件中使用 store 时，ref 自动解包，不要再加 `.value` |
| **computed 依赖外部变量但未追踪** | `computed(() => externalVar + count.value)`，如果 `externalVar` 不是 ref | 外部变化时 computed 不更新 | 确保所有依赖都是响应式的（ref/reactive/computed） |

#### 4. 手动实现 `$reset`（Setup Store 必备）

```ts
const useSetupStore = defineStore('setup', () => {
  const initialState = { count: 0, name: 'pinia' }
  const state = ref(initialState)
  
  function $reset() {
    state.value = { ...initialState }
  }
  
  // 导出时注意把 state 的属性展开，否则需要 store.state.count
  return { ...state.value, $reset }
})
```

更好的做法（避免展开丢失结构）：
```ts
const useBetterStore = defineStore('better', () => {
  const count = ref(0)
  const name = ref('pinia')
  
  function $reset() {
    count.value = 0
    name.value = 'pinia'
  }
  
  return { count, name, $reset }
})
```

### 三、Options vs Setup 核心对比

| 特性 | Options Store | Setup Store |
|------|---------------|-------------|
| 语法风格 | 对象字面量 | 组合函数 |
| state 定义 | `state: () => ({})` | `ref()` / `reactive()` |
| getter 定义 | `getters: { ... }` | `computed()` |
| action 定义 | `actions: { ... }` | 普通 `function` |
| 访问其他 getter/action | 通过 `this` | 直接调用函数/访问变量 |
| TypeScript 推断 | 需手动标注 `state` 类型 | 自动完美推断 |
| 逻辑复用 | 困难（mixin 方式） | 容易（抽取 composable） |
| 生命周期钩子 | 不支持（只能在组件中使用） | 支持（`onMounted` 等） |
| 热更新 (HMR) | 需手动 `accept` | 更好支持 |
| `$reset` 内置 | 是 | 否（需手动实现） |
| 适用项目大小 | 中小型、快速原型 | 大型、复杂逻辑、TS 项目 |
| 迁移 Vuex 成本 | 极低 | 中等（需重写为 composition） |

### 四、如何选择？官方推荐与场景建议

**官方明确推荐：优先使用 Setup Store！**

理由：
- 更灵活的代码组织（按功能而非类型分组）。
- 完美的 TypeScript 支持（无需额外类型标注）。
- 更容易抽离可复用逻辑（例如多个 store 共用的 state + getter + action）。
- 与现代 Vue 3 组合式 API 风格一致。

#### 选择 Options Store 的少数场景：
- **快速从 Vuex 迁移**：可以直接复制 `state`、`getters`、`actions` 对象，稍作修改即可。
- **团队习惯选项式 API**：团队成员不熟悉组合式 API，且项目不大。
- **极简示范或原型**：写示例代码时更紧凑。

#### 选择 Setup Store 的场景：
- **几乎所有生产项目**（尤其是新项目）。
- **项目使用 TypeScript**。
- **需要逻辑复用**（如多个 store 共享分页逻辑、表单校验等）。
- **需要生命周期钩子**（如 `onMounted` 自动拉取数据）。
- **追求最佳性能和可维护性**。

### 五、跨方式调用与混用注意事项

虽然一个应用中两种方式可以共存，但**不建议在同一个 Store 中混用**。不同 Store 之间可以互相调用：

```ts
// Options Store 调用 Setup Store
const useOptions = defineStore('options', {
  actions: {
    callSetup() {
      const setupStore = useSetupStore()
      setupStore.someAction()
    }
  }
})

// Setup Store 调用 Options Store
const useSetup = defineStore('setup', () => {
  const optionsStore = useOptionsStore()
  function callOptions() {
    optionsStore.someAction()
  }
  return { callOptions }
})
```

> 注意循环依赖：如果两个 Store 互相调用可能导致初始化死循环，应避免或通过 `setTimeout` / `nextTick` 解决。

---

### 六、记忆口诀

> **Options 像 Vuex，迁移最快它擅长；**
> **Setup 是主流，组合万物 ts 强；**
> **State 函数返对象，getter/cache 勿修改；**
> **Action 随意写异步，this 与 .value 要分清；**
> **解构记得 toRefs，重置手动自己扛。**

掌握这两种定义方式，你就能根据项目需求选择最合适的方案，并避开所有常见陷阱。
