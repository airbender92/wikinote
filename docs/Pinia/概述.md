在大型项目中用好 Pinia，核心是围绕 **模块化设计、类型安全、性能优化以及工程化治理** 来构建一套清晰、可维护的状态管理体系。

---

### 🏛️ 基石一：按业务域的模块化架构

这是大型项目中最重要的一条原则：**将全局状态按清晰、独立的业务领域进行垂直拆分**。每个 Store 都应遵循“单一职责”原则，专注处理自己领域内的状态、Getters 和 Actions，而不是把所有东西塞进一个大仓库里。同时，确保**统一使用 Setup Store 语法**（即 `defineStore(() => { ... })`），让逻辑表达更清晰。

一个推荐的目录结构如下：

```text
src/
├── stores/                      // 💡 业务领域划分
│   ├── index.ts                 // (可选) 统一导出枢纽
│   ├── core/                    // 核心域 (用户、权限、应用)
│   │   ├── user.ts              // 用户 Store (登录/登出/信息)
│   │   ├── app.ts               // 应用全局 Store (主题、布局)
│   │   └── index.ts
│   └── features/                // 业务功能域
│       ├── order/               // 订单域
│       │   ├── index.ts         // 订单 Store 主逻辑
│       │   ├── types.ts         // 订单域专属 TS 接口/类型
│       │   └── hooks.ts         // 订单域专属的组件逻辑(Hooks)
│       └── permission/          // 权限域
│           └── index.ts
└── types/                       // 🌍 全局共享的类型定义
    ├── common.ts
    └── api.ts
```

### 🦾 基石二：强制类型安全 + 响应式处理

*   **精确的类型定义**：项目若开启 TypeScript，必须为每个 Store 的 `state`、`getters` 和 `actions` 的参数/返回值定义明确的类型。可以按需创建独立的 `types.ts` 文件存放复杂类型，但禁止使用 `any`。
*   **让响应式真正起作用**：在组件中使用 Store 时，为了在解构时保留响应式，必须使用 `storeToRefs` API。

    ```typescript
    import { storeToRefs } from 'pinia';
    import { useUserStore } from '@/stores/core/user';

    const userStore = useUserStore();
    // ❌ 错误，会失去响应式
    // const { name, age } = userStore;
    // ✅ 正确，使用 storeToRefs 包裹
    const { name, age } = storeToRefs(userStore);
    ```

### ⚡️ 基石三：极致的性能优化策略

*   **懒加载 (Lazy Loading) Store**：结合 `defineAsyncComponent` 实现组件级按需加载，仅在实际访问特定路由时，才动态 `import('./stores/core/user')` 对应的 Store，可大幅减小首屏体积，以提升用户体验。
*   **使用 `$patch` 进行批量更新**：如果一次要修改 Store 中的多个状态，建议使用 `$patch` 方法来合并更新，这样只会触发一次的响应式更新，效率更高。
*   **合理使用 `Pinia Colada`**：自动帮你处理重复请求的缓存、去重、加载和错误状态等复杂“脏活累活”，避免手动编写大量模板代码，具体用法可参考之前的对话。

---

### 🧩 基石四：强大且灵活的工程化能力

*   **持久化状态**：使用官方生态的 `pinia-plugin-persistedstate` 插件，并结合**选择性持久化**配置，精准控制哪些状态该存（如用户 Token）、哪些不该存（如临时草稿数据），避免存储空间浪费和安全问题。
*   **自定义插件**：利用 Pinia 强大的插件体系（`pinia.use()`），可以轻松实现如日志记录、通用 Action 装饰器等横切关注点（Cross-Cutting Concerns）功能，提升整体工程质量。
*   **单元测试**：测试是保证大型项目健康的守门人。推荐使用官方提供的 `@pinia/testing` 工具包，专注于 Store 核心逻辑的隔离测试。

---

### 🧭 高级模式：为复杂业务而生

*   **Store 组合复用**：当一个 Store 需要复用另一个 Store 的逻辑时，可直接在内部调用其他 `useStore()` 函数，再将其状态和方法组合使用，从而实现类似组件逻辑复用的效果。
*   **工厂模式与依赖注入**：对于超大型、逻辑极其复杂的应用，可考虑进阶的工厂模式（Factory Pattern），通过工厂函数显式声明一个 Store 所需的外部依赖（如 API 客户端），从而让代码更干净、测试更简单。

---
