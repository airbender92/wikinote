# EARS 原则（Easy Approach to Requirements Syntax）
## 一、基础定义
EARS 是一套**标准化需求撰写语法**，2009年由罗尔斯·罗伊斯航空团队推出，专门解决PRD里需求模糊、歧义、不可测试的问题，广泛用于金融、工控、软件产品文档，非常适配你现在写的**银行灾备演练系统PRD**。
核心目标：所有需求统一句式，**只描述系统该做什么，不写技术实现**，开发、测试、AI（ZCode）都能无歧义读懂。

### 字母全称
**E**asy **A**pproach to **R**equirements **S**yntax
直译：简易需求描述语法

## 二、5种标准EARS句式模板（核心5大类）
固定语序：**前置条件 → 触发事件/状态 → 系统应[行为]**，强制统一结构，杜绝缺条件、描述模糊。
### 1. Ubiquitous 通用型（无任何前置条件，系统永久具备能力）
模板：系统应 [行为]
示例（你的灾备项目）：
系统应持久化存储所有灾备演练流程JSON数据。

### 2. State-Driven 状态驱动（系统处于某状态时触发）
模板：在[系统状态]下，系统应[行为]
示例：
在演练执行页面运行中状态下，系统应锁定画布节点编辑功能。

### 3. Event-Driven 事件驱动（用户/外部触发动作）
模板：当[触发事件]发生时，系统应[行为]
示例：
当用户点击JSON编辑器保存按钮时，系统应将流程数据存入全局列表并跳转管理页面。

### 4. Optional Feature 可选功能（满足前置条件才启用的功能）
模板：若[可选前提]，当[事件]时，系统应[行为]
示例：
若流程包含并行节点，当启动演练时，系统应同步渲染多条并行执行动画。

### 5. Unwanted Behavior 异常/负面场景（报错、失败、异常流程）
模板：如果[异常条件]，系统应[容错处理行为]
示例：
如果JSON格式校验失败，系统应弹窗提示错误位置并禁止保存流程。

## 三、EARS四大核心价值（写PRD必用理由）
1. **消除歧义**
杜绝“大概、可能、尽量”这类模糊描述，每条需求只有一种解读，前端/后端不会理解偏差。
2. **天然可测试**
每条需求都能直接转化测试用例，测试不用额外拆解需求。
3. **隔离实现细节**
只定义业务行为，不写“用React、X6、Redux实现”，需求和技术方案解耦。
4. **统一团队规范**
产品、开发、AI工具（ZCode/Claude）遵循同一套标准，沟通成本大幅降低。

## 四、对比：普通模糊需求 VS EARS规范需求（你的灾备系统举例）
### 差（模糊写法）
用户可以编辑JSON，改完流程图自动变，点保存存起来。
### 优（标准EARS写法）
当用户修改右侧JSON编辑器内容时，系统应实时更新中间X6流程图画布；
当用户点击JSON编辑器保存按钮时，系统应校验JSON结构合法并将流程分页存入本地存储。

## 五、结合你的银行灾备项目实操示范
### 场景1：拖拽画布节点编辑
EARS需求：
当用户从左侧工具栏拖拽节点至画布区域时，系统应生成对应类型节点并弹出属性编辑表单。

### 场景2：演练节点状态切换
EARS需求：
在灾备演练运行状态下，当串行节点执行完成时，系统应将节点标记为绿色「执行成功」并自动流转至下一节点。

### 场景3：异常容错
EARS需求：
如果用户选择不存在的流程ID启动演练，系统应弹窗提示“流程不存在”并停留在流程选择页面。

## 六、写PRD使用EARS的实操步骤
1. 拆解每个页面功能，拆分最小原子行为；
2. 判断属于5类EARS哪一种，套对应模板；
3. 剔除所有技术词汇（antv/x6、redux、vite等，技术写在开发方案，不进PRD需求）；
4. 每条需求独立一行，编号管理，方便后续开发追溯、测试核对。
