# 先给核心结论
1. **`crypto.pbkdf2` 本质：纯 CPU 密集计算，不是 IO 任务**
   没有磁盘读写、没有网络收发，就是循环哈希运算，全程占用CPU。
2. **原生异步 `crypto.pbkdf2()` 默认跑在 libuv 全局线程池（UV_THREADPOOL_SIZE）**
3. **二选一决策：绝大多数场景直接使用原生异步pbkdf2；高并发服务、大量文件IO+加密混跑时，考虑 worker_threads**

## 一、厘清第一个关键概念：为什么CPU计算会进入libuv线程池？
很多人误解：线程池只处理IO。
Node官方文档明确区分两类任务丢进libuv线程池：
- ① **模拟阻塞IO**：fs异步文件读写、dns.lookup（操作系统没有真正非阻塞接口）
- ② **CPU密集运算**：pbkdf2、scrypt、zlib压缩

执行流程：
```
主线程调用 crypto.pbkdf2 → C++绑定 → uv_queue_work → 丢进libuv线程池
线程池内：执行同步的pbkdf2计算（OpenSSL阻塞运算）
计算完成 → 回调入事件循环 → 主线程执行回调
```
✅ 主线程不会阻塞；
❌ **代价：和fs、zlib、dns.lookup共享同一个全局线程池，互相抢占资源**

举个典型线上坑：
默认线程池=4；同时大量 `fs.writeFile` + 密码校验pbkdf2。
文件IO任务占满4条线程，所有pbkdf2排队，登录接口大面积超时。

## 二、libuv线程池 vs worker_threads 本质区别
### 1）libuv 全局线程池（pbkdf2默认使用）
- 整个进程**唯一共享池**，fs/crypto/zlib/dns 全部抢线程
- 只能通过启动环境变量 `UV_THREADPOOL_SIZE` 全局扩容
- 任务是**C++层内置任务**，不需要JS上下文切换
- 开销小，开箱即用，不用自己管理线程生命周期

### 2）worker_threads（用户手动创建工作线程）
- **独立V8隔离实例**，每个worker拥有独立堆栈、堆内存、独立libuv线程池
- 你可以在worker内部执行 `pbkdf2Sync`，**完全不占用主线程的libuv线程池**
- 通信依靠 `postMessage`，存在序列化开销
- 适合：把加密任务和文件IO任务**物理隔离**，避免线程池抢占（头阻塞）

> 重要区分：
> 在worker线程里调用**异步 `crypto.pbkdf2`**，消耗的是**worker内部自己的libuv线程池**，不再占用主线程的池。

## 三、场景化选型（直接套用）
### ✅ 场景A：普通业务，加密请求量不大，文件IO不多
**选择：直接使用原生 `crypto.pbkdf2`（libuv线程池）**
优点：最简单，无额外开发成本；不需要管理worker生命周期。
优化手段：适当调高 `UV_THREADPOOL_SIZE`（建议≈CPU逻辑核心数）。

### ⚠️ 场景B：Web服务，同时大量文件读写 + 大量密码校验（登录、注册）
**风险：fs任务占满libuv线程池，pbkdf2排队，请求延迟飙升**
两种方案：
1. 方案1（简单）：调大UV_THREADPOOL_SIZE；缺点：IO任务和计算任务依旧争抢线程。
2. 方案2（隔离，推荐高并发）：**worker_threads 执行 pbkdf2Sync**
   把CPU加密任务剥离主线程全局线程池，主线程libuv池专门留给文件IO。

### ❌ 不推荐做法
不要盲目开大量worker_threads：
每个worker是独立V8实例，内存开销很高；线程过多会引发CPU上下文切换，吞吐量下降。

## 四、补充一个极易混淆的细节
```js
// 1. 异步API → 丢libuv线程池
crypto.pbkdf2(password, salt, iter, len, 'sha256', callback)

// 2. 同步API → 直接阻塞当前所在线程（主线程/worker线程都一样）
crypto.pbkdf2Sync(password, salt, iter, len, 'sha256')
```
- 在主线程调用 `pbkdf2Sync` → **直接卡死事件循环，严禁生产使用**
- 在worker线程调用 `pbkdf2Sync` → 只阻塞worker自身，安全，这就是隔离方案常用写法。

## 五、极简对比表
|方案|线程来源|资源竞争|开发成本|适用场景|
| ---- | ---- | ---- | ---- | ---- |
|原生async pbkdf2|主线程libuv共享池|和fs/zlib抢占|极低|中小流量、任务类型单一|
|worker_threads + pbkdf2Sync|worker独立上下文|完全隔离|中（需要线程池管理）|高并发、IO与加密混合负载|

太常见了，我给你举**真实业务场景**，你一看就懂：
只要你的 Node 服务**既要读写文件/数据库，又要做密码加密**，这俩就会同时存在、互相打架。

# 1. 最典型：用户登录 / 注册接口
```
登录流程：
1. 从数据库/文件读取用户的盐和哈希（fs 或数据库 I/O）
2. 用用户输入的密码做 crypto.pbkdf2 计算（CPU 计算）
3. 对比结果，返回 token
```

这里：
- **读库 / 读文件 = I/O → 占 libuv 线程池**
- **pbkdf2 = CPU 计算 → 也占 libuv 线程池**

高并发登录时，直接**线程池互相抢资源**。

# 2. 文件上传服务 + 用户鉴权
```
流程：
1. 验证用户 token（可能需要 crypto 运算）
2. 接收上传文件，fs 写入磁盘（大量 I/O）
3. 对文件做哈希校验（crypto 计算）
```

- **大量 fs.write → 占满线程池**
- **crypto 计算排队 → 接口变慢、超时**

# 3. 日志写入 + 接口加密
- 系统在疯狂写日志文件（fs.appendFile）
- 同时大量接口在用 pbkdf2 / 加密签名
结果：**写文件把 4 个线程占满，加密全卡住**

# 4. 后端服务同时做：
- 文件下载、静态资源读取（I/O）
- 用户密码验证、JWT 校验、加密签名（CPU）

这就是标准的 **I/O 与 CPU 密集任务混合**，也是 Node.js 最容易踩坑的场景。

# 核心冲突一句话
**它们共用同一个 libuv 线程池（默认 4 个线程）
一个忙疯，另一个就排队排到死。**

这样两者**完全隔离，互不抢线程**，服务才稳。
