# 先分两件事：普通业务系统 VS SSO
## 1. 普通网站（单独一套登录，不是SSO）
登录成功 → 在**本站域名写入Cookie**（可以设置持久Cookie，不是会话Cookie）
关闭浏览器再打开：
- 如果Cookie是**持久Cookie（带Expires/Max‑Age过期时间）**：文件保存在电脑本地，浏览器关掉再开依然存在，访问网站自动带上 → **保持登录**
- 如果是**会话Cookie（Session Cookie，没有过期时间）**：只存在内存里，**浏览器完全关闭就自动删除，重新打开就要重新登录**

## 2. SSO场景，和上面逻辑一模一样，只是多了一层
`sso.com` 的Cookie也分两种：
1）**持久Cookie**：关掉浏览器重启，Cookie还在。访问a.com跳转到sso，浏览器带上这个Cookie → SSO识别已登录，免密跳回a。
👉 表现就是：**关浏览器重开，直接免登**
2）**会话Cookie**：浏览器一关，`sso.com`的Cookie直接销毁。下次打开访问a.com跳sso，没有凭证，**必须重新输账号密码**

# 现实产品两种设计都存在
- 「记住我 / 7天免登录」：后端下发**持久Cookie**，保存到本地磁盘，关闭浏览器依然有效
- 不勾选记住我：下发**会话Cookie**，浏览器进程关闭就失效

## 关键区分一句话
1. Cookie能不能扛住「关闭浏览器再打开」，**看Cookie类型，不是看是不是SSO**
2. SSO只是把**全局登录凭证单独放到sso.com域名下**，Cookie本身的机制没变；
3. 我们日常体验：关掉浏览器再打开还登着 = 使用了**持久化Cookie，且未过期**。

# 补充一个容易混淆的细节
就算SSO的持久Cookie还在，a.com自己的业务Cookie可能过期！
现象：打开a.com退出登录 → 页面悄悄跳SSO校验，SSO发现你还在线，重新下发token给a.com，刷新a的业务Cookie，你又自动登录成功。
**肉眼感受：直接打开网站就是登录状态，背后悄悄走了一遍SSO跳转流程。**
