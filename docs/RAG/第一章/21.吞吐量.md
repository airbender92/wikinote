# 吞吐量（Throughput）
在大模型里，**吞吐量 = 单位时间内能处理多少 token / 多少请求**，是衡量**服务效率、并发能力、成本**的核心指标。

和你前面问的 Decoder、RAG、流式输出、长度外推都直接相关。

---

# 一、最常用定义
- **吞吐量（Throughput）**
  = 每秒处理的总 token 数（**tokens/sec**）
- 也可以用：**每秒完成请求数（QPS）**

越大越好：
- 同样一批任务，完成更快
- 同样机器，能服务更多用户
- 单机成本更低

---

# 二、和“延迟 Latency”的区别
- **延迟**：单个用户等多久出结果（首包时延、生成时延）
- **吞吐量**：系统整体一秒能扛多少活

典型矛盾：
- 想**高吞吐** → 尽量**大 batch** 一起推理
- 想**低延迟** → 尽量**小 batch、快响应**
系统设计就是在两者之间做 trade-off。

---

# 三、影响大模型吞吐量的关键因素
## 1. Batch Size（批次大小）
- 一次推理同时喂多少条请求
- batch 越大，GPU 利用率越高 → 吞吐量越高
- 太大爆显存 → 吞吐量反而掉

## 2. KV Cache 机制（Decoder 核心）
Decoder 自回归生成会缓存 KV，
- 有 KV Cache：生成极快
- 无 KV Cache：极慢、吞吐量暴跌

但 KV Cache 很吃显存，限制了 batch 大小。

## 3. 序列长度（上下文窗口）
- 输入/输出越长，计算量 O(n²) → 吞吐量**急剧下降**
- 长度外推、长文本会明显拉低吞吐

## 4. 模型架构优化
- **MQA / GQA**：减少 KV 缓存大小 → 更大 batch → 更高吞吐
- **FlashAttention**：提升计算效率，降低显存压力
- **量化（4bit/8bit）**：省显存，能跑更大 batch，吞吐明显提升

## 5. 动态 batching / continuous batching
vLLM、TGI 这类框架用**迭代级批处理**，
不让请求空等，把 GPU 吃满 → 吞吐量大幅提升。

## 6. RAG 对吞吐的影响
- 检索、向量库查询是**CPU/IO 密集**
- 检索慢 → 整体系统吞吐下降
- 文档片段 Chunk 越长，Embedding 越慢，吞吐越低

---

# 四、流式输出与吞吐量
- 流式输出**不提高吞吐量**
- 它只是**提前返回 token**，改善体验
- 总生成 token 数、耗时没变，系统吞吐不变

---

# 五、极简总结（面试一句话）
**吞吐量 = 系统每秒能处理的 token 总数，反映大模型服务的并发承载能力与效率。**
提升手段：
- 增大有效 batch
- KV Cache + GQA/MQA
- FlashAttention
- 量化
- dynamic batching
- 控制序列长度
