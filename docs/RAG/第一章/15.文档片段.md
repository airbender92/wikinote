# RAG：文档片段（Chunk）
文档片段（**Chunk，文本块**），是RAG整套系统最基础的知识单元：**把长篇PDF/文档切分成一段段较小文本单元**，用于向量化、检索，之后送入Decoder大模型做生成。
> 串联前面链路：原始文档 → 文档片段(Chunk) → Embedding向量存入向量库 → 用户提问召回Top‑N片段 → 组装Prompt送入Decoder‑Only大模型。

## 一、为什么必须切文档片段
1. **Embedding模型输入长度有限**，不能直接喂整本书；
2. **向量检索粒度需要匹配问题**：用户问一个小点，只召回相关小段，不要整份文档；
3. **Decoder上下文窗口有限**，不能把整本知识库全部塞进Prompt；
4. 提升检索速度，降低token成本，减少无关噪声进入模型输入。

> 关键点：**RAG系统的上限，很大程度被切分质量决定。切坏了，后面调Embedding、重排都很难救回来**。

## 二、两个核心参数
- **chunk_size**：每个片段最大长度，单位是**token**，不是字符。
- **chunk_overlap（重叠）**：相邻片段之间重复的token，一般取chunk_size的**10%‑20%**，防止完整句子、逻辑被切在边界上，跨块丢失信息。

|场景|chunk_size推荐(token)|
|---|---|
|FAQ、简短定义、客服|200‑400|
|通用文档、手册、技术文档|512‑800（最常用甜点区）|
|论文、复杂长逻辑|800‑1024|
|代码（函数/类）|300‑500，以函数边界切分|

- 块太小：信息碎片化，单块语义不完整；
- 块太大：一块混入大量无关内容，稀释有效信息，引入噪声，浪费Decoder上下文窗口。

## 三、主流切分策略
### 1. 递归字符切分 RecursiveCharacterTextSplitter（工业最常用）
优先按语义分隔符：双换行`\n\n`（段落）→换行`\n`→句号、分号，递归切分；到达`chunk_size`就截断，同时做overlap重叠。
优点：简单稳定；缺点：依然可能把一个完整逻辑切断。

### 2. 基于文档结构切分
利用Markdown标题、PDF章节、HTML标签，**按标题层级切大块，再二次细切小块**；每一个chunk带上元数据（来源文件、章节标题、页码）。
> 元数据非常重要：用于可解释性溯源，回答输出引用来源`[1]`、过滤检索结果。

### 3. 语义切分 Semantic Chunking
计算句子之间Embedding相似度；语义发生突变时才切分，不硬卡固定token。
优点：尽量保证每一块是完整语义单元；缺点：计算量大，速度慢。

### 4. 句子窗口（Sentence‑Window）
检索返回目标句子，同时把该句子前后N句一并带上送入Prompt；解决“关键信息刚好落在chunk边界”的痛点。

## 四、文档片段完整生命周期（离线+在线）
### 离线建库阶段
```
原始文档(PDF/MD/网页)
→ 文本抽取、清洗（去除页眉页脚、乱码）
→ 切分为多个文档片段Chunk，附加元数据（文件名、页码、章节）
→ 每个Chunk调用Embedding模型得到向量
→ 向量 + 原始文本 + 元数据写入向量数据库
```

### 在线问答阶段
```
用户Query
→ Query向量化
→ 向量库ANN检索，粗召回Top‑N候选文档片段
→ Rerank重排模型，筛选出最相关Top‑K片段
→ 将K个文档片段、元数据拼接进Prompt模板
→ 完整Prompt送入Decoder大模型
→ Decoder自回归生成答案（可流式打字机输出）
→ 输出时带上文档片段来源引用，实现RAG可解释性
```

> ⚠️标准Naive‑RAG：**文档片段的原始文本直接拼入Prompt，不是向量送入Decoder**。Decoder看不到向量，只能看到文本token序列。向量只在检索器使用。

## 五、文档片段带来典型故障点
1. **语义被截断**：一条完整逻辑被拆到两个不同chunk；提问只召回其中一块，信息残缺，回答错误。overlap不能完全根治，优先用结构切分。
2. **噪声混入**：一个chunk包含多个无关主题；检索命中，但大量无关文本送入Decoder，误导生成、引发幻觉。
3. **元数据丢失**：不知道这个片段来自哪份文档哪一页，无法溯源，丧失可解释性。
4. **表格、代码被切坏**：表格打散为混乱文本；函数被切一半，语义失效，需要专门处理表格与代码文档。
5. **碎片过多**：chunk设置过小，向量库爆炸，召回大量碎片化片段，挤占Decoder上下文窗口。

## 六、文档片段与前面知识点串联
1. 和**Decoder**：Chunk是Decoder的输入上下文，**不修改Decoder内部任何结构，仅改变输入Prompt内容**；如果召回太多片段，会直接打满Decoder上下文窗口，报错或截断。
2. 和**流式输出**：检索完成拿到全部文档片段之后，才启动Decoder流式生成；检索阶段本身不会流式返回片段。
3. 和**可解释性**：文档片段携带元数据来源；通过输入贡献度/注意力分析，可以判断Decoder在生成答案时，到底使用了哪几条文档片段。
4. 和Fusion‑in‑Decoder（FiD）高级RAG：不把片段文本全部拼接进Prompt；每个文档片段单独Encoder编码，把隐状态送入Decoder做交叉注意力，节省上下文token。

## 七、极简总结
- **文档片段Chunk = RAG的最小知识单元**；长文档被拆成小块，供检索召回，再拼接给Decoder。
- 核心调参：`chunk_size`、`chunk_overlap`；优先用文档结构切分，带上元数据。
- 向量仅做检索；**真正喂给Decoder的是chunk原始文本**。
- RAG很多效果问题根源不在大模型，而在文档片段切分质量。
