# IT项目主流开源许可证【完整汇总版】

按**传染强度分类**，包含你提到的 **ISC**，覆盖依赖扫描、SBOM、license审计日常遇到的全部常见协议；附带商用风险等级。

> Copyleft = “传染性”：引入后是否强制你的代码开源

## 一、宽松协议 Permissive（✅商业项目最安全，无传染）

允许闭源商用、修改、二次分发，仅要求保留版权声明

1. **MIT License（MIT）**
   前端生态最普遍；无专利条款，仅保留版权声明。
2. **ISC License（ISC）**
   npm大量工具库使用；文本比MIT更精简，权利义务≈MIT；**无专利条款**。
3. **BSD-2-Clause（简化BSD）**
   和MIT/ISC几乎等效。
4. **BSD-3-Clause（新BSD）**
   禁止使用原作者名称做产品宣传背书。
5. **Apache License 2.0（Apache-2.0）**
   企业首选；**自带专利授权**，修改文件必须标注变更记录。
6. **Zlib / PNG License**
   图形库小众极简宽松协议。
7. **0BSD（Zero-Clause BSD）**
   极致宽松，甚至可以不保留版权声明。
8. **Unlicense**
   近似公有领域，主动放弃版权。

## 二、弱传染协议 Weak Copyleft（⚠️需要评估集成方式）

传染范围有限，不是整个程序，仅限**文件/库本身**

1. **MPL 2.0（Mozilla Public License）**
   文件级传染：**只要求修改过的源文件开源**，未改动文件可以闭源。
2. **LGPLv2.1 / LGPLv3（Lesser GPL）**
   - 动态链接：你的代码可闭源；
   - 静态编译打包：相关代码需要开源。
     C/C++基础类库高频使用。

## 三、强传染协议 Strong Copyleft（🔴高危，商业产品谨慎引入）

软件对外分发（客户端、安装包、交付给客户）时，整套衍生代码强制开源

1. **GPLv2**
2. **GPLv3**

> 注意：仅内网服务、SaaS网页访问，单纯部署不对外分发，一般不会触发GPL。

## 四、网络传染协议 Network Copyleft（🛑企业红线最高风险）

**只要对外提供网页/API服务（SaaS），即触发开源义务**

1. **AGPLv3**
   很多公司规范：**禁止直接引入AGPL组件**。

## 五、特殊非OSI开源协议（源码可用，但不属于标准开源）

1. **SSPL（MongoDB服务端公共协议）**
   比AGPL约束更强，商用数据库重点避坑。
2. **BSL（商业源码可用协议）**
   限时开源，到期自动转为闭源。

## 六、补充区分（文档/素材，不建议用于代码）

CC系列（Creative Commons，知识共享）
多用于图片、文案、文档；**不适合软件代码**。

| 许可证     | 闭源商用         | 传染风险     | 专利条款 |

| ISC        | ✅               | 无           | ❌       |

# 先说最重要一句话：

**MIT/Apache/ISC/BSD/GPL/AGPL/LGPL 这些标准开源协议本身，不要求你付钱！**
付费风险**不是来自协议本身，而是两种特殊情况**；很多人把「协议义务」和「要不要花钱」搞混了。

## 一、先区分两件事

1. **开源协议约束 = 规则义务（要不要开源代码）**
2. **付费 = 是否需要向作者购买商业授权**
   两者完全独立。

## 二、逐个对应你之前那条规范解释

> 自研代码优先 Apache2.0；依赖只允许 MIT/Apache/ISC/BSD；严禁 AGPL/GPL，尽量避开 LGPL

### 1）MIT / Apache2.0 / ISC / BSD（白名单依赖）

✅ **遵守协议条件下，永久免费，不需要付费**
义务只有：分发产品时保留版权声明。
你可以整合进闭源商业产品、售卖、私有化部署，**不用交钱给原作者**。

⚠️唯一例外：
部分开源项目采用**双重许可模式**（例如一些图形库、数据库组件）：

- 想用开源协议免费使用 → 遵守协议条款；
- 不想遵守开源协议（比如不想开源、规避传染）→ 购买商业授权（付费）。

> 绝大多数前端npm包（Vue、React、工具类）不存在双重许可，直接免费使用。

### 2）GPL / AGPL（严禁引入）

协议本身**不收费**，但风险不是花钱，而是**传染性强制开源**：

- GPL：对外交付安装包/镜像，整套产品代码必须开源；
- AGPL：做成SaaS网页服务对外提供访问，就可能要求开源代码。

👉 风险总结：**不是让你付费，是强制你公开自家业务代码，商业产品直接丧失壁垒。**

举例子：
你用了AGPL图表组件做SaaS系统，一旦修改组件源码，法律上要求公开你整套前端+后端源码，损失远大于付费。

### 3）LGPL（尽量避开）

协议本身同样免费。
前端场景风险：webpack/vite打包属于**静态合并**，业界普遍认定类似静态链接；一旦修改LGPL组件并对外交付，需要开放该组件源码。
不是要钱，是合规流程麻烦，法务极易提出质疑，能替换就替换。

## 三、最容易混淆的场景：什么时候才需要付费？

出现下面情况，才需要花钱买商业授权：

1. **组件是双重许可**
   开源协议（GPL/AGPL）免费，但约束极强；企业不想遵守开源规则，可以付费购买商业授权，解除传染限制。
   典型：MongoDB、一些开源BI、报表组件。

2. **不是OSI标准开源协议（BSL、SSPL、自定义协议）**
   很多源码可见≠免费商用，达到一定规模、商用售卖就必须付费。

3. **购买技术服务、技术支持**
   代码免费，但企业版售后、定制、培训单独收费，和授权本身无关。

## 四、精简总结（可以直接对内宣讲）

1. **MIT/Apache/ISC/BSD：免费使用，只要标注版权，无开源强制要求，放心引入；**
2. **GPL/AGPL：使用不花钱，但一旦对外交付/做SaaS，可能强制开源你自家代码，商业产品禁止引入；**
3. **LGPL：免费，但前端打包场景合规风险高，尽量替换；**
4. **付费只出现在：组件双重许可、非开源自定义协议、购买技术支持，和上面标准开源协议本身无关。**

## 一个常见误区纠正

❌误区：AGPL/GPL不能用，是因为要花钱买授权
✅真相：**不是要钱，是强制开源你的业务代码。**
