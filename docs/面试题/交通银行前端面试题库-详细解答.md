## 一、往年真题(真实面经)

### 1. 笔试选择题考点速查

**【考察点】** 基础广度,覆盖 CSS 盒模型、JS 异步、React/Vue 框架基础。

**【详细解答】**

- **clientWidth / offsetWidth / scrollWidth**(高频):
  - `clientWidth` = 内容宽 + padding,不含滚动条、border、margin
  - `offsetWidth` = 内容宽 + padding + border(含滚动条)
  - `scrollWidth` = 内容实际宽度(含被滚动隐藏的部分)
  - 记忆:client 是"看得见的客户区",offset 是"占位偏移",scroll 是"可滚动内容"
- **Promise**:三种状态 pending/fulfilled/rejected,状态不可逆;`then` 返回新 Promise 支持链式
- **this 指向**:普通函数调用=window、对象方法=对象、new=实例、call/apply/bind=绑定对象;**箭头函数没有自己的 this**
- **宏任务 vs 微任务**:同步 → 微任务全部 → 宏任务 → 微任务全部…循环;微任务(Promise.then、async/await 后续)、宏任务(setTimeout、setInterval)
- **箭头函数特性**:无 this/arguments/super,不能当构造函数(不能 new),没有 prototype
- **redux 数据流**:`dispatch(action) → reducer(纯函数) → 新 state → 订阅者更新视图`,单向数据流
- **跨域**:协议/域名/端口任一不同即跨域
- **Vue 组件传值**:props 下传、$emit 上抛、provide/inject 跨层

**【回答话术】** "笔试覆盖比较基础,主要是 CSS 盒模型、JS 异步和框架基础,我平时都会用到,问题不大。"

**【追问准备】** 面试官若追问:举例说明宏任务微任务执行顺序 —— 见本文"事件循环"一题。

### 2. 简答1:useState / useRef 的使用与原理

**【考察点】** React Hooks 基础 + 对 Hook 内部机制的了解(简历写 React 才会深问,但交行笔试原题考过)。

**【详细解答】**

```jsx
// 使用
const [count, setCount] = useState(0); // 状态 + 更新函数
const ref = useRef(null); // 返回可变 ref 对象

ref.current = document.getElementById("box"); // 常用:拿 DOM
const timer = useRef(null); // 常用:存定时器 ID
// 注意:修改 ref.current 不会触发重新渲染
```

- **useState 原理**:React 在 Fiber 节点上维护一个 **memoizedState 链表**,每个 Hook 按**调用顺序**对应链表中的一个节点;`useState` 首次渲染把初始值存入链表,之后渲染读取链表中的旧值。因此:
  - Hook 的调用顺序必须稳定 → **不能写在条件、循环、嵌套函数里**(顺序变了,状态就错位)
  - `setState` 触发重新渲染,渲染时按顺序"对号入座"取回状态
- **useRef 原理**:本质上也是一个 Hook 节点,`ref.current` 就是链表里存的那个对象引用;它不参与渲染,所以改它不会触发更新,适合存"不需要渲染的变量"(定时器、DOM、上一次的值)

**【回答话术】** "useState 用来声明组件状态,useRef 用来存可变引用(比如 DOM 和定时器)。useState 的原理是 React 把每个 Hook 的状态按调用顺序存在 Fiber 节点上,所以 Hook 不能写在条件里。"

**【追问准备】** `setState` 是同步还是异步?—— React 事件处理中是**异步批量**更新(合并多次 setState),原生事件和 setTimeout 里是同步;React 18 的自动批处理在更多场景合并更新。

### 3. 简答2:手写 sleep(1000) 函数

**【考察点】** Promise / async / generator 的掌握,笔试手写原题。

**【详细解答】**

```js
// ① Promise(最标准)
const sleep = (ms) => new Promise((resolve) => setTimeout(resolve, ms));

// 使用
async function demo() {
  console.log("开始");
  await sleep(1000); // 阻塞 1 秒(不阻塞主线程)
  console.log("1秒后");
}

// ② generator 版(考察 generator 掌握度)
function* sleepGen(ms) {
  yield new Promise((resolve) => setTimeout(resolve, ms));
}
// 需要一个自执行器驱动(或借助 co 库)

// ③ async/await 封装版
async function sleep(ms) {
  return new Promise((resolve) => setTimeout(resolve, ms));
}

// ④ 同步阻塞版(面试时说明:会卡死主线程,不推荐)
function sleepSync(ms) {
  const end = Date.now() + ms;
  while (Date.now() < end) {}
}
```

- 使用场景:接口轮询间隔、动画播放间隔、限流节流、测试模拟延迟
- 关键:用 `setTimeout + Promise`,**await 只是让当前 async 函数等待,不会阻塞浏览器渲染**

**【回答话术】** "我一般用 Promise 实现:`new Promise(resolve => setTimeout(resolve, ms))`;如果要考察 generator,可以用 `yield` 一个 Promise,再配合自执行器。"

**【追问准备】** "为什么不用 while 循环阻塞?"—— 会阻塞主线程,页面直接卡死,setTimeout 是异步的,不会。

### 4. 简答3:webpack 页面体积分析

**【考察点】** 工程化能力:能不能发现并解决"项目越来越重"的问题。

**【详细解答】**

- **分析步骤**:
  1. 安装 `webpack-bundle-analyzer`,构建后生成依赖体积树状图:一眼看到最大的包是哪个、有没有重复打包
  2. Network 面板看实际加载:Transfer Size(传输体积)、加载瀑布图、哪些资源阻塞首屏
  3. Lighthouse / 浏览器 Performance 面板看性能指标
- **常见优化手段**:
  - **路由级代码分割**:`const Home = () => import('@/views/Home.vue')`,首屏只加载当前路由 chunk
  - **第三方库拆包**:`splitChunks` 把 vue/echarts 等 vendor 单独抽 chunk,配合 contenthash 长效缓存,业务更新时 vendor 缓存不失效
  - **按需引入**:echarts 按模块 `import { LineChart } from 'echarts/charts'`;element-plus 用 unplugin 按需
  - **tree-shaking**:ESModule 写法 + 生产模式,自动摇掉未用代码
  - **压缩**:gzip(nginx 开启)/ brotli,静态资源体积普遍降 60%+
  - **图片**:压缩、webp、雪碧图、iconfont 代替图片图标
- **加分回答**:先量化分析定位大头,再针对性优化,避免"盲优化"

**【回答话术】** "先用 bundle-analyzer 看体积分布,再针对最大依赖做拆分:路由级懒加载、vendor 单独拆包、库按需引入,最后开启 gzip,体积能降一半以上。"

### 6. 面试1:埋点是怎么做的?用于什么业务?(交行高频)

**【考察点】** 银行操作留痕与合规审计的落地能力,交行面试几乎必问。

**【详细解答】**

**怎么做(埋点体系设计):**

1. **埋点方式选择**:
   - 代码埋点:业务事件处手动调用 SDK,精准但需人工维护
   - 可视化埋点:后台圈选元素配置,运营友好
   - 无埋点/全埋点:自动采集所有交互,数据全但噪音大、成本高
   - 实际项目:核心业务事件用代码埋点,通用行为用自动采集
2. **采集内容**:页面 PV/UV、点击/曝光/停留时长、业务事件(开户、转账、查询等)、JS 错误、性能指标
3. **上报策略**:
   - 常规上报:队列攒批 + 节流,减少请求量
   - 页面卸载:用 `navigator.sendBeacon` 保证数据送达
   - 失败重试、本地暂存(防丢)
4. **字段设计**:用户 ID、会话 ID、事件名、时间戳、页面路由、设备 UA、版本号;前后端约定字段规范
5. **数据链路**:前端采集 → 上报网关 → 日志/大数据平台 → 分析报表 → 业务决策

**用于什么业务:**

- 用户行为分析:功能使用率、转化漏斗、留存分析,指导产品迭代
- 异常监控:错误率、白屏率告警,快速定位线上问题
- **操作留痕与合规审计(银行重点)**:敏感操作(转账、修改资料、导出数据)必须可追溯"谁、何时、做了什么"
- 风控辅助:异常操作模式识别

**银行注意事项**:埋点遵循**最小化采集 + 脱敏 + 合规**,不采集与业务无关的敏感信息。

**【回答话术】** "我们埋点分两层:通用行为自动采集,核心业务事件代码埋点。上报用队列批量加节流,页面卸载时用 sendBeacon 兜底。主要服务于用户行为分析和线上异常监控,在银行场景还承担操作留痕的合规审计作用。埋点设计会注意最小化采集和数据脱敏。"

### 7. 面试2:组件传值方式

**【考察点】** 框架基本功,必考题。

**【详细解答】**

Vue 体系:

```vue
<!-- 父传子:props -->
<Child :title="msg" />

<!-- 子传父:$emit -->
<button @click="$emit('update', value)">

<!-- v-model 语法糖(value + input) -->
<input v-model="search" />

<!-- 跨层级:provide / inject -->
<!-- 任意组件:EventBus(mitt)、Pinia 全局状态 -->
<!-- $refs 直接调用子组件方法 -->
<!-- $attrs 透传、插槽 slot 传模板 -->
```

- **适用场景选择**:
  - 简单父子:props / $emit
  - 跨多层:provide / inject
  - 兄弟或复杂共享:Pinia(状态多、多处用)
  - 少量临时通信:EventBus(mitt),记得组件卸载时 off 防泄漏
- **单向数据流**:props 只读,子组件不能直接改,要改就 $emit 通知父组件改(便于追踪数据来源,利于维护和调试)

React 体系(对照):props、回调函数、Context、Redux、ref。

**【回答话术】** "Vue 里父子用 props 和 $emit,跨层级用 provide/inject,复杂共享状态用 Pinia。遵循单向数据流,子组件不直接改 props,通过事件通知父组件。"

### 8. 面试3:白屏怎么排查与优化

**【考察点】** 线上问题排查思路,银行项目上线后最常遇到。

**【详细解答】**

**排查步骤(按顺序):**

1. **看 Console**:有没有 JS 报错(最常见原因,如变量未定义、接口数据字段不对)
2. **看 Network**:HTML/JS/CSS 是否 404 或加载失败(CDN 挂了、部署路径错、路由 history 模式刷新 404)
3. **看接口**:首屏接口是否很慢/报错,导致页面一直 loading 或渲染失败
4. **看打包产物**:是否有构建报错、路由懒加载 chunk 加载失败
5. **建立白屏监控**:监听 DOMContentLoaded 后检查根节点是否为空,上报白屏率,主动发现

**优化手段:**

- 骨架屏:加载中先展示占位,体验好
- 首屏资源瘦身:拆包、压缩、按需引入(见 webpack 题)
- 资源加速:CDN、DNS 预解析、preload 关键资源
- 首屏接口优化:合并、加缓存、后端降级
- 错误边界 + 兜底页:Vue 的 `errorCaptured` / React 的 `ErrorBoundary`,出错不白屏而是展示友好页面
- 极端场景:SSR / 预渲染

**【回答话术】** "先按 控制台报错 → 资源加载 → 首屏接口 → 构建产物 的顺序定位,再针对性优化:骨架屏、拆包瘦身、CDN 加速、错误兜底页。同时会上白屏监控主动发现线上问题。"

### 9. 面试4:Redis 和 Swagger 的缺点(简历写 Java 才问)

**【考察点】** 技术栈广度,答不上来也不致命,但别乱编。

**【详细解答】**

**Redis 缺点:**

- 纯内存存储,硬件成本高;数据量大时成本压力大
- 持久化:RDB 可能丢最后一次快照之后的数据,AOF 也非绝对强一致,极端情况可能丢少量数据
- 缓存淘汰策略(LRU/LFU)可能误删需要的数据
- 集群(Cluster/哨兵)运维复杂,扩缩容有成本
- 不适合存超大对象和复杂查询,没有关系型能力

**Swagger 缺点:**

- 注解侵入业务代码,代码变"脏"
- 接口变更后文档容易与实现不一致,维护不及时就形同虚设
- 生产环境必须关闭(暴露接口信息有安全风险)
- 生成文档有序列化性能开销

**【回答话术】** "Redis 主要缺点是纯内存成本高、持久化极端情况会丢少量数据、集群运维复杂;Swagger 主要是注解侵入代码、文档容易和实现不同步,而且生产环境必须关掉。"

### 10. 面试5:HTTP 在哪一层?HTTP 和 HTTPS 的区别?

**【考察点】** 网络基础,必考题。

**【详细解答】**

- **TCP/IP 四层模型**:应用层 / 传输层(TCP、UDP)/ 网络层(IP)/ 网络接口层
- **HTTP 属于应用层**,与 FTP、DNS、SMTP 同层,底层依赖 TCP 的可靠传输

**HTTP vs HTTPS 对比:**

| 对比项   | HTTP                  | HTTPS                   |
| -------- | --------------------- | ----------------------- |
| 安全性   | 明文传输,可被截获篡改 | SSL/TLS 加密 + 身份认证 |
| 默认端口 | 80                    | 443                     |
| 证书     | 不需要                | 需向 CA 申请证书        |
| 性能     | 快                    | 多一次 TLS 握手,略慢    |
| 信任     | 无身份验证            | 可验证服务器身份        |

**HTTPS 加密流程**(简述):

1. 服务器向客户端发送证书(含公钥)
2. 客户端验证证书合法性(CA 签名、域名、有效期)
3. 客户端生成随机对称密钥,用服务器公钥加密后发送
4. 服务器用私钥解密得到对称密钥
5. 之后双方用对称密钥加密通信(兼顾安全与性能)

**【回答话术】** "HTTP 在应用层,底层是 TCP。区别核心是安全:HTTP 明文,HTTPS 加了 SSL/TLS 加密,用非对称加密协商密钥、对称加密传输数据;HTTPS 需要 CA 证书,默认 443 端口。"

### 11. 面试6:Vue 数据双向绑定原理

**【考察点】** Vue 核心原理,必考,要能画出流程图。

**【详细解答】**

**Vue2 实现:**

1. `Observer`:通过 `Object.defineProperty` 递归劫持 data 每个属性的 getter/setter
2. `Dep`:每个响应式属性对应一个依赖收集器(发布者)
3. `Watcher`:渲染 watcher、计算 watcher 等(订阅者)
4. 依赖收集:渲染时访问属性触发 getter,把当前 watcher 收集进 Dep
5. 派发更新:修改属性触发 setter,调用 `dep.notify()` 通知 watcher 更新视图
6. 局限:无法监听新增/删除属性(需 `$set`/`$delete`)、无法监听数组下标修改(重写了 push/pop/splice 等 7 个数组方法)

**Vue3 实现:**

- 改用 `Proxy` 代理整个对象,天然支持新增属性、删除属性、数组下标修改
- 性能更好(惰性代理,不递归初始化)、拦截能力更全

**v-model 原理:**

- 表单元素:`value` + `input` 事件的语法糖
- 组件上:`modelValue` prop + `update:modelValue` 事件的语法糖
- 修饰符:`.trim`、`.number` 等

**【回答话术】** "Vue2 用 Object.defineProperty 劫持属性的 getter/setter,配合 Dep 收集依赖、Watcher 通知更新,形成发布订阅;Vue3 改用 Proxy 代理整个对象,支持新增删除属性和数组下标。v-model 本质是 value + input 事件的语法糖。"

## 二、Vue 核心高频题

### 1. 虚拟 DOM 是什么?为什么需要?

**【详细解答】**

- 虚拟 DOM(VNode):用 JS 对象描述真实 DOM 结构(标签、属性、子节点),是真实 DOM 的轻量级抽象
- 流程:render 函数生成 VNode → 新旧 VNode 通过 **diff 算法**对比 → 只对变化部分做真实 DOM 操作
- **为什么需要**:
  1. **性能**:直接操作 DOM 昂贵(触发重排重绘),diff 后最小化真实操作(注:不是比手动操作绝对快,而是保证在"数据驱动视图"的模型下可控)
  2. **跨平台**:同一套 VNode 可渲染到浏览器、小程序、原生(uni-app、weex、React Native)
  3. **声明式开发**:开发者只关心数据,不用手动操作 DOM
- **diff 策略**:同层对比(不跨层级比较)、key 复用节点、Vue3 快速 diff + 静态提升 + patchFlag

**【回答话术】** "虚拟 DOM 是用 JS 对象描述 DOM,通过 diff 最小化真实 DOM 操作,带来跨平台能力和声明式开发体验。"

### 2. 生命周期钩子

**【详细解答】**

Vue3 组合式 API 钩子顺序:

```
setup → onBeforeMount → onMounted → onBeforeUpdate → onUpdated → onBeforeUnmount → onUnmounted
```

- **setup / created**:初始化数据、非 DOM 依赖的准备工作
- **onMounted**:DOM 就绪,适合:操作 DOM、绑定原生事件、初始化第三方库(echarts)、发首屏请求
- **onUpdated**:数据变化导致视图更新后;注意不要在它里面改数据(会死循环)
- **onUnmounted**:组件销毁,必须清理:定时器、事件监听、echarts 实例 dispose、取消请求——**防止内存泄漏,银行项目必考**
- 父子组件顺序:父 beforeMount → 子 mounted(全部) → 父 mounted;销毁顺序相反(父 beforeUnmount → 子 unmounted → 父 unmounted)

**【回答话术】** "mounted 做 DOM 初始化和发请求,unmounted 一定要清理定时器、事件和 echarts 实例防内存泄漏。"

### 3. computed 和 watch 的区别

**【详细解答】**

| 对比      | computed               | watch                             |
| --------- | ---------------------- | --------------------------------- |
| 用途      | 由已有数据**派生**新值 | 数据变化后执行**副作用**          |
| 缓存      | 有,依赖不变不重算      | 无                                |
| 返回值    | 必须返回一个值         | 不要求                            |
| 同步/异步 | 同步                   | 可异步(发请求)                    |
| 其他      | 不能有副作用           | deep 深度监听、immediate 立即执行 |

```js
// computed:依赖不变得缓存
const total = computed(() => items.value.reduce((s, i) => s + i.price, 0));

// watch:变化后做事
watch(
  () => props.id,
  async (newId) => {
    list.value = await fetchList(newId);
  },
  { immediate: true, deep: true },
);
```

**口诀:派生用 computed,副作用用 watch。**

**【回答话术】** "computed 有缓存、适合派生值;watch 适合数据变化后去做请求、异步这类副作用操作。"

### 5. 刷新页面后状态丢失怎么处理

### 6. 权限控制(银行必考)

**【详细解答】**

完整方案分四层:

1. **登录认证**:登录成功返回 token(短期) + 用户角色/权限码;token 存内存或 HttpOnly cookie
2. **路由级权限**:
   - 方式A(动态路由):权限码过滤路由表,`router.addRoute()` 动态注册,刷新后需重新注册
   - 方式B(静态 + meta):路由 meta 配 `requiresAuth` / `roles`,守卫里校验
3. **按钮级权限**:自定义指令 `v-permission="['btn:export']"`,无权限时移除元素
4. **接口级校验**:后端对每个接口二次鉴权——**前端控制只是体验,安全底线在后端**(银行面试官最看重这句)

```js
// 路由守卫示例
router.beforeEach((to, from, next) => {
  const token = getToken();
  if (to.meta.requiresAuth && !token) {
    next({ path: "/login", query: { redirect: to.fullPath } });
  } else {
    next();
  }
});

// 按钮级权限指令
const vPermission = {
  mounted(el, binding) {
    const codes = store.state.permissionCodes;
    if (!codes.includes(binding.value)) el.parentNode?.removeChild(el);
  },
};
```

- 401 处理:axios 响应拦截器统一清 token、跳登录页

**【回答话术】** "权限分三层:路由层用动态路由或守卫控制页面访问,按钮层用自定义指令控制操作,但最关键的是后端接口必须二次鉴权——前端只是体验层,安全底线在后端。"

### 7. nextTick 是什么?

**【详细解答】**

- **背景**:Vue 的 DOM 更新是**异步批量**的——数据改变后不会立刻更新 DOM,而是推入渲染队列,统一在下一轮执行
- **作用**:`nextTick` 的回调在 DOM 更新完成后执行,此时能拿到最新 DOM
- **原理**:内部把回调放入微任务队列(Promise.then 优先,降级 MutationObserver / setTimeout),在渲染 watcher 更新之后执行

```js
count.value++;
await nextTick();
console.log(el.value.offsetHeight); // 拿到更新后的 DOM
```

- **使用场景**:数据更新后立即测量 DOM(获取高度/宽度)、获取滚动位置、在 watch 里等 DOM 更新完

**【回答话术】** "Vue 的 DOM 更新是异步批量的,nextTick 就是等这次更新完成后执行回调,拿到最新的 DOM。原理是内部用微任务队列排队执行。"

### 8. 前端为什么有跨域问题?怎么解决?

**【详细解答】**

- **同源策略**:浏览器安全机制,协议、域名、端口三者任一不同,请求就是"跨域",浏览器会拦截响应(注意:请求发出去了,是响应被拦)
- **解决方案**:
  1. **开发环境:代理转发**(最常用)
     - Vite:`server.proxy` 配置 `/api → http://backend:8080`
     - Webpack:`devServer.proxy` 同理
  2. **生产环境:Nginx 反向代理**,前端后端同域,从根上避免跨域
  3. **CORS**:后端配置响应头
     ```
     Access-Control-Allow-Origin: https://your.domain
     Access-Control-Allow-Methods: GET,POST,PUT,DELETE,OPTIONS
     Access-Control-Allow-Headers: Content-Type,Authorization
     ```
     携带 cookie 需 `Access-Control-Allow-Credentials: true` + 明确 Origin(不能是 *)
  4. 了解即可:JSONP(仅 GET,script 标签不受同源限制)、postMessage(跨窗口)、iframe

**【回答话术】** "同源是浏览器安全策略。开发环境用代理转发,生产环境用 Nginx 反代让前后端同域,跨域场景配合后端开 CORS 头。"

## 三、JS 手写代码(笔试必考)

### 1. 防抖 debounce

**【详细解答】**

- 原理:触发事件后重置定时器,**只执行最后一次**;连续触发时前面的全部取消
- 应用:搜索框输入(停止输入后再请求)、窗口 resize、表单校验

```js
function debounce(fn, delay = 300) {
  let timer = null;
  return function (...args) {
    clearTimeout(timer);
    timer = setTimeout(() => fn.apply(this, args), delay);
  };
}

// 进阶:立即执行版(第一次立即触发,之后防抖)
function debounceImmediate(fn, delay = 300, immediate = true) {
  let timer = null;
  return function (...args) {
    const callNow = immediate && !timer;
    clearTimeout(timer);
    timer = setTimeout(() => {
      timer = null;
    }, delay);
    if (callNow) fn.apply(this, args);
  };
}
```

**【追问准备】** 问 this 为什么用 apply?—— 保证防抖后的函数 this 指向不变、参数透传。

### 2. 节流 throttle

**【详细解答】**

- 原理:固定时间间隔内只执行一次(时间戳版:间隔内不执行;**定时器版**:间隔结束后执行最后一次)
- 应用:滚动事件、resize、拖拽、按钮连点

```js
// 时间戳版:保证开始即执行
function throttle(fn, interval = 300) {
  let last = 0;
  return function (...args) {
    const now = Date.now();
    if (now - last >= interval) {
      last = now;
      fn.apply(this, args);
    }
  };
}

// 定时器版:保证结束还会补一次
function throttleTimer(fn, interval = 300) {
  let timer = null;
  return function (...args) {
    if (timer) return;
    timer = setTimeout(() => {
      fn.apply(this, args);
      timer = null;
    }, interval);
  };
}
```

**防抖 vs 节流一句话**:防抖是"只执行最后一次",节流是"定期执行一次"。

### 3. 深拷贝(含循环引用)

**【详细解答】**

- 面试考点:基本类型直接返回、Date/RegExp 特殊处理、**循环引用用 WeakMap 记录**、数组保持数组
- 对比方案 `JSON.parse(JSON.stringify())` 的缺点:丢失 undefined/函数/Symbol、Date 变字符串、**循环引用直接报错**、NaN/Infinity 变 null

```js
function deepClone(obj, map = new WeakMap()) {
  if (obj === null || typeof obj !== "object") return obj; // 基本类型
  if (obj instanceof Date) return new Date(obj);
  if (obj instanceof RegExp) return new RegExp(obj);
  if (map.has(obj)) return map.get(obj); // 循环引用
  const clone = Array.isArray(obj) ? [] : {};
  map.set(obj, clone);
  for (const key of Object.keys(obj)) {
    clone[key] = deepClone(obj[key], map);
  }
  return clone;
}
```

**【追问准备】** 现代浏览器可用原生 `structuredClone(obj)`(支持循环引用、Date、Map 等)。

### 4. Promise.all

**【详细解答】**

- 特性:所有成功才成功(结果按传入顺序返回);**一个失败立即整体失败**(reject 第一个错误)
- 应用:并行请求多个接口后一起处理(如页面多个独立数据)

```js
Promise.myAll = function (promises) {
  return new Promise((resolve, reject) => {
    const results = [];
    let count = 0;
    promises.forEach((p, i) => {
      Promise.resolve(p).then(
        (val) => {
          results[i] = val; // 保序
          if (++count === promises.length) resolve(results);
        },
        reject, // 一个失败即失败
      );
    });
  });
};
```

**【追问准备】** 对比:

- `allSettled`:全部返回结果(含失败),永不 reject
- `race`:第一个完成的结果
- `any`:第一个成功的结果,全失败才 reject

### 5. new 操作符

**【详细解答】**

new 做了四件事:

1. 创建空对象
2. 空对象的原型指向构造函数 prototype
3. 执行构造函数,this 绑定到新对象
4. 构造函数返回对象则返回它,否则返回新对象

```js
function myNew(Fn, ...args) {
  const obj = Object.create(Fn.prototype); // 1、2
  const result = Fn.apply(obj, args); // 3
  return (typeof result === "object" && result !== null) ||
    typeof result === "function"
    ? result
    : obj; // 4
}
```

### 6. bind / call / apply

**【详细解答】**

- call:`fn.call(thisArg, a, b)` 立即执行,参数逐个
- apply:`fn.apply(thisArg, [a, b])` 立即执行,参数数组
- bind:`fn.bind(thisArg, a)` 返回新函数,不执行,支持柯里化

```js
Function.prototype.myBind = function (ctx, ...args) {
  const fn = this;
  return function (...rest) {
    // 进阶:new 调用时 this 优先级高于 bind
    if (new.target) return new fn(...args, ...rest);
    return fn.apply(ctx, [...args, ...rest]);
  };
};
```

### 8. 事件循环:宏任务和微任务

**【详细解答】**

- 执行顺序:**同步代码 → 全部微任务 → 一个宏任务 → 全部微任务 → …循环**
- 微任务:Promise.then/catch/finally、async/await 之后的代码、queueMicrotask
- 宏任务:setTimeout、setInterval、I/O、UI 事件、requestAnimationFrame(通常归为宏任务)

```js
console.log(1); // 同步
setTimeout(() => console.log(2), 0); // 宏任务
Promise.resolve().then(() => console.log(3)); // 微任务
async function f() {
  console.log(4);
  await 1;
  console.log(5);
}
f(); // 同步部分先执行
// 输出:1, 4, 3, 5, 2
```

### 9. this 指向

**【详细解答】**

1. 普通函数调用:`window`(严格模式 undefined)
2. 对象方法调用:该对象
3. `new` 调用:新实例
4. `call/apply/bind`:绑定的对象
5. **箭头函数:没有自己的 this**,沿词法作用域向上找(定义时确定),call/apply/bind 也无法改变
6. 优先级:new > 显式绑定(call/apply/bind)> 隐式绑定(对象方法)> 默认绑定

### 10. 闭包

**【详细解答】**

- 定义:函数 + 其词法作用域的引用,使内部函数能访问外部函数变量,且变量不随外部函数结束销毁
- 作用:封装私有变量、柯里化、模块化、防抖节流内部计时器
- 风险:**内存常驻不释放 → 内存泄漏**,用完注意置 null

```js
// 经典题:输出什么?
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0); // 3,3,3(var 全局变量,回调共享)
```

## 四、性能优化与工程化

### 1. 一次渲染 10 万条表格数据

**【详细解答】**

按复杂度分层:

1. **分页/懒加载**:服务端分页或前端滚动分页,一次只渲染一页(银行报表最常用)
2. **虚拟滚动**(核心方案):只渲染可视区内的行(如 30 行)+ 上下缓冲,滚动时用 transform 位移,DOM 数量恒定
   - 原理:容器固定高度 → 计算总高度撑开滚动条 → 根据 scrollTop 计算可视区起始索引 → 只渲染可视区数据
   - 库:vue-virtual-scroller / react-window
3. **时间分片**:`requestIdleCallback` 在浏览器空闲时批量插入节点,避免一次性阻塞主线程
4. 配套:避免大列表内复杂组件、正确使用 key、开启虚拟滚动的表格组件

**【回答话术】** "最常用分页,需要一次性展示全部数据时用虚拟滚动——只渲染可视区的几十行,配合固定容器高度和 transform 位移,10 万条也没问题。"

### 2. 首屏加载优化

**【详细解答】**

- **构建层**:路由懒加载(import())、第三方库按需引入、tree-shaking、代码压缩
- **网络层**:gzip/brotli、CDN 加速、强缓存(hash 文件长缓存)、HTTP/2、DNS 预解析、preload 关键资源
- **图片**:懒加载、webp、尺寸压缩、iconfont 代替图标
- **请求层**:首屏接口合并/精简字段、后端缓存、非关键请求延后、接口超时降级
- **体验层**:骨架屏、loading 态、错误兜底
- 极端场景:SSR / 静态预渲染(首屏直出)

### 3. 浏览器缓存:强缓存与协商缓存

**【详细解答】**

- **强缓存**:命中直接使用本地,不发请求(200 from cache)
  - `Cache-Control: max-age=3600`(HTTP/1.1,优先)
  - `Expires`(HTTP/1.0,已淘汰)
- **协商缓存**:每次发请求,服务器判断
  - `ETag`(内容哈希,优先)/ `Last-Modified`(最后修改时间)
  - 未变返回 304,变了返回 200 + 新资源
- **工程实践**:index.html 不缓存(或 no-cache 走协商),带 hash 的静态资源长缓存——解决"发版后用户还是旧版本"问题

### 4. 从输入 URL 到页面渲染

**【详细解答】**

1. DNS 解析:域名 → IP
2. TCP 三次握手建立连接
3. HTTPS 则进行 TLS 握手
4. 发送 HTTP 请求,服务器返回 HTML
5. 解析 HTML 构建 **DOM 树**(遇 `<script>` 会**阻塞解析**,所以 script 放底部或用 defer/async)
6. 解析 CSS 构建 **CSSOM 树**(CSS 阻塞渲染)
7. DOM + CSSOM 合并成 **渲染树**
8. 布局(Layout):计算几何位置
9. 绘制(Paint):像素绘制
10. 合成(Composite)显示

- 事件:`DOMContentLoaded`(DOM 就绪,不等图片)vs `load`(所有资源加载完)

### 5. 错误监控与异常上报

**【详细解答】**

- **采集**:
  - `window.onerror`(脚本错误)
  - `window.addEventListener('unhandledrejection')`(Promise 未处理)
  - Vue:`app.config.errorHandler` / `errorCaptured`
- **上报内容**:错误信息、堆栈、路由、用户/会话、UA、时间
- **堆栈还原**:线上代码压缩,需 **sourcemap** 还原行号;注意 sourcemap 不能公开部署(源码泄露风险),可内网存储
- **量级控制**:采样率、错误去重聚合、批量上报,防止刷爆接口
- 成熟方案:Sentry / 自研上报网关

### 6. Vite 和 Webpack 的区别

**【详细解答】**

- **开发模式**:Vite 基于原生 ESM,启动秒开、按需编译、HMR 快;Webpack 需全量打包,大项目启动慢
- **构建**:Vite 生产用 Rollup;Webpack 用自身打包器

- 银行老项目多为 Webpack,新项目倾向 Vite;兼容老浏览器时注意 Vite 构建目标配置

### 7. Git 团队协作

**【详细解答】**

- **冲突解决**:`git pull --rebase` 保持线性 → 冲突文件手动合并(保留双方必要代码)→ `git add` → `git rebase --continue` → push
- **分支规范**:main(受保护,可发布)/ develop(开发集成分支)/ feature/xxx(功能分支)/ hotfix(紧急修复)/ release(发版)
- **提交规范**:Conventional Commits

  - 配合 husky + commitlint 强制校验
- 原则:小步提交、提交信息清晰、不直接往 main 提交代码

### 8. 移动端适配方案

- 细节:1px 边框问题(0.5px / transform scale)、`viewport-fit=cover` 适配刘海屏安全区(`env(safe-area-inset-*)`)、图片 2x/3x

## 五、网络与前端安全(银行重点)

### 1. XSS 攻击与防御

**【详细解答】**

- 定义:攻击者注入恶意脚本到页面执行,可窃取 cookie(会话劫持)、篡改页面、钓鱼
- **类型**:
  - 反射型:恶意链接参数带脚本,一次性
  - 存储型:恶意脚本存服务器,所有访问用户中招(危害最大,如评论区)
  - DOM 型:前端 JS 把不可信数据写入 DOM(innerHTML)
- **防御**:
  1. **输出转义**:渲染时编码 `< > & " '`(Vue 插值默认转义)
  2. **v-html 慎用**:只用可信数据,或先白名单过滤
  3. **HttpOnly Cookie**:脚本读不到 cookie
  4. **CSP**:限制脚本来源
  5. 输入校验:长度、格式、特殊字符

### 2. CSRF 攻击与防御

**【详细解答】**

- 定义:诱导用户访问恶意网站,利用用户**已登录的 cookie** 伪造请求执行操作(如转账、改密)
- 原理:浏览器自动携带 cookie,服务器无法区分请求是否用户本意
- **防御**:
  1. 校验 **Origin / Referer** 请求头(简单有效)
  2. **CSRF Token**:请求携带随机 token,服务端校验(不匹配拒绝)
  3. **SameSite Cookie**:`Set-Cookie: SameSite=Strict/Lax`,跨站请求不携带 cookie
  4. **关键操作二次验证**:短信验证码、支付密码、人脸——银行系统标配

### 3. 敏感数据脱敏

**【详细解答】**

- 示例:手机号 `138****1234`、身份证 `310***********1234`、卡号仅显示后四位
- **原则:能后端脱敏就不前端做**——数据在接口层脱敏,前端拿到的就是脱敏数据,更安全
- 前端兜底:展示层统一过滤器/指令(如 `v-mask`),防止某接口漏脱敏
- 配套:
  - 敏感信息不进日志、不存 localStorage
  - 全程 HTTPS 加密传输
  - 导出文件同样脱敏
  - **审计**:记录"谁在什么时候查看了什么敏感数据"(银行合规要求)

### 4. token 和 cookie 的区别?登录态维护

**【详细解答】**

| 对比       | Cookie           | Token                                  |
| ---------- | ---------------- | -------------------------------------- |
| 存储       | 浏览器,自动携带  | 前端存(localStorage/内存),手动放请求头 |
| HttpOnly   | 支持,防脚本读取  | 不适用                                 |
| 跨域       | 受限(需配置)     | 无限制                                 |
| 服务端状态 | 会话状态(或 JWT) | 无状态(JWT)或需刷新                    |

- **银行常用方案**:access token(短时效,如 30 分钟)+ refresh token(长时效)
  - axios 请求拦截器注入 access token
  - 401 时用 refresh token 换新 access token 后重试原请求
  - refresh 也失效 → 清登录态跳登录页
- 安全:token 存内存最安全(刷新即丢),次选 sessionStorage;敏感系统配合 HttpOnly cookie 方案

### 5. HTTPS 加密过程详解

**【详细解答】**

1. 客户端发起 HTTPS 请求
2. 服务器返回**数字证书**(含公钥、域名、CA 签名、有效期)
3. 客户端验证证书(信任链、域名匹配、是否过期;失败则告警)
4. 客户端生成随机**对称密钥**(会话密钥),用服务器公钥加密后发送
5. 服务器用私钥解密获得对称密钥
6. 之后双方用对称密钥加密通信(速度快)

- 核心思想:**非对称加密做密钥协商,对称加密做数据传输**——兼顾安全与性能
- TLS 握手可优化:会话复用(Resumption)、HTTP/2 多路复用减少握手开销

### 6. 常见 HTTP 状态码

**【详细解答】**

- 2xx:200 OK、201 Created、204 No Content
- 3xx:301 永久重定向、302 临时重定向、304 协商缓存命中、307/308 保持方法重定向
- 4xx:400 参数错误、401 未认证、403 无权限、404 不存在、408 超时、429 请求过多
- 5xx:500 服务器内部错误、502 网关错误、503 服务不可用、504 网关超时
- **重点区分 401 vs 403**:401 = 没登录/凭证无效;403 = 已登录但没有权限
- 重点区分 502 vs 504:502 = 网关拿到无效响应;504 = 网关等待上游超时

### 7. axios 拦截器封装

**【详细解答】**

```js
const http = axios.create({ baseURL: "/api", timeout: 10000 });

// 请求拦截:注入 token、加签名、防缓存
http.interceptors.request.use(
  (config) => {
    config.headers.Authorization = `Bearer ${getToken()}`;
    return config;
  },
  (err) => Promise.reject(err),
);

// 响应拦截:统一业务码处理、401、错误提示
http.interceptors.response.use(
  (res) => {
    const { code, data, message } = res.data;
    if (code === 0) return data; // 业务成功
    if (code === 401) {
      clearAuth();
      location.href = "/login";
    }
    ElMessage.error(message || "请求失败");
    return Promise.reject(new Error(message));
  },
  (err) => {
    // 网络错误/超时统一提示;可做重试
    ElMessage.error("网络异常,请稍后重试");
    return Promise.reject(err);
  },
);
```

- 加分:取消重复请求(AbortController)、接口耗时上报、失败重试、loading 统一管理

### 8. CSP 内容安全策略

**【详细解答】**

- 定义:通过 HTTP 响应头或 meta 标签,声明页面允许加载的资源来源,浏览器强制执行
- 示例:
  ```
  Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: https:
  ```
- 作用:即使攻击者注入脚本,浏览器也不执行非白名单来源的脚本 → 有效缓解 XSS
- 注意:配置过严可能误伤(内联脚本、CDN 资源),需灰度调整
- 其他安全实践:密码不明文存储/传输、接口幂等防重复提交、`X-Content-Type-Options: nosniff` 等安全头

## 六、银行业务场景题

### 1. 如果让你做一个"转账"页面

**【详细解答】**

从前端到整体的完整考虑:

1. **防重复提交(重点)**:
   - 前端:提交后按钮置灰 + loading,禁止二次点击
   - 后端配合:幂等键(前端生成 UUID,转账接口以幂等键判重)——即使前端漏了,后端也能挡住重复转账
2. **表单校验**:金额(>0、两位小数、上限)、收款账号格式、收款人姓名、备注长度;提交前二次确认弹窗(展示完整信息让用户核对)
3. **安全验证**:短信验证码 / 人脸 / U 盾 二次验证(银行转账标配);金额超过阈值触发更严格验证
4. **数据安全**:HTTPS、卡号只显示后四位、不存敏感数据、转账凭证下载脱敏
5. **结果处理**:转账是异步操作——轮询或服务端推送最终状态;成功展示回执,失败(余额不足/账号无效/风控拦截)给明确友好提示与处理建议
6. **合规审计**:埋点记录操作留痕(谁、何时、转给谁、金额),满足审计要求
7. **异常场景**:网络超时提示"结果未知,请查询交易记录,切勿重复提交"——银行系统对未知结果的经典处理

**【回答话术】** "转账页面核心是安全与防重:按钮置灰 + 后端幂等键防重复提交,金额账号严格校验,敏感操作二次验证,结果未知时提示用户先查交易记录而不是重复提交,全程埋点留痕满足审计。"

### 2. 银行系统和你做过的互联网系统有什么不同

**【详细解答】**

- **稳定优先**:不允许"先上线再改";变更走审批、灰度发布、双人复核;变更窗口固定
- **安全合规优先**:数据脱敏、审计留痕、防攻击;数据不出行;敏感操作可追溯
- **技术约束**:内网环境无法访问公网 CDN;可能要求兼容老浏览器(如 IE/国产浏览器信创要求);依赖镜像源受限
- **流程规范**:需求评审 → 开发 → 自测 → 联调 → 测试(SIT/UAT)→ 上线窗口 → 回归;文档要求齐全
- **存量系统多**:常对接老系统、历史逻辑,不能随意重构,改动需评估影响面
- 表达要点:体现"我理解并接受这种严谨文化",而不是抱怨流程多

### 3. 埋点上报为什么用 sendBeacon

**【详细解答】**

- 问题:页面跳转/关闭时,普通 fetch/ajax 请求会被浏览器**中断**,数据丢失
- 方案:`navigator.sendBeacon(url, data)`:
  - 异步发送,不影响页面性能
  - 页面卸载时也能送达(浏览器负责送达)
  - 适合:PV 统计、日志上报、用户离开页面的行为上报
- 局限:只能 POST、数据量有限(通常 64KB 内)、无响应回调——常规埋点仍用批量 fetch,只有卸载场景用 sendBeacon

### 4. ECharts 大数据量图表优化

**【详细解答】**

- **降采样**:`sampling: 'lttb'` 保留趋势特征,减少绘制点(上万点时)
- **大数据渲染**:`large: true` 开启,折线图大数据量时用画布整体绘制,不再逐个画点
- **按需引入**:只引入用到的图表,`echarts/core` + 按需注册,包体积从 1MB 级降到几百 KB
- **生命周期**:图表不用时 `chart.dispose()`,组件卸载时一定要释放,防内存泄漏
- **交互优化**:`dataZoom` 只渲染可视区间;数据更新用 `setOption` 增量合并而非整体重建
- 大屏场景:背景用 CSS 渐变/图片,减少 DOM 层级;多个图表共用一个实例管理
