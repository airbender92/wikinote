# React 循环渲染不要用 index 作为 key

> 核心：`key` 是 React Virtual‑DOM diff 的**唯一标识**，用来判断节点是**更新、复用、删除还是新增**。
> 用数组下标 `index` 当 key，数组发生**增、删、排序**时，key 和真实数据错位，导致 diff 判断出错，引发组件错误复用、状态错乱。

## 1.key 的作用

React diff 在对比新旧虚拟DOM列表：

1. 拿**新节点的 key**，去旧节点集合里找相同 key；
2. 找到：复用旧DOM，只做更新；
3. 找不到：销毁旧节点，创建新DOM。

> key 应该代表**这条业务数据的唯一身份**，而不是它在数组里排在第几。

## 2. index 做 key 会出问题的场景

示例数组：

```
const list = [
  { id:1, name:'A' },
  { id:2, name:'B' },
  { id:3, name:'C' }
]
```

用 index 当 key：

```
{list.map((item, index)=> (
  <div key={index}>{item.name}</div>
))}
```

### 场景1：数组头部删除元素

删除第一条 A，数组变成 `[B,C]`

- 旧key：0(A), 1(B), 2(C)
- 新key：0(B), 1(C)

diff 看到：
key=0 还存在 → **复用原来0位置DOM，把内容A改成B**
key=1 还存在 → 复用原来1位置DOM，把B改成C
key=2 消失 → 删除

**表象：DOM没有删除第一个节点，而是原地修改内容。**
如果这个div下面是有内部state的组件（输入框、勾选状态、动画）：

> 组件实例被复用，但是数据换了，**组件内部state保留旧数据，UI状态错乱**。

### 场景2：数组头部新增元素

头部插入一条 D。
旧key：0(A),1(B),2(C)
新key：0(D),1(A),2(B),3(C)

diff：
key0复用旧DOM渲染D；key1复用旧DOM渲染A……全部原地更新；最后新增key3。

> 明明只增加一条，却导致**全部列表组件执行更新**，性能变差，内部状态错乱。

### 场景3：排序、打乱顺序

数组顺序调换。index跟着位置变，key全部错位。React不会移动DOM，而是全部原地复用修改，表单、复选框状态全部乱掉。

## 3.什么时候 index 当key暂时不会出问题？

同时满足下面全部条件，index可以临时用：

1. 列表**不会新增、删除、排序**；只做纯展示；
2. 列表item**没有内部state**，没有输入框、复选框等需要保存状态的组件；
3. 仅做简单渲染。

> 业务开发中很难保证以后不改数组，所以**不推荐作为常规写法**。

## 4.正确做法

使用业务数据的**唯一id**：数据库id、唯一业务标识。

```
{list.map(item=> (
  <div key={item.id}>{item.name}</div>
))}
```

此时删除第一条A：
旧key：1(A),2(B),3(C)
新key：2(B),3(C)

diff发现 key=1消失，直接销毁A对应的DOM；key2、3保持不变，直接复用。DOM操作符合预期，组件状态不会错乱。

## 5.没有id怎么办？

1. 后端补充唯一id；
2. 不要用 Math.random() 当key！>

> 每次render都会生成新随机key，每一轮全部销毁重建DOM，性能灾难。

3. 实在没有唯一标识，可以用库生成稳定唯一值，或者组合多个字段拼接稳定key `key={item.type + '-' + item.code}`，保证每条数据唯一。

## 面试简答

> key是React diff算法用来识别虚拟DOM节点身份的唯一标识，用于节点复用、新增、删除判断。
> 使用index数组下标作为key的问题：
>
> 1. 数组发生头部新增、删除、排序时，index会发生偏移，key和业务数据错位。diff会错误复用DOM组件实例，只更新内容，**组件内部state（输入框勾选、表单状态）保留旧状态，UI错乱**。
> 2. 造成不必要大量组件更新，损耗性能。
>
> index作为key只有在列表不会增删排序、子项无内部状态时才不会暴露问题，但业务迭代很容易踩坑，不推荐。
> 最佳实践：使用业务数据的唯一id作为key；禁止使用Math.random()作为key。

> 一句话记忆：**key代表数据是谁，而不是数据排第几。**
