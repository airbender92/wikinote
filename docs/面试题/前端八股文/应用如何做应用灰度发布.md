# 应用灰度发布（灰度/金丝雀发布）

> **灰度发布（金丝雀 Canary Release）**：让一部分用户先使用新版本，剩下用户继续跑老版本；观察新版本指标、错误日志，确认稳定后，逐步放量全量上线；一旦发现问题，快速切回老版本。
> 核心目标：**降低上线风险，把故障影响范围控制在小部分用户**。

灰度不局限前端；**前端、后端、接口都可以做灰度**。

## 一、灰度常见策略（流量切分规则）

### 1. 按用户特征灰度（精准定向，最常用）

定向特定一小部分用户，不是随机流量：

- 用户ID / 用户ID哈希取模：`userId % 100 < 10` → 10%用户进入新版本
- 用户白名单：指定测试账号、内部员工账号优先灰度
- 用户标签：内部用户、beta测试用户、VIP用户
- 地域：某几个城市先放量

> 优点：固定用户始终走同一版本，用户体验连贯；适合业务系统。

### 2. 按百分比流量灰度（随机流量）

按比例随机切流量：10%流量新版本，90%老版本。

> 缺点：同一个用户刷新可能一会新版本一会老版本；适合无状态接口，**不适合前端页面**。

### 3. 设备/客户端版本灰度

按客户端版本号、设备、浏览器灰度。

## 二、后端服务灰度怎么做

### 架构前提

一般需要网关层（Nginx / Spring Cloud Gateway / Kong / APISIX）或者服务治理框架。

1. **网关层灰度（最主流）**
   网关拿到请求，根据灰度规则（userId、header、ip）判断：

- 命中灰度规则 → 请求转发到**灰度后端服务实例**
- 未命中 → 转发到生产老实例

> 部署两套服务：老版本集群、灰度版本集群。

2. 服务注册中心 + 权重（注册中心灰度）
   同一个服务名，注册两组实例：

- 灰度实例设置权重小；生产实例权重大。
  根据请求上下文，让灰度流量路由到灰度实例。

3. 应用内代码灰度（本地开关）
   代码里面写if判断，根据灰度配置，走新逻辑/老逻辑。

> 缺点：灰度代码会残留在代码里，后期要清理；适合小功能快速灰度，不适合大规模。

### 灰度配置中心

配置中心（Nacos/Apollo）存放灰度规则：白名单、百分比、开关；**不用改代码，动态调整灰度比例**。

## 三、前端应用如何灰度（重点）

前端灰度难点：**前端资源是静态文件（js/css），浏览器缓存很强**。
前端灰度两种主流方案：

### 方案A：多套前端资源包（独立域名 / path路径）

1. 构建出两套资源：老版本、灰度版本。
   - 正式：`shturl.cc/zxlSqxWZI7PonfsB`
   - 灰度：`shturl.cc/Ka8jm82j5efHjqbHwiFhKK2` 或者子域名 `shturl.cc/qEeY`
2. **由后端/网关做路由判断**：
   用户请求进入，网关读取用户信息判断是否命中灰度：

- 命中灰度：302重定向到灰度index.html；
- 不命中：返回正式index.html。

> 优点：完全隔离，灰度包和正式包互不干扰；
> 缺点：重定向会多一次http请求。

### 方案B：同一套index，JS动态判断加载不同资源（灰度标识下发）

1. 用户登录，接口返回给前端当前用户是否为灰度用户（`isCanary:true/false`）。
2. index.html基础壳不变；js根据灰度标识，动态加载对应版本的js chunk。

### 方案C：CDN + Query参数 / 版本号

静态资源带版本hash；网关根据灰度规则，返回不同版本index html。

> ❌前端不能只靠前端JS本地做灰度判断：
> 如果前端自己随机决定版本，用户刷新来回切换版本；并且可以被用户绕过，不安全。**灰度判断逻辑必须在网关/后端做可信判定**，前端只负责接收结果。

### 前端灰度坑

1. 浏览器强缓存：灰度上线后，用户本地缓存旧静态资源，需要处理cache‑control，版本hash。
2. 本地存储localStorage：新旧版本localStorage字段不兼容，要做好兼容逻辑。
3. 灰度前端必须搭配**灰度后端接口**：新版本前端不能调用老后端接口，容易出现协议不兼容。

## 四、完整灰度发布标准流程（真实团队流程）

1. **预准备**
   - 部署**灰度环境实例（后端+前端）**，代码为新版本；生产环境保持老版本。
   - 配置灰度规则：白名单、用户比例，先只开放内部测试人员。
   - 埋点监控准备：错误率、接口响应时间、业务成功率、日志告警。
   - 准备回滚方案：如何一键切回全部老版本。

2. **第一阶段：白名单内测**
   只允许内部员工、测试账号走新版本；其他人全部老版本。
   验证核心业务流程，看报错、监控指标。

3. **第二阶段：小流量放量**
   逐步放大灰度比例：5% →10% →20% →50%。
   每一步观察一段时间，看异常指标。

> 一旦出现错误飙升，立刻停止放量，评估是否回滚。

4. **第三阶段：全量**
   全部流量切新版本；确认运行稳定。

5. **收尾清理**

- 下线老版本服务实例；
- 清理灰度配置、灰度分支、代码里面灰度if‑else死代码；
- 记录发布文档。

> 灰度不是一定要走到100%；如果发现严重bug，可以随时**终止灰度，全部切回老版本**。

## 五、灰度 vs 蓝绿发布，区分（面试高频）

1. **灰度（金丝雀 Canary）**
   同时存在新版本、老版本；**一部分用户新，一部分用户老**；逐步放量。
   资源成本较低；流量逐步迁移；故障只影响灰度用户。

2. **蓝绿发布 Blue‑Green**
   两套完整等价集群：蓝=老版本，绿=新版本。
   全部流量一瞬间切到绿；出问题瞬间切回蓝。

> 特点：**没有中间混合状态，要么全老，要么全新**；需要双倍服务器资源。适合不能接受新旧版本共存的系统。

## 六、风险点 & 注意事项

1. **新旧版本兼容性最重要**

- 接口向前兼容；数据库表结构变更要兼容新旧代码同时运行；

> 如果数据库做了不兼容变更，不能灰度，只能蓝绿或者停机发布。

2. 会话、状态一致性
   同一个用户不能一会新一会老；尽量用**用户ID哈希灰度**，不要随机百分比流量。

3. 监控告警必须提前配置
   重点看：错误率、5xx/4xx、接口耗时、业务异常、前端JS报错。没有监控不要灰度。

4. 灰度环境和生产环境配置要保持一致，不能配置不一样测出来没问题，全量就崩。

5. 灰度代码残留问题：`if(isCanary){新逻辑}else{老逻辑}`，全量上线完成，记得删除灰度分支代码。

6. 回滚预案：上线前就要想好怎么回滚，不要等出问题临时想方案。

## 面试简答

> 灰度发布（金丝雀发布），将新版本只开放给一小部分用户使用，观察系统指标，验证稳定后逐步放大流量直至全量，故障可以快速回滚，降低上线风险。

1. **灰度路由策略**：支持白名单、用户ID哈希取模、百分比流量、地域；优先按用户特征，保证同一用户版本固定。
2. **后端实现**：一般在网关层（Gateway/Nginx）根据请求上下文做路由，将灰度流量转发到灰度实例；也可以使用配置中心动态管理灰度规则；不推荐大量业务代码内写灰度if，容易残留垃圾代码。
3. **前端灰度**：静态资源特性，一般网关判断用户是否命中灰度，重定向到灰度版本静态资源；**灰度判定逻辑必须在服务端，不能完全交给前端JS**，同时要处理静态资源缓存；新版本前端需要配套灰度后端接口，保证协议兼容。
4. **标准流程：白名单内测 → 小比例放量 → 逐步全量 → 清理灰度资源**；全程监控错误率、业务指标，准备回滚方案。
5. 和蓝绿发布区分：灰度是部分用户新部分老，逐步切量；蓝绿两套完整集群，一次性全部切换，需要双倍资源。
6. 重要前提：数据库、接口必须做到新旧版本兼容；不兼容变更不适合灰度发布。
