# 线上用户反馈问题标准化处理流程

用户反馈来源：客服工单、IM反馈、企业微信、测试反馈、监控告警、用户截图、复现步骤、bug描述。
核心目标：**信息收全 → 定级 → 复现定位 → 修复 → 验证闭环 → 沉淀**，避免：信息不全来回追问、问题遗漏、优先级混乱、修复完无确认、同类问题反复出现。

整套分为：**接收录入 → 信息补全 & 问题分类定级 → 排查定位 → 修复开发 → 测试验证上线 → 闭环回复用户 → 复盘沉淀**。

## 一、接收&录入：统一工单模板（最重要）

很多问题卡壳，根源是**用户反馈信息残缺**：只说“页面报错了”，没有截图、没有操作步骤、环境。
统一工单/issue模板，强制必填关键字段，用户/客服提交时尽量收集完整信息。

### 标准工单字段模板

> 内部Jira / GitLab Issue / 飞书工单都可以直接套用

1. **问题标题**：简短概括现象，例：【列表页】批量点击删除偶尔请求失败，不要写“系统有bug”
2. **问题现象**：用户看到什么表现（报错toast？白屏？数据不对？样式错乱？）
3. **复现步骤**：
   1. 进入哪个页面路由
   2. 做了哪些操作
   3. 出现异常
4. **预期结果 / 实际结果**
5. **附件**：截图、录屏、报错控制台截图、网络面板截图
6. **环境信息**
   - 浏览器及版本
   - 设备（PC/手机）
   - 用户账号、账号角色
   - 访问环境：生产/预发
7. **发生时间**：什么时候出现，偶现还是必现，发生频率（必现/偶尔/概率性出现）
8. **监控关联ID**：前端监控sentry/eventId（有就填，直接跳转监控看堆栈、面包屑）
9. **影响范围**：多少用户遇到，个别用户 / 全部用户 / 部分角色
10. **优先级&严重等级**

> 如果用户提供信息不全，不要直接转给开发；客服先按模板追问补齐信息，减少开发无效排查。

## 二、问题分级定级（ severity 严重等级）

用来决定排期、响应速度，避免小bug抢占核心bug资源。

| P0 阻断 | 线上阻断业务，大面积用户不可用，白屏、核心流程完全走不通，大量用户报错。 | **立即处理，停止次要需求，紧急修复** |
| ------- | ------------------------------------------------------------------------ | ------------------------------------ |
| P1 严重 | 核心功能异常，部分用户受影响，不全局阻断，但影响主要业务。               | 当天修复，优先排期                   |
| P2 一般 | 次要功能异常，样式问题、边缘场景，不影响主流程。                         | 迭代内修复                           |
| P3 优化 | 体验建议、交互优化，不算bug。                                            | 排需求迭代评估                       |

> 判定两个关键维度：**影响用户规模 + 是否阻断核心业务**。
> 偶现bug，只要影响核心业务，等级不能定太低。

## 三、排查定位阶段（开发处理）

拿到工单后，分几步排查：

1. **优先核对前端监控**
   - 根据eventId/userId，查看错误堆栈、面包屑（用户操作轨迹）、接口请求记录
   - 看是否已有同类上报，判断是个案还是批量问题
   - 有source‑map解析压缩堆栈，定位代码位置
2. **尝试复现问题**
   - 必现：本地/预发复现，直接调试
   - **偶现问题（线上最头疼）**
     - 严格按照用户复现步骤
     - 核对用户浏览器版本、网络环境
     - 查看监控面包屑，还原用户真实操作路径
     - git bisect 定位引入bug的commit
     - 查看网络：跨域、并发请求、时序问题、缓存、blob、resize、selection等边界场景
3. **区分问题归属**
   - 前端bug / 后端接口bug / 第三方服务问题 / 用户环境问题（浏览器版本、插件干扰、网络）
   - 如果是后端问题：工单转给后端，明确复现步骤、接口入参出参；
   - 如果是用户本地环境问题：整理规避方案，回复用户。

> 工单内持续写排查备注，不要只放在脑子里，方便交接。

**重点：偶现问题找不到复现场景，不要搁置，要把监控证据写到工单，标记“偶现，等待更多用户样本”，持续收集信息。**

## 四、修复阶段

1. 确认根因，不要只修表面现象（比如单纯catch屏蔽报错，不解决根源）
2. 新建分支修复，关联工单ID
3. 写注释：说明这个bug产生原因
4. **补充测试用例**，防止回归

> 紧急P0/P1：走热修复流程，区别普通迭代；记录热修复版本号。

## 五、验证环节（必须闭环，不能开发自测完就关闭工单）

1. 开发自测；
2. 测试人员按照工单里的**复现步骤，完整回归验证**；
3. 验证环境：预发验证，P0紧急问题上线后，还要观察线上监控：确认该类型错误上报量下降/消失。

> ✅关键点：不能只看本地修好；要看**线上监控错误趋势**，确认问题真实消失。

## 六、闭环：回复用户 & 工单关闭

1. 根据等级，同步用户进度：受理中、修复中、已上线；
2. 区分三种回复口径：
   1. 已修复：告知用户版本，刷新即可；
   2. 暂时无法复现：告知已知该问题，持续收集日志监控；
   3. 用户环境/第三方问题：给出规避方案。
3. **工单不可以直接关闭，必须确认：用户确认解决 OR 监控确认问题消失**。

## 七、复盘沉淀（防止重复踩坑）

每一个P0/P1问题，必须做简短复盘，沉淀3类产出：

1. **根因记录**：issue中记录根本原因，为什么会流出到线上（代码问题？测试漏测？边界场景没想到？监控缺失？）
2. **改进措施**
   - 补充单元测试/功能测试用例；
   - 补充前端监控埋点（之前没有捕获该异常）；
   - 修改编码规范；
   - 调整CR评审关注点；
3. 同类bug做聚合，定期汇总线上高频问题，团队同步。

## 八、高频棘手场景处理

### 场景1：用户反馈偶现bug，本地无法复现

> 线上最常见，也是最耗时间

1. 务必拿到监控eventId，看面包屑、堆栈、请求序列；
2. 引导用户提供：录屏、浏览器版本、是否安装插件（很多浏览器插件会篡改DOM/js，产生诡异bug）；
3. 必要时针对性加强监控：增加埋点，采集更多上下文，等待下一次用户触发；
4. 工单状态标记：【偶现，待更多样本】，不关闭，定期跟进。

### 场景2：多个用户反馈同一个问题

1. 工单做关联，不要重复新建多个issue；主工单记录，其他工单关联主工单ID，避免重复处理。

### 场景3：用户报bug，实际是用户操作理解问题，不是程序bug

记录到工单，关闭前更新产品说明、优化交互提示，减少后续同类反馈。

## 九、完整流程极简流程图

```
用户反馈 → 客服按模板收集完整信息 → 创建工单（标题+现象+复现步骤+截图+环境+监控ID）
    ↓
产品/技术做P0‑P3定级
    ↓
开发：查看监控 → 尝试复现 → 定位根因 → 判断归属前端/后端/第三方
    ↓
代码修复，关联工单
    ↓
测试按复现步骤回归验证；上线后核对线上监控指标
    ↓
回复用户，确认问题解决
    ↓
关闭工单；P0/P1完成复盘，沉淀用例、监控、规范
```

## 十、常见踩坑

1. ❌缺少标准化模板，只拿到一句“页面有问题”，开发反复来回询问，浪费时间。
2. ❌复现步骤写得模糊：“操作一下就报错”，没有精确步骤。
3. ❌修完直接关工单，**不核对线上监控，不问用户确认**，问题实际没解决。
4. ❌偶现bug找不到复现就直接关闭issue，问题后续再次爆发。
5. ❌不分优先级，所有bug同等对待，核心阻断问题被淹没。
6. ❌修复只掩盖报错，不解决根因。
7. ❌缺少复盘，同类bug反复出现。
