# 扫码登录实现原理

核心流程：**网页生成二维码 → 二维码绑定唯一令牌 → 手机APP扫描确认 → 网页轮询等待登录结果 → 网页拿到token完成登录**

> 角色：浏览器(网页端)、服务端、手机App

## 整体完整流程

1. **网页端打开扫码登录页**
   网页请求后端，后端生成一个**扫码唯一标识 `qrId`（二维码ID）**，该ID存入服务端，状态标记为：`待扫描`。
   网页把 `qrId` 编码生成二维码图片展示给用户。

> 二维码内容示例：`shturl.cc/aP2PqzJA8cLQtpnpdnWZEQVBrLp`

2. **网页轮询查询扫码状态**
   网页开启轮询（短轮询 / SSE / WebSocket），不停调用接口：`getQrStatus(qrId)`
   查询该qrId状态，状态有三种：

- 0：待扫描
- 1：已扫描，等待确认
- 2：确认登录成功
- -1：二维码过期

3. **用户用App扫描二维码**
   App解析二维码拿到`qrId`，App本身已经是登录状态（手机已经登录账号）。
   App调用后端接口：**上报已扫描 `scan(qrId)`**
   服务端更新状态为：`已扫描，等待确认`。此时网页轮询会感知到状态变更，页面提示：**已扫码，请在手机确认**。

4. **手机App弹窗，用户点击【确认登录】**
   App提交确认接口 `confirm(qrId)`，带上当前App登录用户的userId。
   服务端：把 `userId` 和 `qrId` 做绑定，修改状态为**登录成功**，生成登录凭证(token)。

5. **网页轮询检测到登录成功**
   后端返回token给网页，网页保存token(cookie/localStorage)，跳转主页，登录完成。

6. **二维码过期**
   服务端设置qrId有效期（一般2分钟），超时直接作废该qrId，网页提示二维码失效，刷新重新获取。

---

## 三种状态通知方案（网页怎么知道扫码完成）

### 1. 短轮询（最常用，简单）

前端每隔1~2秒发http请求查询二维码状态。
优点：实现简单，兼容性好；缺点：请求多，有延迟。

### 2. SSE 服务器推送

建立长连接，服务端状态变更主动推送给前端，不用频繁请求。

### 3. WebSocket

前后端长连接，实时推送；适合高并发场景；需要维护ws服务。

> 绝大多数网站扫码登录用**短轮询**。

## 安全关键点（必考点）

1. **qrId一次性，过期作废**，不能重复使用，防止重放攻击。
2. App端必须**本身已经登录**，不能未登录手机直接扫码登录。
3. 扫码只是告知服务器“手机看到这个码了”，**必须用户手动点击确认登录，不能扫完直接登录**，防止恶意二维码钓鱼。
4. token不能放在二维码内！二维码只放随机qrId，真正登录凭证由后端生成下发。
5. 防止钓鱼：App扫码时展示网页的业务域名，让用户核对，提示是否是可信网站。

## 简易时序图文字版

```
浏览器        服务端          APP
  |  请求二维码  |
  |----------->|
  |<-qrId+二维码|
  | 轮询状态(qrId)
  |----------->|
                |       用户扫码
                |<----App上报scan(qrId)
                |更新状态：已扫码
  |<----返回状态已扫码
页面提示：手机确认
                | 用户点击确认
                |<----App confirm(qrId,userId)
                |生成token，状态成功
  |<----轮询返回成功+token
保存token，登录成功
```

## 补充：小程序扫码登录逻辑略有不同

小程序扫码登录，小程序本身不能直接扫网页二维码；一般网页生成二维码，小程序扫描，调用后端接口授权。

## 面试常问

> Q：为什么扫码之后还要手机点确认，不能一扫就登录？
> A：钓鱼风险。攻击者把二维码放到钓鱼网站，如果你一扫直接登录，账号就被盗。必须人工确认，确认“我确实要在这个网页登录”。

> Q：二维码里面存的是什么？是token吗？
> A：不是token，是临时随机qrId。token只在确认登录之后服务端下发给浏览器。
