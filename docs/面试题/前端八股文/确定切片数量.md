# 大文件切片上传：切片数量确定的考量因素

> 切片数量 = 文件总大小 / 单切片大小；**切片数量本质是由「单切片大小」间接决定**，不是直接指定数量，业务上一般配置切片大小，再算出切片总数。下面分维度讲所有关键考量点。

## 1. 文件本身大小

- 文件越小：切片不宜过多。比如几十MB文件，切几十片会造成大量http请求开销，甚至比直接上传更慢。小文件可以直接走**整文件直传，不走切片**。
- 文件越大：切片数量会变多，但不能无限大。几十GB大文件，切片不能切得太小，否则切片数量爆炸。

> 举例：10GB文件，如果切片1MB，就会产生10000个切片，请求数巨大。

## 2. 单切片大小（最核心）

切片大小直接决定切片数量。

### 切片太小 → 切片数量过多带来问题

1. HTTP请求数量暴涨，每个切片都要一次网络请求，带来大量握手、头信息开销；
2. 服务端要存储大量切片临时文件，IO、数据库记录（每个切片记录状态）压力飙升；
3. 并发限制：浏览器/客户端有最大并发请求数，切片太多会排队，上传反而变慢；
4. 合并阶段：服务端需要读取、合并成千上万碎片，CPU、磁盘IO压力大。

### 切片太大 → 切片数量过少带来问题

1. 单个切片网络失败，需要重传**整个大片**，断点续传收益变低；网络抖动环境下体验差；
2. 单切片超时风险：网络差的时候大片容易触发http超时；
3. 内存占用：客户端读取大块切片，内存占用升高。

> 行业常用参考：
>
> - 普通场景：**2MB~10MB** 单切片；
> - 超大文件（>10GB）：5‑20MB；
> - 弱网环境：偏小，2‑5MB；
> - 内网高速传输：可以放大切片，减少切片数量。

## 3. 客户端侧约束

1. **浏览器并发请求上限**
   浏览器同一域名并发一般6‑8个。如果切片数量远大于并发数，大量请求排队，上传速度上不去。切片数量要配合并发数做限流控制。
2. **内存占用**
   JS读取文件切片，分片过大会占用更多内存；切片过小循环处理次数多，CPU开销上升。
3. **断点续传与重试**
   切片数量多，单切片体积小，失败只重传小片；但是要维护每个切片的md5/状态，前端状态管理复杂度上升。
4. 文件读取API性能：Blob、File.slice 本身有性能开销，切片数量越多，slice调用次数越多。

## 4. 服务端侧约束

1. **临时碎片存储**
   每一个切片对应一个临时文件，切片数量巨大，磁盘inode消耗巨大，大量小文件会拖慢文件系统。很多文件系统对目录下文件数量有性能临界点。
2. **数据库压力**
   每一片通常要记录：文件id、切片序号、是否上传完成、md5。切片数量越大，数据库写入查询越多。
3. **合并接口压力**
   全部切片上传完成后触发合并。切片越多，合并需要打开读取的文件数越多，IO耗时越高。极端情况合并接口超时。
4. **服务端超时时间**
   单个切片请求不能超过服务端Nginx、网关设置的超时。切片过大容易超时；切片过多请求总数多，整体总耗时拉长。
5. 对象存储限制（如果对接OSS）
   部分对象存储分片上传有：**最大分片数量限制**（例如阿里云OSS默认最多10000片）。

> ⚠️ 硬约束：**切片数量不能超过存储允许最大分片数**，这是很多人踩坑点。
> 比如OSS最多10000分片，10GB文件，如果设置切片1MB，得到10000分片刚好临界；大于10GB就会超限报错，此时就必须调大切片大小，减少切片数量。

## 5. 网络环境因素

1. **弱网/公网**：倾向切片数量多一点（单片小），失败重传代价小；但也不能无限多。
2. **内网、高速专线**：可以增大单片大小，减少切片数量，减少请求开销。
3. 网络抖动高：单片不宜过大；带宽很高，单片可以适当放大。

## 6. 业务策略：阈值开关（很重要）

不要所有文件都无脑切片。

- 设置一个**切片开启阈值**：例如文件大于 50MB 才启用切片上传；小于阈值直接整文件上传，切片数量=0。避免小文件产生一堆无效切片请求。

## 7. 边界兜底逻辑

1. 最后一片：文件总大小不一定刚好整除切片大小，**最后一片会小于等于分片大小**，计算切片数量要向上取整。

```js
// 切片数量计算公式
const chunkCount = Math.ceil(fileSize / chunkSize);
```

2. 上限保护：算出的切片数量如果超过底层存储最大分片数，要自动增大chunkSize，降低切片数量，防止报错。

## 8. 常见踩坑总结

1. 只固定写死切片大小，不考虑存储最大分片限制，超大文件直接报错；
2. 小文件也走切片，几十个http请求，性能比直传还差；
3. 切片切得极小，成千上万碎片，服务端小文件爆炸，合并卡死；
4. 切片数量远超浏览器并发数，大量请求排队，上传速度不升反降。

## 简单落地策略示例

```
1. 文件 < 50MB：不切片，直接上传
2. 文件 >=50MB：
   预估切片大小默认 5MB
   计算切片数量 = Math.ceil(fileSize / 5MB)
   如果 切片数量 > 存储最大分片数(比如10000)：
       重新计算 chunkSize = ceil(fileSize / 9000)  //留一点余量
   使用新chunkSize，再算最终切片数量
```
