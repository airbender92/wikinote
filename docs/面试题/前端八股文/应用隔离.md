# 微前端为什么大多不选用 iframe 做隔离

> iframe 天然就有很强的隔离：JS 沙箱、CSS完全隔离、全局window隔离，不会污染主应用。**隔离能力iframe很强，但它有大量难以解决的业务痛点，所以主流微前端框架（qiankun、micro‑app）不用iframe作为首选方案，而是采用JS沙箱+样式隔离。**

## 一、iframe 的优点（为什么有人会想到用iframe）

1. **真正强隔离**：子应用拥有独立完整 `window`、`document`。JS、CSS、全局变量、事件完全隔离，几乎不会发生样式污染、变量冲突。
2. 技术栈完全无关，子应用随便什么框架，不需要改造子应用代码。
3. 浏览器原生能力，无框架侵入。

## 二、iframe致命缺点（核心痛点，也是业界放弃iframe做微前端主方案的原因）

### 1. 应用之间通信非常别扭、体验差

主应用与iframe子应用通信只能靠 `postMessage`。

- 参数只能传结构化克隆数据，**不能传函数、DOM对象**；
- 需要大量事件监听，消息需要维护事件ID，容易出现消息丢失、乱序；
- 调用子应用方法、获取子应用返回值，要封装异步消息，同步逻辑全部改成异步，业务代码改造成本高。

对比 qiankun/micro‑app：子应用可以直接导出方法，主应用可以直接调用，调用更贴近普通函数调用。

### 2. DOM割裂，严重影响页面布局

iframe是独立文档：

1. **子应用弹窗、下拉框、浮层无法溢出iframe边界**

> 最经典坑：子应用里面的下拉、弹窗、日历，会被iframe边框截断，不能浮到主应用之上。
> 弹窗本质只能渲染在iframe内部文档，出不来iframe视口。想要浮到外层，需要把DOM抛到主应用document，改造成本极高。

2. 路由、滚动条两套：主页面滚动条 + iframe内部滚动条，页面出现双重滚动条，交互体验很差。

3. 主应用难以操作子应用DOM；子应用也很难操作主应用DOM。

### 3. 路由体验差

- 浏览器地址栏路由同步麻烦。iframe内部路由变化，不会自动同步浏览器地址；需要自己监听iframe内部history变化，同步主应用url；
- 浏览器前进、后退行为会错乱。

### 4. 浏览器存储、Cookie、跨域限制

1. iframe子应用如果是**跨域地址**：
   - 拿不到父页面localStorage；Cookie受第三方Cookie策略限制，部分浏览器会限制iframe内存储、登录态；Safari隐私策略会严格限制iframe存储。
2. 如果同域iframe，存储可以共享，但隔离性又大打折扣。

### 5. 性能与加载体验

1. 每一个iframe都会创建全新完整浏览器上下文：全新的JS引擎环境、全新文档、全新window。**多个iframe内存开销大**。
2. iframe初始化有额外开销；预加载、缓存复用比较麻烦。
3. iframe白屏：子应用每次挂载相当于新开页面，子应用的首屏加载白屏问题比较明显。

### 6. 样式融合困难

主应用有全局主题、公共头部、侧边栏；子应用UI想要和主应用主题、CSS变量、主题色打通非常麻烦。
iframe内部拿不到主应用css变量、主题样式，需要额外把主题参数通过postMessage传给子应用。

## 三、那为什么市面上微前端框架选择 JS沙箱 + 样式隔离（而不是iframe）

以 qiankun / micro‑app 为例：

1. **DOM共享同一个document**
   子应用DOM挂载在主应用的document下。
   ✅弹窗、下拉浮层可以正常溢出，不会被截断；页面只有一套滚动条；布局自然。
   ✅主、子应用可以直接访问DOM；样式变量、主题可以直接共享。

2. **通信简单**
   共享同一个运行环境，可以通过全局对象、props直接传函数、对象，不需要全部走postMessage。

3. 路由天然统一，共用一套history，浏览器前进后退表现正常。

> 代价：失去浏览器原生隔离，所以框架手动实现隔离：
>
> - **JS沙箱**：代理window，防止子应用污染主应用全局变量（快照沙箱、代理沙箱）
> - **样式隔离**：`shadow‑dom` / css加前缀，解决css污染问题。

> JS沙箱是模拟隔离，不是浏览器原生隔离，极端场景依然会有逃逸风险；但换来业务交互体验大幅提升。

## 四、iframe不是完全不能用，什么场景适合用iframe微前端

iframe适合**完全独立的业务，不需要深度交互**：

1. 嵌入第三方系统，完全不希望和主应用有DOM交互；
2. 只做简单展示，没有弹窗、下拉浮层跨应用弹出；
3. 子应用几乎不和主应用频繁调用方法。

> 例如：后台系统嵌入一个第三方报表页面，用iframe很合适。
> 但内部多个业务系统融合，需要频繁交互，大量弹窗下拉，则不适合iframe。

## 五、面试简答

> iframe有浏览器原生强JS、CSS隔离，但不作为微前端主流方案，主要有几个痛点：

1. **DOM隔离带来交互硬伤**：子应用弹窗、下拉浮层无法溢出iframe容器，会被截断；容易出现双重滚动条；DOM无法互通。
2. **通信成本高**：只能依靠postMessage，只能传递可序列化数据，不能传递DOM、函数；同步逻辑全部转为异步，开发复杂度高。
3. **路由同步麻烦**：iframe内部路由不会自动同步浏览器地址栏，前进后退行为容易异常。
4. **浏览器存储限制**：跨域iframe受第三方Cookie、Safari隐私策略限制，登录态、localStorage会受限。
5. 内存开销大，每个iframe创建完整浏览器上下文；主题、CSS变量很难跨框架共享。

> 主流微前端框架（qiankun/micro‑app）选择**共享document + JS模拟沙箱 + 样式隔离**方案：牺牲浏览器原生完全隔离，换取DOM互通、友好的交互体验、简单通信、统一路由；再手动通过沙箱机制解决污染问题。
> iframe适合简单嵌入第三方页面，不适合内部复杂业务微前端。

> 补充：两者取舍
> iframe：隔离强，**交互差**；
> JS沙箱微前端：隔离靠代码模拟，**交互体验好**。
