# 页面退出前发送埋点（上报积压数据）

业务场景：用户关闭标签页、刷新、跳转页面，需要把内存里积压的埋点上报。

> ❗普通 `fetch/axios` 在页面卸载时，浏览器会直接中断请求，**不一定发得出去**。

## 核心方案对比

1. **`beforeunload` + fetch(keepalive:true)** ✅ 现代浏览器首选
2. **`navigator.sendBeacon()`** ✅ 专门为此设计，异步，不会阻塞页面关闭
3. 同步XHR：不推荐，会阻塞页面关闭，体验差，部分浏览器已限制

> 关键点：页面卸载阶段，JS主线程会被终止；普通异步请求会被丢弃。

---

## 1. navigator.sendBeacon【标准方案】

`sendBeacon` 由浏览器后台排队，**页面就算销毁，浏览器依旧会尽力完成网络请求**，不会阻塞关闭页面。

- 限制：**只支持 POST**；数据总大小一般上限约 64KB，适合埋点批量上报。
- 返回 boolean：`true`=浏览器成功加入队列；`false`=队列满/数据超限。

```
/**
 * 退出页面上报积压埋点
 * @param {Array} eventList 积压埋点数组
 */
function flushBeacon(eventList) {
  if (!eventList || eventList.length === 0) return;
  const data = JSON.stringify({ events: eventList });
  // sendBeacon 只能传 Blob / FormData / String
  const blob = new Blob([data], { type: 'application/json; charset=UTF-8' });
  // 接口地址
  const url = '/api/track/beacon';
  const ok = navigator.sendBeacon(url, blob);
  console.log('beacon提交', ok ? '入队成功' : '入队失败');
}

// 监听页面卸载
window.addEventListener('beforeunload', () => {
  // pendingEvents 内存中积压的埋点数组
  flushBeacon(pendingEvents);
});
```

> 后端注意：`sendBeacon` 发Blob，请求头是 `application/json`，后端要能解析body。

### sendBeacon 缺点

1. **无法获取响应状态**，拿不到 http 200/500，不知道成功失败；浏览器只管入队。
2. 数据不能太大，超过64KB会返回false发送失败。
3. 部分老旧浏览器不支持（现在基本不用考虑）。

## 2. fetch keepalive 方案

fetch 设置 `keepalive: true`，页面卸载后请求依然可以完成。
可以拿到响应，支持自定义header，比sendBeacon更灵活。

```
function flushFetchKeepalive(eventList) {
  if (!eventList || eventList.length === 0) return;
  fetch('/api/track/beacon', {
    method: 'POST',
    keepalive: true, // 关键：页面卸载依然完成请求
    headers: {
      'Content-Type': 'application/json'
    },
    body: JSON.stringify({ events: eventList }),
    // 卸载阶段，不要 await，不要处理响应，主线程马上销毁
  });
}

window.addEventListener('beforeunload', () => {
  flushFetchKeepalive(pendingEvents);
});
```

> ⚠️重要：**不要 await fetch**！`beforeunload` 里面不要等待返回；页面销毁，await后面代码不会执行。只管发，不要处理返回值。

keepalive 限制：每个浏览器有总字节限制（一般 ~64KB），不能超大报文。

### sendBeacon vs fetch keepalive

| 方案                 | 能否拿响应     | 请求类型   | 大数据 | 备注                   |
| -------------------- | -------------- | ---------- | ------ | ---------------------- |
| navigator.sendBeacon | ❌拿不到返回   | POST       | ≤64KB  | 专门埋点上报，兼容性好 |
| fetch keepalive      | ✅可以拿到响应 | 任意method | ≤64KB  | 功能更强，现代浏览器   |

> MDN建议：优先 `sendBeacon`；需要读取响应、自定义请求头时用 `fetch+keepalive`。

## 3. 事件选择：beforeunload / visibilitychange

> ⚠️`beforeunload` 在部分移动端浏览器不一定可靠，有些场景不会触发。

**更好的策略：双保险**

1. 当页面隐藏（切后台、切tab）触发 `visibilitychange`，优先上报；
2. `beforeunload` 做兜底上报。

```
// 页面隐藏时上报（切后台、锁屏）
document.addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'hidden') {
    flushBeacon(pendingEvents);
  }
});

// 关闭/刷新兜底
window.addEventListener('beforeunload', () => {
  flushBeacon(pendingEvents);
});
```

> 移动端很多浏览器，关闭tab不一定触发beforeunload，但**visibilitychange=hidden 很大概率触发**，这是移动端埋点上报的关键。

## 4. 本地缓存兜底（防止埋点丢失）

用户直接杀进程，以上两个API全部失效，请求发不出去。
优化：埋点产生时，除了内存数组，同时写一份到 `localStorage`。
页面下次打开，优先读取localStorage里面残留埋点，立刻上报，上报成功后清空存储。

伪代码逻辑：

```
// 埋点产生时
function addTrack(event) {
  pendingEvents.push(event);
  // 写入本地存储兜底
  const cache = JSON.parse(localStorage.getItem('track_cache') || '[]');
  cache.push(event);
  localStorage.setItem('track_cache', JSON.stringify(cache));
}

// 页面初始化，上报上次残留埋点
function initTrack() {
  const cache = JSON.parse(localStorage.getItem('track_cache') || '[]');
  if(cache.length>0){
    fetch('/api/track/beacon',{
      method:'POST',
      headers:{'Content-Type':'application/json'},
      body:JSON.stringify({events:cache})
    }).then(()=>{
      //上报成功清空缓存
      localStorage.removeItem('track_cache');
    })
  }
}
initTrack();
```

## 5. 避坑清单（高频踩坑）

1. ❌不要用 axios 在 beforeunload 上报：axios底层是fetch/xhr，没有自动开启keepalive，页面关闭请求直接断掉。要用原生fetch手动开启keepalive，或者sendBeacon。
2. ❌不要 await，不要写.then()回调指望执行；页面卸载，回调函数直接被抛弃。
3. ❌不要使用同步XMLHttpRequest，`XMLHttpRequest synchronous` 已废弃，会阻塞页面关闭，浏览器弹出警告。
4. 数据报文不能过大，sendBeacon、keepalive总上限64KB；埋点太多要做分片。
5. Safari 有一些特殊限制：跨域情况下 sendBeacon / keepalive 受CORS策略，后端要配置允许。
6. `beforeunload` 在部分移动端webview，杀进程完全不会触发；**必须配合 localStorage 持久化兜底**。

## 6. Vue3 TS简易埋点上报类示例

```
// track.ts
let pendingEvents: any[] = [];

export class Track {
  // 添加埋点
  static add(event: Record<string, any>) {
    pendingEvents.push(event);
    // 本地存储兜底
    const cache = JSON.parse(localStorage.getItem('track_cache') || '[]');
    cache.push(event);
    localStorage.setItem('track_cache', JSON.stringify(cache));
  }

  // 批量上报
  static flush() {
    if (pendingEvents.length === 0) return;
    const list = [...pendingEvents];
    pendingEvents = []; // 清空内存队列
    const data = JSON.stringify({ events: list });
    const blob = new Blob([data], { type: 'application/json' });
    navigator.sendBeacon('/api/track/beacon', blob);
  }

  // 初始化，上报上次遗留埋点
  static init() {
    const cache = JSON.parse(localStorage.getItem('track_cache') || '[]');
    if (cache.length > 0) {
      fetch('/api/track/beacon', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ events: cache }),
        keepalive: true
      }).then(() => {
        localStorage.removeItem('track_cache');
      }).catch(() => {
        //失败则放回内存队列，等待下次flush
        pendingEvents.push(...cache);
      })
    }
    // 注册监听
    document.addEventListener('visibilitychange', () => {
      if(document.visibilityState === 'hidden') Track.flush();
    })
    window.addEventListener('beforeunload', () => Track.flush());
  }
}

// main.ts
Track.init();
// 使用 Track.add({event:'page_view'})
```

### 总结最佳实践

1. **`visibilitychange(hidden)` 为主，`beforeunload` 兜底**
2. 优先 `navigator.sendBeacon`；需要响应用 `fetch keepalive:true`
3. **localStorage持久化埋点**，下次启动补发，应对杀进程场景
4. 上报时不要await，不要依赖回调；
5. 埋点队列做分片，单批次不要超过几十KB。

你提的这个点非常关键，**上面示例代码确实有缺陷：调用 `flush()` 只清空内存队列 `pendingEvents`，没有清理 localStorage 的缓存**。
会造成严重问题：

> 每次页面隐藏/关闭 flush，localStorage 数据还在；下次打开页面，又把**同一批埋点重新上报一遍，产生重复埋点**。

## 问题根源

- `pendingEvents`：内存队列，flush 之后置空
- `localStorage track_cache`：持久化缓存，flush 上报时**没有删除**
- 只有「页面初始化上报历史缓存成功」才删 localStorage；但**页面运行期间 flush 上报的这批数据，存储里还留着**

### 两种缓存定位要分清

1. **内存队列 pendingEvents**：当前会话新产生埋点，临时存放
2. **localStorage track_cache**：兜底持久缓存，防止杀进程丢失埋点

> 逻辑原则：**只要这批埋点已经成功发出去，就要把 localStorage 对应的记录删掉**。
> 但 `sendBeacon` 最大痛点：**无法知道上报成功还是失败，它只是把请求交给浏览器队列，没有返回结果**。
> 👉 这就是埋点上报的经典难题。

# 正确设计思路

因为 `sendBeacon()` **拿不到成功/失败响应**，分两套策略：

### 方案A：两套队列分开（推荐，解决重复上报）

> 内存队列：本次会话待上报埋点；
> localStorage 只保存**还没有尝试上报过**的埋点。

1. `add()`：埋点进来，同时 push 内存队列，**写入 localStorage**
2. `flush()`：
   - 取出内存队列数据上报（sendBeacon / fetch keepalive）
   - ✅**上报发起后，立刻清空 localStorage缓存**>
   > 风险：极端情况浏览器队列没发出去（网络差、杀进程），埋点丢失。
   > 折中：sendBeacon 场景下，我们无法确认后端收到，只能赌浏览器尽力发送。
3. 页面初始化：读取 localStorage，如果还有残留，说明上次 flush 没成功发出，执行补发。

> 矛盾点：
>
> - 如果 flush 就删 storage：可能真实网络失败，埋点丢失
> - 如果 flush 不删 storage：下次打开重复上报
>   sendBeacon 本身没有回执，**做不到100%既不丢又不重复**。

✅ 折中工业界通用做法：

- `visibilitychange / beforeunload` 使用 sendBeacon：**发起上报后直接清空本地存储，接受极小概率丢埋点**
- 页面初始化补发用 `fetch keepalive`，可以捕获异常，失败就不删 storage，下次继续重试。

## 修改后的完整 TS 关键代码

```
let pendingEvents: any[] = [];
const STORAGE_KEY = 'track_cache';

export class Track {
  static add(event: Record<string, any>) {
    pendingEvents.push(event);
    // 持久化兜底
    const cache = JSON.parse(localStorage.getItem(STORAGE_KEY) || '[]');
    cache.push(event);
    localStorage.setItem(STORAGE_KEY, JSON.stringify(cache));
  }

  static flush() {
    if (pendingEvents.length === 0) return;
    const list = [...pendingEvents];
    // 1.清空内存队列
    pendingEvents = [];

    const data = JSON.stringify({ events: list });
    const blob = new Blob([data], { type: 'application/json; charset=UTF-8' });
    // sendBeacon，无法知道成功失败
    navigator.sendBeacon('/api/track/beacon', blob);

    // ⚠️重点：发起上报后直接清空localStorage，避免下次打开重复上报
    localStorage.removeItem(STORAGE_KEY);
  }

  static async init() {
    // 页面初始化：补发上次遗留埋点，这里用fetch，可以判断成功失败
    const cacheStr = localStorage.getItem(STORAGE_KEY);
    if (cacheStr) {
      const cache = JSON.parse(cacheStr);
      try {
        await fetch('/api/track/beacon', {
          method: 'POST',
          headers: { 'Content-Type': 'application/json' },
          body: JSON.stringify({ events: cache }),
          keepalive: true
        });
        // 请求成功，清除缓存
        localStorage.removeItem(STORAGE_KEY);
      } catch (e) {
        // 网络失败，不删除存储，下次打开继续重试
        console.warn('历史埋点补发失败，下次继续尝试', e);
      }
    }

    document.addEventListener('visibilitychange', () => {
      if (document.visibilityState === 'hidden') {
        Track.flush();
      }
    });
    window.addEventListener('beforeunload', () => Track.flush());
  }
}
```

## 上面方案存在的取舍

1. 用户切后台触发 `visibilitychange`，调用 `flush()`，调用 sendBeacon，立刻清空 localStorage。
   - 正常：浏览器后台把http发出去，埋点正常。
   - 异常：手机立刻杀掉进程，浏览器来不及发送，**埋点丢失**（代价）。
2. 页面初始化补发走 fetch，有 catch，失败不删存储，下次继续重试。

> 现实埋点SDK（神策、埋点SDK）如何解决这个两难？

### 工业级优化方案：不要把全部埋点塞一个数组，改用序号标记

1. localStorage 存储结构改为对象：`{ seq: number, list:[] }`，每条埋点带上序列号。
2. 上报时带上最大 seq。后端返回已经接收的最大seq。
3. 前端根据后端返回 seq，**只删除storage中seq小于等于返回值的埋点**。

但是！**`sendBeacon`拿不到后端返回，这套机制在页面卸载场景无法使用**，只能用于普通正常上报（非退出阶段）。

### 现实业务选型

1. **非退出场景flush（定时器批量上报）**：用普通fetch，可以拿到响应，后端回执之后再删localStorage，做到不丢不重。
2. **页面卸载/切后台场景 flush（sendBeacon）**：没有回执，只能二选一：
   - A：flush就删存储 → 极小概率丢埋点，不会重复上报（绝大多数业务选这个）
   - B：flush不删存储 → 不会丢埋点，但会出现重复上报，后端需要做**去重**（依赖埋点唯一eventId）

## 补充最佳实践

1. 业务埋点每一条生成**全局唯一 eventId(uuid)**，后端做幂等去重。就算前端重复上报，后端直接丢弃重复id，彻底解决重复上报。这是最可靠兜底。
2. 增加定时批量上报：比如30s自动flush一次，不要全部堆积等到页面关闭才上报，减少卸载阶段一次性上报压力。

```
// 增加定时上报，降低beforeunload压力
setInterval(()=>{
  if(pendingEvents.length>0) Track.flush();
}, 30000)
```

3. 队列上限保护，内存和localStorage埋点数量设置最大值，防止异常无限膨胀。

## 总结回答你的原始问题

> 每次执行flush难道不清除localstorage里缓存的？

原始示例代码确实没有清除，会造成**重复上报bug**。

- `sendBeacon` 没有响应回调，无法确认后端接收；
- 所以代码层面只能「发起上报之后直接删掉localStorage」，接受极小概率丢埋点；
- 想要完全不丢埋点，就不能删localStorage，但要后端依靠eventId做去重；
- 页面初始化补发使用普通fetch，可以根据网络成功与否控制是否删除存储。
