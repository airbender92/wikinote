# 代码重构怎么做

> **重构定义：不改变外部功能行为，只修改内部代码结构、可读性、可维护性；重构≠写新功能，不要一边改业务逻辑一边重构。**

核心原则：**小步重构、持续测试、风险可控**，不要一次性大改整个模块。

## 一、重构前准备（非常关键，防止改崩）

1. **保证有测试用例**
   - 单元测试、接口测试、手工回归步骤；**没有测试不要大规模重构**。
   - 如果没有自动化测试，先梳理出该模块的输入输出、边界场景，记录回归清单。
2. **先稳定bug，不要带着bug重构**
   先把已知bug修复，再重构；否则分不清bug是原有还是重构引入。
3. **拆分任务，拒绝大爆炸重构**
   不要一次性把几千行全部重写；拆成多个小MR/PR，分批上线。
4. **版本隔离：单独分支做重构，不和新功能混在一起**
   一个PR只做重构，**不要掺杂业务新逻辑**，方便review、出问题快速回滚。

## 二、识别坏代码（坏味道），确定重构目标

下面这些信号适合重构：

- 函数超长，几百行一个函数；一个函数做多件事
- 大量重复代码，复制粘贴多处
- 嵌套很深：if‑else嵌套、回调嵌套
- 魔术字符串、魔术数字到处写死
- 变量/函数命名模糊，看名字不知道干什么
- 条件分支过多：大量if‑else / switch
- 类过大，职责混乱（一个类干很多毫不相干的事）
- 入参过多，函数参数5个以上
- 注释一大堆，代码本身看不懂（好代码优先自解释，少靠注释）
- 复杂表达式，一行代码逻辑非常绕
- 硬编码，常量散落各处

## 三、常用重构手法（实际开发高频操作）

### 1. 提取函数（Extract Function）

> 一段逻辑反复出现，或者一个大函数里面某一块可以独立。
> 把一段代码抽成独立函数，**函数名描述它做什么**。

❌坏：

```js
function getUserInfo() {
  // 一大段：校验参数、格式化时间、处理头像、组装返回
}
```

✅重构：拆成小函数

```js
function getUserInfo() {
  validateParams();
  const avatar = formatUserAvatar();
  const time = formatCreateTime();
  return assembleResult();
}
```

> 原则：**一个函数只做一件事**。

### 2. 提取常量/配置

魔术数字、魔术字符串抽常量，统一管理。
❌ `if(status === 2)`
✅ `const STATUS_SUCCESS = 2`

### 3. 提取类 / 提取对象（面向对象）

一组高度相关的数据和行为，封装成类或者对象，不要散在各处。

### 4. 变量、函数重命名（Rename）

> 重命名是成本最低、收益最大的重构。
> 名字要表达意图，不要简写、不要a/b/c、不要fn1、handleClick2。
> IDE全局重命名，不要手动搜索替换，避免漏改。

### 5. 消除重复代码

- 完全重复：直接抽取公共函数、公共组件、公共工具；
- 大部分逻辑相同只有少量差异：抽公共函数，差异做成入参。

### 6. 简化条件分支

1. 卫语句提前return，减少嵌套
   ❌多层if嵌套

```js
function calc(data) {
  if (data) {
    if (data.id) {
      //业务逻辑
    }
  }
}
```

✅卫语句提前返回，扁平化

```js
function calc(data) {
  if (!data) return;
  if (!data.id) return;
  //业务逻辑
}
```

2. 复杂switch/if‑else过长 → 使用**对象映射表**替换

```js
// 替代大量if else
const handlerMap = {
  add: handleAdd,
  edit: handleEdit,
  delete: handleDelete,
};
const fn = handlerMap[type];
fn?.();
```

3. 合并条件表达式，去除冗余判断。

### 7. 函数参数优化

- 参数过多：封装成对象传入 `fn({a,b,c,d})`
- 去除无用参数；不要传不需要的值。

### 8. 拆分大组件（前端Vue/React）

组件上千行：拆成子组件，**单一职责**，一个组件只负责一块UI逻辑。

> 区分：容器组件（处理数据逻辑）、展示组件（只渲染UI）。

### 9. 去除无用代码

删除注释掉的代码、废弃变量、废弃函数，版本git已经记录，不需要留在代码里。

### 10. 数据处理：抽取工具函数

通用判空、格式化、转换逻辑，抽到utils，不要页面到处复制。

## 四、重构的工作流程（标准小步重构流程）

1. 写/梳理测试用例，保证现有功能正确
2. 选一小块代码，做一次小修改（例如提取一个函数）
3. 跑测试，验证**功能完全不变**
4. commit / 提交小PR
5. 继续下一小块，循环迭代

> ❌禁止：一次性改几百行，最后再测试。一旦出错，很难定位哪里引入问题。

## 五、重构风险与避坑点

1. **重构期间禁止改动业务逻辑！**

> 重构只改结构，输入输出、交互、返回结果必须和原来完全一致。

2. 不要过度重构：不要为了“优雅”无限优化，追求适度，够用即可。

> 不要对稳定、几乎不会改动的老代码强行美化，收益很低风险高。

3. 不要重构正在快速迭代的业务模块，业务还在频繁改需求，重构会大量冲突。
4. 大遗留系统：**绞杀者模式**，不要一次性全部替换；新功能写新模块，旧代码只在修改该功能时顺带局部重构。

> 遇到旧页面bug，修改这个bug的时候，顺手把附近坏味道代码重构，而不是专门花时间全盘重写。

5. 重视回归：重构后重点回归边界case、异常分支。
6. 前端特别注意：不要不小心改变响应式、组件生命周期、异步时序。

## 六、什么时候不适合重构

1. 马上要上线，时间很紧；优先修bug，重构排后面。
2. 代码很少改动、已经稳定，后续几乎不会维护。
3. 同时在做复杂新需求，需求还经常变动。

## 七、面试简答版本

> 代码重构是在**不改变外部业务行为的前提下，优化内部代码结构，提升可读性、可维护性**。

1. 重构前优先保障测试用例，没有自动化测试要梳理回归用例；单独分支，不和新功能混MR。
2. 识别代码坏味道：长函数、重复代码、嵌套过深、命名混乱、大量硬编码等。
3. 使用小步重构：提取函数、重命名、抽常量、消除重复、卫语句扁平化分支、拆分大组件、对象映射简化if‑else等。
4. 每完成一小步就做验证，保证功能不变，分批提交，拒绝一次性大爆炸重写。
5. 遗留系统采用绞杀者模式，修改某块业务时顺带局部重构，避免全盘重写带来巨大风险。
6. 区分重构和业务开发，重构不改外部逻辑；避免过度重构，评估投入产出。
