# 核心问题解析
```js
// 你写的代码
const asyncActions = {
  setInfoAsync: (params) => async (dispatch) => {
    // 异步逻辑
    dispatch(actions.setInfo(xxx))
  }
}

// 组件调用
dispatch(asyncActions.setInfoAsync())
```
> 为什么可以直接 `dispatch(函数)`？**这就是 redux‑thunk 的本职工作**。
> thunk 中间件的作用：**判断你 dispatch 的是不是函数，如果是函数，就执行这个函数，把 `dispatch, getState` 传给它；如果是普通对象，直接交给原始 redux 流程**。

## 1. redux‑thunk 完整工作流程
1. 你执行：`dispatch(asyncFunc)`，这里 `asyncFunc` 是一个函数，不是普通 action 对象 `{type:xxx}`
2. thunk 中间件捕获到：**payload 是 function**
3. thunk 自动执行这个函数：`asyncFunc(dispatch, getState)`
4. 在你的 async 函数内部，做完接口请求之后，手动再 `dispatch(普通action对象)`，去修改 reducer state
5. 如果 dispatch 的是普通对象 `{type:'xxx'}`，thunk 什么都不干，直接放行给 reducer

> ✅所以：**不是 thunk 去帮你执行异步请求，thunk 只负责允许你 dispatch 一个函数，并把 dispatch 交给这个函数内部使用。异步逻辑完全是你自己手写。**

---

## 2. RTK 和 thunk 的关系
`@reduxjs/toolkit` 的 `configureStore()` **默认内置开启 redux‑thunk，不需要手动安装、引入**。
所以你项目里：
- 你手写这种返回函数的 thunk 函数，可以直接 `dispatch(xxxThunk())`，完全正常；
- `createAsyncThunk` 只是 RTK 封装好的工具函数，**它最终生成的也是这种 thunk 函数**，是语法糖，不是另一种新能力。

### 等价关系
```js
// 方式A：你手写 thunk（项目里你现在写的）
export const setInfoAsync = (params) => async (dispatch) => {
  const res = await api.fetch(params)
  dispatch(actions.setInfo(res.data))
}

// 方式B：createAsyncThunk 封装，底层产出同样是 thunk函数
export const setInfoAsync = createAsyncThunk(
  'user/setInfo',
  async (params) => {
    const res = await api.fetch(params)
    return res.data
  }
)
```
> 两者 `dispatch(setInfoAsync(params))` 行为底层一致。
> 区别只是：
> - 手写 thunk：**自己手动 dispatch 同步 action**，loading、error 状态全部自己维护；
> - createAsyncThunk：自动生成 `pending/fulfilled/rejected` action，配合 `extraReducers` 自动管理 loading/error。

---

## 3. 为什么你感觉“没有被thunk影响”？
> “我写async函数返回函数，直接dispatch，一切正常，好像thunk没干活”

因为 thunk 是**透明中间件**：
1. 没有侵入你的业务代码，看不见它；
2. 它只做一件事：遇到 dispatch 的是函数就执行；是对象就放行；
3. 如果你把 thunk 中间件删掉，**你的代码立刻报错**！
> ❗删掉 thunk 之后：`dispatch(thunkFunc)`，redux 会报错误：`Actions must be plain objects. Use custom middleware for async actions.`
> 因为原生 redux 只接受普通对象 action，不接受函数。

> 👉你项目之所以能跑，恰恰就是 thunk 在默默生效，只是你感知不到。

---

## 4. 手写 thunk vs createAsyncThunk 取舍（业务真实场景）
### ✅手写 thunk（你现在写法）
优点：
- 灵活，逻辑完全自己掌控；
- 不需要写 extraReducers；
- 多个 dispatch、分支判断很自由。

缺点：
- loading、error、请求状态需要你自己在slice中写字段、自己手动dispatch修改；
- 没有统一的错误捕获规范；
- 没有内置的请求生命周期。

### ✅createAsyncThunk
优点：
- 自动 pending / fulfilled / rejected；统一维护 loading error；
- rejectWithValue 统一错误处理；
- 适合通用列表、查询接口，模板化。

缺点：
- 复杂多步业务逻辑写 extraReducers 会啰嗦；
- 不能在 thunk 内部随意 dispatch 多个自定义action（不是不能写，写法别扭）。

> 真实业务：简单查询用 `createAsyncThunk`；复杂多步骤异步、多dispatch，很多人依然手写 thunk，这是正常写法，不算错误。

## 5. 容易踩的坑
1. ❌错误：忘记外层返回函数
```js
// 错！这是直接执行async函数，dispatch接收 Promise，不是 thunk函数
const bad = async (params) => {
  const res = await api.get(params)
  dispatch(setInfo(res))
}
dispatch(bad()) // ❌ dispatch(Promise)，thunk不会处理Promise！！
```
✅正确：必须返回 `async (dispatch)=>{}`
```js
const good = (params) => async (dispatch) => {
  const res = await api.get(params)
  dispatch(setInfo(res))
}
dispatch(good(params))
```

2. thunk 函数第二个参数可以拿到 `getState`，读取仓库状态
```js
const setInfoAsync = (params) => async (dispatch, getState) => {
  const state = getState()
  console.log(state.user)
  dispatch(actions.setInfo())
}
```

3. thunk 只能做**执行异步 + 内部dispatch**；**依然不能直接修改 state**，state 修改还是靠 dispatch 普通 action 进入 reducer。

---

## 一句话总结
> redux‑thunk 不是帮你跑异步请求，它只允许你 `dispatch(函数)`；
> 你手写返回 `async(dispatch)=>{}` 的函数就是标准 thunk；RTK 的 createAsyncThunk 只是封装该模式的语法糖；
> 你的代码能跑 = thunk 在工作；把 thunk 移除代码直接报错。

### 对比记忆串联
- mitt：on监听，onUnmounted off，事件消息；
- Pinia：actions 内部直接写async，内部可以修改state，不需要dispatch；
- Redux RTK：reducer 不能写异步；异步要么手写 thunk 返回 `async(dispatch)=>{}`，要么 createAsyncThunk，内部靠 dispatch 普通action改state。

如果你需要，我可以给你一段：**移除 thunk 之后复现报错的极简demo**。


```js

import thunk from 'redux-thunk';
const middlewares = [thunk]

export default middlewares;


// store
import { applyMiddleware, compose, createStore} from 'redux';
import rootReducer from '@/redux/reducers'
import middlewares from './middlewares'

const store = createStore(
    rootReducer,
    {},
    compose(applyMiddleware(...middlewares))
)

export default store

// redux/reducers
import { combineReducers } from "redux";

const context = require.context("./", false, /\.js$/);
const keys = context.keys().filter((path) => !path.includes("index.js"));

const reducers = {};

keys.forEach((path) => {
  const reducer = context(path).default;
  const name = path.match(/\/(\w+)\.js/)[1];
  reducers[name] = reducer;
});

export default combineReducers(reducers);


```
