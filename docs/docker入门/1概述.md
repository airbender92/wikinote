**Docker 是一个开源的容器化平台**，它能让应用程序及其依赖环境打包成一个轻量级、可移植的容器，在任何支持 Docker 的 Linux 系统上运行。

### 核心要点（基于你提供的资料）

- **诞生背景**：2013 年由 dotCloud 公司开源，使用 Go 语言开发，后来加入 Linux 基金会并推动 **OCI（开放容器联盟）**。
- **技术原理**：利用 Linux 内核的 **cgroup**（资源限制）、**namespace**（隔离）以及 **UnionFS**（联合文件系统）等技术，实现进程级别的隔离，因此被称为“容器”。
- **与传统虚拟机的区别**：
  - **传统虚拟机**：虚拟硬件 → 运行完整客操作系统 → 运行应用（体积大、启动慢）
  - **Docker 容器**：直接共享宿主机内核 → 只包含应用及依赖（体积小、秒级启动）

### 一句话总结
> Docker 是一种“轻量级虚拟化”技术，它把应用和运行环境打包成镜像，通过容器快速启动、隔离运行，真正实现了“一次构建，到处运行”。

简单来说，Docker 镜像就是一个**只读的、特殊的文件系统**，它包含了运行一个程序所需要的所有东西：代码、运行时、库、环境变量和配置文件。

---

## 一、Docker 镜像的核心要点

### 1. 镜像是什么？
- **类比**：相当于一个**精简的操作系统的 root 文件系统**（如 `ubuntu:16.04` 镜像就是一个最小化的 Ubuntu 系统）
- **包含**：
  - 程序、库、资源、配置文件
  - 运行时配置参数（如环境变量、匿名卷、用户等）
- **不包含**：
  - Linux 内核（共享宿主机内核）
  - 动态数据（镜像构建后**只读，永不改变**）

### 2. 为什么需要“分层存储”？
- 镜像体积通常很大（一个完整的 root 文件系统）
- **UnionFS 技术**：将镜像设计为**多层文件系统联合组成**，而不是一个单一的大文件

---

## 二、分层存储的核心机制

```
┌─────────────────┐
│   容器层（读写）  │  ← 容器运行时添加（容器删除即消失）
├─────────────────┤
│   镜像层 3       │  ← 只读，记录对前一层的新增/修改/删除标记
├─────────────────┤
│   镜像层 2       │  ← 只读，构建时叠加
├─────────────────┤
│   镜像层 1       │  ← 只读，基础层（如 ubuntu:16.04）
└─────────────────┘
```

### 关键特性：
| 特性 | 说明 |
|------|------|
| **前一层是后一层的基础** | 逐层叠加，每一层只记录本层的变化 |
| **每一层构建后不再改变** | 保证镜像的稳定性和可复用性 |
| **删除操作只是“标记删除”** | 并不是真的删除前一层文件，只是在当前层标记“已删除”，运行时看不到，但文件仍然存在于镜像中（因此要**清理无用内容**，否则镜像会臃肿） |
| **镜像复用** | 可以用一个基础镜像，叠加新层，定制出多个不同镜像 |

---

## 三、分层存储带来的好处

| 好处 | 说明 |
|------|------|
| **镜像复用** | 多个镜像可以共享相同的基础层（如 `ubuntu:16.04`），节省存储空间 |
| **定制简单** | 在基础镜像上增加新层即可定制，无需从头构建 |
| **构建快速** | 只需重新构建变化的层，不变层使用缓存 |
| **便于维护** | 每一层职责单一，易于理解和修改 |

---

## 四、一句话总结

> **Docker 镜像是多层只读文件系统的联合，通过分层存储实现了高效复用、快速构建和灵活定制。**

---

## 五、与虚拟机镜像的对比（补充）

| 对比项 | Docker 镜像 | 传统虚拟机镜像（如 ISO） |
|--------|------------|--------------------------|
| 组成 | 多层只读文件系统 + 分层存储 | 单个完整的大文件 |
| 体积 | 较小（共享内核 + 分层复用） | 很大（包含完整 OS） |
| 修改方式 | 增加新层，原层不变 | 直接修改原文件（或创建快照） |
| 复用性 | 极高（基础层可被多个镜像共享） | 低（每个镜像独立） |

---

## 一、镜像与容器的关系

| 概念 | 类比 | 特点 |
|------|------|------|
| **镜像（Image）** | 类 | 静态定义，只读，包含文件系统和配置 |
| **容器（Container）** | 类的实例 | 动态实体，可创建、启动、停止、删除 |

> 镜像是**死的**，容器是**活的**。容器 = 镜像 + 一个可读写的存储层。

---

## 二、容器的本质

**容器就是一个进程**，但运行在隔离的环境中，拥有自己的：

- root 文件系统
- 网络配置（IP、端口等）
- 进程空间（PID 命名空间）
- 用户 ID 空间

这种隔离基于 Linux 的 **命名空间（namespace）** 技术。因此：

- 容器内的进程看不到宿主机或其他容器的进程
- 就像在一个独立的操作系统中运行
- **比直接在宿主机运行应用更安全**

> 正因为这种隔离特性，初学者容易把容器误认为“轻量级虚拟机”。

---

## 三、容器的存储层

### 1. 容器存储层
- 以镜像为基础层，**在上面叠加一个可读写的容器层**
- 容器运行时，所有修改（创建、修改、删除文件）都发生在这个**容器存储层**
- 容器删除时，**这个存储层也随之删除**，其中的数据**永久丢失**

### 2. 最佳实践：保持容器无状态

> **容器不应该向它的存储层写入任何数据** — 因为存储层会随容器消失。

正确的做法：
- 使用 **数据卷（Volume）** 或 **绑定宿主目录（Bind Mount）** 来保存数据
- 这些位置的读写**跳过容器存储层**，直接操作宿主机文件系统（或网络存储）
- 性能更高、更稳定

---

## 四、数据卷（Volume）的作用

| 特性 | 说明 |
|------|------|
| 生命周期 | **独立于容器**，容器删除时数据卷不会自动删除 |
| 数据持久性 | 容器重建后，重新挂载同一个数据卷，数据依然存在 |
| 适用场景 | 数据库、日志、配置文件等需要持久化的数据 |

---

## 五、类比总结

| 场景 | 说明 |
|------|------|
| 镜像 | 相当于一个 **只读的模板**（如安装光盘 ISO） |
| 容器 | 从模板启动的 **运行实例**（如正在运行的操作系统） |
| 容器存储层 | 运行过程中的**临时草稿**（关机/重启即丢失） |
| 数据卷 | **独立的移动硬盘**（即使容器销毁，数据还在） |

---

## 六、一句话概括

> **容器是镜像运行后的进程实例，拥有隔离的环境和临时存储层；要实现数据持久化，必须使用数据卷，而不是依赖容器存储层。**

## 一、Docker Registry 是什么？

**Docker Registry** 是一个用于**集中存储、管理和分发 Docker 镜像**的服务。

- 类似于“镜像的中央仓库”
- 构建好的镜像可以推送到 Registry，其他服务器可以从 Registry 拉取并使用

---

## 二、核心概念关系

```
Registry（注册服务器）
   └── Repository（仓库）
         └── Tag（标签） → 指向一个具体的镜像
```

| 概念 | 说明 | 示例 |
|------|------|------|
| **Registry** | 存储镜像的服务（可包含多个仓库） | Docker Hub、私有 Registry |
| **Repository** | 同一软件不同版本的镜像集合 | `ubuntu`、`redis` |
| **Tag** | 标识某个镜像的具体版本 | `16.04`、`latest` |
| **镜像地址** | `<仓库名>:<标签>` | `ubuntu:16.04` |

- 若省略标签，默认使用 **`latest`**
- 仓库名常为**两段式**：`用户名/软件名`（如 `jwilder/nginx-proxy`），便于多用户管理

---

## 三、公开 Registry 服务

### 1. Docker Hub（最常用）
- 官方默认 Registry
- 拥有大量**官方镜像**（如 ubuntu、nginx、redis）
- 网址：https://hub.docker.com

### 2. 其他公开服务
| 服务 | 特点 |
|------|------|
| Quay.io | CoreOS 团队维护，存放 CoreOS 相关镜像 |
| Google Container Registry | 存放 Kubernetes 相关镜像 |
| 国内加速器 | 阿里云、DaoCloud 等，解决访问慢问题 |
| 国内镜像市场 | 时速云、网易云、阿里云镜像库等 |

> **注意**：国内访问 Docker Hub 较慢，建议配置**镜像加速器**（如阿里云加速器）。

---

## 四、私有 Registry

### 1. 什么时候需要私有 Registry？
- 公司内部镜像不想公开
- 内网环境无法访问公网
- 需要更高的访问控制、审计能力

### 2. 搭建私有 Registry 的方式

| 方式 | 说明 |
|------|------|
| **官方 Registry 镜像** | 运行 `docker run -d -p 5000:5000 registry` 即可启用基础功能 |
| **Docker Trusted Registry（DTR）** | 官方商业版，提供图形界面、用户管理、访问控制等高级功能 |
| **第三方实现** | VMWare Harbor、Sonatype Nexus，提供 Web UI 和更丰富特性 |

---

## 五、补充：Registry vs Repository vs Index

- **Registry**：存放镜像的实际服务器（负责存储、传输）
- **Repository**：同一类镜像的集合
- **Index**：负责用户认证、权限、搜索等（如 Docker Hub 的网页部分）

但对于日常使用，**Registry 和 Repository 常混用**，能理解即可。

---

## 六、一句话总结

> **Docker Registry 是镜像的集中存储与分发中心，官方提供 Docker Hub，企业可搭建私有 Registry；镜像通过 `<仓库名>:<标签>` 唯一标识。**

## 一、从仓库获取镜像

- **命令**：`docker pull`
- **格式**：`docker pull [选项] [仓库地址[:端口]/]仓库名[:标签]`
- 示例：
  ```bash
  docker pull ubuntu:16.04
  ```
- 如果不指定仓库地址，默认从 **Docker Hub** 拉取
- 如果不指定标签，默认拉取 `latest`

> 拉取过程是一层一层下载的，这正是分层存储的体现。

---

## 二、管理本地镜像

| 操作 | 命令示例 | 说明 |
|------|----------|------|
| 列出镜像 | `docker image ls` | 显示仓库名、标签、镜像ID、大小等 |
| 查看镜像详情 | `docker inspect <镜像名或ID>` | 查看配置、层信息等 |
| 删除镜像 | `docker image rm <镜像名或ID>` | 可以指定短ID、长ID、镜像名、摘要 |
| 清理无用镜像 | `docker image prune` | 删除虚悬镜像（dangling images） |

### 虚悬镜像（dangling image）
- 仓库名和标签都是 `<none>`
- 原因：新旧镜像同名，旧镜像名称被取消
- 可以通过 `docker image ls -f dangling=true` 查看并清理

---

## 三、镜像实现的基本原理

- **分层存储**（UnionFS）：镜像由多层只读文件系统组成
- **写时复制（CoW）**：容器运行时在镜像顶层加一个可写层
- **共享基础层**：多个镜像可共享相同的基础层（如 `ubuntu:16.04`），节省空间

> 更深入的原理（如 AUFS、OverlayFS、devicemapper）会在后续章节讲解。

---

## 四、常用组合技巧

1. **批量删除镜像**（结合 `-q` 和过滤）：
   ```bash
   docker image rm $(docker image ls -q redis)
   ```

2. **查看镜像占用空间**：
   ```bash
   docker system df
   ```

3. **按格式输出镜像列表**（使用 Go 模板）：
   ```bash
   docker image ls --format "table {{.Repository}}\t{{.Tag}}\t{{.Size}}"
   ```

## 一、为什么需要 Dockerfile？

与 `docker commit` 相比，Dockerfile 有以下优势：

| 问题 | `docker commit` | `Dockerfile` |
|------|----------------|--------------|
| **重复性** | 手动操作，无法精确复现 | 脚本化，可重复构建 |
| **透明性** | 黑箱操作，别人不知道做了什么 | 每一条指令都公开，任何人都能理解 |
| **体积控制** | 容易产生冗余层，镜像臃肿 | 可通过最佳实践控制每层内容 |

> **结论**：Dockerfile 是定制镜像的推荐方式，`docker commit` 只适合临时保存现场（如调试）。

---

## 二、Dockerfile 的基本结构

```dockerfile
FROM nginx
RUN echo '<h1>Hello, Docker!</h1>' > /usr/share/nginx/html/index.html
```

- 每个 **指令（Instruction）** 会构建一层
- 第一行必须是 `FROM`，指定 **基础镜像**

---

## 三、`FROM` 指令详解

### 1. 作用
指定当前镜像基于哪个镜像构建。  
**必备**，且必须是第一条非注释指令。

### 2. 常见基础镜像类型

| 类别 | 示例 | 用途 |
|------|------|------|
| 服务类 | `nginx`、`redis`、`mysql`、`python`、`node` | 直接运行特定服务或语言环境 |
| 操作系统类 | `ubuntu`、`debian`、`centos`、`alpine` | 提供完整的 Linux 用户空间，方便安装软件 |
| 空白镜像 | `scratch` | 不依赖任何系统，适合静态编译的二进制文件 |

### 3. 特殊基础镜像：`scratch`

- 是一个**虚拟的空镜像**，不包含任何文件
- 适用场景：Go 语言等静态编译的程序（所有依赖已打包进二进制）
- 效果：镜像体积极小（只有二进制文件本身）

示例（Go 应用）：
```dockerfile
FROM scratch
COPY hello /
CMD ["/hello"]
```

> 这是为什么 Go 在容器微服务架构中受欢迎的原因之一。

## 四、扩展：`RUN` 指令（书中的下一个指令）

您提供的示例中用了 `RUN`，它用来执行命令。建议 **每个 `RUN` 只做一件事**，并且注意清理临时文件，避免镜像臃肿。

**不推荐的写法**（会产生多余层）：
```dockerfile
RUN apt-get update
RUN apt-get install -y curl
```

**推荐的写法**（合并为一条 `RUN`，并清理缓存）：
```dockerfile
RUN apt-get update && apt-get install -y curl \
    && rm -rf /var/lib/apt/lists/*
```

## 五、完整的简单 Dockerfile 示例

创建一个简单的 Nginx 自定义首页：

```dockerfile
# 1. 指定基础镜像
FROM nginx:alpine

# 2. 修改默认首页
RUN echo '<h1>Hello from Dockerfile!</h1>' > /usr/share/nginx/html/index.html

# 3. 暴露端口（仅声明）
EXPOSE 80
```

构建并运行：
```bash
docker build -t my-nginx .
docker run -d -p 8080:80 my-nginx
# 访问 http://localhost:8080
```

## 六、小结

- **Dockerfile 是镜像定制的脚本**，优于 `docker commit`
- **`FROM` 指定基础镜像**，可以是官方服务镜像、操作系统镜像或 `scratch`
- **`scratch` 适合静态编译程序**，能制作极致小巧的镜像
