## Item 82 详细讲解：按依赖图自底向上逐模块迁移

当你的项目已经准备好构建工具链（Item 81）并使用了现代 JavaScript 语法（Item 79）后，就可以开始真正的迁移工作：将 `.js` 文件逐个转换为 `.ts`，并添加类型注解。关键原则是**按照依赖图从叶子节点（不依赖其他模块的模块）向根节点迁移**，这样每转换一个模块，其依赖都已类型化，类型信息可以向上流动，避免反复修改。

---

### 1. 为什么要自底向上？

- **类型信息是流动的**：如果你先转换一个被许多模块导入的“底层模块”，那么所有导入它的模块在转换时，就能立刻享受到准确的类型提示和检查。反之，如果先转换顶层模块，你会因为依赖的模块还是 `.js`（类型为 `any`）而遇到大量错误，不得不暂缓或使用 `any` 断言。
- **一次转换，持续受益**：每个模块转换完成后，就可以将其视为类型安全的“构建块”，不会被后续转换破坏。

**类比**：修建一座塔，应该先打好地基（底层模块），再一层层向上砌墙。

---

### 2. 迁移顺序

1. **第三方依赖**  
   首先确保所有使用的第三方库都有类型声明。通常通过安装 `@types/xxx` 完成。这些库不依赖你的代码，因此是绝对的叶子节点。

2. **外部 API 的类型声明**  
   如果你的代码调用外部接口（如 REST API、GraphQL），可以为响应和请求定义类型，这也能让类型从边界向内流动。

3. **项目内部的基础模块**  
   - 工具函数（`utils.js`）
   - 辅助类、常量定义
   - 数据模型/接口定义

4. **业务逻辑模块**  
   它们会导入基础模块，依赖较少。

5. **入口模块 / 根模块**  
   例如主页面逻辑、路由等。

6. **测试文件**（最后迁移）  
   因为生产代码不依赖测试，测试位于依赖图的顶部。迁移测试之前，生产代码已经全部类型安全，测试的运行结果不会因迁移而改变，可以作为验证正确性的重要保障。

---

### 3. 可视化依赖图，辅助排序

使用工具（如 `madge`）生成项目依赖图（如图 10-3），可以帮助你识别出哪些模块是底层、哪些存在循环依赖。对于循环依赖，需要先重构打破循环，否则无法确定迁移顺序。

**常用命令**：

```bash
npx madge --image graph.png src/
```

- 箭头方向：`a → b` 表示 `a` 导入 `b`。
- 叶子节点（没有出边的节点）应该最先迁移。
- 可以运行拓扑排序来得到理论上的迁移顺序。

---

### 4. 迁移中的注意事项

#### 4.1 聚焦于添加类型，不要同时重构

- 迁移过程中你可能会发现代码设计问题（过长的方法、混乱的变量命名等）。**此时不要重构**，因为重构会引入新的风险，并使代码审查复杂化。
- 记录下这些“异味”，等 TypeScript 迁移完成后再单独进行重构。
- 如果某个类型暂时无法准确描述，允许使用 `any` 或 `@ts-expect-error`，但应留下 `TODO` 注释。

#### 4.2 处理常见错误

##### 未声明的类成员

JavaScript 类可以不声明成员，但 TypeScript 要求显式声明。重命名 `.js` 为 `.ts` 后，会报大量“属性不存在”的错误。

**快速修复**：使用 VS Code 提供的“添加所有缺失成员”快速修复（图 10-4）。它会根据构造函数和方法的赋值自动添加属性声明，但类型可能被推断为 `any`，需要你后续修正。

```ts
class Greeting {
  greeting: string;   // 推断正确
  name: any;          // 需要手动改为 string
  constructor(name: string) { ... }
}
```

##### 动态添加属性的对象

```ts
const state = {};
state.name = 'New York'; // 错误：{} 上没有 name
```

**解决方案**：
- 一次性构建对象（Item 21）：
  ```ts
  const state = { name: 'New York', capital: 'Albany' };
  ```
- 如果必须逐步添加，可以使用类型断言：
  ```ts
  const state = {} as State;
  ```

类型断言是可接受的临时手段，但应尽快重构。

##### 从 JSDoc 迁移类型时丢失类型安全

如果你之前使用了 `@ts-check` 和 JSDoc 类型注解，直接重命名为 `.ts` 后，JSDoc 不会再被强制检查，函数参数类型会变为 `any`，导致失去类型安全。

**示例**：

```js
// 原 .js 文件
// @ts-check
/**
 * @param {number} num
 */
function double(num) { return 2 * num; }
double('trouble'); // 错误，正确
```

转换为 `.ts` 后：

```ts
/**
 * @param {number} num
 */
function double(num) { return 2 * num; }
double('trouble'); // 不再报错，因为 num 是 any
```

**解决方案**：使用 TypeScript 提供的快速修复“将 JSDoc 类型复制到 TypeScript 类型注解”（图 10-5），将 `@param` 转换为 `num: number`，并删除 JSDoc（Item 31）。

---

### 5. 迁移测试文件

测试文件应该最后转换，原因有二：
- 它们是依赖图的顶层（测试导入生产代码，反之不成立）。
- 当所有生产代码都已类型化且通过类型检查后，转换测试文件时，测试代码本身可能暴露出类型错误（例如 mock 数据不匹配），这些错误可以帮助你发现测试与实现的差异。

重要的是，在迁移过程中**测试应该持续通过**，因为类型迁移是纯重构行为，不应改变运行时行为。如果测试失败，说明迁移引入了错误，应立即回滚。

---

### 6. 总结步骤

1. 安装所有 `@types` 依赖，为外部 API 编写类型声明。
2. 使用 `madge` 生成依赖图，识别底层模块。
3. 从最底层模块开始，逐个将 `.js` 重命名为 `.ts`，修复类型错误。
   - 对类成员使用快速修复添加声明。
   - 对动态对象使用一次性构建或断言。
   - 将 JSDoc 转换为 TypeScript 注解。
4. 每转换一批模块，运行测试和类型检查，确保无回归。
5. 最后迁移测试文件。
6. 当所有文件都转为 `.ts` 后，可以逐步收紧 `tsconfig.json` 中的严格选项（如 `strict`）。

**最终建议**：耐心、渐进。不要试图一次性转换整个项目。利用依赖图指导顺序，每完成一个模块就提交代码，保持主干始终可用。TypeScript 迁移是一项投资，正确的顺序会让你事半功倍。
