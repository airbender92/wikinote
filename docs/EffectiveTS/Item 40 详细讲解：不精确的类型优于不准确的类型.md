## Item 40 详细讲解：不精确的类型优于不准确的类型

这一节的核心是：**在类型声明中，追求极致的“精确”有时会导致“不准确”，从而破坏类型系统的可信度和开发体验。** 一个不准确（inaccurate）的类型（例如声称 `coordinates` 只能是 `[number, number]` 但实际允许三个元素）比一个不精确（imprecise）但正确（例如 `number[]`）的类型更糟糕，因为它会给出虚假的安全感，并迫使使用者绕过类型系统（使用 `as any` 或断言）。

书中通过两个例子来说明：GeoJSON 坐标类型和 Mapbox 表达式语言。

---

### 例子一：GeoJSON 坐标类型

#### 初始版本（不精确但正确）

```ts
interface Point {
  type: 'Point';
  coordinates: number[];
}
```

这里 `coordinates` 是 `number[]`，可以接受任意长度的数字数组。这**不精确**（不能表达“必须是两个数字”），但它是**准确**的：GeoJSON 标准中，点坐标可以是两个数字（经纬度），也可以是三个数字（加上海拔），甚至更多。`number[]` 允许所有这些合法情况。

#### “过度精确”的版本（不准确）

开发者为了提高精度，定义了元组类型：

```ts
type GeoPosition = [number, number];
interface Point {
  type: 'Point';
  coordinates: GeoPosition;
}
```

现在类型声称坐标只能是两个数字。但实际 GeoJSON 允许第三个元素（海拔）。因此这个类型**不准确**：它拒绝了一些合法的 GeoJSON 数据。使用这个类型声明的库会令用户困惑，用户要么被迫使用类型断言（`as any`），要么放弃使用该库。

**结论**：不精确但准确的 `number[]` 优于精确但不准确的 `[number, number]`。后者会导致用户不信任类型系统。

---

### 例子二：Mapbox 表达式语言

Mapbox 使用一种类似 Lisp 的 JSON 表达式来描述地图样式，例如：

```json
12
"red"
["+", 1, 2]          // 3
["/", 20, 2]         // 10
["case", [">", 20, 10], "red", "blue"]   // "red"
["rgb", 255, 0, 127] // "#FF007F"
```

作者尝试为这种表达式编写 TypeScript 类型，从最简单到最复杂，经历了几个层次。每个层次都提高了精度，但也带来了新的问题。

#### 第1-2层：非常不精确，但完全准确

```ts
type Expression1 = any;                         // 太宽，无意义
type Expression2 = number | string | any[];    // 简单，允许所有合法表达式
```

`Expression2` 可以接受任何合法的 Mapbox 表达式，但也会接受许多非法表达式（例如 `true`、`["**", 2, 31]`）。它**不精确**（很多误报），但**准确**（不会拒绝合法程序）。

#### 第3层：使用字面量联合约束函数名

```ts
type FnName = '+' | '-' | '*' | '/' | '>' | '<' | 'case' | 'rgb';
type CallExpression = [FnName, ...any[]];
type Expression3 = number | string | CallExpression;
```

现在 `["**", 2, 31]` 会被正确拒绝（`"**"` 不在 `FnName` 中）。但仍然接受错误数量的参数（如 `["rgb", 255, 0, 127, 0]` 会通过，因为它只是 `[FnName, ...any[]]`，不限制后续元素个数）。这个类型更精确了，但仍准确（没有拒绝合法表达式），不过维护成本增加（新增函数需更新 `FnName`）。

#### 第4层：递归检查参数数量和类型

作者进一步尝试强制每个函数有正确数量的参数。例如 `MathCall` 要求两个参数，`RGBCall` 要求三个，`CaseCall` 要求偶数个参数（通过接口的 `length` 属性限制为 4,6,8,...）。

```ts
type Expression4 = number | string | CallExpression;
type CallExpression = MathCall | CaseCall | RGBCall;
type MathCall = [ '+' | '-' | '/' | '*' | '>' | '<', Expression4, Expression4 ];
interface CaseCall {
  0: 'case';
  [n: number]: Expression4;
  length: 4 | 6 | 8 | 10 | 12 | 14 | 16;
}
type RGBCall = ['rgb', Expression4, Expression4, Expression4];
```

这个类型现在非常精确，能够捕获参数个数错误（例如 `["rgb", 255, 0, 127, 0]` 会因为长度不匹配而报错）。**但是，它变得不准确了**：

- Mapbox 规范中，`+` 和 `*` 可以接受两个以上的参数（例如 `["+", 1, 2, 3]` 是合法的），但 `MathCall` 固定为两个参数，会错误地拒绝合法表达式。
- `-` 可以接受一个参数（取反），但这里要求两个参数。

作者写道：

> 再一次，在试图变得更精确的过程中，我们过头了，变得不准确了。

**结果**：使用者可能会遇到类型错误，费尽心思调试，最终发现是类型声明本身有 bug，这会严重打击对类型系统的信心。

### “恐怖谷”效应

作者用“恐怖谷”来比喻：当一个卡通形象越来越逼真时，我们会觉得它更真实；但当它几乎逼真却仍有细微瑕疵时，我们会特别在意那些瑕疵，反而觉得更诡异。同样：

- 从 `any` 到 `number|string|any[]` 是巨大改进，大家会赞赏。
- 从 `Expression3` 到 `Expression4` 虽然更精确，但出现了不准确之处（拒绝了合法表达式），用户会因为这些虚假错误而痛苦，最终可能放弃使用这些类型。

**结论**：宁可保持不精确但准确（例如 `number[]`），也不要追求精确却不准确（例如 `[number, number]`）。如果无法准确建模，就承认不足，使用 `any` 或 `unknown` 作为逃生舱，并附上注释说明限制。

---

### 实践建议

1. **测试你的类型**（Item 55）。准备一组合法输入和非法输入，确保类型不会拒绝合法输入（不准确），也不会接受非法输入（不精确）。但优先保证准确性。
2. **关注错误消息和自动补全体验**。复杂的类型可能导致难以理解的错误消息，破坏开发体验。
3. **避免过度工程**。如果类型变得极其复杂且容易出错，考虑回退到更简单的类型，并接受一定的不精确性。

**最终原则**：在“精确”和“准确”之间，**准确优先**。一个不会阻止正确程序的宽松类型，比一个错误地拒绝正确程序的严格类型要好得多。
