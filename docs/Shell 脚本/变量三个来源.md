# 梳理整套链路：Dockerfile → CMD → 执行sh脚本 → shell变量 → cat >> <<EOF写入nginx配置

整套流程：

```
Dockerfile CMD ["./run.sh"]
    ↓
容器启动，执行 run.sh（bash脚本）
    ↓
sh脚本内部定义/读取 $变量，echo打印
    ↓
cat >> /etc/nginx/conf.d/default.conf <<EOF
这里直接使用 $变量，会被bash提前替换成真实值
EOF
```

## 1、sh脚本里面这些`$XXX`变量三个来源

### 来源①：脚本内直接赋值（shell自定义变量）

run.sh

```
#!/bin/bash
# ✅脚本内部自己定义
NGINX_PORT=80
BACKEND_URL=http://127.0.0.1:3000

echo "端口：$NGINX_PORT"
echo "后端地址：$BACKEND_URL"

cat >> /etc/nginx/conf.d/default.conf <<EOF
server {
    listen $NGINX_PORT;
    location /api/ {
        proxy_pass $BACKEND_URL;
    }
}
EOF
```

> `$NGINX_PORT`、`$BACKEND_URL`：**bash脚本的本地变量，写在sh里面赋值**。
> `cat >> <<EOF` 属于脚本内部，**bash会先把变量替换完，再把文本写入nginx配置文件**。
> ⚠这里的`$NGINX_PORT`是**shell变量**，≠ nginx的内置`$remote_addr`变量！两者完全不是一回事！

### 来源②：Docker 环境变量（docker run -e 或者Dockerfile ENV）

Dockerfile

```
ENV BACKEND_URL=http://node:3000
CMD ["./run.sh"]
```

启动容器时也可以覆盖：

```
docker run -e BACKEND_URL=http://127.0.0.1:3000  xxx镜像
```

sh脚本**不需要额外定义**，直接就能 `echo $BACKEND_URL`，直接在here‑doc里面使用。

> ENV定义的变量会成为容器的系统环境变量，sh脚本继承环境变量。

### 来源③：脚本传入的位置参数 $1 $2

```
# CMD ["./run.sh","8080"]
port=$1
```

> 重点区分两套完全不同的`$变量`（非常容易混淆）

1. **Shell/bash变量（sh脚本里面）**：`$BACKEND_URL`、`$NGINX_PORT`
   - 来源：脚本赋值 / Docker ENV / docker run ‑e
   - **在执行cat >> <<EOF的时候，bash就把变量替换成真实字符串**，写入到nginx.conf是**已经替换完成的静态文本**。
   - nginx读到的配置里面**没有$符号了**，是实实在在的 `proxy_pass http://node:3000;`
2. **Nginx内置变量（nginx.conf里面）**：`$remote_addr``$host`
   - 来源：nginx C源码，http请求到达的时候才生成
   - 写在conf文件里保留`$`符号，**nginx运行请求阶段才解析**

## 关键原理：`cat >> file <<EOF` 的变量替换时机

```
BACKEND=http://node:3000
cat > test.conf <<EOF
proxy_pass $BACKEND;
EOF
```

1. bash解析脚本，识别`$BACKEND`，替换为真实字符串 `http://node:3000`
2. 写入磁盘test.conf文件内容：

```
proxy_pass http://node:3000;
```

✅**生成出来的nginx配置文件，已经没有美元符号$了！**

> 如果写 `<<'EOF'`（EOF加单引号），bash关闭变量替换，文件里面原样保留 `proxy_pass $BACKEND;`，这个就会交给nginx去解析，这大概率是bug。

## 完整的Dockerfile+sh最小示例

`Dockerfile`

```
FROM nginx:alpine

# 设置环境变量
ENV BACKEND_SERVER=http://127.0.0.1:3000
COPY run.sh /
RUN chmod +x /run.sh

# 容器启动就执行sh脚本
CMD ["/run.sh"]
```

`run.sh`

```
#!/bin/bash
echo "后端地址变量 BACKEND_SERVER=$BACKEND_SERVER"

# 动态生成nginx配置
cat > /etc/nginx/conf.d/default.conf <<EOF
server {
    listen 80;
    location /api/ {
        proxy_pass $BACKEND_SERVER;
        proxy_set_header Host \$host;
        proxy_set_header X‑Real‑IP \$remote_addr;
    }
}
EOF

# 启动nginx
exec nginx -g "daemon off;"
```

> 注意这里：`\$host`、`\$remote_addr`，**加反斜杠转义！**

- `$BACKEND_SERVER`：不加反斜杠 → bash替换shell变量；
- `\$host`：加反斜杠 `\$` → bash不处理，把文本 `$host`原样写入nginx配置，**留给nginx运行时解析**。

❗这是高频坑：
如果你不写反斜杠：

```
proxy_set_header Host $host;
```

bash会把`$host`当成shell变量，shell里面`$host`为空，写入conf就变成：

```
proxy_set_header Host ;
```

nginx直接启动报错。
所以动态生成nginx配置的sh脚本，**nginx内置变量必须写 `\$remote_addr` 转义**。

## 变量溯源排查方法（怎么看这个$变量来自哪里）

进入运行起来的docker容器内部：

```
docker exec -it 容器id sh
# 打印所有环境变量，看有没有该变量
env
# 看run.sh源码，看脚本内部有没有赋值
cat /run.sh
```

1. 如果`env`输出有该变量 → 来自Dockerfile ENV / docker run -e传入
2. env没有该变量 → 在sh脚本内部直接赋值定义

## 总结核心逻辑

1. sh脚本里的`$VAR`是shell变量，来源：脚本内赋值 / Docker ENV / run‑e传入。
2. `cat >> <<EOF`，**bash在写入文件前完成shell变量替换**，写到磁盘的配置是静态文本。
3. 如果需要把**nginx内置变量`$host/$remote_addr`原样写入配置**，sh脚本here‑doc里面必须写成 `\$host`，反斜杠转义，阻止bash替换。
4. Dockerfile的`CMD ["./xxx.sh"]`：容器启动的时候运行这个shell脚本，作为入口，脚本动态渲染nginx配置，最后拉起nginx服务。

> 现实业务场景：不同环境后端地址不一样，不用改镜像，启动容器`‑e BACKEND_URL=xxx`传入环境变量，sh脚本动态生成nginx代理配置。
