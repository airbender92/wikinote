## 报错解读

```
.husky/commit-msg: line 1: #!/bin/sh: No such file or directory
code 127
```

根本原因：**文件换行还是 CRLF（Windows换行）**
Git Bash 读到第一行实际是：`#!/bin/sh\r`
末尾多了一个 `\r` 回车符，系统把 `#!/bin/sh\r` 当成完整命令去找，自然找不到。

> 之前虽然加了 `#!/bin/sh`，但是没彻底处理换行符，依然报错。

# 一次性修复方案（严格按顺序操作）

## 1. 删除旧文件

```powershell
Remove-Item .husky/commit-msg -Force
```

## 2. 打开 VSCode 终端 → 切换成 **Git Bash**（不要用PowerShell执行下面命令）

运行：

```bash
cat > .husky/commit-msg <<-'EOF'
#!/bin/sh
npx --no -- commitlint --edit $1
EOF
```

这条命令生成出来**天然是 LF 换行，不会带 \r**，避开PowerShell编码坑。

## 3. 验证换行（必做）

VSCode打开 `.husky/commit-msg`
右下角确认显示 **LF**，不是 CRLF。

## 4. 测试提交

```bash
git commit -m "feat: test husky"
```

# 备选方案：如果你不想折腾 shell 脚本（Windows稳定方案）

husky 支持用 node 方式写钩子，彻底避开 `#!/bin/sh` 换行坑
删除 commit-msg，新建 `.husky/commit-msg`

```js
const { execSync } = require("child_process");
const args = process.argv.slice(2);
execSync(`npx --no commitlint --edit ${args[0]}`, { stdio: "inherit" });
```

然后在文件第一行加上：

```
#!/usr/bin/env node
```

完整内容：

```
#!/usr/bin/env node
const { execSync } = require('child_process')
const args = process.argv.slice(2)
execSync(`npx --no commitlint --edit ${args[0]}`, { stdio: 'inherit' })
```

优势：不依赖 bash，Windows 环境兼容性最强，不会出现 `#!/bin/sh` 找不到的问题。

# 额外优化：全局固定 git 换行策略，杜绝以后再次踩坑

Git Bash 执行

```bash
git config core.autocrlf input
```

## 补充一个极简判断小技巧

Git Bash 执行这条命令查看隐藏的 `\r`

```bash
cat -A .husky/commit-msg
```

正常：

```
#!/bin/sh$
npx --no -- commitlint --edit $1$
```

异常（有问题）：

```
#!/bin/sh^M$
npx --no -- commitlint --edit $1^M$
```

看到 `^M` 代表存在 `\r`，就是元凶。
