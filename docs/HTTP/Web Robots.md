你贴出的这段文字是《HTTP权威指南》第 9 章“Web Robots”的开篇，非常清晰地定义了 **Web 机器人（Web Robots）** 的概念并给出了几个生动的例子。

结合我们之前讨论的代理（Proxy）、隧道（Tunnel）、中继（Relay），**Web 机器人是另一种重要的 HTTP 客户端类型**。它与浏览器这类由人直接操作的客户端不同，最大的特点是**自动化**和**无需人工干预**。

### 核心概念提炼

1.  **定义**：Web 机器人是自动化执行 HTTP 事务的软件程序。
2.  **行为模式**：它们通常会从一个初始 URL 集合（根集，Root Set）出发，抓取内容，解析其中的超链接，然后递归地继续抓取，像一张网一样在 Web 上扩散。这就是它们被称为“爬虫”（Crawler）或“蜘蛛”（Spider）的原因。
3.  **典型应用**：
    *   **搜索引擎**：Google、Bing 等使用爬虫抓取网页，建立索引数据库。这是最广为人知的用途。
    *   **价格比较**：比价网站的机器人会定期抓取电商网站的商品页面，获取价格信息。
    *   **网站监控**：监测网站是否可用、内容是否更新。
    *   **链接验证**：检查网站中的链接是否失效（死链检查）。
    *   **数据采集**：收集特定类型的数据，如新闻、股票信息、论文摘要等。

### 与之前讨论的 HTTP 组件的联系

*   **与普通客户端的区别**：浏览器等客户端代表“人”发起请求，而机器人代表“程序”或“算法”。机器人需要处理诸如链接提取、循环避免、请求频率控制等问题。
*   **与代理/缓存的关系**：机器人的大量请求会给目标服务器带来负载。**缓存**的存在可以显著减轻这种负载——如果多个机器人或用户请求同一资源，缓存可以直接返回，减少对源服务器的压力。而机器人也可以通过遵守 `Cache-Control` 等头信息来更高效地利用缓存。
*   **与网关/隧道的区别**：网关和隧道主要处理协议转换或数据转发，而机器人是主动发起 HTTP 请求的消费者。

### 机器人带来的关键问题（本书后续会详细展开）

正如引言所暗示，机器人虽然强大，但也带来了一系列必须考虑的问题，书中后续章节会深入探讨：

1.  **性能与负载**：不加以控制的机器人可能像“闪光人群”（Flash Crowd）一样，对服务器造成巨大的瞬时压力，甚至导致拒绝服务。因此，机器人需要实现**节制（Throttling）**，限制对同一服务器的请求频率。
2.  **循环与陷阱**：Web 的超链接结构可能形成循环。如果机器人没有记录已访问的 URL，它可能会陷入无限循环。更糟糕的是，某些网站会故意设置“爬虫陷阱”（Robot Trap，如无限生成的动态页面）来困住不守规矩的机器人。
3.  **过时内容**：机器人抓取的内容可能很快过时。这涉及到我们之前讨论过的**缓存验证**机制（如 `If-Modified-Since` 和 `ETag`），机器人可以利用它们高效地判断内容是否更新，只抓取变更的部分。
4.  **隐私与排除协议**：不是所有内容都希望被机器人抓取。因此有了 **`robots.txt`** 这个“君子协定”。网站通过 `robots.txt` 文件告知机器人哪些目录或文件不允许抓取。尊重 `robots.txt` 是任何行为端正的机器人的基本**礼节**。

### 总结与延伸

简单来说，Web 机器人是把 HTTP 从一个“请求-响应”的人机交互协议，扩展到了“程序-程序”的自动化数据处理协议。它们构成了现代互联网搜索、监控和数据服务的基础。

### 爬虫的核心工作流程

1.  **起点：根集（Root Set）**
    爬虫从一个或多个初始URL开始，这些URL构成了“根集”。根集的选择至关重要，通常包括：
    -   **高人气站点**：如Yahoo、CNN首页，能覆盖大量链接。
    -   **新站点提交**：用户或站长主动提交的新URL。
    -   **待发现列表**：上次爬取中解析出但尚未访问的URL。

2.  **循环：链接提取与递归**
    -   爬虫请求一个URL，获得HTML页面。
    -   它解析HTML，提取出其中所有的`<a href="...">`链接。
    -   将相对URL转换为绝对URL（例如，将`/tools.html`补全为`http://www.joes-hardware.com/tools.html`）。
    -   将这些新URL加入待抓取队列，然后继续处理队列中的下一个URL。
    -   这个过程不断重复，如同沿着蜘蛛网不断向外探索。

3.  **核心挑战：避免循环与重复**
    这是爬虫设计中最关键的问题。Web结构天然存在循环（例如 A→B→C→A）。如果不做处理，爬虫会永远在这几个页面中打转，浪费大量资源。常见策略包括：
    -   **记录已访问URL**：使用哈希表、布隆过滤器等数据结构，在抓取前判断一个URL是否已经处理过。这是基础中的基础。
    -   **规范化（Canonicalization）**：将各种语义相同但写法不同的URL（如`http://example.com`和`http://example.com/index.html`）转换为标准形式，避免重复抓取。
    -   **限制URL长度和深度**：设定规则，拒绝抓取过长的URL或过深的目录层级，以防御某些故意构造的“陷阱”。

### 与你之前讨论的HTTP组件的关系

-   **与缓存（Caching）的协同**：为了对源服务器保持友好，爬虫应该充分利用HTTP缓存机制。在发送请求时，可以携带`If-Modified-Since`或`If-None-Match`头。如果服务器返回304 Not Modified，则无需下载整个页面内容，这能极大节省网络和计算资源。
-   **与机器人排除协议（robots.txt）的结合**：任何行为端正的爬虫，在抓取一个站点**之前**，必须首先请求该站点的`/robots.txt`文件，并严格遵守其中的`Disallow`规则。这是整个爬虫社区的基本“礼节”。
-   **对代理/隧道的影响**：大量爬虫流量可能会被企业或ISP的代理服务器拦截。对于完全遵守HTTP规范的透明代理，这通常没有问题。但如果爬虫使用了我们之前讨论过的**隧道（Tunnel）** 技术来规避防火墙，则可能违反目标网站的管理策略，甚至引发法律风险。

### 爬虫的“社会性”与工程挑战

书中后续还会提到，一个优秀的爬虫不能只懂技术，还必须具备“社会意识”：

-   **节制（Throttling）**：必须主动限制对同一站点每秒/每分钟的请求次数，绝不能像压力测试一样发起洪水攻击。这既是技术需要，也是为了防止被目标站点永久封禁IP。
-   **身份标识（Identification）**：应在请求头中设置独特且真实的`User-Agent`字段，并在`From`字段中包含联系方式。这样，当网站管理员发现异常时，能够联系到你而不是直接拉黑。
-   **处理动态内容**：现代Web大量使用JavaScript动态加载内容。简单的HTML解析器无法抓取这类页面，需要爬虫能执行JS代码（如使用Puppeteer、Playwright等无头浏览器框架），这极大地增加了复杂度和资源消耗。

**总结来说，你所贴出的段落是爬虫概念的起点。一个能在生产环境稳定运行的大型爬虫，本质上是HTTP协议专家、分布式系统工程、海量数据处理和网络礼貌规范的综合体。**

简单来说，根集就是爬虫启动时的那一批“种子 URL”。选择什么样的根集，直接决定了爬虫能覆盖多大的范围、能否发现那些“藏在深巷”里的页面，以及整个抓取任务的效率。

### 根集选择的困境与策略

书中用图 9-1 的一个小型网络模型，清晰地说明了这个困境：

-   **覆盖不全**：从单一的 A 点出发，无论如何也到达不了 G、N、S 等区域。这在真实的 Web 上极其常见——互联网不是一张完全连通的网，存在大量互不相连的“孤岛”或“子图”。
-   **孤立页面**：像 S、T、U 这样的页面，没有任何入链（没人链接到它们）。仅靠跟随链接的爬虫，理论上永远无法发现它们。

为了解决这个问题，生产级的爬虫（如 Google、Bing 的爬虫）会采用**混合型根集**策略，通常包含以下几类来源：

1.  **高流行度站点**：例如 Yahoo、CNN、Wikipedia 等。这些站点本身是巨大的枢纽（Hub），从它们出发可以抵达海量的其他页面。这是保证覆盖率的基础。
2.  **用户/站长提交的 URL**：这是发现“孤立页面”最有效的方法。许多搜索引擎都提供“提交网址”的入口。站长主动提交的新站点或深层页面，会被直接加入根集。
3.  **过往抓取记录中的“陈旧”URL**：上一次大规模抓取过程中，那些因为网络超时、服务器错误等原因未能成功抓取的 URL，会被保留下来，作为下一次抓取的起点之一。
4.  **外部链接数据**：从购买的链接数据库、公开的 DNS 列表、甚至社交媒体分享链接中提取的 URL。

### 一个更根本的问题：Web 的“可爬取性”

根集的选择背后，其实是一个更深层的、哲学意味的问题：**如果没有任何一个页面链接到它，一个页面是否应该（或是否能够）被爬虫发现？**

-   **理论答案**：不能。纯跟随链接的爬虫，其探索范围被限制在“从根集出发通过链接可达”的子图内。那些孤立的页面永远无法触及。
-   **实践答案**：可以通过上面第 2、3、4 类手段，将这些“无入链”的 URL 直接“注入”到待抓取队列中。因此，现代商业爬虫的“根集”是动态、多源、持续增长的。

### 与你之前讨论的 HTTP 组件的关联

1.  **与 `robots.txt` 的关系**：根集中的 URL，即使是用户提交的，在真正抓取之前，爬虫**仍然必须先检查目标站点的 `robots.txt`**。如果该站点的根目录下有一个 `Disallow: /` 规则，那么即使这个 URL 是用户强烈要求抓取的，遵守规范的爬虫也必须放弃。
2.  **与“礼貌爬行”的关系**：根集的选择会直接影响爬虫对**特定站点**的请求频率。例如，如果根集里包含了 `cnn.com` 的 1000 个不同子页面 URL，一个幼稚的爬虫可能会瞬间对这同一个域名发起大量并发请求。一个好的爬虫实现，必须对根集进行按域名归并（Host Grouping），确保对每个站点的请求是节制的。
3.  **与 DNS 和连接管理的联系**：根集中的 URL 可能指向成千上万个不同的域名。爬虫在启动阶段会经历一个 **DNS 解析风暴**。我们之前在第 4 章讨论过的 TCP 连接建立延迟、慢启动、甚至 `TIME_WAIT` 等问题，在大规模爬虫的根集抓取初期会被成百上千倍地放大。

### 总结

你贴出的这段文字，把爬虫从一个简单的“递归抓取器”提升到了“战略规划”的层面。根集的选择，本质上是在**覆盖率**（抓到更多页面）、**资源消耗**（避免浪费带宽和计算）和**礼貌性**（不把友好站点抓垮）三者之间寻找平衡。

一个优秀的根集，就像一张好渔网——网眼（链接）够密，能兜住大多数鱼；网脚（起始锚点）又足够分散，能把网撒到整个湖面。

### 1. 链接提取与规范化：从相对到绝对

爬虫抓取的HTML页面中，链接通常以两种形式存在：

-   **绝对URL**：例如 `http://www.joes-hardware.com/tools/hammer.html`。可以直接使用。
-   **相对URL**：例如 `../images/logo.gif` 或 `./tools.html`。**这种链接无法直接放入待抓取队列**，因为缺少协议、主机名等关键信息。

**规范化**就是将相对URL转换为绝对URL的过程。其步骤大致如下：

1.  **确定基础URL**：
    -   优先使用页面HTML `<head>` 中 `<base href="...">` 标签声明的URL。
    -   如果没有 `<base>` 标签，则使用当前被抓取页面的URL作为基础。
2.  **合并**：按照RFC 1808等标准定义的算法，将相对路径与基础URL的路径部分进行合并，处理 `..`（上一级目录）、`.`（当前目录）等特殊符号。
3.  **生成绝对URL**：最终得到完整的 `scheme://host/path` 格式。

**为什么容易出错？** 许多网页的HTML并不规范（标签未闭合、引号缺失、使用不标准的转义等）。一个健壮的爬虫需要一个容错性很强的HTML解析器（如lxml、BeautifulSoup），而不能仅仅依靠正则表达式。

### 2. 循环避免：爬虫的“记忆”与“判断力”

你引述的图9-2展示了最直观的循环：A→B→C→A。如果爬虫没有记忆，它会永远在A、B、C三个页面之间绕圈。

**循环会带来几个严重后果：**

1.  **资源浪费**：无休止地抓取同一批页面，消耗网络带宽和计算资源。
2.  **服务器负载**：对目标服务器造成本不应有的请求压力，甚至可能被视为攻击。
3.  **内容无效**：重复抓取不会带来任何新内容，只会使任务永远无法完成。

**核心解决方案：记录“已访问URL”**

这是避免循环最基础、也是最重要的手段。爬虫维护一个**已访问URL集合**，在抓取一个新URL之前，先检查它是否已经在集合中。如果在，就跳过。

**但这个看似简单的方法，在实践中会遇到挑战：**

-   **别名（Aliases）问题**：多个不同的URL可能指向同一个资源。例如：
    -   带 `www` 和不带 `www`：`http://example.com` 和 `http://www.example.com`
    -   默认端口：`http://example.com` 和 `http://example.com:80`
    -   默认文件：`http://example.com/` 和 `http://example.com/index.html`
    -   IP与域名：`http://example.com` 和 `http://93.184.216.34`
    -   大小写差异（取决于服务器配置）：`http://example.com/About.HTML` 和 `http://example.com/about.html`
    -   URL参数顺序：`http://example.com/page?a=1&b=2` 和 `http://example.com/page?b=2&a=1`

一个简单的字符串比较无法识别这些别名。因此，爬虫在检查循环前，需要先对URL进行**规范化**，例如：统一转小写、补全默认端口、移除缺省的页面文件名（`index.html`）、对参数进行排序等。但有些别名问题（如IP与域名的对应关系）则需要通过查询DNS甚至实际访问才能确认。

-   **海量数据下的“记忆”**：对于一个需要抓取数十亿页面的搜索引擎爬虫，维护一个包含所有已访问URL的集合是不现实的。因此，大型爬虫会使用**概率性数据结构**（如**布隆过滤器**）来“模糊”地记忆已访问URL。它可能会产生“假阳性”（误判一个新URL为已访问），但绝不会产生“假阴性”，且内存占用极小。

-   **动态陷阱**：比简单的A→B→C循环更麻烦的是恶意构造的**爬虫陷阱**。例如，一个动态页面生成的链接每次都不一样（如 `page?id=1` → `page?token=abc` → `page?token=def`...），它会无限地产生新URL，绕过基于URL字符串的去重机制。对此，爬虫需要结合**限制URL长度**、**限制请求深度**、**检测重复内容**（如计算页面内容的哈希值）等多种手段来综合防范。

### 与你之前讨论的HTTP组件的关系

-   **与缓存的关系**：`已访问URL集合` 本质上是一种“负面缓存”——记录哪些URL不用再去。而浏览器/代理缓存是记录哪些内容可以直接用。两者都是利用历史信息来避免重复的HTTP事务。
-   **与`ETag`/`Last-Modified`的关系**：在避免循环的同时，对于已经抓取过但可能更新的页面，爬虫可以利用**条件请求**，只下载发生变化的内容，而不是每次重新抓取。

### 三大危害的深层解读

1.  **资源黑洞（爬虫自身被“饿死”）**
    -   **现象**：爬虫陷入 A→B→C→A 的循环，永远在这几个页面间打转。
    -   **后果**：所有的网络带宽、CPU、内存都被这些无意义的请求耗尽。队列中真正新的、有价值的URL永远得不到处理。这本质上是**活锁（Livelock）**——爬虫一直在忙，但忙的毫无意义。

2.  **对源服务器的“无意识攻击”**
    -   **现象**：一个高速、并发的爬虫以每秒数百次的速度反复请求同一组页面。
    -   **后果**：这等同于一次拒绝服务攻击（DoS）。如果爬虫属于商业搜索引擎，而受害者是一个小型的个人博客，服务器可能会因此崩溃。网站所有者完全有理由提出法律索赔或要求封禁该爬虫的IP。
    -   **现实案例**：早期某些爬虫因代码Bug导致对特定网站发起洪水般请求，被网站管理员公开声讨。

3.  **索引污染（搜索结果失效）**
    -   **现象**：搜索引擎的索引数据库被同一个页面的无数个副本（通过不同URL访问）填满。
    -   **后果**：用户搜索某个关键词时，返回的前10个结果可能指向**同一个文档**的不同URL变体。这极大地降低了搜索体验，也浪费了索引存储空间。

### 为什么“简单的URL去重”不够？

你之前看到的“已访问URL集合”可以解决最简单的A→B→C→A循环。但现实中的循环和重复远比这复杂。下面两个例子是去重难以应对的：

| 类型 | 示例 | 为什么难处理 |
| :--- | :--- | :--- |
| **动态URL陷阱** | `/calendar?month=1` → `/calendar?month=2` → ... → `/calendar?month=999` | URL不同，但内容可能只是微小变化（日历下个月）。爬虫会无限抓取下去。 |
| **别名（Alias）** | `http://example.com` 与 `http://example.com/index.html` | 字符串不同，但内容完全相同。简单的字符串比较无法识别。 |

### 工程实践中的应对策略

1.  **规范化（Canonicalization）—— 处理别名**
    -   在将URL加入“已访问集合”之前，先进行规范化处理：
        -   将主机名转小写。
        -   移除默认端口（80、443）。
        -   对路径进行绝对化（`/a/b/../c` → `/a/c`）。
        -   移除缺省的文件名（如 `index.html`，但需谨慎，某些站点默认文件可能是 `default.aspx`）。
        -   对查询参数进行排序（`?b=2&a=1` → `?a=1&b=2`）。
    -   但有些别名（如IP地址与域名）无法通过规则解决，可能需要DNS反向查询。

2.  **限定深度和宽度—— 防范动态陷阱**
    -   **限制抓取深度**：设定一个最大链接深度（例如10层）。超过这个深度的URL不再抓取。
    -   **限制单站点页面数**：对同一个域名，设定最大抓取页面数（例如100万页）。超过后不再抓取该站点的新URL。
    -   **限制URL长度**：拒绝抓取超过设定长度（如2048字符）的URL。很多动态陷阱会通过不断添加参数使URL变长。

3.  **内容指纹（Fingerprinting）—— 终极去重**
    -   对于内容完全相同但URL不同的情况（如镜像站点、缺省文件），唯一可靠的方法是**比较内容本身**。
    -   **做法**：对抓取的页面内容（通常是HTML主体，去除动态时间戳、广告等噪音）计算**哈希值**（如MD5、SHA-1）。如果两个页面的哈希值相同，则判定为重复。
    -   **优点**：无论URL怎么变，都能识别重复。
    -   **缺点**：计算成本高（需要下载完整页面），并且对极小改动（如页脚日期）会误判为不同。

4.  **遵守 robots.txt 和 Meta 标签**
    -   很多陷阱站点会明确在 `robots.txt` 中声明 `Disallow` 规则。尊重它是避免纠纷的第一道防线。
    -   页面内部的 `<meta name="robots" content="noindex, nofollow">` 也是明确的信号。

### 与你之前讨论内容的关联

-   **与HTTP缓存的关系**：`Etag` 和 `Last-Modified` 本质上是服务器提供的“内容指纹”的轻量级替代。爬虫可以利用条件请求来检查页面是否更新，避免重复下载。
-   **与“礼貌爬行”的关系**：限制单站点的请求频率和并发数，不仅能保护服务器，也能防止自己陷入动态陷阱——因为陷阱通常需要大量请求才能触发。

### 1. 树与哈希表：精确但昂贵

-   **原理**：将每个URL字符串存入内存中的平衡二叉树（如红黑树）或哈希表。查询时，通过树查找或哈希计算快速定位。
-   **优点**：**精确**，没有假阳性（不会误判一个新URL为已访问）。
-   **缺点**：**内存消耗极大**。如书中计算，500亿个平均40字节的URL，仅存储字符串就需要20GB，加上指针、哈希表开销（通常2-3倍），可能达到50-60GB以上。对于需要抓取数百亿页面的搜索引擎，这完全不可行。
-   **适用场景**：中小规模爬虫（百万级URL），或作为分布式架构中单个节点的本地去重。

### 2. 有损存在位图（布隆过滤器 Bloom Filter）

这是工业级爬虫最核心的去重数据结构。

-   **原理**：
    -   初始化一个m位的位数组（全部为0）。
    -   使用k个相互独立的哈希函数。对一个URL，计算它的k个哈希值，并将位数组中对应的k个比特位设为1。
    -   查询时，对新URL计算k个哈希值。**只有当所有对应的k个比特位都为1时，才认为该URL可能已访问**；否则，一定未访问。
-   **优点**：**内存极小**。要达到1%假阳性率，每个URL只需约9.6比特（比书中的例子压缩了30倍以上）。500亿URL大约需要60GB**位**，即7.5GB内存（500亿 × 9.6位 ÷ 8 = 60GB？等等，重新算一下：500亿 × 9.6 bits = 4800亿 bits = 60 GB。哦，这仍然很大。实际上常用的是每个URL 10-20 bits，500亿×16 bits = 8000亿 bits = 100GB。所以布隆过滤器并非魔法，它只是比存整个URL节省了约3-5倍的内存，同时允许假阳性。更激进的做法是使用更小的假阳性率（如0.1%），每个URL约需14 bits，500亿×14=7000亿 bits≈87.5GB。还是很大。实际上，Google等公司会在数千台机器上分布式布隆过滤器，每台负责一部分URL。）
-   **缺点**：**有假阳性**（可能会漏掉一些新URL）；**无法删除**（标准布隆过滤器不支持删除）。
-   **变种**：**计数布隆过滤器** 支持删除，但内存更大；**布谷鸟过滤器** 支持删除且在某些场景更优。
-   **实践**：几乎所有大型爬虫都使用布隆过滤器或其变种，配合**分区**（见第4点）来将内存需求分摊到多台机器。

### 3. 检查点（Checkpointing）

-   **原理**：定期将内存中的“已访问URL”数据结构（如布隆过滤器位图、哈希表）持久化到磁盘。爬虫崩溃后，可以从最近的检查点恢复，而不必从头开始。
-   **挑战**：对于数百GB的内存数据，序列化和写入磁盘可能需要数分钟甚至数小时。因此需要**增量检查点**或**日志结构合并树（LSM-Tree）** 等技术，或者利用分布式系统的**复制**而非传统检查点。
-   **实践**：现代分布式爬虫通常使用**主从复制**或**共识协议**（如Raft）来保持元数据的容错，而不是单纯依赖本地检查点。

### 4. 分区（Partitioning）：分布式爬虫

-   **原理**：将URL空间按照某种规则（如哈希（hostname）或一致性哈希）划分成多个“桶”，每个爬虫节点负责一个桶。例如，可以按**域名**划分，确保同一个网站的所有页面被同一个节点抓取，这样有助于控制对目标服务器的礼貌性（因为只有一个节点负责该域名）。
-   **优点**：
    -   **线性扩容**：增加节点即可增加容量和吞吐量。
    -   **单节点内存可控**：每个节点只需要维护自己负责的那部分URL的去重数据结构。
-   **挑战**：
    -   节点间可能需要通信：当节点A解析出的链接指向节点B负责的域名时，需要通过内部RPC将URL转发给节点B。
    -   负载不均：某些域名（如`facebook.com`）可能有数百万页面，而其他域名只有几个页面。需要使用**动态负载均衡**或**虚拟节点**来缓解。
    -   **协调**：需要中心化的**调度器**（Master）来管理节点状态、分配任务、处理节点故障。
-   **实践**：Google的**Caffeine**、**Pregel**等系统展示了这种架构。开源项目如**Apache Nutch**、**Scrapy Cloud**、**StormCrawler**也采用了类似思想。

### 为什么别名对爬虫是致命问题？

如果爬虫只做简单的字符串比较，那么：
- 它会将 `http://example.com` 和 `http://example.com:80` 当作两个不同的页面，抓取两次。
- 它会将 `http://example.com/README.HTM` 和 `http://example.com/readme.htm` 当作两个不同的页面，即使服务器可能返回同一个文件。

后果：
- **浪费网络带宽和存储**：重复抓取相同内容。
- **降低爬虫效率**：队列中塞满冗余 URL，延迟发现新页面。
- **索引质量下降**：搜索同一个文档出现多次，用户体验差。

### 爬虫如何解决别名问题：URL 规范化（Normalization）

规范化是将不同形式的 URL 转换为一个**标准形式**的过程。常见的规范化步骤包括：

1.  **端口归一化**：如果端口是默认端口（HTTP 为 80，HTTPS 为 443），则移除 `:80` 或 `:443`。
2.  **转义字符解码**：将 `%7E` 还原为 `~`，将 `%20` 还原为空格等。但需谨慎：某些特殊字符的编码可能是故意的（如 `%2F` 代表 `/`，解码后会改变路径语义，通常不解码）。
3.  **移除片段标识符**：去掉 `#` 及其后的内容。
4.  **路径规范化**：
    -   将路径中的 `.` 和 `..` 解析（例如 `/a/./b` → `/a/b`，`/a/b/../c` → `/a/c`）。
    -   移除结尾的斜杠（如 `/dir/` → `/dir`），但需注意某些服务器将有无斜杠视为不同资源（常见于目录 vs. 文件）。通常做法是将两者归一化为不带斜杠，或者保留原样但通过其他手段去重。
5.  **大小写归一化**：
    -   主机名（Host）部分转为小写。
    -   路径部分：**谨慎处理**。许多服务器（尤其是 Unix/Linux）区分大小写，不能简单转小写。但若已知服务器不区分大小写（如通过 `robots.txt` 或历史抓取结果推断），则可以转小写。大型爬虫通常会保留原样，依靠内容去重来处理。
6.  **默认文档处理**：如果路径以 `/` 结尾，可以尝试补充默认文件名（如 `index.html`），但前提是服务器确实返回默认文档。这需要预先知道服务器的配置，通常通过试探性抓取来学习。另一种做法是不做这种替换，而是依靠内容去重。
7.  **主机名归一化**：
    -   将域名转小写（`WWW.Example.COM` → `www.example.com`）。
    -   **不推荐**将域名替换为 IP 地址，因为 IP 地址可能对应多个虚拟主机，且 IP 会变化。

### 无法通过规范化解决的别名

有些别名即使规范化也无法处理，例如表 9-1 中的 f（域名 vs. IP）以及内容完全相同但 URL 参数顺序不同（如 `?a=1&b=2` vs `?b=2&a=1`）。对于这些情况，爬虫需要依赖：

-   **内容指纹（Content Fingerprinting）**：即使 URL 不同，如果页面内容（或关键部分）的哈希值相同，则判定为重复。
-   **语义分析**：对于参数排序，可以在规范化阶段对参数键进行排序。
-   **站点地图（Sitemap）**：网站提供的 `sitemap.xml` 中列出的规范 URL 可以辅助判断。

### 别名与循环的关联

别名并不直接造成循环，但它会使**重复（Dups）** 问题更严重。如果一个网站有 1000 种不同 URL 指向同一资源，爬虫会抓取 1000 次。这不仅浪费资源，还可能触发该站点的反爬机制（被视为攻击）。因此，一个成熟的爬虫必须实现多级去重：URL 规范化去重 → 内容指纹去重 → 行为模式检测（如请求过于频繁）。

2.  **百分号解码**：`%7E` → `~`
3.  **移除片段标识符**：`#early` 及之后的内容全部丢弃

这三步可以有效处理表 9-1 中的 **a, b, c** 三类别名：
-   **a**：默认端口被显式写出 → 补全后统一。
-   **b**：转义字符与原始字符 → 解码后统一。
-   **c**：不同锚点 → 移除后统一。

这些都属于 **语法级别** 的变换，不依赖服务器配置，可以安全地对所有 URL 执行。

### 规范化不能做什么：依赖服务器语义的别名

对于 **d, e, f**，仅靠字符串操作无法判断：

| 例子 | 问题本质 | 为什么规范化解决不了 |
| :--- | :--- | :--- |
| d | 路径大小写不敏感（`readme.htm` ≠ `README.HTM`？） | 取决于服务器文件系统（Windows/Unix）或 Web 服务器配置。爬虫无法提前知道。 |
| e | 目录默认文档（`/` 与 `/index.html`） | 取决于服务器配置（`DirectoryIndex` 指令）。不同目录可能不同。 |
| f | 域名与 IP 地址指向同一主机 | 取决于虚拟主机配置。同一 IP 可能托管多个域名，直接替换会导致错误。 |

### 爬虫如何应对这些“语义级”别名？

1.  **试探与学习**：
    -   对于大小写问题：可以先发送一个 HEAD 或 GET 请求，观察服务器是否返回相同内容或重定向。
    -   对于默认文档：请求 `/` 和 `/index.html`，比较响应（状态码、内容哈希）。如果相同，则可以建立映射。
    -   对于 IP 与域名：请求 `http://domain/` 和 `http://ip/`，如果返回相同内容且 IP 没有虚拟主机冲突，则可以视为别名。

2.  **利用站点提供的信息**：
    -   **`<link rel="canonical" href="...">`**：现代网站常用 canonical 标签告知搜索引擎哪个 URL 是首选。爬虫应优先尊重。
    -   **Sitemap**：网站提供的 `sitemap.xml` 中列出的 URL 通常是规范形式。
    -   **`robots.txt`** 中的规则有时也能暗示目录结构。

3.  **内容指纹（Content Fingerprinting）**：
    -   无论 URL 是什么形式，如果两个页面内容（或主要部分）的哈希值相同，则判定为重复。这是最可靠的后备方案，但成本较高。

4.  **启发式规则 + 人工配置**：
    -   对于已知常见情况（如 Apache 默认 `index.html`，IIS 默认 `default.aspx`），可以内置规则。
    -   对于特定站点，可以人工配置别名映射（较少见，通常用于高价值站点）。

### 实际工程中的规范化流程

一个工业级爬虫的 URL 规范化管道通常是**分阶段、可配置**的：

1.  **语法规范化（无条件）**：解码、移除片段、补全端口、路径解析（`.` / `..`）。
2.  **主机名规范化**：转小写，去除末尾点号，将 Punycode 编码的国际域名转为 Unicode（显示用）或保留编码（抓取用）。
3.  **可选规范化（依赖启发式或试探结果）**：
    -   移除 `www.` 前缀（如果站点配置为重定向到无 `www`）。
    -   路径大小写折叠（仅当已知服务器不区分大小写）。
    -   默认文档移除或添加。
4.  **参数排序**：将查询参数按键排序，使 `?b=2&a=1` 变成 `?a=1&b=2`（常用于动态网站的去重）。
5.  **指纹兜底**：对可疑页面进行内容比较。

### 总结

你引用的这段文字准确地指出了规范化的价值（消除语法别名）和天花板（无法处理语义别名）。一个成熟的爬虫必须在规范化之后，结合试探请求、站点元数据（canonical 标签）和内容指纹，才能有效地进行去重。而现实中，许多爬虫（包括部分搜索引擎）会优先依赖 **`rel="canonical"`**，因为这是网站所有者明确指出的规范 URL，比任何猜测都可靠。

你贴出的这段内容，展示了爬虫面临的一种**特殊且隐蔽的循环**：文件系统符号链接（Symbolic Link）导致的无限深度目录。

### 问题本质

图 9-3b 中，`/subdir` 是一个指向根目录 `/` 的符号链接。因此：
-   `/subdir/index.html` 实际上就是 `/index.html`。
-   `/subdir/subdir/index.html` 仍然是 `/index.html`。
-   理论上，路径可以无限延长：`/subdir/subdir/subdir/.../index.html` 都指向同一个文件。

### 为什么这对爬虫是陷阱？

1.  **URL 字符串不同**：`/index.html`、`/subdir/index.html`、`/subdir/subdir/index.html` 在表面上完全不同。简单的 URL 去重（已访问集合）无法识别它们指向同一资源。
2.  **无限延伸**：如果爬虫没有限制，它会一直生成更长的 URL（每多一层 `/subdir/`），直到超出 URL 长度限制或服务器超时。
3.  **可被恶意利用**：攻击者可以故意创建这样的符号链接结构，作为**爬虫陷阱**。一个不设防的爬虫会陷入无限循环，耗尽带宽和资源，甚至导致服务器压力过大。

### 爬虫如何防御？

1.  **限制 URL 长度**：设定一个最大 URL 长度（例如 2048 字符）。当 URL 超过该长度时，不再抓取。这是最简单有效的防线——大多数合法的 URL 不会无限长。
2.  **限制目录深度**：设定最大路径深度（例如 20 层）。超过后不再继续深入。
3.  **内容指纹（Content Fingerprinting）**：
    -   即使 URL 不同，如果页面内容的哈希值（MD5、SHA-1）与之前抓取过的某个页面相同，则判定为重复，不再抓取其链接。
    -   在示例中，`/index.html` 和 `/subdir/index.html` 内容完全相同，爬虫计算哈希后会识别出重复，从而避免继续生成 `/subdir/subdir/index.html`。
4.  **路径规范化（Path Normalization）**：
    -   检测并消除路径中的“自引用”循环。例如，如果发现 `/subdir/` 指向 `/`，则可以将后续的 `/subdir/subdir/` 等价为 `/subdir/`，从而截断。
    -   但这需要爬虫能够探测符号链接的真实目标，这通常需要服务器端的支持（如通过 WebDAV 或特定配置），在普通 HTTP 协议层面很难做到。
5.  **检测重复的路径段**：如果路径中出现重复模式（如 `/subdir/subdir/subdir/...`），可能是循环的迹象。爬虫可以设置规则：当同一个路径段连续出现超过阈值时，停止抓取。

### 与其他循环类型的关联

-   **符号链接循环** 与 **动态网关陷阱**（无限生成新 URL）不同：前者 URL 结构有规律（不断重复相同前缀），后者可能完全不可预测（每次都不同参数）。
-   与 **重定向循环**（HTTP 301/302 循环）不同：符号链接循环发生在服务端文件系统层面，客户端看到的是正常的 200 响应，只是 URL 路径变长。检测难度更高。

### 总结

你引用的这段文字揭示了爬虫防御体系中一个重要的实践原则：**不要无条件信任 URL 的路径结构**。一个健壮的爬虫必须组合使用多种防御策略：

| 策略 | 作用 | 成本 |
| :--- | :--- | :--- |
| URL 长度限制 | 防止无限延伸 | 极低 |
| 深度限制 | 防止过深嵌套 | 极低 |
| 内容指纹 | 识别重复内容 | 中（需要下载页面并计算哈希） |
| 路径模式检测 | 提前识别可疑循环 | 低 |

实际上，绝大多数生产爬虫都会设置合理的 URL 长度和深度限制，并结合内容指纹来避免此类陷阱。仅靠 URL 字符串去重是远远不够的。

你贴出的这段内容，是 **Robots Exclusion Standard（机器人排除标准）** 的核心实现细节。它明确了爬虫在访问任何站点之前必须执行的第一步操作：**获取并解析 `robots.txt` 文件**。

### 核心原则

-   **一站点一文件**：每个“源站”（由协议、主机名、端口号共同定义）最多只有一个 `robots.txt` 文件。对于虚拟主机，每个虚拟 docroot 可以有自己独立的 `robots.txt`。
-   **必须先检查再抓取**：爬虫在请求该站点**任何其他 URL** 之前，必须先成功获取 `robots.txt`（或明确其不存在）。
-   **无局部覆盖**：`robots.txt` 作用于整个站点，不能在每个子目录中放置单独的 `robots.txt` 进行细粒度覆盖。站长需在一个文件中汇总所有规则。

### 获取 `robots.txt` 的 HTTP 细节

-   **方法**：`GET /robots.txt HTTP/1.x`
-   **必须携带的身份头**：`User-Agent`（爬虫名称）和 `From`（联系方式），以便站长追踪和联系。
-   **示例请求**：
    ```http
    GET /robots.txt HTTP/1.0
    Host: www.joes-hardware.com
    User-Agent: Slurp/2.0
    From: crawler@example.com
    ```

### 根据 HTTP 响应码的行为逻辑

| 响应码 | 含义 | 爬虫行为 |
| :--- | :--- | :--- |
| 2xx（成功） | 服务器返回了 `robots.txt` 内容 | 必须解析文件内容，并严格遵守其中的 `Allow` / `Disallow` 规则。 |
| 404（Not Found） | 站点没有 `robots.txt` 文件 | 视为没有访问限制，可以抓取该站点的任何 URL。 |
| 401 / 403 | 访问被拒绝（需要认证或被禁止） | 应视为整个站点完全受限，**不抓取任何页面**。 |
| 503（Service Unavailable） | 临时故障 | 应延迟一段时间后重试，暂不抓取该站点的其他内容。 |
| 3xx（重定向） | `robots.txt` 被重定向到其他位置 | 必须跟随重定向，直到最终获得资源（或达到重定向上限）。 |

### 重要说明与陷阱

1.  **`robots.txt` 可能动态生成**：它不一定是文件系统中的静态文件，也可以是网关程序动态生成的。但这不影响爬虫的处理逻辑。
2.  **404 不等于“所有内容可抓取”**：404 仅意味着没有显式的排除规则，但站点可能仍通过其他方式（如 `meta` 标签、IP 封锁）限制爬虫。不过，按照标准，爬虫可以自由抓取。
3.  **重定向链的处理**：如果 `robots.txt` 被重定向（例如从 `http://` 重定向到 `https://`），爬虫必须跟随。但应限制重定向次数（通常最多 5 次），避免循环。
4.  **缓存 `robots.txt`**：为了减少对服务器的压力，爬虫应当缓存 `robots.txt`，并根据 `Cache-Control` 或 `Expires` 头决定刷新频率。如果没有这些头，通常默认缓存 24 小时。

### 与之前讨论内容的关联

-   **与虚拟主机的关联**：如果多个域名共享同一 IP 地址（虚拟主机），每个域名可能有自己的 `robots.txt`。因此爬虫必须使用 `Host` 头来区分，否则可能获取到错误的文件。
-   **与代理的关联**：如果爬虫通过代理访问，代理可能缓存 `robots.txt`。这可能导致爬虫看到过时的规则。因此，爬虫应尽量直接连接源服务器获取 `robots.txt`，或使用 `Cache-Control: no-cache` 绕过代理缓存。
-   **与 HTTP 状态码处理**：之前在第 3 章讨论过状态码的分类，这里具体应用到爬虫场景。

### 实际生产中的补充

-   **`User-Agent` 的匹配规则**：`robots.txt` 中可以使用 `User-Agent: *` 匹配所有爬虫，也可以针对特定爬虫（如 `User-Agent: Googlebot`）设置不同规则。爬虫应选择**最匹配自己名称**的规则组（区分大小写？规范说大小写不敏感，但实际最好按原始匹配）。
-   **`Allow` 与 `Disallow` 的优先级**：原始标准中只有 `Disallow`，后来扩展了 `Allow`。对于特定路径，通常 `Allow` 优先于 `Disallow`，但实现有差异。现代爬虫应同时支持。
-   **`Sitemap` 指令**：虽然不是标准的一部分，但许多搜索引擎支持在 `robots.txt` 中添加 `Sitemap: http://example.com/sitemap.xml`，爬虫可据此发现站点地图。

### 总结

你引用的这段内容定义了爬虫与网站之间的 **“社会契约”**：网站通过 `robots.txt` 声明自己的“领地”和“禁区”，爬虫则必须首先阅读这个契约并严格遵守。不遵守 `robots.txt` 的爬虫被视为“不礼貌”甚至“恶意”，可能会被法律或技术手段封禁。

你贴出的这段内容，详细说明了 `robots.txt` 文件的具体语法规则。这是爬虫必须严格遵守的“君子协定”，也是网站管理员控制爬虫行为的核心工具。

### 文件结构

-   **逐行文本**：支持三种行：空行、注释行（以 `#` 开头）、规则行（`字段: 值`）。
-   **记录（Record）**：由一个或多个 `User-Agent` 行 + 零个或多个 `Allow`/`Disallow` 行组成。记录之间用空行分隔。
-   **匹配顺序**：爬虫按照 `User-Agent` 行的出现顺序查找第一个匹配自己名称的记录。若没有匹配的 `User-Agent` 行，则查找通配符 `User-Agent: *`；若都没有，则视为无限制。

### User-Agent 匹配规则

-   **大小写不敏感**：`User-Agent: googlebot` 可以匹配 `GoogleBot`。
-   **子串匹配**：`User-Agent: bot` 会匹配 `bot`、`robot`、`Spambot` 等任何名称中包含 `bot`（不区分大小写）的爬虫。这可能导致意外匹配，因此建议使用完整且唯一的爬虫名称。
-   **通配符**：`User-Agent: *` 匹配所有未匹配到特定记录的爬虫。

### Disallow / Allow 规则详解

-   **路径前缀匹配**：规则中的路径是 **区分大小写** 的，且作为 URL 路径的 **前缀** 进行匹配。
-   **示例**：`Disallow: /tmp` 会阻止所有以 `/tmp` 开头的 URL，包括 `/tmp/pliers.html`、`/tmp/`，甚至 `/tmpspc/stuff.txt`（因为 `/tmp` 是 `/tmpspc` 的前缀）。因此需要谨慎使用，避免意外屏蔽过多内容。
-   **空字符串**：`Disallow:`（空值）表示允许所有 URL（无限制）。而 `Disallow: /` 表示屏蔽站点根路径下的所有 URL，即完全禁止抓取。
-   **通配符**：在 `Disallow`/`Allow` 中，`*` 和 `?` 没有特殊含义（与 `User-Agent` 不同）。若要匹配任意字符，无法使用通配符，只能依靠前缀匹配。但某些搜索引擎扩展支持了 `*`（如 `Disallow: /*.pdf$`），然而这不是标准。
-   **转义处理**：规则中的 `%XX` 和 URL 中的 `%XX` 会在比较前解码。但斜杠 `%2F` 是例外，必须严格匹配，不解码。
-   **规则顺序**：爬虫应按顺序检查所有 `Allow`/`Disallow` 规则，**第一个匹配的规则生效**。若没有任何规则匹配，则默认允许访问。
-   **`Allow` 的优先级**：虽然原始标准只有 `Disallow`，但扩展标准中 `Allow` 可以覆盖同级的 `Disallow`，前提是 `Allow` 规则更具体（即路径更长）。但不同爬虫实现可能有差异。为了兼容，建议避免使用 `Allow`，或者确保规则逻辑清晰。

### 局限性

-   **无法按文件类型屏蔽**：例如无法直接写出 `Disallow: *.pdf`，除非 PDF 文件都存放在特定目录下。
-   **无法表达“除某子目录外全部屏蔽”**：只能通过枚举允许的路径来间接实现，较为繁琐。
-   **区分大小写导致混淆**：`Disallow: /Private` 不会屏蔽 `/private`。对于大小写不敏感的文件系统，这可能产生预期外的结果。

### 实际工程注意事项

-   **爬虫应支持 `Crawl-delay` 指令**（非标准但广泛使用）：`Crawl-delay: 10` 表示两次请求之间至少间隔 10 秒。
-   **`Sitemap` 指令**：可以在 `robots.txt` 中添加 `Sitemap: http://example.com/sitemap.xml`（位置任意，不依赖 `User-Agent` 记录）。
-   **缓存刷新**：爬虫应尊重 `Cache-Control` 和 `Expires` 头，若未提供则默认缓存 24 小时。频繁请求 `robots.txt` 是不礼貌的。
-   **处理重定向**：如果 `robots.txt` 返回 3xx，爬虫应跟随，但需限制重定向次数（如最多 5 次）。
-   **错误处理**：若获取 `robots.txt` 时返回 5xx 或超时，建议指数退避重试，而非直接允许全部抓取。
