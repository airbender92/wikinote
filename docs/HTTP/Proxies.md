**代理（Proxy）** 是位于客户端和服务器之间的**中间人**，负责在两者之间转发 HTTP 报文。本章将全面介绍 HTTP 代理服务器的原理、功能、部署方式以及使用中可能遇到的复杂情况。

## 🧠 补充说明

- 代理与网关的边界在现代 Web 中已模糊：许多代理也做协议转换（如 HTTPS 解密），而网关也常复用 HTTP 协议。
- 代理按位置和功能可分为：
  - **正向代理（forward proxy）**：代表客户端访问外网（常用于企业、ISP 缓存）。
  - **反向代理（reverse proxy / surrogate）**：代表服务器接收请求（常用于负载均衡、缓存加速、安全防护）。
  - **透明代理（transparent proxy）**：客户端无感知，网络设备（如路由器）拦截 80/443 端口流量。

## 📌 代理是 HTTP 中间人

**Web 代理服务器** 位于客户端与服务器之间，代表客户端完成事务。其核心特点：

- **无代理**：HTTP 客户端直接与服务器通信。
- **有代理**：客户端与代理通信，代理再与服务器通信。客户端通过代理完成事务。

---

## 🧩 代理的双重角色：既是服务器又是客户端

如图 6-1 所示，代理必须同时扮演两个角色：

| 角色           | 行为描述                                   | 技术要求                                   |
| -------------- | ------------------------------------------ | ------------------------------------------ |
| **Web 服务器** | 接收客户端发来的请求报文，返回响应         | 必须正确解析 HTTP 请求、管理连接、返回响应 |
| **Web 客户端** | 向目标服务器（或上游代理）发送请求，接收响应 | 必须符合 HTTP 客户端规范（构造请求、处理重定向等） |

> 如果你要**自己实现 HTTP 代理**，必须同时遵循 HTTP 服务器和 HTTP 客户端的规范。

---

## 👥 私有代理与共享代理

| 类型           | 别名            | 服务对象         | 特点                                                                 | 典型示例                             |
| -------------- | --------------- | ---------------- | -------------------------------------------------------------------- | ------------------------------------ |
| **私有代理**   | Private proxy   | 单个客户端       | 资源独占，通常运行在客户端本地机器或专用设备上                       | 浏览器辅助插件、本地调试代理（Fiddler、Burp Suite） |
| **共享代理**   | Public proxy    | 多个客户端       | 集中部署，成本低，易管理；缓存类代理的用户越多，缓存越有效           | 企业网关代理、ISP 缓存代理、公共 CDN 反向代理 |

### 共享代理的优势
- **经济高效**：一台服务器服务成百上千用户。
- **管理简单**：只需维护一个中央代理，无需为每个客户端单独配置。
- **缓存命中率高**：用户越多，重复请求的可能性越大，缓存越有效（如 ISP 缓存）。

### 私有代理的典型场景
- 浏览器扩展程序（如广告拦截器、自动表单填充）。
- 开发调试工具（抓包代理，如 Charles、mitmproxy）。
- 某些 ISP 或企业为用户预配置的本地代理（例如预装配置的浏览器）。

---

## 🔄 代理与网关的区别（书中后续会展开）

简要区分：
- **代理**：客户端和服务器使用**相同协议**（如 HTTP ↔ HTTP）。
- **网关**：连接使用**不同协议**的双方（如 HTTP ↔ FTP、HTTP ↔ POP3、HTTP ↔ SMTP）。

但在实际产品中，两者功能常常重叠。例如，一个代理可能也支持 `ftp://` 协议的转换，此时它兼具网关功能。

## 📌 私有代理（Private Proxy）与共享代理（Public Proxy）

根据服务的客户端数量，代理服务器可以分为两大类：

| 类型           | 又称       | 服务对象         | 特点                                                                 | 典型示例                                     |
| -------------- | ---------- | ---------------- | -------------------------------------------------------------------- | -------------------------------------------- |
| **共享代理**   | 公共代理   | 多个客户端       | 集中部署，管理方便，成本低；用户越多，缓存命中率越高，效果越好       | 企业网关代理、ISP 缓存代理、CDN 反向代理     |
| **私有代理**   | 专用代理   | 单个客户端       | 通常运行在客户端本地，用于扩展功能、提升性能、注入广告或协助调试     | 浏览器辅助插件、本地调试代理、ISP 预装的小型代理 |

---

## 🌐 共享代理（Public Proxies）

- **主流形态**：绝大多数代理都是共享的。
- **优势**：
  - **经济高效**：一台服务器服务成百上千用户。
  - **易于管理**：集中配置和更新，无需接触每台客户端。
  - **缓存增益明显**：用户越多，重复请求的概率越高，**缓存命中率**和**字节命中率**随之提升，节省带宽效果更显著。
- **典型应用**：
  - 企业出口代理（安全过滤、访问控制）
  - ISP 缓存代理（减少国际带宽费用）
  - 反向代理集群（负载均衡、加速 Web 服务）

---

## 🖥️ 私有代理（Private Proxies）

- **常见程度**：不如共享代理普遍，但在特定场景下很有价值。
- **部署位置**：通常直接运行在客户端计算机上。
- **典型用途**：
  1. **扩展浏览器功能**：广告拦截、自动填充表单、网页翻译等。
  2. **提升性能**：本地缓存静态资源，加速重复访问。
  3. **托管广告**：某些免费 ISP 通过本地代理向用户浏览的页面插入广告，以换取免费上网服务。
  4. **开发调试**：抓包工具（如 Fiddler、Charles、mitmproxy）本质上是一个私有代理，捕获并修改浏览器与服务器之间的流量。

- **优点**：
  - 可针对单一用户**高度定制**行为。
  - 不依赖网络基础设施，可独立控制。
- **缺点**：
  - 无法利用多用户共享带来的缓存效益。
  - 需要部署和维护每台客户端，成本较高。

---

## 🔄 现代视角的变化

- **私有代理的复兴**：随着浏览器扩展（Extension）和用户脚本（UserScript）的流行，许多以前需要系统级私有代理的功能现在通过浏览器 API 实现，但底层原理仍类似。
- **ISP 插入广告的式微**：早期一些免费 ISP（如 NetZero）使用本地代理植入广告，现在已基本被付费宽带模式和 HTTPS 普及所取代（代理难以解密 HTTPS）。
- **调试代理的进化**：现代开发者常用 **Browser DevTools** 直接查看网络请求，但更复杂的场景（断点修改响应、模拟慢网络）仍需专用代理。

---

## 💡 补充知识：代理的另一种分类维度

除了私有/共享，还可以按代理对客户端的可见性分为：

- **显式代理（Explicit Proxy）**：客户端明确配置代理地址。
- **透明代理（Transparent Proxy）**：客户端无感知，网络设备（路由器、防火墙）拦截流量并转发给代理。

这两种分类可以组合：例如，企业出口处的共享代理可以是显式配置的，也可以是通过策略路由透明的。

## 📌 严格区分：代理 vs 网关

| 维度       | 代理（Proxy）                     | 网关（Gateway）                                |
| ---------- | --------------------------------- | ---------------------------------------------- |
| **协议**   | 连接使用**相同协议**的双方        | 连接使用**不同协议**的双方，充当“协议转换器”   |
| **典型场景** | HTTP 客户端 ↔ HTTP 代理 ↔ HTTP 服务器 | HTTP 客户端 ↔ HTTP/POP 网关 ↔ POP 邮件服务器 |
| **示例**   | 正向代理、反向代理、缓存代理       | Web 邮箱（Yahoo! Mail、Hotmail）、HTTP/FTP 网关 |

## 🖼️ 图 6-2 示意说明

根据书中描述：

- **图 6-2a – HTTP 代理**：  
  客户端 → 代理 → 服务器，三者均使用 HTTP 协议通信。代理转发请求和响应，不改变协议。

- **图 6-2b – HTTP/POP 网关**：  
  客户端使用 HTTP 发送邮件请求，网关将其转换为 POP（邮局协议）与后端邮件服务器通信，结果再转回 HTTP 返回给客户端。用户因此可以在浏览器中直接查看邮件，无需专用邮件客户端。

## 🔀 实践中的模糊界限

书中明确指出：**在实际产品中，代理和网关的界限是模糊的**。原因包括：

1. **版本转换**：浏览器和服务器可能使用不同 HTTP 版本（如 HTTP/1.0 与 HTTP/1.1），代理必须做协议适配，这就暗含了“转换”功能。
2. **多功能代理**：许多商业代理产品同时支持：
   - SSL 加密隧道（需要处理 HTTPS，涉及加密协议）
   - SOCKS 防火墙代理（不同协议）
   - FTP 访问（HTTP/FTP 网关功能）
   - Web 应用加速（可能涉及协议转换）

> 因此，一个设备往往**既是代理，也是网关**。通常“代理”泛指转发 HTTP 流量的中间设备，而“网关”则强调协议转换。

## 🧠 补充说明

### 网关的常见类型
| 类型                     | 协议转换                        | 示例                                   |
| ------------------------ | ------------------------------- | -------------------------------------- |
| 服务器端网关             | HTTP 请求 → 其他协议（访问服务器） | HTTP/FTP 网关、HTTP/POP 网关          |
| 客户端端网关             | 其他协议 → HTTP 请求（访问客户端） | SSL 加速器（HTTPS → HTTP）            |
| 应用服务器网关           | HTTP → 应用程序 API（CGI、Servlet） | 动态网站、Web API 后端                 |

### 为何区分仍重要？
- **设计意图**：代理侧重**转发、过滤、缓存**；网关侧重**协议转换**。
- **部署位置**：代理通常在网络边缘（企业出口、ISP），网关常用于**前后端解耦**。
- **安全策略**：代理可做内容检查；网关可隐藏后端协议细节。

## 📌 代理的多种用途（Why Use Proxies?）

代理服务器不仅能转发 HTTP 流量，还能**监控、修改、过滤、优化**流量，从而实现许多增值服务。书中列举了以下典型应用场景：

---

### 1. 儿童过滤器（Child Filter）
- **原理**：学校或家庭在出口部署过滤代理，根据 URL 黑名单或内容分类，**阻止成人内容**，同时允许访问教育类网站。
- **图 6-3 示意**：儿童请求被代理拦截，若目标是色情网站则拒绝，若为教育网站则放行。
- **常见产品**：如 Netsweeper、CleanBrowsing、OpenDNS FamilyShield。

---

### 2. 文档访问控制器（Document Access Controller）
- **原理**：在企业中，所有 Web 请求强制经过中央代理，代理根据**客户端 IP、用户身份、时间等**策略统一控制访问权限，并生成审计日志。
- **优势**：无需在每个后端服务器上分别配置访问控制，集中管理，尤其适合多厂商、多版本的异构环境。
- **图 6-4 示例**：
  - 客户端1：可无限制访问服务器 A 的新闻
  - 客户端2：无限制访问互联网
  - 客户端3：访问服务器 B 前需要密码认证

---

### 3. 安全防火墙（Security Firewall）
- **原理**：代理作为应用层防火墙，位于网络边界，**只允许特定的应用层协议（如 HTTP、HTTPS）通过**，并可以深度检查流量内容（如病毒扫描）。
- **图 6-5 示意**：代理位于 DMZ，外部请求先到代理，经安全策略检查后再转发到内部服务器。
- **典型应用**：防病毒网关（如扫描 HTTP 下载文件）、数据防泄漏（DLP）。

---

### 4. Web 缓存（Web Cache）
- **原理**：代理缓存热门文档的本地副本，后续相同请求直接从缓存返回，减少对源服务器的访问和广域网带宽消耗。
- **图 6-6 示意**：客户端1和2从附近缓存获取对象 A，客户端3和4仍从源服务器获取。
- **效益**：降低延迟、节省带宽、减轻服务器负载。

---

### 5. 反向代理 / 服务器加速器（Surrogate / Reverse Proxy / Server Accelerator）
- **原理**：代理**伪装成源服务器**（即反向代理），接收客户端的请求，从后端真实服务器获取内容后缓存并返回。
- **图 6-7 示意**：代理位于服务器的前面，客户端以为直接访问服务器，实际由代理响应或转发。
- **用途**：
  - 加速慢速服务器的内容交付
  - 负载均衡
  - SSL 终结（解密后转发给内部 HTTP 服务器）
  - 安全防护（隐藏真实服务器 IP）

---

### 6. 内容路由器（Content Router）
- **原理**：代理根据**网络流量状况、内容类型、用户付费等级**等动态将请求转发到最合适的服务器（如最近的缓存副本或专用压缩代理）。
- **图 6-8 示例**：
  - 付费用户（Sharon）被路由到附近的副本缓存。
  - 免费用户（Rob）仍被路由到源服务器。
  - 服务器 A 购买了内容分发服务，其请求被路由到副本缓存；服务器 B 未购买，请求直接到源服务器。

---

### 7. 转码器（Transcoder）
- **原理**：代理在传输过程中修改内容格式，实现**设备适配或内容优化**。
- **常见转换**：
  - GIF → JPEG（减少大小）
  - 高分辨率图像 → 低分辨率（适合电视屏幕）
  - HTML → 纯文本（适合手机/寻呼机）
  - 实时翻译（英文 → 西班牙文）
- **图 6-9 示意**：代理将英文 HTML 页面实时转为西班牙文，并简化为适用于手机屏幕的文本格式。

---

### 8. 匿名代理（Anonymizer）
- **原理**：主动移除或修改请求中的**身份标识信息**，保护用户隐私。
- **图 6-10 示例修改**：
  - 删除 `User-Agent` 中的操作系统和浏览器版本
  - 删除 `From` 头（邮件地址）
  - 删除 `Referer` 头（来源页面）
  - 删除 `Cookie` 头（追踪标识）
- **常见用途**：绕过地理限制、防止网络跟踪、增强匿名性。

## 🔗 代理层级（Proxy Hierarchies）

### 静态层级（图 6-12）
- 代理可以串联成**链**，报文依次经过多个代理最终到达源服务器，响应沿原路返回。
- **父子关系**：
  - **父代理（parent）**：更靠近服务器（入站方向）
  - **子代理（child）**：更靠近客户端（出站方向）
- 示例：`客户端 → 代理1（子） → 代理2（子+父） → 代理3（父） → 源服务器`

### 动态内容路由（图 6-13）
层级**不必是静态的**。代理可以根据多种因素动态选择下一个目标（父代理或源服务器）。书中举例：
- **付费分发**：若请求的对象属于已付费内容分发服务的 Web 服务器，则路由到附近的专用缓存服务器。
- **特定图像类型**：若请求特定图像格式，则路由到专用的压缩代理，先压缩再返回，以加速客户端下载。

### 动态父代理选择的其他策略
| 策略                 | 说明                                                      |
| -------------------- | --------------------------------------------------------- |
| **负载均衡**         | 根据父代理当前的负载情况选择负载最轻的。                  |
| **地理就近路由**     | 选择负责该源服务器地理区域的父代理。                      |
| **协议/类型路由**    | 根据 URI 的类型（如 `.mp4` 或 `/api/`）选择不同的父代理。 |
| **订阅式路由**       | 若发布商付费获取高性能服务，则将请求路由到大缓存或压缩引擎。 |

> 动态路由逻辑的实现方式包括：配置文件、脚本语言、动态可执行插件（如代理软件的可编程模块）。

## 💡 补充说明与实际应用

### 1. 代理层级的常见拓扑
- **两层**：客户端 → 本地缓存（子）→ 上游父缓存（如 ISP 缓存）
- **三层**：客户端 → 企业出口代理 → ISP 缓存 → 国家骨干缓存 → 源服务器
- **网状（meshed）**：代理之间可以互相查询（如 ICP、CARP 协议），第 20 章会详细讨论。

### 2. 现代 CDN 中的反向代理
- CDN 边缘节点本质上就是**反向代理层级**。例如：客户端请求 `www.example.com`，DNS 解析到最近的边缘代理（替代），边缘代理若未命中则向父层或源服务器回源。

### 3. 动态路由的应用
- **A/B 测试**：按比例将部分用户路由到实验版本服务器。
- **内容感知**：视频请求路由到专用流媒体服务器；API 请求路由到应用服务器。
- **故障转移**：父代理不可用时自动切换到备用父代理或直接访问源服务器。

## 📌 核心问题：客户端流量如何被引导到代理？

在默认情况下，客户端直接与源服务器通信。为了让 HTTP 流量经过代理，可以采用以下四种常见方式（图 6-14 示意）：

---

### 1️⃣ 修改客户端（Modify the client）

- **原理**：在客户端（浏览器）上**显式配置代理**。用户或管理员手动填写代理的 IP 地址和端口，或者通过自动配置脚本（PAC）动态决定是否使用代理。
- **实现方式**：支持手动配置（如浏览器设置 → 网络 → 代理）或自动配置（如 PAC 文件、WPAD）。
- **特点**：客户端**明确知晓**代理的存在，主动将请求发给代理而非源服务器。
- **优点**：灵活、可控，可针对不同 URL 选择不同代理。
- **缺点**：需要客户端支持并正确配置；若代理故障，客户端需手动切换。
- **图 6-14a 示意**：客户端直接连接到代理，代理再连接到源服务器。

---

### 2️⃣ 修改网络（Modify the network）—— 透明代理

- **原理**：利用网络基础设施（交换机、路由器）**拦截** HTTP 流量，无需客户端任何配置。这种代理称为 **透明代理（intercepting proxy）**。
- **实现技术**：
  - 策略路由（PBR）：根据源 IP、目标端口（80、443）将流量重定向到代理设备。
  - WCCP（Web Cache Coordination Protocol）：路由器与缓存代理协商，拦截并转发流量。
  - 四层交换机的重定向功能。
- **特点**：客户端**无感知**，仿佛直接与源服务器通信。
- **优点**：无需修改客户端配置，对用户透明，部署方便。
- **缺点**：难以处理 HTTPS（若不做中间人解密，只能透传；若解密则需安装根证书）。
- **图 6-14b 示意**：客户端发出的请求被网络设备劫持，送往透明代理，代理再转发给源服务器。

---

### 3️⃣ 修改 DNS 命名空间（Modify the DNS namespace）

- **原理**：将源服务器的域名解析到**反向代理（surrogate）** 的 IP 地址，而不是真实的服务器 IP。代理可以自己响应请求，或向后端服务器获取内容。
- **实现方式**：
  - 手动修改 DNS 记录，将 `www.example.com` 指向代理的 IP。
  - 使用动态 DNS 服务，根据客户端位置、服务器负载等实时决定返回代理 IP 还是真实服务器 IP。
- **特点**：代理**伪装**成源服务器，接管所有流量。这种代理常称为**反向代理**或替代（surrogate）。
- **优点**：无需改动客户端，能很好处理 HTTPS；可实现全球负载均衡（如 CDN）。
- **缺点**：DNS 变更生效有延迟（TTL）；若代理故障，需快速更改 DNS。
- **图 6-14c 示意**：客户端解析域名得到代理 IP，请求发往代理；代理再决定从何处获取内容。

---

### 4️⃣ 修改 Web 服务器（Modify the web server）

- **原理**：源服务器返回 **HTTP 重定向**（状态码 `305 Use Proxy`），告知客户端“请使用某个代理来访问我”。
- **实现方式**：服务器配置特定规则，对某些请求返回 `305` 响应，并在 `Location` 头中给出代理的 URI。
- **特点**：每个请求需要额外的一次重定向往返，增加延迟。
- **优点**：可动态决定是否使用代理，且可以利用现有 HTTP 基础设施。
- **缺点**：`305` 状态码在实际中很少实现，部分客户端可能不支持；会增加延时。
- **图 6-14d 示意**：客户端先请求源服务器，服务器返回 `305` 并告知代理地址；客户端再次请求代理，代理再与源服务器通信。

---

## 📊 四种方式对比总结

| 方式               | 是否需客户端配置 | 客户端感知 | 延迟影响 | 典型用例                       |
| ------------------ | ---------------- | ---------- | -------- | ------------------------------ |
| 修改客户端         | 是               | 是         | 无额外   | 企业显式代理、浏览器插件       |
| 修改网络           | 否               | 否         | 极小     | ISP 透明缓存、学校过滤网关     |
| 修改 DNS           | 否               | 否（但看到不同IP） | 无额外   | CDN、反向代理、服务器加速器     |
| 修改 Web 服务器    | 否               | 是（重定向） | 一次往返 | 负载均衡、临时迁移（实际很少用） |

## 📌 客户端代理配置的四种方法

现代浏览器（如 Netscape、Microsoft IE 等）支持多种方式配置代理，书中列举了四种：

| 配置方式                     | 说明                                                                 | 优点                         | 缺点/注意事项                         |

| **浏览器预配置**             | 浏览器厂商或分销商在**交付前**已将代理设置预置在浏览器中（如 ISP 定制版） | 开箱即用，用户无需干预       | 缺乏灵活性，代理变动需重新分发浏览器  |
| **代理自动配置（PAC）**      | 用户提供一个 **PAC 文件** 的 URI，浏览器下载该 JavaScript 文件，执行其中的 `FindProxyForURL(url, host)` 函数，**动态决定**每个请求是否使用代理、使用哪个代理 | 灵活强大，可按 URL、时间、负载等条件选择代理 | 需部署 PAC 文件服务器；编写 JavaScript 脚本有一定复杂度 |
| **WPAD 代理发现**            | 浏览器自动（无需用户配置）发现网络中的配置服务器，从中下载 PAC 文件 | 零配置，即插即用             | 需网络支持 DHCP 或 DNS 服务；早期实现有安全漏洞 |

## 🔍 各方式详解

### 1. 手动配置
- 典型操作路径（以 IE 为例）：`工具 → Internet 选项 → 连接 → 局域网设置 → 为 LAN 使用代理服务器`。
- 可分别为 HTTP、HTTPS、FTP 等协议设置不同代理。
- **局限性**：无法根据 URL 动态选择代理；代理故障时需手动切换。

### 2. 浏览器预配置
- 常见于 **ISP 定制版浏览器** 或企业内部预装镜像。例如，早期 AOL 的光盘中浏览器已预设了代理。
- 本质上仍是“手动配置”的静态值，只是由厂商代为填写。

### 3. PAC（Proxy Auto-Configuration）
- **文件扩展名**：`.pac`
- **MIME 类型**：`application/x-ns-proxy-autoconfig`
- **核心函数**：
  ```javascript
  function FindProxyForURL(url, host) {
      if (shExpMatch(url, "http://example.com/*")) return "DIRECT";
      return "PROXY proxy.example.com:8080";
  }
  ```
- **返回值选项**：
  - `"DIRECT"`：直连，不经过代理
  - `"PROXY host:port"`：使用指定 HTTP 代理
  - `"SOCKS host:port"`：使用指定 SOCKS 代理
  - 可返回多个（空格分隔），作为故障转移列表，如 `"PROXY proxy1:8080; PROXY proxy2:8080; DIRECT"`
- **优势**：可按域名、IP 段、时间、目标端口等条件灵活选择代理，甚至实现负载均衡和故障转移。

### 4. WPAD（Web Proxy Autodiscovery Protocol）
- **目标**：实现**零配置**的代理自动发现。
- **工作流程**：
  1. 浏览器通过 DHCP 或 DNS 查询获取配置文件的 URL。
  2. 下载 PAC 文件。
  3. 执行 PAC 确定代理。
- **发现顺序**（WPAD 标准）：
  - DHCP（选项 252）
  - DNS A 记录（`wpad.domain.com`）
  - DNS SRV 记录等
- **安全历史**：早期 IE 的 WPAD 实现存在安全漏洞（可被恶意服务器劫持），后续版本已修复（限制查询范围、要求证书等）。
- **现代应用**：少数企业环境仍在使用，但更常见的是通过 **组策略（GPO）** 或 **MDM** 分发代理设置。

## 📌 为什么需要 PAC 文件？

**手动配置代理**的缺点：
- **不灵活**：只能为所有流量指定单一代理，无法按 URL、时间等条件区分。
- **无故障转移**：代理宕机时，浏览器无法自动切换到备用代理。
- **管理困难**：当数千台客户端需要变更代理时，逐一修改不现实。

**PAC（Proxy Auto-Configuration）** 通过 **JavaScript 程序** 动态决定每个请求是否使用代理、使用哪个代理，解决了上述问题。

---

## 🧠 PAC 文件的工作原理

1. **配置**：在浏览器中填写 PAC 文件的 **URI**（通常放在 Web 服务器上），如 `http://proxy.example.com/proxy.pac`。
2. **获取**：浏览器下载该 PAC 文件（MIME 类型为 `application/x-ns-proxy-autoconfig`，扩展名一般为 `.pac`）。
3. **执行**：浏览器为每次请求调用 PAC 文件中的 `FindProxyForURL(url, host)` 函数，根据返回结果决定连接方式。
4. **缓存**：PAC 文件通常被缓存，避免每次请求都下载。

---

## 📝 `FindProxyForURL` 的返回值（表 6-1）

| 返回值格式                     | 含义                                         | 示例                              |
| ------------------------------ | -------------------------------------------- | --------------------------------- |
| `"DIRECT"`                     | 直连，不使用代理                             | `"DIRECT"`                        |
| `"PROXY host:port"`            | 使用指定的 HTTP 代理                         | `"PROXY proxy.example.com:8080"`  |
| `"SOCKS host:port"`            | 使用指定的 SOCKS 代理                        | `"SOCKS socks.example.com:1080"`  |
| `"PROXY ...; PROXY ...; DIRECT"` | 多选（空格分隔），表示依次尝试直到成功或直连 | `"PROXY p1:8080; PROXY p2:8080; DIRECT"` |

---

## 📄 示例 6-1 解读

```javascript
function FindProxyForURL(url, host) {
    if (url.substring(0,5) == "http:") {
        return "PROXY http-proxy.mydomain.com:8080";
    } else if (url.substring(0,4) == "ftp:") {
        return "PROXY ftp-proxy.mydomain.com:8080";
    } else {
        return "DIRECT";
    }
}
```

- **HTTP 请求**（以 `http:` 开头）→ 使用 `http-proxy.mydomain.com:8080`
- **FTP 请求**（以 `ftp:` 开头）→ 使用 `ftp-proxy.mydomain.com:8080`
- **其他协议**（如 HTTPS、file 等）→ 直连

> 注：HTTPS 请求以 `https:` 开头，此例未单独处理，会走 `else` 分支直连。实际中可增加类似逻辑。

## 🔍 PAC 的扩展能力（第 20 章会详述）

- **按域名区分**：`dnsDomainIs(host, ".example.com")`
- **按 IP 子网**：`isInNet(host, "192.168.1.0", "255.255.255.0")`
- **按时间**：`var now = new Date(); now.getDay() == 6`（周末特殊处理）
- **负载均衡/故障转移**：返回多个代理，浏览器自动重试
- **随机种子**：`Math.random()` 可实现简单的轮询

## 🌐 WPAD（Web Proxy Autodiscovery Protocol）

**WPAD** 的目标是实现 **零配置代理自动发现**。浏览器无需手动填入任何代理信息，即可自动找到 PAC 文件。

### 工作流程（4 步）
1. **发现**：通过一系列资源发现技术找到 PAC 文件的 URI。
2. **获取**：下载该 PAC 文件。
3. **执行**：运行 `FindProxyForURL` 确定代理。
4. **使用**：用该代理发送请求。

### 发现机制（按顺序尝试，直到成功）
| 技术                       | 说明                                                         |
| -------------------------- | ------------------------------------------------------------ |
| **DHCP（首选）**           | 查询 DHCP 选项 252（一个包含 PAC 文件 URL 的字符串）。        |
| **SLP（Service Location Protocol）** | 较少使用。                                               |
| **DNS 已知主机名**         | 查询 `wpad.<domain>` 的 A 记录，例如 `wpad.example.com`。若成功，PAC URL 为 `http://wpad.example.com/wpad.dat`。 |
| **DNS SRV 记录**           | 查询 `_wpad._tcp.<domain>` 的 SRV 记录。                     |
| **DNS TXT 记录**           | 查询 `wpad.<domain>` 的 TXT 记录，内含 PAC URL。             |

> 浏览器会从当前域名的**最左侧部分**开始逐级向上尝试（例如 `host1.sub.example.com` → `sub.example.com` → `example.com`），直到获得 PAC 文件或超出范围。

---

## ⚠️ WPAD 安全性历史

- **早期漏洞**：IE 浏览器（2000 年代初期）的 WPAD 实现可通过恶意 DHCP/DNS 服务器伪造 PAC 文件，劫持所有 HTTP/HTTPS 流量（中间人攻击）。
- **缓解措施**：
  - 后续版本要求 PAC 文件必须来自可信源（如公司内部域名）。
  - 结合 HTTPS 下载 PAC 文件（`https://wpad.example.com/wpad.dat`）。
  - 企业网络中禁用 WPAD 或使用组策略指定静态配置。

## 📌 WPAD 是什么？

**WPAD（Web Proxy Autodiscovery Protocol，Web 代理自动发现协议）** 是一种让浏览器 **自动发现并获取 PAC 文件** 的算法，无需用户手动配置代理。它的目标是实现 **零配置代理部署**。

### WPAD 的四步工作流程
1. **发现 PAC URI**：通过多种资源发现技术（DHCP、DNS 等）找到 PAC 文件的 URL。
2. **获取 PAC 文件**：从该 URL 下载 PAC 文件（通常名为 `wpad.dat`，MIME 类型 `application/x-ns-proxy-autoconfig`）。
3. **执行 PAC 文件**：运行其中的 `FindProxyForURL(url, host)` 函数，决定每个请求使用哪个代理（或直连）。
4. **使用代理**：根据函数返回值发送请求。

---

## 🔍 WPAD 的发现机制（按顺序尝试，直到成功）

书中列出了 WPAD 规范定义的 **五种技术**，按优先级从高到低依次尝试：

| 顺序 | 技术                       | 说明                                                                 |
| ---- | -------------------------- | ------------------------------------------------------------------ |
| 1    | **DHCP**                   | 查询 DHCP 选项 252，该选项应包含 PAC 文件的完整 URL（如 `http://wpad.example.com/wpad.dat`）。 |
| 2    | **SLP**（Service Location Protocol） | 查询 SLP 服务类型 `service:wpad:http` 获取 PAC URL。较少使用。        |
| 3    | **DNS 已知主机名**         | 查询 `wpad.<domain>` 的 A 记录。若返回 IP，则 PAC URL 为 `http://wpad.<domain>/wpad.dat`。浏览器会从完整域名逐步向上尝试（如 `wpad.sub.example.com` → `wpad.example.com` → `wpad.com`）。 |
| 4    | **DNS SRV 记录**           | 查询 `_wpad._tcp.<domain>` 的 SRV 记录，获取提供 PAC 文件的服务器的域名和端口。 |
| 5    | **DNS TXT 记录**           | 查询 `wpad.<domain>` 的 TXT 记录，其中应直接包含 PAC 文件的 URL。     |

> 客户端会依次尝试这些方法，一旦某种方法成功获得 PAC URL 并且能下载到有效的 PAC 文件，就停止后续尝试。

## 📁 PAC 文件命名与位置约定

- **文件名**：通常为 `wpad.dat`（但实际可以是任意名称，只要 URL 正确）。
- **MIME 类型**：`application/x-ns-proxy-autoconfig`
- **典型 URL 示例**：
  - DHCP 直接返回：`http://proxy.example.com/proxy.pac`
  - DNS A 记录：`http://wpad.example.com/wpad.dat`

> 注意：PAC 文件的 URI 必须是 HTTP 协议（不支持 HTTPS，因为需要先配置代理才能访问 HTTPS）。这带来了一定的安全风险。

## ⚠️ 安全性考虑与漏洞

### 早期 WPAD 安全漏洞（如 IE 浏览器）
- **攻击原理**：恶意用户在同一网络内提供恶意的 DHCP 或 DNS 响应，将 WPAD 指向攻击者控制的 PAC 文件，从而**劫持所有 HTTP/HTTPS 流量**（中间人攻击）。
- **影响**：可窃取 Cookie、登录凭据、修改页面内容等。

### 缓解措施（现代实践）
- **禁用 WPAD**：在不需要自动发现的企业网络中，通过组策略或系统配置禁用 WPAD。
- **仅使用可信 DNS/WPAD 服务器**：配置 DHCP 下发可信的代理配置，不依赖不可控的 DNS。
- **限制域名搜索范围**：浏览器只查询公司内部域名的 WPAD，不向上递归到顶级域。
- **升级到 HTTPS PAC**：某些新方案支持从 HTTPS 下载 PAC 文件（需先配置一个安全通道），但这需要初始引导。
- **使用浏览器策略**：Chrome/Edge 可通过 `ProxySettings` 等策略强制指定代理，不使用 WPAD。

## 🔍 要点 1：代理请求中的 URI 与服务器请求中的 URI 有何不同？

### 普通服务器请求（无代理）
当浏览器直接连接源服务器时，HTTP 请求行中**只包含路径部分**（以及可能的查询参数），不包含协议、主机名和端口。

```
GET /index.html HTTP/1.1
Host: www.example.com
```

### 显式代理请求
当浏览器配置了代理时，请求行中**包含完整的 URI**（协议 + 主机 + 端口 + 路径）。

```
GET http://www.example.com/index.html HTTP/1.1
Host: www.example.com
```

> 注意：即使请求行中已有完整 URI，`Host` 头依然需要保留（某些代理或服务器可能依赖它）。

### 为什么会有这种差异？
- **历史原因**：最早的 HTTP 设计假设客户端直接与单一服务器通信，服务器自身知道自己的主机名，因此无需在请求中重复。
- **代理出现后**：代理需要知道目标服务器的主机名和端口才能建立连接。因此，HTTP/1.0 开始要求显式代理请求使用完整 URI。

### 实际影响
- 如果一个代理收到**不完整 URI**（如拦截代理收到的可能是普通服务器格式），它必须能够正确重构目标 URI，否则无法转发。

---

## 🕵️ 要点 2：拦截代理和反向代理如何隐藏服务器主机信息？

### 拦截代理（透明代理）
- 客户端**不知道**代理存在，因此发送的是**不完整 URI**（如同发给源服务器）。
- 代理必须从以下信息中推断目标主机：
  - 目标 IP 地址（可能对应多个虚拟主机，不准确）
  - `Host` 头（HTTP/1.1 必须，但 HTTPS 加密后不可见）
  - 之前解析的域名（如果代理能通过 SNI 或其他方式获取）

### 反向代理（替代 / Surrogate）
- 反向代理**伪装成源服务器**（即 DNS 解析后直接指向代理 IP）。
- 客户端发送的请求 URI 也是不完整的（因为客户端以为自己在直接与源服务器通信）。
- 代理必须根据 `Host` 头或配置的规则将请求映射到后端的真实服务器。

### 问题场景
- 如果多个虚拟主机共享同一 IP，拦截代理可能无法区分请求应发往哪个后端。
- 当 `Host` 头缺失或错误时（如旧客户端），代理可能返回错误或默认站点。

---

## ✏️ 要点 3：URI 修改的规则与陷阱

### 代理可以修改 URI 吗？
- **理论上**：代理不应随意修改 URI，尤其是路径部分，否则可能破坏语义。
- **实践中**：某些代理会进行“规范化”（canonicalization），例如：
  - 将 `http://example.com:80/foo` 中的 `:80` 删除（因为默认端口）。
  - 将 ``, ```` 等编码后的字符解码。
  - 补全缺失的尾部斜杠（对目录请求）。

### 为什么会有问题？
- 某些服务器依赖 URI 中的特定格式（如大小写敏感、保留某些转义字符）。
- 修改后的 URI 可能导致缓存失效、访问控制错误，或者破坏数字签名（如某些安全机制基于原始 URI）。

### 安全建议
- 代理应**只修改绝对必要**的内容（例如为了正确路由）。
- 对于使用摘要认证或签名认证的请求，代理应避免任何 URI 修改（包括大小写、编码），否则认证会失败。

---

## 🌐 要点 4：代理如何影响浏览器的自动补全和主机名扩展？

### 无代理时浏览器的智能行为
当用户输入不完整的主机名（如 `oreilly`），浏览器会尝试：
- 自动添加 `www.` 前缀和 `.com` 后缀。
- 查询 DNS，若失败则继续尝试其他组合（如 `.net`、`.org`）。
- 使用系统 DNS 后缀搜索列表（如 `oreilly.company.local`）。

### 显式代理时浏览器行为的变化
- 浏览器会将**用户输入的原始 URL 原样发送给代理**，不再进行自动扩展。
- 例如用户输入 `http://oreilly`，浏览器会发送 `GET http://oreilly/` 给代理，而不是尝试补全为 `http://www.oreilly.com/`。
- **原因**：代理可能位于一个完全不同的网络环境，其 DNS 解析策略可能与客户端不同。浏览器无法确定应该使用哪种扩展规则。

### 问题与解决方案
- 用户可能因为忘记输入完整域名而遇到“无法连接”错误，即使该站点实际可访问。
- **解决**：一些智能代理会**模仿浏览器的扩展逻辑**，在接收到短主机名时自动尝试添加常见后缀（`www.`、`.com` 等），然后再转发。

### 对拦截代理的影响
- 拦截代理对客户端完全透明，浏览器认为自己在直接访问服务器，因此**仍然执行自动扩展**。
- 但拦截代理可能会遇到一个问题：浏览器可能已经尝试了多个 IP 地址（其中一些可能已失效），而代理需要在不破坏连接的情况下正确处理这些情况。

您引用的这段内容，精确指出了HTTP协议中一个关键但常被误解的设计差异：**发给原始服务器的请求和发给代理服务器的请求，其请求行中的URI格式是不同的。**

简单来说，规则如下：

-   **发给原始服务器**：使用**部分URI**（也称为请求目标）。格式为 `方法 路径 版本`，例如 `GET /index.html HTTP/1.1`。这是因为服务器根据已建立的TCP连接和`Host`请求头就能确定目标。
-   **发给代理服务器**：使用**完整URI**。格式为 `方法 完整URL 版本`，例如 `GET http://www.example.com/index.html HTTP/1.1`。代理本身不是最终目的地，它需要你明确告知**目标服务器是谁**以及**使用什么协议（如http或https）**。

造成这种差异的根本原因是**历史演进**：

1.  **HTTP/0.9/1.0 时代**：协议设计之初没有代理和虚拟主机的概念，客户端与服务器直接通信。服务器通过TCP连接就能知道自己在和谁说话，因此客户端发送部分URI (`GET /path`) 是种简洁的优化。
2.  **代理的出现**：代理需要根据客户端请求去联系另一个服务器。如果客户端只发送 `/index.html`，代理就无法知道目标服务器的域名、端口和协议。因此，协议要求客户端向代理发送请求时，必须使用**完整URI**。

### 总结与关键点

-   **客户端角色**：客户端是根据自身配置来决定发送哪种URI。配置了代理，就发完整URI；没配置，就发部分URI。
-   **代理的角色**：一个稳健的代理服务器必须能同时处理两种格式的请求，因为它可能收到来自不同配置的客户端的请求，或者处于“拦截代理”的场景中。
-   **拦截代理的特殊性**：即使客户端未配置代理，网络流量也可能被路由到一个“透明/拦截代理”。此时，客户端以为自己在和原始服务器通信，所以发的是部分URI。这就要求拦截代理必须具备**通过其他信息（如`Host`头）来还原完整URI的能力**。
-   **“缺失的”主机信息**：这个设计缺陷同样困扰过**虚拟主机**。这也是`Host`头成为HTTP/1.1必需项的原因——它为部分URI提供了辨别具体网站所需的主机名。

总而言之，代理和服务器使用不同URI格式，是早期互联网协议演进过程中解决实际问题的产物。理解这一点，对调试代理相关问题和设计网络程序都很有帮助。

### 1. 正向代理 vs. 反向代理的关键区别

| 特性 | 正向代理 | 反向代理 |
|------|----------|----------|
| **谁配置** | 客户端（浏览器、App）需要**主动配置**代理地址 | 客户端**无感知**，请求直接发给目标域名的IP/DNS |
| **客户端认知** | 客户端明确知道自己要经过代理 | 客户端以为自己就是在和“真正的服务器”通信 |
| **请求行格式** | **完整URL**（因为要告诉代理去哪个服务器） | **部分URI**（客户端不知道有代理，所以按普通服务器请求格式发） |
| **常见例子** | 公司内网上网代理、VPN代理、科学上网工具 | Nginx 反代、Apache 反代、云负载均衡器 |

### 2. 为什么书上说“发给代理用完整URI”？

那是指**正向代理**下，客户端必须明确告诉代理：“请帮我去拿 `http://www.example.com/index.html` 这个资源”。如果不带协议和主机名，代理无法知道要去连接哪里。

```http
# 发给正向代理的请求
GET http://www.example.com/index.html HTTP/1.1
```

### 3. 你为什么看到项目里前端请求是部分URI + Nginx？

因为你的 Nginx 是作为**反向代理**部署的。例如：

- 前端代码中请求 `GET /api/user`
- 浏览器解析域名 `myapp.com`，连接服务器（可能是 Nginx 的 IP）
- Nginx 收到请求行 `GET /api/user HTTP/1.1`，这是一个**部分URI**
- Nginx 根据配置（如 `proxy_pass http://backend-server`）将请求转发给后端的应用服务器，同时自己会加上 `Host` 头等信息

这个过程，浏览器完全不知道背后有 Nginx，所以它发送部分URI是完全符合HTTP规范的（因为它以为自己是在和原始服务器对话）。

### 4. 那条规则的真正适用范围

“发给代理用完整URL，发给服务器用部分URI”这条规则只要求**客户端**根据它的配置来决定。

- 如果客户端配置了**正向代理** → 发完整URL
- 如果没有配置代理，或者配置的是反向代理（对客户端透明） → 发部分URI

### 总结一句话

**书里说的规则是针对“客户端主动配置正向代理”的情况；你项目里 Nginx 是反向代理，对客户端透明，所以前端仍然使用部分URI，两者并不冲突。**

这正是你之前困惑的根源——为什么有些地方要发完整URI，有些地方只用部分URI+Host头。

### 问题本质相同：缺少目标主机信息

无论是正向代理还是虚拟主机，服务器收到一个部分URI（如 `GET /index.html`）时，都无法知道客户端真正想访问的是哪个网站。

- **正向代理**：不知道要去连接哪个服务器（`www.example.com` 还是 `www.another.com`）
- **虚拟主机**：不知道要返回哪个网站的 `/index.html`（因为多个网站共用同一个IP）

### 解决方案不同：历史与现实的选择

| 场景 | 解决方案 | 原因 |
|------|----------|------|
| **正向代理** | 请求行使用**完整URI**<br>`GET http://www.example.com/index.html` | 代理需要知道**协议、主机、端口**才能建立到目标服务器的连接。这是HTTP/1.0为解决代理问题而引入的。 |

理论上，让所有请求都发完整URI是最简单的。但HTTP/1.0流行时，数以万计的服务器已经只接受部分URI。如果突然要求所有客户端都发完整URI，整个Web会崩溃。因此，设计者做了务实的妥协：

- **代理场景**：新问题，可以要求新格式（完整URI）
- **虚拟主机**：老问题，在旧格式上打补丁（Host头）

你项目中的Nginx作为**反向代理**时，实际上同时处理了这两种模式：

1. **从客户端收到的请求**（因为是反向代理，客户端无感知）：

2. **Nginx向后端服务器转发时**，它可以根据配置决定发送什么格式。通常它仍然发送部分URI + Host头（因为后端也往往是虚拟主机），但Nginx内部需要知道目标主机，这个信息来自客户端请求的Host头或者`proxy_pass`指令中指定的地址。

3. **宁可不 “改进”，也不要破坏**：很多看起来无害的“规范化”操作，恰恰是破坏现有服务的元凶。因为服务可能依赖某些“不规范”但已被广泛使用的特性。

### 问题核心：浏览器的故障转移被“骗”过了

- **无代理时**：浏览器的责任链包括“连接重试”。它会自己尝试所有IP，直到成功或全部失败。
- **有拦截代理时**：浏览器把“连接”这一步交给了网络，代理过早地确认了连接成功，浏览器不再重试其他IP。**故障转移的责任从浏览器转移到了代理身上**。

### 代理需要做什么？

为了弥补这个“责任转移”，代理**必须自己实现DNS故障转移逻辑**：

- **重新解析主机名**：从客户端请求的 `Host` 头中提取主机名（如 `www.oreilly.com`），重新进行DNS解析，获得IP列表。
- **按序尝试连接**：尝试每个IP，直到成功建立到真实源服务器的TCP连接。
- **反向DNS查找**：如果无法获取主机名（比如只有IP地址），可以通过反向DNS查找该IP对应的其他可能IP（但效果有限，不如直接重新解析可靠）。

### 对实际部署的影响

| 代理类型 | 是否需要实现DNS故障转移 | 原因 |
|----------|------------------------|------|
| **显式正向代理** | **需要** | 浏览器把完整URI交给代理后，不再做任何IP重试；代理必须自己解析主机名并处理多IP故障转移。 |
| **拦截代理** | **需要** | 如上所述，浏览器的重试机制被劫持，责任转移到代理。 |
| **反向代理** | **通常不需要** | 反向代理的目标是固定的后端服务器（往往通过负载均衡器或域名配置），一般已经保证了高可用。但如果后端域名解析出多IP，反向代理也应做好重试，但不是因为浏览器的原因，而是自身的高可用需求。 |

### 一句话总结

**拦截代理让浏览器“误以为”连接已成功，从而放弃了多IP故障转移。代理必须自己承担起解析主机名、尝试多个IP的责任，否则当真实服务器的某个IP宕机时，用户就会遇到访问失败。**

当请求链中某个环节出现问题时，我们需要一种方法**追踪消息的完整路径**，就像用`traceroute`追踪IP包经过的路由器一样。HTTP提供了两个关键工具：**Via头部**和**TRACE方法**。

### 1. Via 头部：记录每一跳的“签证”

每个代理在转发请求时，必须在`Via`头部末尾追加自己的信息（协议版本、主机名、可选注释）。当响应返回时，每个代理同样会添加自己的`Via`条目。

**请求发往服务器时的 Via 头部示例：**
```
Via: 1.1 proxy-62.irenes-isp.net, 1.0 cache.joes-hardware.com
```
- 第一跳（离客户端最近）：代理 `proxy-62.irenes-isp.net` 使用 HTTP/1.1
- 第二跳：代理 `cache.joes-hardware.com` 使用 HTTP/1.0

**响应返回客户端时的 Via 头部：**
顺序会反转，从源服务器侧代理开始，最后是离客户端最近的代理。

**用途：**
- 诊断消息是否被某个代理错误修改
- 检测环路（如果自己的标识出现在`Via`中，说明存在循环转发）
- 了解沿途代理的协议能力（版本号）

### 2. TRACE 方法：发送一个“回声”请求

`TRACE`方法让最终服务器将收到的请求原封不动地返回（放在响应体中）。客户端可以对比自己发出的请求和服务器收到的请求，从而发现中间代理做了哪些修改（添加、删除、更改了哪些头部）。

**典型用法：**
```
TRACE /path HTTP/1.1
Host: www.example.com
Max-Forwards: 2
```
- `Max-Forwards` 限制经过的代理数量，每经过一跳减1，当值为0时，当前代理不再转发，直接返回`TRACE`响应。
- 这允许你观察请求在代理链中特定位置的形态。

### 3. 为什么需要这些机制？

- **多厂商异构环境**：不同代理可能实现不同的功能，甚至存在bug，影响请求的正确处理。
- **内容复制与CDN**：全局分布的代理缓存（如CloudFront、Akamai）可能改变请求/响应的路径，需要验证。
- **安全与合规**：某些代理可能注入广告、修改头部或删除隐私信息，追踪可检测这些行为。

### 实际使用建议

- 作为普通用户/开发者，你可以使用`curl -X TRACE`或类似的工具，观察响应中的`Via`和返回的请求体。
- 许多网络和CDN服务商默认不启用`TRACE`（出于安全原因，可能泄露内部信息），但在内网或测试环境中非常有用。
- 如果你运维代理服务，务必正确添加`Via`头部，这对错误排查是极大的帮助。

### 一句话总结

**当HTTP请求穿越多个代理时，`Via`头部分段记录经过的每一个代理，`TRACE`方法则能直接观察请求是否被篡改。两者是代理网络诊断的“瑞士军刀”。**

### Via 头的内部结构

每个 `Via` 头部包含一个或多个路径点（waypoint），用逗号分隔。每个路径点描述了一跳（hop）的信息。

**示例**：
```
Via: 1.1 cache.joes-hardware.com, 1.1 proxy.irenes-isp.net
```

### 路径点的四个组成部分

每个路径点的完整结构如下（方括号表示可选）：

```
waypoint = received-protocol received-by [ comment ]
```

#### 1. received-protocol（接收到的协议）
- 格式：`[ protocol-name "/" ] protocol-version`
- 例如：`HTTP/1.1`、`HTTPS/1.1`、`FTP/1.0`（若协议名省略，默认为 `HTTP`）
- 作用：记录该代理**收到**上一个节点发送的消息时所使用的协议及版本。

#### 2. received-by（接收者标识）
- 格式：`host [ ":" port ]` 或 `pseudonym`
- 例如：`cache.joes-hardware.com`、`proxy.irenes-isp.net:8080`
- 作用：标识该代理的主机名（或别名）及其端口（若未指定，默认使用该协议的默认端口）
- 隐私考虑：如果组织不希望暴露内部主机名，可以用假名（如 `hidden-proxy`）代替真实域名。

#### 3. comment（注释，可选）
- 格式：任意字符串，通常用括号包围
- 例如：`(Apache/2.4.29)`
- 作用：可包含代理软件的品牌、版本、附加诊断信息。不是标准化字段，但很常用。

### 一个完整的例子分解

假设响应头中有：
```
Via: HTTP/1.1 cache.example.com:3128 (Squid/4.13), 1.1 10.0.0.1 (internal-proxy)
```

- 第一跳：
  - `received-protocol = HTTP/1.1`
  - `received-by = cache.example.com:3128`
  - `comment = (Squid/4.13)`
- 第二跳：
  - `received-protocol = 1.1`（省略协议名，默认 HTTP）
  - `received-by = 10.0.0.1`
  - `comment = (internal-proxy)`

### 重要注意事项

1. **协议名大小写不敏感**：`http/1.1` 与 `HTTP/1.1` 等效。
2. **版本号独立于 HTTP 版本**：`1.1` 表示该代理与上一个节点通信时使用的是 HTTP/1.1。
3. **假名 vs 真实主机名**：防火墙或隐私保护要求下，可用假名代替真实主机名，但仍应保留 `received-by` 字段以记录拓扑。
4. **多个路径点顺序**：离客户端最近的代理会将自己的路径点**追加在已有 Via 列表的最左侧**（即第一跳在最左边）？**需要确认顺序**：
   - 根据 HTTP 规范，请求从客户端发出，每经过一个代理，该代理将自己的信息**追加**到 `Via` 头部的末尾（即最右边）。
   - 因此，最左边的路径点是离服务器最远（离客户端最近）的代理，最右边的是离服务器最近（最后一跳）的代理。
   - 响应消息的 `Via` 头部是请求 `Via` 的逆序，这样能保持路径的对称性。

### 实际使用建议

- **实现代理时**：务必在转发消息前正确解析和追加 `Via` 头，不要删除已有的路径点（除非涉及安全过滤）。
- **调试网络问题**：查看 `Via` 头可以快速定位是哪个代理引入了问题（比如添加了错误的缓存控制头）。
- **安全考虑**：如果代理位于安全边界，可以用假名或压缩多个路径点为单个条目，避免暴露内部拓扑。

### 1. 请求与响应：Via 的逆序对称

由于请求和响应通常通过同一个 TCP 连接传输，响应是沿请求路径的相反方向返回的。假设请求依次经过代理 **A → B → C** 到达源服务器，那么响应会依次经过 **C → B → A** 回到客户端。

因此，响应消息中的 `Via` 头几乎是请求 `Via` 头的**逆序列表**。

**示例**：
- 请求的 `Via`：`Via: 1.1 A, 1.1 B, 1.0 C`
- 响应的 `Via`（假设每个代理都添加了自己的条目）：`Via: 1.0 C, 1.1 B, 1.1 A`

这种对称性让两端都能了解完整的代理路径，方便诊断。

### 2. 网关与非 HTTP 协议：received-protocol 的作用

当代理具有网关功能，需要与使用非 HTTP 协议的后端服务器通信时，`Via` 头必须记录**实际接收到的协议**，而不仅仅是 HTTP。

书中给出的例子是：HTTP 客户端请求 `ftp://...`，经过一个 HTTP/FTP 网关。该网关与 FTP 服务器通信，收到的是 FTP 协议响应。网关生成响应给客户端时，在 `Via` 头中写明：

```
Via: FTP/1.0 proxy.irenes-isp.net (Traffic-Server/5.0.1-17882 [cMs f ])
```

- **received-protocol** = `FTP/1.0`（协议名 `FTP`，版本 `1.0`）
- **received-by** = `proxy.irenes-isp.net`
- **comment** = `(Traffic-Server/5.0.1-17882 [cMs f ])` —— 包含代理软件名称、版本及厂商诊断信息

这样，后续的 HTTP 应用就能知道：在这条路径上，曾发生过协议转换（HTTP → FTP），从而正确理解整个链路的实际能力。

### 3. 实际意义

- **诊断多协议网关**：如果请求经过一个 HTTP/HTTPS 网关，`Via` 中会显示 `HTTPS/1.1` 之类的协议名，帮助你识别加密端点。
- **理解性能瓶颈**：不同协议的处理开销不同，记录了协议信息后，可以更准确地分析延迟来自何处。
- **实现注意事项**：如果你开发网关，务必正确填写 `received-protocol`；如果你实现通用代理，则要能解析包含非 HTTP 协议的 `Via` 头，且不能剔除这些条目。

### 一句话总结

**`Via` 头在请求和响应中呈逆序对称；当网关转换协议时，必须在 `received-protocol` 中明确标出实际使用的协议（如 FTP、HTTPS），以便下游应用了解整个代理链的能力与转换。**

### 1. Server 头 vs. Via 头：各司其职

- **`Server` 响应头**：描述**源服务器**的软件信息（如 Apache、IIS）。它代表内容的最终提供者。
- **`Via` 请求/响应头**：记录**沿途代理**的信息，每个代理追加一条。

**关键规则**：代理在转发响应时，**绝对不能修改或删除原始的 `Server` 头**，因为那是源服务器的身份标识。代理只能通过添加自己的 `Via` 条目来表明自己参与了传输。

### 2. Via 头的隐私与安全：隐藏内部拓扑

当代理位于防火墙或安全边界内时，直接在 `Via` 中暴露内部主机名和端口会泄露网络架构信息，给攻击者提供线索。因此：

#### 基本做法：使用假名（Pseudonym）
- 不转发真实主机名，而是替换为一个代号（如 `proxy-internal`、`fw-01`）。
- 仍然保留一个 `Via` 条目（即使内容模糊），以保证路径的完整性，同时隐藏细节。

#### 高级做法：合并连续的内部条目
对于有严格隐私要求的组织，可以将**多个连续的、同一协议版本**的内部代理条目合并为一个模糊条目。

**原始**：
```
Via: 1.0 foo, 1.1 devirus.company.com, 1.1 access-logger.company.com
```
**合并后**：
```
Via: 1.0 foo, 1.1 concealed-stuff
```

**合并条件**：
- 所有被合并的条目必须属于**同一组织控制**下。
- 它们的 `received-protocol` 值必须完全相同（例如都是 `1.1`，不能混合 `1.0` 和 `1.1`）。
- 主机名已经替换为假名（不能混合真实主机名和假名）。

**禁止合并的情况**：
- 不同协议版本的条目（如 `1.0` 和 `1.1`）不能合并。
- 跨组织边界的条目不能合并。

### 实际意义

- **安全合规**：许多企业的安全策略要求不向外网暴露内部域名或IP，`Via` 的假名/合并机制正好满足这一需求。
- **故障排查的权衡**：合并会丢失拓扑细节，使得诊断问题更困难。因此仅在隐私要求极高时才使用合并，一般场景下用假名即可。
- **实现注意**：代理软件应提供配置选项，允许管理员选择是否启用假名、是否合并条目。

### 一句话总结

**代理不能修改源服务器的 `Server` 头，只能通过 `Via` 记录自己；为保护内部网络拓扑，`Via` 中的主机名可用假名代替，甚至可将多个连续的内部条目合并为一个模糊条目，但合并时需满足协议版本相同、组织控制一致等条件。**

### 1. TRACE 方法：让服务器“回声”收到的请求

当客户端发送一个 `TRACE` 请求时，沿途的每个代理都会原样转发，直到请求到达源服务器。源服务器不会像处理 `GET` 那样返回资源，而是将**收到的整个请求消息（包括请求行、各个头部）原封不动地封装在响应体中**，再返回给客户端。

**典型响应特征**：
- 状态码：`200 OK`
- `Content-Type: message/http`（表示响应体包含一个完整的 HTTP 消息）
- 响应体：就是源服务器收到的请求原文

**用途**：
- 观察请求在穿越代理链后是否被修改（例如是否被添加了 `X-Forwarded-For`、是否某些头部被删除）。
- 检查代理链的拓扑结构（通过响应中的 `Via` 头）。
- 定位某个代理引入的故障。

### 2. Max-Forwards 头：控制“回声”的距离

默认情况下，`TRACE` 请求会一直走到源服务器。但有时我们只想测试到代理链中的某一跳就停止，这可以通过 `Max-Forwards` 头实现。

- 语法：`Max-Forwards: n`，其中 `n` 是一个非负整数。
- 每经过一个代理，该代理将 `Max-Forwards` 值减 1，然后转发。
- 当某个代理收到 `Max-Forwards: 0` 的请求时，它**不再继续转发**，而是直接充当“终点”，生成 `TRACE` 响应，将当前收到的请求回送给客户端。
- 这个机制可以用于：
  - 检测代理环路：如果配置了环路检测，某个代理看到自己的标识重复出现且 `Max-Forwards` 还没减到 0，可以报错。
  - 分段诊断：先发 `Max-Forwards: 1` 观察第一跳代理的修改，再发 `Max-Forwards: 2` 观察第二跳，依次深入。

### 3. 实际应用注意

- **安全风险**：`TRACE` 响应会返回请求头，可能泄露认证信息（如 `Authorization` 头）或内部网络细节。因此许多生产环境会禁用 `TRACE` 方法（例如返回 `405 Method Not Allowed`）。
- **与 OPTIONS 的关联**：`Max-Forwards` 同样可用于 `OPTIONS` 请求，限制其转发的跳数。
- **代理实现要求**：所有符合 HTTP/1.1 的代理都**必须**支持 `Max-Forwards` 处理，并在转发时递减该值；当值为 0 时，必须生成 `TRACE` 响应而非继续转发。

### 4. 一个简单的诊断示例

**客户端发送**：
```
TRACE /path HTTP/1.1
Host: www.example.com
Max-Forwards: 2
User-Agent: curl/7.68.0
```

如果经过两个代理后 `Max-Forwards` 变为 0，第二个代理将返回类似下面的响应：
```
HTTP/1.1 200 OK
Content-Type: message/http
Via: 1.1 proxy1.company.com, 1.0 proxy2.internal

TRACE /path HTTP/1.1
Host: www.example.com
Max-Forwards: 0
User-Agent: curl/7.68.0
X-Forwarded-For: 192.168.1.100
```

客户端就能看到：在第二跳时，请求中多了 `X-Forwarded-For` 头，且 `Host` 头没变，等等。

### 一句话总结

**`TRACE` 方法让源服务器原样返回收到的请求，结合 `Max-Forwards` 可控制反射点，是诊断代理链修改和环路的有效工具，但生产环境中需谨慎启用以避免信息泄露。**

### 1. 代理认证：控制访问的“门禁”

HTTP 为代理服务器定义了一套独立的认证机制，用于控制客户端对代理资源的访问，与源服务器的认证（401 + `WWW-Authenticate`）类似，但使用不同的状态码和头部：

- **`407 Proxy Authentication Required`**：代理要求客户端提供身份凭证。
- **`Proxy-Authenticate`**：代理发送给客户端，描述认证方式和域（realm）。
- **`Proxy-Authorization`**：客户端发送给代理，携带用户名和密码等凭证。

**工作流程**：
1. 客户端请求受限资源 → 代理返回 `407` + `Proxy-Authenticate`。
2. 客户端收集凭证（弹出对话框或从本地读取）→ 重试请求，添加 `Proxy-Authorization` 头。
3. 代理验证凭证 → 有效则转发请求到下一跳，无效则再次返回 `407`。

**现实局限**：当代理链中存在多个需要认证的代理时，该机制效果不佳。HTTP 标准曾提议将认证凭证与特定路径点关联，但该增强特性**未被广泛实现**。实际部署中，通常只在代理链的入口处进行一次认证。

### 2. 代理互操作：不认识的头部和方法怎么办

由于客户端、代理、服务器可能由不同厂商开发、版本各异，代理必须具备一定的**容错和转发能力**：

- **不认识的头部字段**：必须原样转发，且保持同名字段的相对顺序不变。代理不应因不认识某个扩展头部而丢弃它。
- **不认识的方法**：应尽可能尝试转发到下一跳，而不是直接拒绝。例如，某些应用（如早期 Hotmail 通过 Outlook 访问）会使用 HTTP 扩展方法，不支持隧道这些方法的代理在现代网络中会难以生存。

这呼应了前面提到的“代理不应充当协议警察”的原则——**宽容转发，而非严格拦截**。

### 3. OPTIONS 方法：发现服务器能力

`OPTIONS` 方法允许客户端（或代理）在发起实际请求前，先探测服务器的功能支持情况，从而提高互操作性。

**两种用法**：
- `OPTIONS * HTTP/1.1` —— 查询整个服务器的能力。
- `OPTIONS http://www.example.com/index.html HTTP/1.1` —— 查询特定资源的能力。

**成功响应**：
- 状态码 `200 OK`
- 必须包含 `Allow` 响应头，列出该资源或服务器支持的 HTTP 方法（如 `GET, HEAD, PUT, POST, OPTIONS, TRACE`）。
- 响应体可选（未在标准中定义具体格式）。

**代理的行为约束**：代理**不能修改** `Allow` 头，即使代理自身不支持列表中的某些方法。因为客户端可能有其他路径与源服务器直接通信，代理不应擅自删减源服务器声明的能力。

### 4. Allow 头的双重角色

- **响应头**：声明资源实际支持的方法（由源服务器填写）。
- **请求头**：客户端可以向服务器**建议**资源应支持的方法，但服务器没有义务采纳，最终仍以响应中的 `Allow` 为准。

### 一句话总结

**代理可通过 `407` 挑战进行访问控制（但多级链支持不佳）；转发时对不认识的头部和方法应持宽容态度；客户端可用 `OPTIONS` 方法提前了解服务器能力，代理不得篡改返回的 `Allow` 头。**
