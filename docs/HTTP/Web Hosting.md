## 一、什么是 Web 托管？

- **定义**：存储、代理和管理 Web 内容的综合任务  
- **核心角色**：Web 服务器需要托管内容，提供访问、日志记录和管理功能  
- **托管服务（Hoster）**：为不愿自己管理硬件/软件的组织提供托管服务，按需租用服务器资源，通常包括安全、报表、易用性等  
- **托管商的典型做法**：将多个网站集中部署在强大的服务器上，以降低成本、提高可靠性和性能

---

## 二、本章三个核心主题（书中第 18 章目录）

| 主题 | 简要说明 |
|------|----------|
| **虚拟托管（Virtual Hosting）** | 多域名共享同一台物理服务器，通过 Host 头区分，解决 HTTP/1.0 缺少主机信息的问题 |
| **提高可靠性** | 使用镜像服务器、服务器集群、内容分发网络（CDN）等方式，避免单点故障，应对流量峰值 |
| **加速访问** | 通过代理缓存、负载均衡、内容压缩、边缘服务器等手段减少延迟 |

---

## 三、虚拟托管的核心问题与解决方案

### 问题背景（HTTP/1.0 的缺陷）
- HTTP/1.0 请求中只发送 URI 路径（如 `GET /index.html`），不包含主机名  
- 多个网站共享一个 IP 时，服务器无法区分请求属于哪个站点

### 解决方案（书中详细介绍）
1. **Host 头（HTTP/1.1 必须）**：客户端在请求中携带 `Host: www.example.com`，服务器据此区分虚拟站点  
2. **基于 IP 的虚拟托管**：每个虚拟站点分配独立 IP（但 IP 资源稀缺）  
3. **基于端口的虚拟托管**：不同站点用不同端口（如 81、82），但不友好  
4. **URL 路径虚拟托管**：在路径中加入站点标识（如 `/siteA/index.html`），体验差

> 现代 Web 服务器（Apache、Nginx、IIS）普遍支持 **基于域名的虚拟托管**（Name-Based Virtual Hosting），依赖 Host 头。

---

## 四、提高网站可靠性

- **镜像服务器（Mirroring）**：主服务器内容复制到多台从服务器，通过 DNS 轮询或负载均衡分配请求  
- **服务器集群（Server Farm）**：多台服务器组成集群，通过前端负载均衡器分发请求  
- **内容分发网络（CDN）**：将内容缓存到全球边缘节点，既提高可靠性又加速访问  
- **故障转移**：监测服务器健康状态，自动将流量切换到健康节点

---

## 五、加速网站访问

- **反向代理缓存**：如 Varnish、Nginx 缓存，减少后端服务器压力  
- **负载均衡**：分发请求到多个后端，避免单点过载  
- **内容压缩**：使用 gzip/Brotli 压缩文本资源，减少传输大小  
- **边缘计算**：CDN 边缘节点缓存热门内容，缩短用户距离  
- **HTTP/2 与 HTTP/3**：多路复用、服务器推送等特性提升性能

---

## 六、总结

Web 托管不仅仅是“把文件放上服务器”，而是涉及 **资源隔离（虚拟托管）**、**高可用架构** 和 **性能优化** 的综合工程。HTTP 协议本身（尤其是 `Host` 头、缓存控制头、负载均衡相关扩展）在这些领域扮演了关键角色。

## 一、Web 托管服务的演进

| 阶段 | 特点 | 挑战 |
|------|------|------|
| **早期（自建）** | 组织自己购买硬件、建设机房、申请网络带宽、管理服务器软件 | 成本高、技术门槛高、维护复杂 |
| **托管服务兴起** | 专业公司提供机房空间、电力、网络、服务器硬件及管理服务 | 客户只需提供内容，按需付费 |

托管服务商提供的服务层次从基础的**物理设施管理**（机柜、空调、布线）到**全托管**（客户只提供内容，其余全由服务商负责）。

## 二、专用托管（Dedicated Hosting）示例

### 场景
- Joe's Hardware 和 Mary's Antiques 都需要高流量网站  
- Irene's ISP 拥有大量相同配置的高性能服务器，可以租赁给客户

### 工作方式（书中图 18-1）
- Joe 和 Mary 分别租用 **不同的物理服务器**，彼此隔离  
- 浏览器请求 `www.joes-hardware.com` 解析到 Joe 的服务器 IP  
- 浏览器请求 `www.marys-antiques.com` 解析到 Mary 的服务器 IP

### 优点
- **成本效益**：托管商批量采购硬件，降低成本  
- **专业维护**：托管商负责硬件更换、操作系统补丁、网络连通性  
- **弹性扩展**：客户业务增长时，可快速增加服务器（如再租一台）  
- **可靠性**：托管商通常选用经过验证的硬件，并提供冗余电源、网络等

### 与共享托管的区别
- 专用托管：一台服务器只服务一个客户（或多个网站但全归同一客户）  
- 共享托管（虚拟托管）：一台服务器服务多个客户的多个网站，通过 Host 头区分

## 三、托管服务对 HTTP 的影响

- **请求路由**：专用托管下，每个客户有独立 IP，无需 `Host` 头即可区分  
- **性能隔离**：一个客户的流量不会影响其他客户（专用硬件）  
- **SSL/TLS**：每个客户可拥有自己的 IP 和证书，无需 SNI 扩展（因为 IP 独立）  
- **可扩展性**：托管商可提供负载均衡、CDN 等增值服务

---

## 一、什么是虚拟托管（共享托管）？

- **背景**：许多小网站流量低，单独租用一台物理服务器（专用托管）成本太高  
- **解决方案**：多客户的多个网站共享同一台物理服务器，每个网站逻辑上独立，用户无感知  
- **术语**：虚拟托管 = 共享托管  
- **规模**：一台服务器可托管成百上千个网站；大型托管商还会使用 **服务器农场（server farm）** 克隆多台服务器分摊负载

---

## 二、HTTP/1.0 的设计缺陷

- HTTP/1.0 请求只发送 **路径**（如 `GET /index.html`），不包含主机名  
- 虚拟托管服务器收到多个域名的请求（如 `joes-hardware.com` 和 `marys-antiques.com` 都请求 `/index.html`），无法区分  
- 图 18-3 清楚地说明了这个问题：两个请求内容完全相同

---

## 三、四种虚拟托管解决方案（书中按优劣排序）

| 方法 | 原理 | 缺点 | 使用情况 |
|------|------|------|----------|
| **URL 路径** | 在路径中加入站点标识（如 `/joe/index.html`） | 用户体验差，URL 丑陋，无法使用标准首页 | 很少使用 |
| **端口号** | 不同站点使用不同端口（如 80、81、82） | 用户需在 URL 中显式输入端口号（如 `http://example.com:81`） | 很少使用 |
| **IP 地址（虚拟 IP）** | 每个虚拟站点分配独立 IP，服务器根据目标 IP 区分 | IP 地址稀缺，操作系统有虚拟 IP 数量限制；扩展时需更多 IP | 常用（尤其在 SSL 时代） |
| **Host 头（HTTP/1.1）** | 客户端在请求中添加 `Host: www.example.com` 头，服务器据此区分 | 需要客户端支持（现代浏览器都支持） | **标准方案，最推荐** |

---

## 四、各方案详细说明

### 1. URL 路径法
- 示例：`http://www.joes-hardware.com/joe/index.html`  
- 问题：路径中的 `/joe` 冗余且混乱；用户习惯只输入域名就访问首页，无法工作

### 2. 端口法
- 示例：`http://www.joes-hardware.com:82/index.html`  
- 问题：用户需记住端口号，体验极差

### 3. 虚拟 IP 法
- 每个站点有独立 IP，服务器绑定多个 IP  
- 收到请求时，检查 TCP 连接的目标 IP 地址，映射到对应站点  
- 缺点：IP 地址消耗大；操作系统限制虚拟 IP 数量（如 Linux 可配数百个，但上千个可能性能下降）  
- 仍广泛使用，尤其当需要 SSL 证书且不支持 SNI 时（每个证书需独立 IP）

### 4. Host 头法（最终标准）
- HTTP/1.0+ 扩展引入，HTTP/1.1 强制要求  
- 客户端在每个请求中包含 `Host: www.joes-hardware.com`  
- 服务器根据 Host 头选择虚拟站点  
- 优点：一个 IP 可托管无数站点，节省 IP 资源  
- 图 18-5 展示了 Host 头如何区分请求

---

## 五、Host 头的关键点

- **语法**：`Host = "Host" ":" host [ ":" port ]`  
- **必选**：HTTP/1.1 要求所有请求必须包含 Host 头  
- **代理**：即使使用代理，Host 头也必须填写**源服务器**的主机名，而非代理  
- **缺失处理**：HTTP/1.1 服务器收到无 Host 头的请求应返回 `400 Bad Request`

---

## 六、现代实践与遗留问题

- 几乎所有现代浏览器和服务器都支持 Host 头，因此 **基于域名的虚拟托管（Name-Based Virtual Hosting）** 是主流  
- 但在 **HTTPS** 场景中，TLS 握手发生在 HTTP 请求之前，服务器不知道 Host 头，因此需要 **SNI（Server Name Indication）** 扩展，或在 SSL 时代使用独立 IP（虚拟 IP 法）  
- 书中提到的“虚拟 IP 法的缺点”（IP 稀缺、数量限制）在 SNI 普及后已缓解

---

## 七、总结表

| 方法 | 需要客户端支持 | 用户体验 | IP 消耗 | 是否标准 |
|------|---------------|----------|---------|----------|
| URL 路径 | 无 | 差 | 无 | 非标准 |
| 端口号 | 无 | 很差 | 无 | 非标准 |
| 虚拟 IP | 无 | 好 | 高 | 可用但不佳 |
| **Host 头** | HTTP/1.1+ | 极好 | 无 | **标准** |

---

## 一、Host 头的语法与基本规则

```
Host = "Host" ":" host [ ":" port ]
```

- **必须包含**：HTTP/1.1 要求所有请求消息必须携带 `Host` 头  
- **端口可选**：不指定端口时，默认使用请求方案的默认端口（HTTP 为 80，HTTPS 为 443）  
- **内容来源**：从请求 URL 中提取的主机名和端口

### 重要约定（书中列举）
| 情况 | 要求 |
|------|------|
| URL 中包含 IP 地址 | `Host` 头应使用相同的 IP 地址 |
| URL 中包含主机名 | `Host` 头必须使用该主机名（不能用 IP 地址替代） |
| 使用代理 | `Host` 头必须填写 **源服务器（origin server）** 的主机名和端口，而不是代理服务器 |
| 不使用代理且 URL 为绝对路径 | `Host` 头用于确定目标主机 |

> 为什么不能用 IP 地址替代主机名？因为虚拟托管服务器可能在同一 IP 上托管多个域名，若 `Host` 头使用 IP 地址，服务器无法区分是哪个虚拟站点。

---

## 二、缺失 Host 头的处理

- **老式浏览器**：少数老浏览器不发送 `Host` 头  
- **服务器行为**：虚拟主机服务器通常会将没有 `Host` 头的请求导向一个**默认站点**（如托管商的主页）或返回错误页面，提示用户升级浏览器  
- **HTTP/1.1 强制要求**：服务器**必须**对缺少 `Host` 头的 HTTP/1.1 请求返回 `400 Bad Request`

---

## 三、服务器解释 Host 头的优先级（书中规则）

1. 如果请求行中的 URL 是 **绝对 URL**（包含 scheme 和 host），则忽略 `Host` 头，直接使用 URL 中的主机信息  
2. 如果请求行中的 URL 是 **相对路径**（无主机信息），则使用 `Host` 头的值  
3. 如果以上都无法确定有效主机，返回 `400 Bad Request`

> 这条规则确保了与旧版本 HTTP 的兼容性，同时支持虚拟托管。

---

## 四、Host 头与代理的常见错误

- **错误场景**：某些旧版本浏览器配置了代理后，错误地将代理服务器的主机名填入 `Host` 头，而不是目标源服务器  
- **后果**：源服务器收到错误的 `Host` 头，可能导致无法正确识别虚拟站点，或代理自身处理异常  
- **解决方案**：现代浏览器已修复此问题；代理服务器也应在转发前检查并修正（若可能）

---

## 五、示例（书中给出）

```
GET http://www.joes-hardware.com/index.html HTTP/1.0
Host: www.joes-hardware.com
```

注意：即使请求行使用了绝对 URL（`http://...`），`Host` 头仍然应该存在，以便不支持绝对 URL 的旧代理或服务器能正确处理。

---

## 六、总结表

| 方面 | 规则 |
|------|------|
| 必须性 | HTTP/1.1 客户端必须在所有请求中包含 `Host` 头 |
| 内容 | 源服务器的主机名和端口（从 URL 提取） |
| 代理时 | 填写源服务器，而非代理 |
| 缺失响应 | HTTP/1.1 服务器返回 `400 Bad Request` |
| 解释优先级 | 绝对 URL > Host 头 > 400 |

## 一、网站常见的故障原因

- **服务器宕机**：硬件故障、系统崩溃、软件错误  
- **流量峰值**：突发新闻、促销活动导致瞬间请求激增，服务器过载  
- **网络中断**：ISP 故障、骨干网问题、路由错误

---

## 二、镜像服务器农场（Mirrored Server Farms）

### 基本架构（图 18-6）
- 一组 **配置相同的服务器**（服务器农场）  
- 内容在所有服务器之间 **镜像**（完全相同）  
- 前端使用 **交换机**（或负载均衡器）将请求分发给各服务器  
- 对外只暴露一个 IP 地址（交换机的 IP）

### 主从关系（图 18-7）
- **主源服务器（Master Origin Server）**：内容创作的源头，负责将内容推送到副本服务器  
- **副本源服务器（Replica Origin Server）**：接收主服务器同步的内容，实际处理客户端请求  
- 示例：芝加哥主服务器，纽约、迈阿密、小石城副本服务器

### 客户端请求路由到特定服务器的两种方式（书中第 20 章详述）
| 方法 | 原理 | 特点 |
|------|------|------|
| **HTTP 重定向** | 主服务器收到请求后，返回 `302` 或 `307` 并附带副本服务器的 URL | 增加一次额外往返，但可做精细负载均衡 |
| **DNS 重定向** | DNS 解析时返回多个 IP 地址（轮询），或根据客户端地理位置返回最近副本的 IP | 减少客户端延迟，但 DNS 缓存可能导致不均衡 |

---

## 三、内容分发网络（CDN）

CDN 是专门用于内容分发的网络，节点可以是 Web 服务器、**反向代理（Surrogate）** 或 **代理缓存（Proxy Cache）**。

### 1. 反向代理缓存（Surrogate Caches）
- 也称为 **反向代理** 或 **服务器加速器**  
- 部署在源服务器前方，代表源服务器接收请求  
- **与镜像服务器的区别**：  
  - 镜像服务器存储完整的、预先同步的内容  
  - 反向代理是 **需求驱动（demand-driven）** 的：只缓存被请求过的内容，不主动同步全部数据  
- 支持 **预取（prefetching）**：提前将热门内容拉入缓存，减少首次访问延迟  
- 可形成 **缓存层次结构**（父缓存、子缓存）

### 2. 代理缓存（Proxy Caches）在 CDN 中的应用
- 与反向代理不同，传统代理缓存可以接收 **指向任意源服务器** 的请求（无需预先建立信任关系）  
- 也是 **需求驱动**，可预加载热门内容  
- 支持 **拦截配置（Interception Configuration）**：二层/三层设备（交换机/路由器）将 HTTP 流量透明地重定向到代理缓存（图 18-8）  
- 拦截配置要求网络设备能将所有相关 HTTP 请求物理导向缓存（详见第 20 章）

---

## 四、提高可靠性的关键技术总结

| 技术 | 作用 | 关键组件 |
|------|------|----------|
| 镜像服务器农场 | 消除单点故障，分散负载 | 主服务器、副本服务器、交换机 |
| HTTP 重定向 | 将客户端引导到合适的副本 | 状态码 302/307、Location 头 |
| DNS 重定向 | 基于地理位置或负载选择 IP | DNS 服务器、多 A 记录 |
| CDN（反向代理） | 边缘缓存，减少源服务器压力 | 反向代理、预取、缓存层次 |
| 代理缓存拦截 | 透明缓存，无需客户端配置 | 交换机/路由器、代理缓存 |

---

## 五、总结

- **镜像服务器农场** 通过内容复制和请求分发，提高了容错能力和扩展性  
- **CDN** 通过边缘缓存和需求驱动的内容分发，既提高了可靠性又降低了延迟  
- 两种技术常结合使用：大型网站通常会在自己的数据中心部署镜像集群，同时接入第三方 CDN（如 Cloudflare、Akamai）作为外层缓存
