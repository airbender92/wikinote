---

## 一、为什么需要重定向？

- **可靠性**：避免单点故障，将请求分散到多个服务器  
- **降低延迟**：让客户端访问离自己最近的资源  
- **节省带宽**：避免拥塞，充分利用网络资源  
- **负载均衡**：自动将负载分布到多个后端服务器或代理

重定向与负载均衡相辅相成：任何负载均衡方案都涉及重定向，反之亦然。

---

## 二、重定向发生的层级

| 层级 | 控制点 | 示例 |
|------|--------|------|
| 客户端 | 浏览器配置 | 手动代理配置、PAC、WPAD |
| DNS | 域名解析 | 轮询、地理位置路由、负载感知 |
| 网络层 | 路由器/交换机 | IP MAC 转发、IP 地址转发、Anycast |
| 应用层 | Web 服务器 | HTTP 重定向（3xx 状态码） |
| 代理/缓存层 | 代理协议 | ICP、HTCP、CARP、WCCP |

---

## 三、通用重定向方法（表 20-1）

| 方法 | 工作原理 | 优点 | 缺点/限制 |
|------|----------|------|-----------|
| **HTTP 重定向** | 服务器返回 3xx 及 Location 头，客户端重试 | 灵活，可基于客户端 IP 做精细决策 | 额外一次往返，首台服务器可能成为瓶颈 |
| **DNS 重定向** | DNS 服务器返回多个 IP，轮询或基于策略选择 | 简单，无客户端改动 | DNS 缓存导致不均衡；无法感知客户端真实距离（只能看到 Local DNS） |
| **Anycast 路由** | 多台服务器共享同一 IP，路由器自动选择最近的一台 | 网络层自动优化 | 路由变化可能导致 TCP 连接中断；需要网络设备支持 |
| **IP MAC 转发** | 交换机根据 MAC 地址重定向到下一跳服务器 | 速度快，二层转发 | 服务器必须与交换机直连（单跳） |
| **IP 地址转发（NAT）** | 四层交换机修改目标 IP 地址，转发到后端服务器 | 可跨路由器 | 可能丢失客户端 IP 地址（除非使用 X-Forwarded-For 等） |

## 四、代理/缓存专用重定向方法（表 20-2）

| 方法 | 工作原理 | 优点 | 缺点/限制 |
|------|----------|------|-----------|
| **显式浏览器配置** | 用户或服务商手动配置浏览器代理地址 | 简单直接 | 改动麻烦，不适合动态网络 |
| **PAC（Proxy Auto-Config）** | 浏览器从配置服务器获取 JavaScript PAC 文件，决定每个 URL 使用的代理 | 灵活，可编程 | 仍需配置 PAC 文件 URL |
| **WPAD（Web Proxy Autodiscovery Protocol）** | 浏览器通过 DHCP/DNS 自动发现 PAC 文件 URL | 完全自动，无需用户配置 | 支持有限，有安全风险（早期版本） |
| **WCCP（Web Cache Coordination Protocol）** | 路由器与缓存代理交互，重定向 HTTP 流量到缓存 | 保留客户端 IP，支持多缓存负载均衡 | 需路由器支持 WCCP |
| **ICP（Internet Cache Protocol）** | 缓存之间互相查询是否有某 URL 的副本（UDP 广播/组播） | 简单，支持层次化 | 仅用 URL 查询，可能误判（假命中） |
| **HTCP（Hyper Text Caching Protocol）** | 类似 ICP，但支持完整 HTTP 头部匹配，减少假命中 | 更精确，支持缓存策略控制 | 协议较复杂 |
| **CARP（Cache Array Routing Protocol）** | 使用哈希函数将 URL 映射到特定缓存，内容无重叠 | 无查询开销，确定性路由 | 需所有客户端配置一致，缓存失效需重新哈希 |

## 五、HTTP 重定向详解（书中示例）

- **状态码**：302（临时重定向）、303（See Other）、307（临时重定向）等  
- **流程**：  
  1. 客户端请求 `www.joes-hardware.com/hammers.html`  
  2. 服务器返回 `302` 及 `Location: http://161.58.228.45/hammers.html`  
  3. 客户端自动向新地址发起请求  
- **缺点**：增加一次往返；首台服务器负载可能很重；若首台服务器故障，整个站点不可用

---

## 六、DNS 重定向详解

### DNS 轮询（Round Robin）
- 为同一域名配置多个 A 记录  
- DNS 服务器每次应答时轮换顺序  
- **示例**：`www.cnn.com` 返回 20 多个 IP，每次顺序不同  
- **局限**：无法感知服务器负载；客户端和中间 DNS 缓存可能固定使用第一个 IP，导致不均衡

### 增强型 DNS 重定向
- **负载感知**：DNS 服务器根据后端服务器实时负载调整顺序  
- **临近路由**：根据请求来源的 Local DNS IP 返回最近的数据中心 IP  
- **故障屏蔽**：自动排除不可达或故障的 IP

> 书中指出：权威 DNS 服务器只能看到 Local DNS 的 IP，无法获取真实客户端 IP，可能不是最优。

---

## 七、Anycast 路由

- 多台服务器配置**相同的 IP 地址**  
- 通过 BGP 等路由协议将该 IP 宣告到网络  
- 路由器自动将数据包转发到**最近的**（路由度量最小）的服务器  
- **问题**：路由变更可能导致已建立的 TCP 连接中断（因为后续包可能被路由到不同服务器）

---

## 八、IP MAC 转发与 IP 地址转发（NAT）

- **IP MAC 转发**：在二层交换机上修改目标 MAC 地址，将包重定向到代理或缓存。要求代理与交换机直连。  
- **IP 地址转发（NAT）**：在四层交换机上修改目标 IP 地址，将包重定向到后端服务器。可能丢失客户端源 IP，需通过 `X-Forwarded-For` 等扩展头传递。

---

## 九、总结：如何选择重定向技术？

| 场景 | 推荐技术 |
|------|----------|
| 全球负载均衡，简单实现 | DNS 轮询 |
| 需要基于客户端真实 IP 决策 | HTTP 重定向（首跳服务器） |
| 数据中心内部流量分发 | IP MAC 转发、IP 地址转发（NAT）、四层负载均衡 |
| 透明缓存部署 | WCCP、拦截式 NAT |
| 客户端自动发现代理 | WPAD + PAC |
| 缓存集群协作 | CARP（确定性哈希）、ICP/HTCP（查询式） |

---

## 一、Anycast 寻址的核心原理

- **多台服务器共享同一个 IP 地址**  
- 服务器通过路由协议（如 BGP）向相邻路由器通告自己拥有该 IP  
- 路由器根据 **最短路径优先（SPF）** 原则，将发往该 IP 的数据包转发到 **最近** 的通告者  
- 客户端完全无感知，仍使用标准的 IP 地址

### 书中图 20-5 示例
- 三台服务器（LA、NY、其他地方）都使用 IP `10.10.10.1`  
- 每个服务器向本地路由器宣告该 IP  
- 来自不同地区的客户端请求 `10.10.10.1` 时，路由器自动选择最近的服务器

---

## 二、Anycast 的优点

- **自动就近访问**：无需客户端配置或特殊 DNS 逻辑  
- **负载分散**：流量天然分散到不同地理位置的服务器  
- **高可用性**：某台服务器故障时，路由自动切换到其他健康的服务器

---

## 三、Anycast 的缺点与挑战

| 问题 | 说明 |
|------|------|
| **路由表冲突** | 互联网通常假定一个 IP 对应一台主机，多台服务器宣告同一 IP 可能导致路由泄露或冲突 |
| **TCP 连接中断** | 路由变更（如某服务器下线）可能导致同一 TCP 连接的后缀包被发到不同服务器，连接失效（UDP 无此问题） |
| **需要自治网络** | 通常需要自己拥有 AS 号并能与上游 ISP 协商 BGP 宣告，不适合普通用户 |
| **实验性技术** | 书中（2002 年）认为仍是实验性的；如今（2026 年）已被大规模用于 DNS 根服务器、CDN 边缘节点（如 Cloudflare、Google Public DNS） |

---

## 四、与其它重定向方法的对比

| 方法 | 层级 | 是否改变目标 IP | 优缺点 |
|------|------|----------------|--------|
| Anycast | 网络层（IP 路由） | 不改变，但路由表决定哪台服务器接收 | 自动就近，但有状态协议（TCP）可能断连 |
| IP MAC 转发 | 二层（MAC） | 不改变 IP，只改 MAC | 速度快，但服务器必须在同一广播域（单跳） |
| IP 地址转发（NAT） | 四层（IP 地址转换） | 改变目标 IP（可能也改源 IP） | 可跨路由器，但可能丢失客户端 IP |

---

## 五、IP MAC 转发与 IP 地址转发简述

### IP MAC 转发（图 20-6、20-7）
- 交换机根据 **MAC 地址** 将帧重定向到代理或缓存  
- 要求代理/缓存与交换机 **直连**（单跳）  
- 优点：二层转发速度快  
- 缺点：拓扑限制

### IP 地址转发（NAT，图 20-8、20-9）
- 四层交换机修改数据包的 **目标 IP 地址**（可能也修改源 IP）  
- 可跨路由器，不要求直连  
- 需要解决 **路由对称性**：返回流量必须经过同一交换机  
  - **Full NAT**：同时修改源 IP 为交换机 IP，后端服务器看到的客户端 IP 是交换机地址（丢失真实客户端 IP）  
  - **Half NAT**：只修改目标 IP，需要网络拓扑确保返回流量不绕过交换机（否则连接失效）

---

## 六、NECP（Network Element Control Protocol）

- 允许 **网络元素（NE）**（路由器/交换机）与 **服务器元素（SE）**（Web 服务器/缓存）通信  
- SE 告诉 NE 如何转发流量（MAC 转发、GRE 封装、NAT）  
- 支持 **例外（exception）**：SE 可以指定某些源 IP 不转发给 SE，直接送往源服务器  
- 消息类型：`NECP_INIT`、`NECP_START`、`NECP_EXCEPTION_ADD` 等（表 20-3）

---

## 七、总结

Anycast 是一种网络层重定向技术，适合无状态或能容忍短暂中断的协议（如 UDP、DNS），对于 TCP 存在连接重置风险，但现代 CDN 和 DNS 广泛使用。IP MAC 转发和 IP 地址转发更常用于数据中心内部的流量重定向。NECP 则提供了网络设备与应用服务器之间的控制协议，实现更精细的流量管理。

---

## 一、为什么需要专门的缓存重定向？

- 普通重定向（DNS、HTTP、NAT）只能将请求送到“某一台服务器”，但无法做到 **内容感知（content-aware）**  
- 缓存重定向的目标：将请求发送到 **最有可能已经缓存了该内容** 的代理缓存，从而提高命中率、减少源服务器负载  
- 典型协议：WCCP、ICP、HTCP、CARP（本章后续会介绍）

---

## 二、WCCP 概述

- **开发者**：Cisco Systems  
- **版本**：WCCP2（开放协议，书中以 WCCP2 为准）  
- **作用**：路由器与缓存代理之间的通信协议，实现：
  - 缓存健康检查（心跳）
  - 流量负载均衡
  - 特定流量定向到特定缓存
- **部署方式**：在支持 WCCP 的路由器和缓存代理之间建立 **服务组（Service Group）**

---

## 三、WCCP 重定向工作流程

1. **服务组配置**：一组路由器和缓存代理组成服务组，定义哪些流量需要重定向以及负载均衡策略  
2. **请求到达路由器**：路由器检查 HTTP 请求，根据配置选择一台缓存（基于 IP 哈希 或 掩码/值对）  
3. **转发方式**：将原始 IP 包 **封装（GRE）** 或 **二层 MAC 转发** 到所选缓存  
4. **缓存处理**：若缓存命中则直接响应，若未命中则解封装后将请求回送给路由器（路由器再转发到源服务器）  
5. **心跳与故障检测**：缓存定期发送 `HERE_I_AM` 消息，路由器回复 `I_SEE_YOU`；若缓存停止心跳，路由器将其从服务组移除，流量直通 Internet

---

## 四、WCCP2 消息类型（表 20-4）

| 消息 | 发送方 | 作用 |
|------|--------|------|
| `HERE_I_AM` | 缓存 → 路由器 | 通告自身存在，携带服务组信息 |
| `I_SEE_YOU` | 路由器 → 缓存 | 确认 `HERE_I_AM`，协商转发方式和安全 |
| `REDIRECT_ASSIGN` | 指定缓存 → 路由器 | 分配负载均衡的哈希桶或掩码/值对 |
| `REMOVAL_QUERY` | 路由器 → 缓存 | 查询沉默缓存是否应被移除（心跳超时 2.5× 间隔） |

---

## 五、消息组件（表 20-5）

每个 WCCP2 消息包含一个头（版本、类型、长度）和多个组件，常见组件包括：

- **Security Info**：认证方式（无或 MD5）  
- **Service Info**：服务类型（标准：HTTP；动态：自定义端口/协议）  
- **Router/Web Cache Identity Info**：设备身份  
- **Assignment Info**：哈希桶分配  
- **Capabilities Info**：支持的转发方法（GRE / MAC 转发等）

---

## 六、GRE 封装（图 20-12）

- 为了保留客户端原始 IP 地址（避免 NAT 丢失），WCCP 路由器将原始 IP 包封装进一个新 IP 包，目标地址为缓存的 IP，协议字段设为 **GRE（Generic Router Encapsulation）**  
- 缓存收到后解封装得到原始客户端 IP 和请求，处理完成后可直接返回响应（无需再经过路由器，但通常响应仍会回到路由器以维持对称路由）

---

## 七、WCCP 负载均衡

- **分发方法**：
  - **哈希（Hash）**：基于源/目的 IP、端口等计算哈希值，映射到固定缓存（保证同一连接或同一客户端始终去同一缓存）  
  - **掩码/值对（Mask/Value）**：更灵活的匹配规则  
- **健康检测**：心跳机制，故障缓存自动摘除，恢复后自动加入  
- **会话保持**：通过哈希或掩码规则，避免同一 TCP 连接的请求分散到不同缓存（否则可能导致连接失败）

---

## 八、WCCP 与其他缓存重定向协议的对比（书中后续会介绍）

| 协议 | 特点 | 典型使用场景 |
|------|------|--------------|
| **WCCP** | 路由器与缓存直接交互，GRE 封装保留客户端 IP | 透明缓存部署（ISP、企业网络） |
| **ICP** | 缓存之间 UDP 查询是否存在 URL（仅 URL，易假命中） | 缓存邻居查询 |
| **HTCP** | 类似 ICP，但支持完整 HTTP 头，更精确 | 精确缓存协作 |
| **CARP** | 哈希分配，无查询开销，内容无重叠 | 代理阵列（如 Microsoft ISA） |

---

## 九、总结

WCCP 是一种 **网络层透明缓存重定向协议**，通过路由器与缓存代理的协作，实现：
- 流量自动导入缓存
- 负载均衡与故障转移
- 保留客户端 IP（通过 GRE 封装）
- 支持标准 HTTP 及自定义服务

它适合大型 ISP 或企业网络部署透明缓存，但需要路由器支持 WCCP 协议（主要是 Cisco 设备）。现代环境中，此类功能逐渐被 **服务链（Service Chain）** 或 **策略路由 + 四层负载均衡** 替代，但 WCCP 仍有其应用价值。

---

## 一、ICP（Internet Cache Protocol）

### 定位与作用
- **缓存集群协议**：允许缓存之间互相查询是否存在某个 URL 的对象  
- **对象发现协议**：通过 UDP 多播/广播向相邻缓存（兄弟姐妹）发送查询，收到 `HIT` 或 `MISS` 响应后决定从何处获取内容

### 消息格式（简单、轻量）
- 使用 **UDP**（效率高但不可靠，需超时重试）  
- 消息为 32 位对齐的二进制结构，包括：
  - `Opcode`：`ICP_OP_QUERY`（请求）、`ICP_OP_HIT`/`MISS`（响应）
  - `Version`：版本 2（Squid 使用）
  - `Message length`：最大 16383 字节
  - `Request number`：匹配请求与响应
  - `Options`：如 `ICP_FLAG_HIT_OBJ`（是否返回对象数据）、`ICP_FLAG_SRC_RTT`（请求 RTT 估计）
  - `Payload`：请求中包含请求者 IP 和 URL；响应中可包含对象数据（如果请求了 `HIT_OBJ`）

### 特点
- **简单、轻量**，但仅基于 URL 匹配，容易产生 **假命中**（fake hit）：因为不同请求头（如 `Accept-Language`）可能导致缓存副本不适合客户端，但 ICP 只问 URL  
- 支持 **层次化查询**：兄弟缓存都 MISS 时，可向上级父缓存查询（图 20-13）

## 二、CARP（Cache Array Routing Protocol）

### 定位与作用
- 由 Microsoft 和 Netscape 提出，将一组代理服务器虚拟成一个 **逻辑缓存阵列**  
- **确定性哈希路由**：对每个 URL 计算哈希值，直接决定由阵列中哪台缓存负责，**无需查询**（无 ICP 那样的广播风暴）

### 工作方式
1. 维护一个参与缓存服务器的列表（含负载因子）  
2. 对每个缓存服务器计算一个哈希值（考虑其负载能力）  
3. 对请求 URL 计算另一个哈希值  
4. 将 URL 哈希与各服务器哈希值组合，取最大值对应的服务器作为目标  
5. 由于计算确定，同一 URL 总是落到同一缓存，内容在阵列中 **无重叠**（每个 URL 只存在于一台缓存）

### 优点
- 无查询延迟，可扩展性好  
- 无重复内容，总存储容量大  
- 可在客户端（浏览器插件）或代理层执行

### 缺点
- 缓存服务器故障时，需重新计算哈希分配（重新洗牌），代价高  
- 所有 CARP 客户端必须使用完全一致的配置（服务器列表、哈希算法），否则同一 URL 可能被映射到不同服务器，降低命中率  
- 不支持缓存之间的临时借调或层次化（如 ICP 的 parent）

---

## 三、HTCP（Hyper Text Caching Protocol）

### 定位与作用
- ICP 的增强版，解决 ICP 仅基于 URL 的假命中问题  
- 支持在查询中携带 **HTTP 请求头**（如 `Accept`、`Accept-Language` 等）和响应头，实现更精确的匹配  
- 还支持 **缓存策略控制**：可以请求其他缓存添加、删除文档或修改缓存策略

### 消息结构（图 20-15）
- 包含 Header、Data、可选的 Authentication 部分  
- Data 部分包含：
  - `Opcode`：`NOP`（ping）、`TST`（测试存在）、`MON`（监控）、`SET`（设置策略）、`CLR`（清除）
  - `Response code`：指示成功/失败原因  
  - `Transaction ID`：唯一标识事务  
- 支持 **HMAC-MD5 认证**（表 20-8），防止伪造

### 优点
- 减少假命中  
- 支持动态缓存策略调整（如修改 `Cache-Vary`、`Cache-Expiry` 等）  
- 比 ICP 更精细的控制

### 缺点
- 协议更复杂，实现难度高  
- 未广泛普及（Squid 支持，但默认不开启）

## 四、三种协议对比总结

| 特性 | ICP | CARP | HTCP |
|------|-----|------|------|
| **类型** | 查询式 | 确定性哈希 | 查询式（增强） |
| **传输层** | UDP | 无查询（直接 HTTP） | UDP（可 TCP） |
| **请求内容** | 仅 URL | URL 哈希 | URL + HTTP 头部 |
| **假命中风险** | 高 | 无（因为无查询，直接映射） | 低 |
| **缓存内容重叠** | 可能重叠 | 无重叠 | 可能重叠 |
| **故障恢复** | 自动（心跳） | 需重新哈希洗牌 | 自动（心跳） |
| **策略控制** | 无 | 无 | 支持 SET/CLR 等 |
| **认证** | 无 | 无 | 可选 HMAC-MD5 |
| **典型实现** | Squid | Microsoft ISA / Netscape | Squid（可选） |

## 五、实际应用演变

- **ICP** 曾是早期 Squid 缓存集群的标配，但因假命中问题逐渐被替代  
- **CARP** 被 Microsoft 用于 ISA 服务器阵列，适合企业环境，但对故障敏感  
- **HTCP** 提供了更精确的控制，但复杂度高，未大规模普及  
- 现代 CDN 和代理缓存更多使用 **基于 HTTP 的主动推送** 或 **全局哈希（如一致性哈希）** 方案，结合健康检查和配置管理（如 Consistent Hashing + Gossip 协议）
