# 一、本段核心主旨
现在我们准备写 SimpleDotCom 的真实方法实现，但**不直接写功能代码，而是先写测试代码**。
这种**先写测试、再写功能**的思路来自极限编程（XP）里的 **TDD 测试驱动开发**，能让写代码更快、逻辑更清晰。

# 二、极限编程 XP（Extreme Programming）介绍
## 1. 起源与定位
90年代末诞生的敏捷开发方法论，从小型工作室到大企业（福特等）都在用。核心目标：**让客户随时拿到想要的功能，即便需求中途变更也能快速适配**。



## 2. XP 标志性核心实践
1. **先写测试代码（TDD）**：本章重点，功能代码出现前先写单元测试
2. 小版本、高频发布，分迭代开发
3. 不额外开发需求外的功能，拒绝“为未来预留功能”
4. 可持续工作节奏，不疯狂加班赶工期
5. 随时重构优化代码，保证简洁
6. 代码必须全部通过测试才能上线
7. 结对编程、代码集体所有权，全员熟悉项目全部逻辑
8. 持续集成、简单设计、客户全程参与测试

# 三、TDD 先写测试的好处（对应本章小游戏开发）
1. **提前理清接口与行为**
   写测试时就要确定：`setLocationCells`、`checkYourself` 怎么调用、输入输出是什么，倒逼你把类的设计想清楚。
2. **自带校验标准**
   写完功能代码直接运行测试，命中、miss、kill 三种场景自动验证，不用手动反复输入数字试游戏。
3. **重构安全网**
   后续修改 DotCom 逻辑（比如扩展为二维网格），只要测试全部通过，就不用担心改坏原有功能。
4. **缩小调试范围**
   测试失败能精准定位是方法内部逻辑出错，而非整个游戏流程问题。

# 四、结合 SimpleDotCom 的测试编写思路
在写 `checkYourself`、`setLocationCells` 实现前，先新建测试类，覆盖三类场景：
1. 猜测数字不在数组内 → 返回 `miss`
2. 命中其中一格，总命中不足3次 → 返回 `hit`
3. 第三次命中，全部格子击中 → 返回 `kill`

测试代码会提前定义好方法该有的行为，之后我们只需要写刚好能让测试通过的 Java 代码。
