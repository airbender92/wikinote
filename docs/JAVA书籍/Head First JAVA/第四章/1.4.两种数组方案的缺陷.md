# 两种数组方案的缺陷 & 最优ArrayList方案对比
## 一、方案一：单独开辟 `hitCells` 标记数组
### 实现思路
1. 主数组 `locationCells` 存放站点全部坐标（如`{4,5,6}`）；
2. 额外创建等长布尔数组 `hitCells`，专门记录每个格子是否被击中；
3. 每次玩家猜测前，**先循环遍历hitCells**，判断该坐标是否已经命中过；
4. 若从未命中：`numOfHits++`，并把对应位置标记为已击中。

### 缺点（原文评价：too clunky 繁琐笨重）
1. **多一套数组同步维护**，两套数组必须一一对应，代码量大；
2. 每次猜测都要额外循环检查标记数组，重复遍历；
3. 容易出现数组下标错位、同步更新遗漏的bug；
4. 新增/修改站点长度时，两套数组都要同步调整，维护成本高。

## 二、方案二：原数组用 `-1` 标记已击中格子
### 实现思路
仅用单一`int[] locationCells`，规则：
- 正常未击中：存有效坐标（4、5、6）
- 被击中后：把该位置数值替换为 `-1`
遍历数组时只匹配不等于`-1`的有效数字。
示例：`locationCells = {4, -1, 6}`，代表5号格子已被击中。

### 缺点（原文：less clunky but inefficient 略好但低效）
1. **每次猜测必须完整遍历全部3个格子**，哪怕多个位置已经变成`-1`无效值，循环不会提前缩短；
2. 依然要额外判断`cell != -1`，增加分支判断代码；
3. 数组长度固定，永远要遍历全部下标，无法减少循环次数；
4. 逻辑冗余，只是用特殊值占位，没有真正移除无效数据。

## 三、两种数组方案共同痛点
1. 数组长度固定，元素无法真正删除，只能靠额外标记区分有效/无效；
2. 每次猜测都需要完整循环数组，性能差；
3. 大量额外判断、同步逻辑，代码冗长、易出错。

## 四、最优方案：`ArrayList<Integer>`（本书最终方案）
### 核心优势解决全部痛点
1. **命中直接移除元素**：`list.remove(index)`，被击中坐标彻底从容器删除，不存在`-1`、标记数组这类占位逻辑；
2. 无需完整遍历判断重复：`list.indexOf(guess)`直接查找，不存在的元素直接判定miss；
3. 容器动态缩短，后续循环/查找只保留剩余未击中格子，效率更高；
4. 代码极简，不需要两套数组、不需要特殊标记值，消除同步bug风险；
5. 无需手动维护`numOfHits`计数器，`list.isEmpty()`直接判断是否击沉站点。

### 总结
固定数组无论新增标记数组、还是用-1占位，都属于笨拙的折中写法；`ArrayList`可变集合从根源上消除“重复命中计数”的bug，代码简洁高效，是Java API提供的更优工具。当前文件内容过长，豆包只阅读了前 85%。
