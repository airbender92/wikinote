# utf8mb4 + utf8mb4_unicode_ci 完整解读

## 1、什么是 utf8mb4

MySQL里**utf8≠真正完整UTF‑8**

- `utf8`：MySQL旧实现，最多只支持3字节，**不能存emoji表情、部分生僻汉字、特殊符号**（比如😀、部分古汉字会直接报错或乱码）
- `utf8mb4`：**真正完整的UTF‑8，最多4字节**，可以存储全部Unicode字符，包括表情、生僻字、特殊符号。

> ✅新项目一律用 `utf8mb4`，不要再用旧的`utf8`。MySQL8.4版本默认已经是utf8mb4。

## 2、排序规则 utf8mb4_unicode_ci

排序规则：**控制字符串怎么比较、排序、大小写是否敏感**。
拆分名字：
`utf8mb4`_`unicode`_`ci`

1. **unicode**：基于标准Unicode规则比对，符合国际语言规范，支持多语言（中文、英文、日文、韩文等）排序。
2. **ci = case‑insensitive** → **大小写不敏感**
   - `A` 和 `a` 认为相等；查询 `where name='abc'`，`ABC`也能查出来。

### 常见另外2个对比（分清区别）

1. `utf8mb4_general_ci`
   老版本常用，速度略快，但**对复杂语言排序有bug**，现在不推荐新项目用。
2. `utf8mb4_bin`
   二进制模式，**大小写敏感**，`Abc` 和 `abc` 是两个完全不同的值；适合密码、验证码字段，一般不作为库默认排序。

### 三个常用规则对比

| 排序规则           | 大小写敏感 | 特点                        | 适用场景                |
| ------------------ | ---------- | --------------------------- | ----------------------- |
| utf8mb4_unicode_ci | ❌不敏感   | 标准Unicode，多语言排序正确 | ✅**数据库/表默认首选** |
| utf8mb4_general_ci | ❌不敏感   | 性能稍快，排序有缺陷        | 老项目兼容，新项目不用  |
| utf8mb4_bin        | ✅敏感     | 严格二进制比对              | 密码、验证码字段        |

## 3、为什么库要设置这套组合

```sql
CREATE DATABASE demo1 DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
```

- `DEFAULT CHARACTER SET utf8mb4`：**库的默认字符集**，新建表如果不手动指定字符集，自动继承utf8mb4。
- `COLLATE utf8mb4_unicode_ci`：**库的默认排序规则**，新建表、字段自动继承。

> ⚠️注意：库的设置只是**默认继承**；如果建表的时候手动写了别的字符集，会覆盖库设置。

## 4、实际业务现象演示（ci大小写不敏感）

```sql
-- 表中存 "Hello"
select * from t where col='hello';
-- 依然可以查询到结果，ci忽略大小写
```

如果你业务要求用户名区分大小写，那对应字段单独改成`utf8mb4_bin`，**不要改库级别**。

## 5、实操建议

1. 所有新建数据库：**字符集utf8mb4，排序utf8mb4_unicode_ci**（就你DBeaver里选的这套）。
2. 不要用MySQL的`utf8`，它是残缺版本。
3. 只有密码、验证码这类字段，单独设置字段collate为`utf8mb4_bin`。
4. MySQL8.0/8.4默认就是这套，5.7必须手动指定。

### 坑提醒

老项目迁移，如果原来库是`utf8`，直接改成`utf8mb4`要做迁移处理，不能直接改配置。

> 简单记口诀：
> **存全量字符用mb4，通用排序选unicode_ci；要区分大小写就用bin。**
